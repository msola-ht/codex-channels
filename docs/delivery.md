# 渠道关键结果投递箱

Gateway 将需要渠道展示的最终正文、Turn 开始与完成、操作终态、上下文压缩开始、子代理启动/联系/完成、连接中断/恢复、Thread 占用/名称变化和结果通知先写入独立投递箱，再调用平台。同一 Conversation 的独立通知按顺序保留，不因前序结果积压或渠道离线而丢弃；恢复后可能延迟展示。辅助通知发送结果未知时保留记录供核对，但解除其对后续投递的顺序屏障，详见下文。整体服务重启先停止 Gateway 再停止 App Server，避免在 Gateway 即将退出时新建断开通知；历史上已留下的未知通知不会因此自动删除，也不能据此判定已送达。微信仍遵循自身展示策略，不新增其他操作或子代理消息；审批与用户输入交互不跨重启重放。

此分类沿用现有数据库 schema v1 和加密载荷外层 v1；授权 owner 使用下文规定的 v2 身份合同。回退到不支持上述新增持久通知的版本前，应先排空投递箱并按下文停写备份；仍有未确认记录时保留当前版本处理，不删除记录来绕过旧版载荷校验。

计划、思考计时、操作运行状态、Thread 状态、账户与 MCP 状态只保留最新快照；CLI 输入镜像按 Item 暂存，不在 Gateway 持久化输入正文。共享快照缓存最多 512 个键、8 MiB；同键最多一份在途状态和一份最新替换值，两份内容共同计费。预算直到实际渠道操作结束才释放，不能把入队视为送达。普通状态等待阻塞投递的持久结果排空；CLI 输入镜像按进程内到达序号插入前序持久通知与后续结果之间，重启恢复的旧记录仍先于本次输入。平台调用前再次核验原归属。重复状态合并，操作终态、Turn 完成、新轮次或断线会取消相应旧状态的排队操作与刷新计时器，防止迟到的“运行中”覆盖终态。CLI 输入镜像不因轮次结束而过期，仍可说明对应结果。此缓存仅存在于进程内，不作为历史或跨重启的状态事实。触及缓存预算时明确报告故障并沿现有故障流程停止接收，不扩大无界队列。逐字正文增量不另建恢复队列，完整正文由完成 Item 的持久记录保证。

状态发送失败、队列拒收或结果未知会记录未确认诊断，不自动重发该次状态；后续新状态仍可继续展示。取消不能撤回平台已经接收的消息。永久隔离账号时移除其临时快照，取消尚未发送的队列操作并释放预算；在途内容继续计费，直到实际操作结算。该账号的持久结果继续保留，其他账号可使用释放的临时预算。关键结果仍按持久记录的失败与恢复合同处理。

TG/飞书的实时本地生命周期处理独立于平台投递：开始事件登记回复关联，断线立即清理对应渠道流式状态；TG 同时停止输入状态计时器。恢复重放只发送原通知，不再次清理已恢复的新状态。已经排队的可靠正文持有自己的发送内容引用，清理流式缓存不会取消该正文；可靠正文没有任何平台成功检查点时，拒绝确认。飞书正文与完成信息共享同一次流式终态，避免清理后漏发或重复发送。事件接收不等待平台网络请求。

正文流、回复消息 ID、计划、思考与操作消息只能复用当前 Conversation 的展示状态。飞书结束流缓存同时绑定 Conversation、Thread 和 Turn；断线清理后，在途终态仍可完成原来的可靠正文，但不能重新登记旧卡片。完成通知若已失去可复用卡片，则向当前授权目标正常发送，不能以其他会话的卡片更新确认当前结果。

Telegram 对全空白 commentary 明确不展示、不新建投递记录；现有投递箱中尚未发送的同类记录也按此规则结算，不伪造平台成功检查点。非空 commentary 与最终正文仍要求实际发送确认。已经标为 `uncertain` 的历史记录不会自动重发或清除，仍需按下文离线核对处理。

只有本地事务成功的记录属于“已持久接收”。记录不因时间、重试次数或容量被自动删除；平台确认并成功写回后清除正文。App Server 通知没有逐条持久确认协议，提交前崩溃或容量耗尽后的新结果存在接收缺口。投递箱不是完整聊天历史，不能替代 App Server 历史。

## 存储与容量

目录是当前 `storage.database_path` 所在目录下的 `delivery-outbox`，默认位于用户数据目录的 `data/` 下。`outbox.sqlite3` 保存独立 schema v1，`payload.key` 保存独立 AES-256-GCM 密钥，`writer.sqlite3` 仅用于单写者锁。数据库索引和发送检查点中的身份、状态、消息 ID 是明文元数据；正文与原授权归属快照经过认证加密。目录及文件采用当前用户私有权限。

| 边界 | 上限 |
| --- | --- |
| 全局未确认记录 | 256 MiB / 20,000 条 |
| 单账号未确认记录 | 64 MiB / 5,000 条 |
| 单条加密前载荷 | 4 MiB |
| 每条预留的检查点空间 | 64 KiB，最多 256 个检查点 |
| 快照至事务完成的待提交窗口 | 8 MiB / 128 条逻辑载荷 |
| 所有输出总线订阅的在途预算 | 32 MiB / 2,048 项逻辑载荷 |
| 协议通知总线订阅的在途预算 | 32 MiB / 4,096 项逻辑载荷，不合并协议通知 |
| 进程内最新展示状态（含在途、待替换和待释放内容） | 512 个键 / 8 MiB 逻辑载荷 |
| 单渠道 Outbox 与路由各自的排队及执行操作 | 各 512 项，跨所有 Conversation 计数 |
| 平台并行执行 | 全局最多 8 个 Conversation，每个 Conversation 串行 |

逻辑载荷预算不是 JavaScript 堆内存测量值；编码、Worker 复制与加密会占用额外的有界工作空间。单条记录额度包含图片快照的 Base64 和事件元数据，因此可持久接收的图片小于 3 MiB；超过上限明确拒绝并隔离渠道，不截断后宣称送达。普通渠道图片命令原有的 10 MiB 上限不因此变更。

SQLite 固定 4 KiB 页，主库最多 512 MiB；部署时还需为 rollback journal 留出同量空间和至少 64 MiB 控制余量。备份另占空间。每条预留检查点空间参与全局及账号计费；条数上限与字节上限以先到者为准。

存量达到字节或条数额度的 80% 时暂停 Gateway 新执行及新 Queue 输入；低于两项额度的 60% 后恢复。重启时处在中间水位的存量保守地继续暂停，避免重启绕过低水位恢复条件。停止当前任务、只读查询和删除 Queue 条目仍可用。硬账号额度故障隔离该渠道；全局额度、邮箱或磁盘故障停止 Gateway 自身消费，保留已接收记录。共享 App Server 和原生 TUI 不被停止，它们仍可能继续生成结果。

周期计划任务在调度容量检查及创建 Thread 前复核投递准入；短暂超载沿现有容量不足策略处理当次运行，不将周期任务永久标为授权失败。创建 Thread 后再次遇到 Turn 准入拒绝时，释放新后台绑定并保留后续调度。

Telegram 可靠终态正文不复用流式预览的截断内容；长回复文件使用已入箱的完整正文。文件发送结果未知时保留完整记录，平台确认前不清除正文。

微信可靠正文的有界文本或文件预览不代表全文送达。超过 1,000,000 字节的文件上限、文件端口不可用或发送失败时，未完整送达的记录保留为 `uncertain`，阻止同 Conversation 后续关键结果越过；其他 Conversation 继续。完整附件与其检查点确认后才允许清除原文；文件大小上限和普通非持久文本的展示分片策略不变。

飞书 CardKit 降级为 Post 时按编码字节重新分片，与后续卡片共享原有消息数量预算。流式失败恢复也使用同一分片入口，首片保留回复关系，后续片作为普通消息发送；不会把长正文直接放入单条回复 Post。可靠正文在卡片、流式终态或 Post 路径出现截断时，需要另行确认包含原文的完整附件；已有完整附件确认则不重复发送。附件不可用或发送失败时保留记录，不将预览成功当作全文成功；未知平台结果仍不自动重发。

## 状态与发送确认

- `pending`：已持久接收，尚未开始发送。
- `sending`：已写入发送尝试，正在调用平台。
- `uncertain`：发送超时、断线、取消或发送期间崩溃，无法确认是否送达。保留检查点，不自动重试整条；除下述辅助通知外，阻止同 Conversation 后续关键结果越过它。
- `blocked`：恢复或发送前的当前授权、目标归属复核未通过。旧结果不会转发到新绑定的目标。

Thread 在同一接收归属内正常前后台切换或释放绑定，不撤销已入箱结果的接收归属。发送仍按原 Actor、Workspace 和仍配置的 Provider 复核；原 Workspace 必须仍存在于当前 Registry，且 ID 与规范化目录必须同时匹配，历史选择值不能代替当前授权；Actor、Workspace 选择改变、同 ID 改目录、撤权或 Thread 当前已绑定其他目标时拒绝投递。其他 Conversation 可独立继续。授权 owner v2 保存所选及 Thread 绑定工作区的目录快照；只接受当前版本，缺少版本的旧 owner 或未知版本不获得发送授权。旧载荷保留原文，不自动补写、迁移或重发；遇到授权检查时转为 blocked，已有 uncertain 保持待核对状态。

Gateway 关闭时先禁止新执行和交互，停止通知来源及后台生产者，在持久输出入口仍可接收时限时排空已收到的入站通知及输出登记队列，再以共享 5 秒期限结算已确认的子代理终态，等待快照入箱后关闭渠道。指标等待超时按统计不可用生成终态，不为仍运行的子代理伪造完成。入站排空超时会报告关闭失败，不能当作全部入箱成功；共享 App Server 不被主动终止。

以下辅助通知处于 `uncertain` 或 `blocked` 时，仅解除会话顺序屏障：连接中断/恢复、Turn 开始、Thread 名称/占用变化、会话空闲释放、带 `globalIdle: true` 的全局空闲释放提醒、子代理启动/联系，以及 `contextCompaction` 的 `running`（压缩开始）。成功的过程通知（`command`、`fileChange`、`mcpTool`、`dynamicTool`、`webSearch`、`imageView`、`sleep`、`plan` 的 `completed`）也解除屏障，带图片载荷或明确非零退出码的命令除外。它们仍保留载荷、检查点和容量计费，不重发、不删除、不伪造确认；后续正文、状态和交互可以继续，同一会话的平台队列仍串行。失败或被拒绝的操作、图片生成、Review 与子代理操作、压缩完成/失败、最终正文、Turn/子代理完成、MCP 授权结果及其他警告不属于辅助通知，继续保留屏障。

执行准入与投递顺序独立：单条 `uncertain` 或 `blocked` 仅影响该 Conversation 的后续投递和审批展示，不禁止新执行、Queue 新增/更新/启动或计划任务。旧记录授权失效不替代当前输入的 Actor、Workspace 与审批校验。新产生的关键结果仍先入箱并遵守原投递顺序，不能据此宣称用户已收到。账号/全局高低水位、存储不可用、渠道存储隔离及关闭状态仍暂停新执行；提示区分全局容量、账号容量和存储不可用。停止、查询和 Queue 删除继续可用。重启按存量恢复容量保护，不因旧失败记录恢复执行封锁。

全局空闲释放提醒沿用载荷已有的 `globalIdle` 标记；没有该标记的历史警告不靠正文猜测分类。符合条件的旧提醒重启后也解除投递屏障，原文、检查点、未确认状态与容量占用不变。此调整不修改数据库或配置格式，不自动重发、不伪造送达；回退旧代码会恢复旧版的投递和执行阻塞行为。

重启从认证载荷重新判定通知分类与会话阻塞；这一分类机制沿用数据库 schema v1，不需要额外数据库字段，授权 owner 的 v2 合同另见上文。未知辅助通知继续出现在离线列表和容量统计中，仍需人工核对；持续积压仍会触发容量限制。回退到不支持这些例外的旧版本会重新阻塞未解决的通知。成功过程通知的新分类同样作用于重启恢复的旧 `uncertain` 或崩溃遗留 `sending`，不改写载荷、状态、检查点或容量；辅助通知因授权变化成为 `blocked` 时同样保留记录并解除顺序屏障，不恢复旧授权或发送旧通知。正常 `pending`/`sending` 仍等待本次平台调用结算，只有变成 `uncertain` 或 `blocked` 后才按分类解除阻塞。

同 Conversation 的审批与问题等待前序阻塞结果确认后才展示，等待占用原交互期限；前序结果未知、超时、撤权或 Gateway 停止时安全取消，不跨重启恢复交互。不同 Conversation 不共享这条等待屏障。

发送检查点记录每个发送/更新操作的开始、明确成功或明确拒绝。既有有界重试仅覆盖已证明未接受或幂等的操作；Telegram 格式拒绝及飞书尚未发送消息的 CardKit 创建失败仍允许安全回退。微信 HTTP 5xx 与网络超时不能证明未送达，不自动重试。平台成功到本地确认之间的崩溃仍有不可消除的窗口，因此这里不承诺恰好一次。新记录入箱、本地确认写入或调度存储失败会立即停止调度及执行准入，并报告 `storage`，不能误报为平台发送失败；记录保留，重启仍将未确认的 `sending` 视为 `uncertain`，不自动重发。存储 Worker 空闲退出会通知 Gateway 清理，并立即影响执行准入与审批等待判定，不能因为内存队列为空就认定投递已完成。入箱时显示配置明确隐藏的操作不持久化；已入箱结果若后来被展示规则禁止，保留为未知结果供核对，不按无发送成功删除。可靠入口会立即排空终态查询操作的展示聚合，避免只存在内存缓冲就清除持久记录。

Telegram `editMessageText` 明确返回 `400 message is not modified` 时，表示请求正文已在目标消息上，统一按编辑确认记录；只接受该方法的结构化平台错误。网络异常、取消、其他方法及其他 400 错误不能靠相似文案变成成功。

## 消息突然停止时的排查

先读取日志，无需停止服务：

```sh
codexc service status all
codexc service logs gateway -n 100
```

新投递日志的 `persistentDeliveryId` 与 `codexc delivery list` 的记录 `id` 一致，可从入箱后的故障定位到渲染、排队和平台调用；分片仍有各自的 `deliveryId` 和 `diagnosticId`。历史日志缺少该字段时不能追补。关联 ID 不包含正文或凭据，也不新增持久字段。

飞书消息 API 失败日志中的 `operation` 标识发送或更新方法，`diagnosticId` 关联本地诊断；
`httpStatus` 是实际返回且通过校验的 HTTP 状态，`platformCode` 是飞书非零业务码，
`platformRequestId` 是可供平台排查的追踪 ID。字段缺失表示未取得，不从 `ERR_BAD_REQUEST`
推断具体 HTTP 状态或业务原因。不输出异常原文、响应正文、Authorization 或 Cookie。
SDK 正常返回但包含非零业务码同样是失败，不能因为附带消息 ID 就确认送达。

出现 `delivery-uncertain` 时，说明至少一条已接收结果没有完成送达确认；进程 active 不表示
会话投递正常。最终正文、操作失败等关键记录会阻塞同会话后续消息；白名单内的成功过程通知发送未知时只保留核对，不再挡住后续正文。不要通过重复重启、删除数据库、
批量确认送达来解除阻塞。先按下节停止 Gateway 并核对记录；共享 App Server 无需停止。

- 平台已有完整结果：核对全部分片或附件后，才可对准确 ID 执行 `confirm --confirmed-delivered`。
- 平台没有结果：先根据错误码修复权限、内容或平台限制，再对准确 ID 执行 `retry --allow-duplicate`；允许重复是显式选择，不代表系统能证明先前未送达。
- 无法判断：保留记录继续核对，不能把未知当作成功或确定丢失。

处理后启动 Gateway，再检查日志和飞书端。修复诊断代码只改善部署后的新错误，不能还原历史已丢失的
平台错误细节，也不会自动清除已有未确认记录。数值错误码不单独证明某条消息可安全重发；本流程不增加自动重试。

## 离线核对

以下维护命令必须先停止 Gateway；单写者锁会拒绝与正在运行的 Gateway 同时维护。无需停止共享 App Server。

```sh
codexc service stop gateway
codexc delivery status
codexc delivery list
```

`status` 输出存储计数和逻辑字节数，并附带 `retainedNotices`（未知或授权失效但不阻塞的辅助通知）、`blockingRecords`（仍参与顺序屏障的记录，含正常排队）和 `blockedConversations`（因未知结果或授权阻塞而暂停后续投递的会话数量）。`list` 分页输出记录 ID、Conversation、状态、检查点、事件类型、Thread/Turn、操作种类/状态，以及 `blocksFollowing`、`blocksExecution`。`blocksExecution` 固定为 false，表示单条记录本身不禁止执行；账号/全局存储容量保护独立计算。`blocksFollowing` 表示投递顺序策略，后续排队项仍可能被前序记录挡住，不表示每条记录都会立刻发送。投递箱被运行中的 Gateway 占用时，命令明确提示先停止 Gateway，不并发打开写入者。两命令从认证载荷提取限定字段，不输出正文、通知内容、图片或授权快照。打开投递箱时，崩溃留下的 `sending` 会转为 `uncertain`，所以这些命令属于离线维护，不是 `doctor` 的只读检查。

自行核对平台消息及 App Server 历史后，选择其中一种处理：

```sh
codexc delivery retry DELIVERY_ID --allow-duplicate
codexc delivery confirm DELIVERY_ID --confirmed-delivered
codexc service start gateway
```

`retry` 明确重发整条结果，可能重复已送达的分片；清除旧尝试检查点，但保留尝试计数，启动后仍复核授权。`confirm` 仅在已自行确认结果送达后删除记录。两者只接受 `uncertain` 或 `blocked`，不会删除正在排队或发送的正常记录。恢复授权前重发 `blocked` 仍会被拒绝投递；辅助通知按上述分类解除顺序屏障，其他结果继续保留屏障。缺少 v2 身份证据的旧 owner 即使执行 `retry` 也不能获得授权；此命令不会补写身份。只能保留记录供人工核对；`confirm` 仍要求已确认送达，不能用来清空未送达结果。

所有子命令支持 `-h` 和 `--help`。不提供按年龄或容量清空未确认记录的命令。

WebUI 左侧导航的“渠道投递队列”独立页面（`#/delivery`）可在 Gateway 运行时查看不含正文的持久记录快照，不触发恢复或改变状态。WebUI 重试和忽略无需停止 Gateway：预览确认后通过投递箱私有 IPC 交给正在运行的单写者处理；Gateway 未运行时才使用独占锁离线维护。WebUI 支持勾选当前页记录批量重试或忽略（最多 50 条），忽略明确表示永久移除、不再发送，不代表已经送达；CLI confirm 仍只用于确认送达。WebUI 在线处理由 Coordinator 暂停取出新投递，拒绝目标会话仍有在途投递的批次，在单个事务内核对整批修订，并同步容量与顺序屏障后恢复调度；离线维护模式使用独占锁。两种方式只处理所选记录，不恢复其他 `sending` 或清理临时图片；不自动重试未知结果或修改数据格式，恢复发送仍复核原授权。WebUI 通过鉴权 SSE 订阅 Gateway 队列变化，合并通知后读取快照，不固定轮询元数据；隐藏页面断开，重连后补查。WebUI 直接在列表补充事件类型及短文本摘要，不再展开详情；摘要按页批量读取并按记录修订复用，快照刷新不重复读取未变化正文。完整界面与 API 说明见 [WebUI](webui.md#前端)。

## 停写备份、恢复和回滚

采用 owner v2 前，先停止 Gateway，按以下步骤备份数据库与独立密钥并验证副本。StateStore、投递数据库 schema v1、加密外层 v1 均不改变；支持读取这些外层中的旧 owner 以供离线核对，但不支持将旧 owner 自动升级为可发送的 v2。启动失败、授权阻止发送或验证失败时保留原文件，不删除投递箱；旧记录阻塞所属 Conversation 是预期的安全结果。

需要回滚时同时恢复原程序与经验证的停写备份，并核对对应 Workspace 配置。原版本不能修复目录身份缺失问题，不得借回滚在已更换目录的配置下自动发送旧结果。v2 记录也不能通过删除版本字段“降级”；备份后有新发送或新记录时，先保留完整新状态并人工核对，禁止直接覆盖和启动，避免丢失或重复投递。尚未送达的旧记录继续保留，不虚假确认。

初版采用人工停写备份，不自动迁移、轮换密钥或清理未确认数据：

1. 停止 Gateway，并确认 `codexc delivery status` 能取得独占锁后正常退出；保持 Gateway 停止，禁止另一个维护进程并发写入。
2. 在私有、全新备份目录复制 `outbox.sqlite3`，将 `payload.key` 独立备份到另一个受保护位置。使用当前用户私有权限，记录 schema v1、时间、记录计数及两个文件的 SHA-256。不要备份 `writer.sqlite3`，也不要把密钥贴入日志或聊天。
3. 在隔离目录将数据库副本与对应密钥分别还原为 `outbox.sqlite3` 和 `payload.key`，验证当前版本能够打开、认证解密并读取相同数量及顺序。自动测试使用临时目录覆盖这个流程；正式恢复前仍需检查自己的备份。
4. 正式恢复前保留原目录，不覆盖唯一副本。保持 Gateway 停止，将已验证副本放入新的私有投递目录后切换目录；当前 Runtime 只接受 v1，不用删除数据库“修复”未知版本、缺失密钥或认证失败。
5. 备份后如果发生过新的平台投递，不能直接还原旧快照并启动自动发送，否则其中的旧 `pending` 可能重复送达。先保留两份状态并逐条核对；不能证明未投递的旧快照不得投入自动恢复。

未来持久格式升级必须另行提供支持版本范围、停写备份、副本迁移、验证及回滚步骤。卸载或停用 Gateway 不应删除本目录。开发源码直接运行需先构建 Worker，使用 `npm run build` 后再启动开发入口。
