## 主要问题与判断

### 迁移逐渐变成重新设计业务逻辑

用户的核心担忧是：原有业务逻辑已经存在，Rust 工作却逐渐变成按模块重新实现、重新建立规则，
随后再修复这些规则在真实链路中的冲突。仅把排期从模块改成用户链路，不能自动解决这个问题。

旧计划依次铺设 CLI、Client、Storage、Router、Core 和 Delivery，再接入 Telegram 正式消费。
这提供了实现基础，但部分关键衔接直到正式消费时才暴露。例如 P2.4 的 `/new` 修复涉及旧租约
核验、绑定事务与退订顺序、历史用量重放造成的错误在途判定，以及显式解绑和输出交接。

这些记录支持“行为对齐发生得偏晚”的判断，不能据此认定所有 Rust 模块都设计错误。
部分机制是资源所有权和并发适配所需，部分涉及用户可见语义；应逐项对照，不能笼统归为必要重写。
`/new` 的显式解绑调整在批次记录中有用户选择和授权，也不能定性为未经授权的改动。

后续需要对每项实质变化回答：原 TS 如何处理，现行合同要求什么，Rust 改了什么，为什么必须改，
对用户及恢复路径有什么影响。已确认的旧缺陷应单列，避免复制缺陷或借修复扩大范围。

### 实现完成与可独立交付混在一起

crate 存在、静态检查通过和本地提交完成，都不能证明该模块已作为独立业务能力交付。
旧记录中明确完成的是 P1.1 开发基线和 P1.2 终端与配置事务；它们跨多个 crate，
并不表示整个 CLI、Runtime 或所有配置管理场景已经完成。

| 已有成果 | 记录支持的范围 | 仍不能得出的结论 |
| --- | --- | --- |
| 终端与配置事务 | P1.2 范围内的交互、保存重读、冲突和取消已有观察 | 完整 CLI 和三平台交付完成 |
| 指标查询、Provider 管理、渠道接入、投递箱维护 | 已有实现及部分隔离或真实使用观察 | 所有外部消费、服务激活和故障恢复完成 |
| Rust Telegram 文本链 | 文本、停止、网关单独重启、恢复后新会话已有观察 | Telegram 全能力、后台释放及完整故障验收完成 |
| 协议、授权、存储等基础库 | 已有明确能力和消费者，可供后续评估复用 | 每个基础库均可独立作为产品交付 |

已有代码应保留供比较和复用。是否保留某段实现由行为、依赖和证据决定，不能仅凭投入量或 crate 数量判断。

### 检查点过期和历史堆叠误导恢复

Rust 主检查点仍称最近业务提交为 `81d98baf`、追加修复未提交，但实际保留点已是 `c710d1fc`。
同一检查点还混有多轮旧作业、失败候选、待复验描述和后续成功结果，增加了重复执行旧动作的风险。

如果将来恢复工作，先核对真实 Git 和运行状态，再更新唯一当前入口。当前状态只保留有效基线、
完成范围、剩余阻塞和下一动作；历史方案、撤回候选和详细运行记录保存在对应记录中。
已履行的提交授权不能自动变成新任务授权。

### 批次边界没有充分收敛

P2.4 从接通文本链推进到恢复语义修正，并出现“第二批后台恢复与释放”的安排。
必要修复可以跨模块，但后续工作必须明确哪些是已开放能力的缺陷，哪些是尚未开放的新能力，
以及完成方法。不能用不断追加子批次替代收尾，也不能通过减少验收要求迁就已有实现。

P1 未验收完成就进入 P2 有记录的暂缓授权，不直接视为越阶段；暂缓项仍然是交付缺口。

## CLI 合入 main 的结论

历史上存在进入 P2 前的 P1 分离节点 `78af2559`，当时 CLI 尚未依赖 Rust Bootstrap。
当前 Rust CLI 已增加 Bootstrap 依赖与隔离 Gateway 入口，因此直接合整个 Rust 分支不等于只合 CLI。
P2 期间还修改过共用配置事务、初始化及代理等能力，机械截取旧节点可能遗漏适用于 CLI 的后续修复。

技术上可整理独立 CLI 候选，但尚未完成该候选的完整审查和验收。真实服务部署、升级恢复、
部分账户消费及 Windows/macOS 实机缺口仍存在，不能直接替换正式 `codexc`。
讨论中“可拆出合入”的判断只是可行性判断；最终决定是暂停 Rust，不创建 CLI 合入候选。

## 现有模型请求代理的独立边界

| 能力 | 运行与依赖边界 |
| --- | --- |
| Provider Proxy | 由 App Server 的 Node 监管宿主持有，在宿主中创建代理服务；模型转发不依赖 Gateway 持续运行，但不是单独可部署的代理程序 |
| Model Relay | 有独立服务入口，向外部调用方提供模型 API；不依赖 App Server 会话能力，仍复用项目配置、凭据读取及公共转换和网络能力 |
| 请求指标 | 两者经私有 IPC 送往 Gateway 唯一数据库写入者；模型转发独立不等于指标入库独立 |

对应边界见 [Provider Proxy](../src/provider-proxy/README.md)、[Model Relay](../src/model-relay/README.md)
和 [Relay 合同](provider-api-relay-development.md)。这描述当前实现责任，不表示本次重新观察了服务运行。

若将来只重写 Gateway，可以保留官方 App Server、现有监管宿主、Provider Proxy 和独立 Relay，
先固定它们与新 Gateway 的接口。将代理拆成独立项目是另一项设计工作，需要明确配置、凭据、
路由、生命周期和指标接口，不能随网关重写自动纳入。

## 后续重写的建议流程

以下是重新启动前可采用的流程，不是当前执行计划。先选择“保持行为的网关迁移”还是
“允许改变产品范围的新项目重写”；两者都需要明确行为合同，但允许改变的范围不同。

1. **固定产品范围。** 列明保留、调整、暂缓和放弃的能力，确定首发平台；首版可从一个渠道、
   一个 Provider 和基本文本会话开始。暂缓功能明确反馈，不静默降级。
2. **固定外部边界。** 明确 Gateway 与 App Server、代理、存储、CLI 和 WebUI 的接口及资源所有者。
   指标接收、计划任务和管理接口各自指定责任和接入批次，避免遗漏或全部挤入首批。
3. **建立行为对照。** 每项能力记录旧行为、现行合同、拟变更和理由；语言适配与业务变化分开。
   若采用新项目存储格式，先确定旧数据保留、导入及失败恢复方式。
4. **交付最小真实闭环。** 配置启动、授权文本输入、App Server 调用、完整回复及正常退出同批完成。
   CLI 先提供闭环需要的入口，不先重建全部管理功能。
5. **按能力扩展。** 会话控制与重启恢复、审批与异步交互、运行故障处置、管理能力及其他渠道逐批加入。
   每批都处理自身的授权、失败、取消和容量限制，不把可靠性统一推迟到最后。
6. **按同一流程收尾。** 行为合同、最小设计、实现、相关静态检查、真实路径与失败挑战、证据及限制
   一起收齐。遵守现有不新增或维护测试的约束；已完成证据仅在输入仍有效时复用。
7. **单独安排安装与切换。** 固定产物，观察目标平台安装和恢复，确认停旧、备份、启新及回退条件，
   再按明确授权切换；旧实现退役另行决定。

模块与 crate 服务于责任划分，不作为主要完成单位。新抽象应有当前消费者；代码与旧实现可以组织不同，
但不能在没有理由的情况下改变用户行为。已有 Rust 和 TS 均可参考，复用前核对适用范围。

## 网关重写必须守住的条件

- App Server 仍是 Thread、Turn、Queue 和历史的权威来源。本地缓存不能变成第二套会话引擎。
  请求受理、操作终态、持久化和平台确认分别表达。
- Actor、Conversation、Workspace、Provider、Thread、Turn 与有效连接及绑定代次贯穿整条链。
  撤权、迟到结果和切换不能导致跨用户或跨会话应用结果。
- `/new`、`/stop`、后台保留和恢复先定义产品语义。不能把未知默认为空闲，也不能要求上游
  无法提供的证明，造成正常操作永久拒绝；这种冲突需要重新审查语义。
- 输入平台确认与输出平台确认分别设计。明确崩溃可能丢失或重复的范围；入队不代表完成，
  未知发送不自动重放，分片必须核对完整交付。
- 每类连接、任务、队列和 writer 有唯一资源所有者。取消不等于退出，超时不等于清理完成；
  避免网络等待占用业务锁，并检查停止操作在满载时是否仍能执行。
- 启动、关闭和恢复失败提供受控且可定位的诊断。Gateway 退出不得主动终止共享 App Server。
- 新旧系统隔离账号与数据；正式切换确认唯一消费者和 writer。保持格式不意味着可以双写；
  已发生平台发送或新数据写入后，不能直接回放旧备份制造重复或丢失。

如果简单操作开始依赖大量未实现模块，或新增规则不断阻塞原有正常行为，先停止扩大编码，
判断是实现错误、上游限制还是产品语义调整。不要继续叠加状态、限制和例外来掩盖边界问题。
