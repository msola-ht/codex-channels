# 渠道展示与调试模式

本页说明 Gateway 完成卡片、`/metrics` 命令和信息类聊天指令的展示口径，以及全局调试模式
启用的技术字段。根目录 README 只保留常用操作，细节以本页为准。

微信发送非 `commentary` 的完成正文，包括 Cline 等 Provider 未提供 `phase` 的消息；空阶段保持
官方“阶段未知”的含义，不改写为 `final_answer`。这些正文同样进入可靠投递，超长时使用文本文件发送；
明确标记的 `commentary` 过程消息仍不占用微信回复窗口。

## Telegram 交互回复

普通问题、异步问题和 MCP 表单的消息以粗体“Codex 交互回复”开头，长消息的每个分片都保留该标记。
回复没有对应活动请求的旧消息时，Gateway 提示已处理或失效，不将内容提交到当前会话。
重启或最近 1,000 条消息身份缓存淘汰后，仍通过当前 Bot 的非转发消息来源和固定标记识别，
不恢复旧交互，也不持久化问题或表单正文。普通引用与其他发送者的消息不凭正文关键词判为交互。
普通回答或面板使用同名首行时，文字保持不变，首行不加粗；Rich Markdown 也遵循该规则，避免引用普通回答时被误判失效。

## 异步问题

模型调用 `request_user_input_async` 时，Telegram、飞书和微信显示“异步问题（任务继续执行）”。
工具是否可用取决于上游模型目录，Gateway 没有额外开关。问题不会暂停任务，也不计作最终答复；
等待回答不会挡住命令、文件或权限审批。异步回答不授予这些审批权限。

- Telegram 通过按钮选择建议答案，或选择其他答案后回复对应消息；纯文本问题直接回复问题消息。
- 飞书在原问题表单中选择或填写答案后提交。
- 微信使用问题中提供的带令牌回答命令，支持选项序号与自由文本。

每批最多展示三个问题，较多问题依次分批，每批完整回答后提交一次普通用户消息。
提交时仍须属于原 Thread：当前有活动 Turn 时追加输入，空闲时在原 Thread 启动新 Turn。
普通 Turn 完成后，尚未过期的问题仍可回答；问题本身不自动创建后台队列或重放输入。
卡片显示已提交回答表示渠道已收集表单；如果 App Server 提交失败或结果未知，会另行提示核对原会话，
不会自动重发。

问题只在当前 Gateway 进程内保存，沿用审批超时配置，整个问题组从收到通知开始计时。
切换或解绑会话、回退历史、失败或中断 Turn、App Server 或对应渠道账号连接断开与 Gateway 停止会使问题失效；
渠道恢复后不会重新打开旧问题组的后续批次；已发往 App Server 的回答无法撤回，结果未知时仍提示核对原会话。
后台会话问题不弹出可提交交互，而是提示当前无法回答。重启后不恢复问题卡片，请核对会话后重新发送消息。
问题内容不保存到 Gateway 数据库。上游没有异步问题的跨客户端解决通知，因此在原生 TUI 回答不会自动关闭渠道卡片。

## 等待式问题

模型调用官方 `request_user_input` 时，Gateway 响应原来的 `item/tool/requestUserInput` 请求，
不把回答改发为普通消息。`isBlocking: true` 显示“Codex 等待回答”，`false` 显示“Codex 请求补充信息（可跳过）”。
渠道交互沿用配置的有效期；过期、取消或渠道不可用时返回空答案，不代选建议项。
已弃用的 `autoResolutionMs` 不再决定渠道有效期；缺失或畸形的 `isBlocking` 请求返回空答案。

原生 TUI 对非阻塞问题采用 60 秒宽限加 60 秒倒计时，无人操作时返回空答案继续；
开始操作会停止自动跳过，阻塞问题没有这项倒计时。渠道表单没有统一的开始输入事件，
因此不复制 TUI 的倒计时与输入暂停机制，使用上述渠道有效期。工具等待不意味着必须收到非空答案才能继续。

固定版本在 Default 执行模式下默认不开放该工具；上游 `default_mode_request_user_input` 仍为开发中开关，
Gateway 不自动启用。隔离 App Server 探测确认启用后可等待回答并在原 Turn 接续，且仍返回 `isBlocking: false`；
这不构成暂停全部后台命令或其他任务的保证，也不会把已经发出的异步问题转换成等待问题。

## 完成汇报

WebUI、CLI 人类可读输出、转储详情和渠道的耗时展示统一为自适应单位：不足 1 秒使用整数 `ms`，四舍五入；不足 1 分钟使用 `s`，
最多保留两位小数并省略末尾零；更长耗时四舍五入到整秒，不足一小时组合为 `min` 与 `s`，达到小时后只显示 `h` 与分钟，省略秒和零分钟，例如 `672 ms`、`1.25 s`、`1 min 5 s`、`2 h 57 min`。
进位后切换单位；缺失值保持未知，不显示为零。数据库、API、JSON/CSV 的 `*Ms` 字段仍为毫秒原值。

每次 Turn 完成后，卡片标题表明运行状态，标题下直接展示本次指标，不重复“本次运行”分区标题；随后显示“当前会话”和可选的“账户状态”。会话信息下方展示递归包含子代理的请求数和 Token，缓存命中率作为 Token 下子项展示，不另设统计分区。

启动通知、Turn 启动卡、完成卡和 `/status` 都显示当前 Session 的“审批方式”。该值来自 App Server
的 Thread 启动、恢复或分叉响应及 `thread/settings/updated` 权威设置：`user` 显示“手动审批”，
`auto_review` 显示“自动审查（Auto-review）”，上游兼容值 `guardian_subagent` 显示“自动审查（guardian_subagent）”。
尚未绑定、未取得或无法识别时显示“未知”，不使用全局 Codex 用户设置推断已有 Thread。
Codex 默认审批方式修改只设置新会话默认值；当前会话显示仍以 App Server 的实际设置为准。
`/autoreview` 查询当前会话审批方式，`/autoreview on|off` 为当前会话后续轮次切换自动审查或手动审批。
未绑定时不创建会话；实际值未知或为 `guardian_subagent` 时只读。仅权威设置确认后显示已切换，
未确认结果提示重新查询，不能把未知结果描述为成功或确定未修改。
飞书和 Telegram 当前会话按钮标明“当前会话：自动审查 / 手动审批”，绑定生成时的 Thread、Conversation 和用户，五分钟内有效且一次性；
与工作区按钮使用不同动作和令牌作用域，微信使用相同文本命令。
渠道 `/workspaceperm` 展示工作区默认审批方式，与当前会话的实际值区分。
`/workspaceperm autoreview on|off|clear` 设置工作区覆盖，适用于新建、分叉、卸载后恢复的会话；已加载会话保留实际审批方式。
`clear` 删除覆盖，新会话跟随 Codex 默认，恢复历史会话可能保留其已保存设置。
飞书和 Telegram 三种按钮均标明“工作区默认”，提供自动审查、手动审批、跟随 Codex 默认的显式选择，微信显示对应文本命令；
尚未绑定 Thread 时仍可设置工作区默认值。按钮绑定生成时的工作区与用户，
过期、重复使用或工作区已切换时须重新查询，不把旧卡片的选择应用到新工作区。
工作区修改回执按本次操作说明范围：审批方式修改提示已加载会话保持原值，并提供 `/autoreview` 入口；
只有清除覆盖时说明新会话与历史恢复的差别，其他权限修改不附加审批方式说明。
飞书命令中心当前状态面板保留模型设置、工作区、权限查询与当前会话审批方式按钮，正文只展示实际状态。

飞书、Telegram 和微信实时显示“自动审查开始 · 审查中”及“自动审查完成 · 已通过 / 已拒绝 / 已超时 / 已中止”。
这些通知只报告 App Server 已发布的状态，没有人工审批按钮，不改变实际审批决定，也不显示原始动作、命令或审查理由。
同一 Thread、Turn、Review ID 和阶段去重，迟到的开始通知不会把终态倒退为审查中；状态通知独立于指标写入，
经既有关键结果投递路径发送，微信也将其纳入回复窗口生命周期通知。子代理审查仅按已确认的精确父子 Turn
关系转发到仍有授权的父会话，并标明“来源：子代理”；缺少归属时保留有界短期等待并记录不可路由状态，
不向其他会话广播。通知等待和去重只存在于进程内，不重放 Gateway 停止期间未观察到的审查事件。

飞书、Telegram 和微信完成卡在本次运行中展示“自动审查通过”，统计截至卡片生成时已记录的
本轮及按官方父子运行关系递归关联的子代理审查。只计官方自动审查代理完成并返回 `approved`
的结果，同一 Review ID 不重复计数；规则或缓存直接放行、手动审批、被拒绝及未完成的审查不计入。
审查计数及观测完整性持久保存，Gateway 重启后可读取已有记录；官方历史不提供的审查事件不补推。
连续观察完整时显示 `自动审查通过：3 次（含子代理）`，明确的零次显示 `0 次（含子代理）`。
断线等观测缺口显示 `已记录 3 次（含子代理；统计不完整）`；完整性未知时，有记录显示
`至少 3 次（含子代理；统计不完整）`，没有记录显示 `未知（含子代理；统计不完整）`，不能把未知显示为零次。
未提供该统计字段的完成事件省略此项。完整仅表示截至卡片生成时的观测范围；原 Turn 的迟到审查结果
仍归属原轮并落库，已发出的完成卡不保证追更，也不把迟到结果算入下一轮。

完成卡片的上下文压缩默认只显示次数与 Token，例如 `1 次 · 225.13 K Token`。
压缩模型与本轮模型不同时另显示模型，混合或未知模型也明确标注；仅追加非零的客户端中断、其他失败与未完整观测数量。
调试模式和 `/metrics` 保留模型及完整结果分类。压缩 Token 是已有总计的子项，不重复相加。

- 普通前台用户 Turn 收到官方 `completed` 终态却没有产生非空最终回复时，完成汇报显示
  “无最终回复”，并提示重试或在上下文较高时使用 `/compact`；该诊断不改变官方 Turn 状态，
  也不把没有用户输入的手动压缩 Turn 或后台任务误报为异常。
- 运行区把统计代理捕获到的本 Turn 全部模型请求聚合为请求次数，并在存在异常尝试时拆分完成、
  中断、未完整观测和失败数量，同时展示 Token 与缓存命中；官方 `Turn.durationMs` 可用时另显示
  从本轮开始到完成的总耗时。主 Turn 与子代理完成卡片不显示“上游轮次首 Token”；上游原始指标采集与存储保留。
  完成卡仅以“本轮耗时”显示官方 `Turn.durationMs`，起点是 App Server 开始执行本轮，包含模型请求与工具执行；不是最后一次模型请求的耗时。官方未提供时明确显示“未提供”，不隐藏该行。
  Turn 完成卡显示“首 Token”和“速度”：首 Token 是本 Thread/Turn 普通模型请求已观测首内容时间的平均值，零毫秒有效；首内容包括非空思考、正文、拒绝文本和工具参数，不包含状态、额度或仅有用量的事件，缺失不以首包回填。速度仅对已完成、输出 Token 和请求总耗时均大于零的请求，计算总输出 Token 除以请求耗时之和，不依赖首 Token 或生成区间。此为请求平均输出速度，包含等待、思考、正文、工具参数和网络接收；不平均各请求速度。不含压缩、其他轮次或子代理。无效请求的 Token 与请求耗时同时排除；没有对应有效样本时显示 `—`。数据从指标库恢复，毫秒显示整数，速度显示如 `56.8 /s`，不附带括号、平均说明或样本数。
  两次模型请求之间的工具执行等待只计入本轮耗时，不计入请求速度的分母；上游在单次请求内部执行工具的等待无法独立剥离，保留在请求耗时中。
  当前会话同样显示“首 Token”和“速度”，沿用会话 Token 的递归范围，包含子代理的普通模型请求；均值、加权速度和缺失处理与本轮一致。历史缺失首 Token 不补算，不妨碍完整输出量与总耗时样本参与速度统计。
  会话的“上下文压缩”保留 App Server 次数；落库的“压缩请求”另列次数与 Token，复用本轮的模型去重和非零异常展示，二者统计来源不同，不相加。
  `/metrics`、子代理完成卡不显示速度或上游首 Token。请求明细与调用详情的列头为“首 Token”“速度”和“请求耗时”，具体见[WebUI 请求明细](webui.md)。本地观测的 `firstTokenMs` 与上游原始 `upstreamTtftMs` 不混用。
  当前锁定 Codex 0.160.0 的首轮 `generate=false` WebSocket 预热不属于模型推理，
  不计入请求数或 Token。Turn 完成前会等待当前 Thread 与 Turn 已入队的指标写入，并从本地指标库重建本轮统计；因此 Gateway
  在长 Turn 中途重启后，完成卡片仍包含重启前后的本次用量，会话累计也包含本轮已经落库的请求。等待有总预算，
  指标库拥堵或不可用时按当前可用值生成卡片并记录告警，避免一个慢指标库阻塞其他 Surface 与 Conversation 的输出投递。
  Git 分支通过异步子进程读取，与统计补全共享 250 ms 预算；超时取消读取并省略分支。可选信息补全出现未预期异常时，持久与非持久路径都用原始完成事件继续发送，保留已有本轮信息。
- 会话区在正式与调试模式都显示当前工作区、Session 名称和 Session ID，保留 Session 累计上下文、压缩次数、Goal 与 Git 分支，并显示递归包含全部已关联子代理后代的
  模型请求数、Token 总量和缓存命中率；缓存命中率与 Token 总计一样默认
  显示，不依赖调试模式。历史子代理仍计入会话累计，但不会被猜测归属到任何父 Turn 的某一次运行。
- 会话区的“总耗时”累计当前 Thread 截至本次完成轮次的官方 `Turn.durationMs`，即各次“本轮耗时”之和，
  包括已中断或失败轮次中官方提供的耗时；不计两轮之间的等待，不额外叠加子代理并行耗时。
  官方终态耗时按 Thread/Turn 唯一记录到指标库，卡片与 WebUI 共用查询，会话总数不重复存储。
  Gateway 首次观测某会话完成或恢复既有绑定后在后台补齐历史，每次最多读取 100 页、每页 100 轮、总预算 5 秒；
  失败或历史尚未包含完成轮次时，在同一预算内最多尝试三次，仍失败则保持未补齐状态。
  后续终态幂等更新；清理后再次完成、写入失败、绑定恢复或 Revert 会触发补齐，不依赖下一轮修复当前写入失败。
  断线使对应 Provider 已观测会话的完整性标记失效，恢复绑定后重新同步。完整性以数据库为准，同步标记不保存历史内容或累计耗时。
  总数限于指标库保留范围；耗时缺失时保留“已知累计”并注明缺失轮数，历史未补齐时另行注明；全部耗时未知或当前轮次已被回退时显示“未提供”。缺失值不按零处理，部分合计不冒充完整总数。
- 父 Turn 确有直接子代理运行时，运行区另显示“任务合计（含子代理）”，按
  `subagent_turns` 中父子 Thread + Turn 的精确关系，汇总父 Turn 自身及其全部后代运行的请求数、Token、
  子项；缺失的运行关系不按时间补推。父 Turn 的“本次运行”保持自身口径，子代理完成卡片
  仍独立展示。
- 推理 Token 计数对所有 Provider 展示；指标库不保存推理正文；Chat 转换层会处理推理回传，显式开启的调用转储可能保存原始推理内容，见[调用详情](user-guide.md#模型请求转储)。
- 原生 OpenAI 账户对应的 Codex Provider 明确显示为“OpenAI 官方”；配置的自定义主模型
  Provider（如 `model_providers.OpenAI`）显示为“OpenAI · 自定义”，与官方直连区分。
- Cline Pass 在渠道提供商菜单、模型摘要、状态、完成卡片和用量中保留 `clp-<账户>` 标识，
  例如 `clp-main`；Setup 品牌入口与 WebUI 账户卡片使用完整名称 Cline Pass。
- 同一 Turn 中模型请求遇到 `429/5xx` 或上游 WebSocket 断流后由 Codex 重试并最终完成时，完成
  卡片显示“自动重试、最终成功”；真实失败尝试仍保留在
  指标库与异常报告中。
- OpenAI 完成卡在本轮与“当前会话”分别显示 `OpenAI Credits`，来源为本地采集的单次
  `usage_metadata.amount`。本轮只汇总精确 Thread + Turn；会话累计递归包含已关联子代理后代；
  “任务合计（含子代理）”按现有父子 Turn 关系单独汇总，含正常响应、重试尝试和压缩请求。
  只汇总 Provider 为 `openai` 的记录，不混入第三方同名数值。使用精确十进制求和，明确零值显示 `0`；
  全部缺失或统计不可用时隐藏该项，部分缺失显示已知小计及“部分，N 次请求未提供”。
  会话数值仅覆盖本机保留的指标记录，不承诺完整账户账单；不与余额或官方 Thread 估算相加。
- Gateway 不在本地计算或估算模型价格与费用，完成卡片不展示总价、均价、单价或峰谷档位，也不
  保存价格快照或刷新价格目录。账户与额度仍展示官方来源的数据：OpenAI 周限、
  DeepSeek 账户余额、OpenCode Go / Cline Pass 官方配额窗口和 CCG Credits；这些数据不是本地价格估算。
- 完成卡片正式模式在本次运行和会话信息之外，保留精简的“账户状态”：OpenAI 优先显示
  OpenAI 官方周限；OpenCode Go、Cline Pass 显示各窗口“剩余百分比 · 重置时间”，CCG 显示剩余额度和可用窗口，DeepSeek 显示官方余额。重置时间缺失时省略，不推算；余额与 Credits 不转换为百分比。
  第三方在投递完成卡时按本次 Turn 的精确 Provider/账户查询，与本地统计并行、最多等待 2 秒；查询失败或超时省略账户区块，不使用其他账户或旧快照。额度为零仍显示，Gateway 关闭会取消查询。此读取不阻塞 App Server Reader。
  正式与调试模式均显示可用的重置时间和剩余时长；账户区块含重置时间时统一标注“时区：IANA 标识”，跟随 Gateway 进程的日期显示时区。仅余额、Credits 或无重置时间的窗口不增加时区行。
  完整账户信息仍可通过 `/usage` 或 WebUI 控制台查看和刷新。

## /usage 命令

OpenAI `/usage` 先展示账户活动摘要；当前账户选择和 Conversation 实际绑定都属于 OpenAI 时，
在同一回复追加“当前 Thread 官方估算”区块。待生效的第三方 Provider 选择仍按既有规则决定
`/usage` 的账户来源，不会为其查询当前 OpenAI Thread。官方估算按当前锁定的 0.160.0 App Server 活动
账户读取，只覆盖精确当前 Thread，不递归或合计子代理，也不写入本地指标库。

- Credits 和可选美元费用按百万分之一整数单位转换为有界小数；缺少美元值时不显示费用行。
- 仅对所有分组都提供的 Token 字段求和，缺失字段不按零累计；分组最多显示 8 组，缺失分组名称显示“其他”。
- `threadUsage` 不可用时保留账户摘要，并说明该官方计费能力仅向部分 Business/Enterprise 工作区开放；
  查询失败时显示稳定重试提示。账户摘要失败仍沿用既有失败行为。
- 没有当前 Thread 时不发起官方 Thread 查询；DeepSeek、OpenCode Go、CCG、CLP 和其他第三方 Provider 保持自身账户余额或额度口径。
- 官方估算可能在 Turn 完成后延迟结算；本地请求明细与子代理累计继续使用 `/metrics`，两类金额不得相减或合并为真实账单。

## Luna Reserve 自动回退

OpenAI App Server 对当前 ChatGPT 账户明确返回 Luna Reserve 权益，并且最终 `turn.error` 分类为
`usageLimitExceeded` 时，Gateway 会在该 Turn 完成后读取一次完整额度状态。权益、账户 ID、受限模型
和隐藏的 `gpt-reserve` 目录项一致时，当前 Thread 的模型、思考等级、服务层级及 Default/Plan 模式
通过 `thread/settings/update` 一次性切换；写请求失败不重试，也不会先改本地显示状态。

切换成功后三个渠道都会提示重新发送失败消息。Gateway 不保存或重放消息正文；已经进入 App Server
原生 Queue 的下一 Turn 仍由 App Server 管理，可能在回退请求完成前自动开始并再次遇到额度错误。
Gateway 检测到活动 Turn 时会等其完成后再写入设置，避免把已启动 Turn 误报为 Reserve。切入后每分钟
按账户执行一次共享的轻量额度读取；只有同一账户明确
恢复普通用量、权威普通额度桶没有剩余消费控制或限额阻断、没有未知后端权益 Banner、当前模型仍是
`gpt-reserve`，且原模型仍在可用目录中时才自动切回。用户手工改模、切换账户、关闭、归档或删除 Thread
会取消自动切回。原模型只保存在当前 Gateway 进程内，因此 Gateway 在 Reserve 期间重启后不会猜测
切回目标。

已经由 App Server 接受的设置写入无法撤销。若写入完成前账户发生变化，Gateway 不会把该结果认作
当前账户的自动切换，也不会用补偿写入覆盖新账户或原生 TUI 的后续选择；三个渠道会提示用户确认
当前 Session 模型，并说明自动切回已取消。Reserve 自身用量耗尽时，完成卡片会与普通用量耗尽明确区分。

## /metrics 命令

`/metrics` 可查看当前 Thread 最近 Turn 的运行聚合，以及递归包含全部显式子代理后代的 Thread 会话累计。
`/metrics global|providers|models <范围>` 按同一口径汇总指标库全部保留记录，并显示请求、Token、缓存、
压缩和错误统计；历史无 Turn 记录不再形成单独的会话分栏。
`/metrics errors` 按提供商、模型、状态、HTTP 状态和错误类型汇总异常请求，显示异常率与最近
发生时间。它不会替代 `/status` 的 App Server 上下文统计。
本机 `codexc metrics run <Thread ID>` 的会话累计使用上述递归口径；
`codexc metrics turns <Thread ID>` 仍列出指定 Thread 自身的 Turn 明细，不把子代理任务拆入公开
Turn 行，避免改变既有输出结构。渠道 `/metrics` 只查询当前绑定 Thread，不接受任意 Thread ID。
范围统一为滚动窗口 `24h` / `7d` / `30d` / `90d` 和 `all`，渠道、CLI 与 WebUI 使用相同名称。
CLI 与 WebUI 还支持 `today` / `yesterday`，分别统计今天截至当前时刻、昨天完整自然日。
WebUI 的每日分组和所有格式化时间统一跟随服务端进程时区，缺省为系统时区，可用
[`codex.timezone`](model-timezone.md) 覆盖；浏览器时区不改变日期归属。
CLI 人类可读的指标报告、导出与菜单使用执行主机本地时间，报告标明 IANA 时区名称，不附加查询时刻的
UTC 偏移；历史记录按各自时间戳采用当时的夏令时规则。转储列表、详情与跟随输出使用同一时区标签，
显示时间统一为 `YYYY-MM-DD HH:mm:ss`。WebUI 顶部实时时钟的 UTC 偏移与显示时刻对应，仍保留。
JSON/CSV 中的时间戳和
UTC ISO 时间以及原始上游转储保持原格式，不迁移历史记录；耗时不受时区影响。
WebUI 菜单只展示今天、昨天、最近 7 天、最近 30 天、全部历史和自定义日期。
本机 CLI 需要精确自然日或账期时使用 `--from YYYY-MM-DD --to YYYY-MM-DD`。
`threads`、`turns`、`report` 与 `export` 共用时间和请求筛选：Provider、模型、`response|compact`
操作、`completed|failed|incomplete|unknown` 状态及关键词可组合使用。`--thread` 精确指定会话，
`--turn` 必须同时指定会话；`turns <Thread ID>` 的会话由位置参数提供。`threads`、`turns`
默认全部保留历史，`report`、`export` 默认最近 30 天。日期按执行主机本地时区解析并包含结束日，
最多查询到当前时刻。

```bash
codexc metrics threads --range 7d --provider openai
codexc metrics turns <Thread ID> --from 2026-09-01 --to 2026-09-15
codexc metrics export --range 7d --thread <Thread ID> --turn <Turn ID> --status failed --format csv
```

期间查询先按请求记录时间筛选，再按 Thread 或 Turn 汇总；跨越时间边界的一轮只计算范围内的
请求。轮数是本机指标库中有记录的不同 Turn 数，不代表完整官方历史轮数。会话列表、每轮明细与
精确 Thread 请求筛选只计算各会话自身，子代理以独立 Thread 列出；`run` 和渠道 `/metrics`
的全部历史累计继续递归包含已关联子代理。请求导出在数据库内筛选，读取全部匹配页；JSON 保留
所用范围与筛选条件，JSON/CSV 保留精确数值。

渠道、CLI 与 WebUI 的 Token 统一使用 `K`、`M`、`B` 紧凑单位：`K` / `M` 最多保留两位小数，
`B` 最多保留三位小数；渠道、CLI 和 WebUI 的汇总请求数使用相同单位且最多保留两位小数，逐条明细及
JSON / CSV 导出仍保留精确整数。
未发起上游请求的 Turn 级失败（例如 OpenAI 用量上限拒绝 turn/start）同样作为无 Token 的
failed 请求计入异常记录，避免这类错误完全不可见。

请求累计将结果分为「完成」「客户端中断」「其他失败」「未完整观测」：已观测到完成响应的请求计入完成；
其余请求中，`client_disconnected` 计入客户端中断，明确的 `failed` 计入其他失败，`incomplete`、
`unknown` 及历史未观测到响应的记录计入未完整观测。原始请求状态和错误类型保持不变，仍可在异常明细中查询。
JSON 中的 `requestOutcomes` 提供四类精确计数；`unsuccessfulRequestCount` 仍表示全部非完成请求，
不能直接作为失败数。失败率仅使用「其他失败」除以总请求数，完成率仍以总请求数为分母。

渠道完成卡的请求结果简写为「完成 · 中断 · 失败 · 不完整」，不另列中断后成功、未观测到后续成功或中断用量缺失说明。
指标查询的会话和 Turn 摘要仍保留中断后同轮有成功请求、未观测到后续成功，以及用量未完整观测的中断次数。
「同轮后续成功」要求相同 Thread、非空 Turn ID，且成功响应的结束时间严格晚于中断结束时间；
它只表达时间关联，不证明自动重试、成功恢复或主动取消。范围查询只采用同一筛选范围内的记录，
缺少时间或关联信息时不推测成功。中断请求的输入或输出 Token 缺失即视为用量未完整观测；
已收到的用量仍保留在汇总中，缺失用量不代表零消耗，也不根据请求时长估算。

统计代理把 `/responses` 上的上下文压缩（remote compaction v2）保留为
`compact` 操作：其请求与 Token 继续计入总计，同时在完成卡片、会话指标和全局/提供商/
模型汇总中单列压缩次数、实际请求模型与 Token。这里的模型是代理实际观测到的请求模型。
当前锁定的 Codex CLI 0.160.0 没有独立压缩模型配置；常规压缩复用 Turn 模型，模型切换兼容压缩
可能先使用上一模型，并在受支持的失败条件下回退当前模型。

完成卡片的模型/提供商之下会单列「自动压缩：X%」。受管第三方 Provider 只配置模型目录里的
`context_window`，压缩阈值由上游按窗口默认推导，因此不显示该字段（会话区「上下文」分母已反映
当前窗口）；官方模型优先读取主配置覆盖值（`model_context_window` / `model_auto_compact_token_limit`），
未覆盖时显示默认 95%。
`codexc config` 的「Codex 新会话与用户偏好 → 模型上下文与自动压缩」可读取并设置官方模型的
上下文窗口与自动压缩百分比，未设置时按模型默认展示。

- HTTP 与 WebSocket 客户端在完成事件前断开都计为中断；HTTP/SSE 已完成后的正常收尾断开不重复
  记为失败；上游 WebSocket 断流按可重试失败保留，在 Turn
  完成时归入“自动重试”。
- HTTP 200 但没有模型、Usage 或完成事件的响应计为“未完整观测”，中断与未完整观测都不冒充
  成功请求。
- 缺少 `Content-Type` 但正文包含合法 Responses SSE 事件时仍按正文受限识别，不会误丢成功请求。

请求指标、会话状态、运行完成卡、CLI 指标报告与 WebUI 的输入 Token 明细统一使用“缓存”和“无缓存”：
前者仍指缓存命中的输入 Token，后者仍按输入 Token 减缓存输入计算；“缓存命中率”保留原名，计算与持久化字段不变。

## /limits 额度与周限估算

渠道额度、用量、`/status` 卡片及 `/metrics errors` 异常报告统一显示“时区：<实际 IANA 时区>”，取当前进程实际用于格式化时间的
时区，不使用客户端设备时区。OpenAI 每日用量仍按上游 `startDate` 展示，区块标注“官方日期口径”，
不按显示时区重新分组；剩余时长按时间戳差计算。

OpenAI 渠道额度卡片在套餐下仅显示“凭证刷新时间”，读取当前 Codex Home 的 `auth.json.last_refresh`，
沿用卡片服务时区并包含年份。仅在登录凭据账户 ID 与 App Server 额度账户 ID 一致时显示，字段缺失、
缓存不可读或账户不匹配时显示“未提供”。不显示登录 Token 内的订阅截止和检查日期。
手动 `/limits` 直接查询官方额度并只读取已有凭证刷新时间；额度查询、启动预热和后台轮询均不主动刷新登录凭据。
该时间不替换为查询时间，不代表订阅续费时间，不写入数据库或官方额度快照，也不展示凭据内容。

飞书同一菜单卡片的“额度”查询及结果卡片发送尚未结束时，重复点击复用该次操作，不重复查询或追加结果卡片；
操作结束后可再次点击查询。结果仍通过当前聊天的有序输出队列发送。

OpenAI Codex 额度卡在时区下方显示生成卡片时的“当前时间”，与重置时间使用同一时区，显示到分钟；该时间不代表额度采集时间或凭证刷新时间。

OpenAI `/limits` 显示可用额度重置券数量，并按到期时间合并 App Server 返回的每券明细；没有到期
时间的券显示为“无到期时间”。服务端只返回数量或限制明细条数时，界面会明确标出未提供到期明细，
不把用量窗口的自然重置时间当作重置券到期时间。有到期时间的明细同时显示查询时刻的剩余天数、
小时与分钟，以 `D`、`H`、`min` 表示，如“剩余：5 D 17 H 42 min”（不足整分钟舍去）；不足一分钟显示“剩余：不足 1 min”，
已到期显示“已到期”。
渠道额度、状态、完成卡和第三方用量窗口统一显示剩余百分比（由 100 减已用比例，并限制在 0–100）；主窗口与次窗口分别显示三行：首行“剩余：59%（7天）”，下方两行分别为“重置：10月7日 18:36”和“剩余：5 D 17 H 42 min”；周期或重置时间缺失时省略对应部分，不推算。带窗口名称的状态、完成卡和第三方用量使用“周限：剩余 59%”的组合形式，避免连续冒号。个人消费限额与重置券列表/确认卡也显示剩余时长；重置时间已过显示“重置时间已过”，券到期显示“已到期”。运行耗时与审批有效期保留原有精度。

OpenAI `/limits` 在额度响应包含 10,080 分钟周窗口和有效重置时间时，从本机统计代理读取相同
`resetAt` 的额度快照。代理对 HTTP/SSE 使用受控额度响应头，对 Responses WebSocket 使用
`codex.rate_limits` 事件，并把快照和对应请求指标写入同一指标记录。
`quotaObservedAtMs` 记录本机收到有效额度响应头或额度事件的时间，与请求结束后的入库时间
`recordedAtMs` 分开保存。缓存用量窗口保留缓存刷新时的观测时间，不以请求结束时间刷新旧快照。
若一条记录同时携带两类独立来源的额度快照，单个采集时间无法对应两者，保持空值。
额度估算、最新额度及历史窗口按采集时间排序，同毫秒按入库顺序排序；未观测采集时间的记录保持空值，
查询时只能按入库时间近似排序。该字段是本机观测时间，不是上游额度的生成时间。

第一个快照只建立基线；同一周窗口按已观测到的最高已用比例计算增长。百分比不变或回退时继续
累计后续请求，只有超过此前最高值才闭合区间，用区间累计 Token 除以新增百分点；回退后恢复到
原值不重复计数，也不把单次回退视为额度重置。重置时间在 5 分钟内的小幅抖动归为同一窗口，
不同窗口的快照会断开未完成区间；再次遇到原窗口时保留其最高值，重新建立采样基线。

“本周期本机实际”统计重置时间前 7 天至查询时刻的本机 Provider 请求；“每 1%”只使用闭合区间，
不包含首个基线请求或尚未闭合的尾部请求，因此不能直接用周期总 Token 除以观测百分点。
观测百分点表示采样覆盖的增长，不等同于当前已用比例；剩余百分比仍以官方额度响应为准。
未形成区间时显示正在采样。其他设备或云端活动若发生在相邻快照之间仍会影响估算，
请求完成顺序与额度快照时序也可能不同，Token 换算只是本机样本估算。

## 信息命令格式

信息类聊天指令输出统一为 Markdown 列表：`##` 标题、`###` 小节、`-` 字段列表、明细缩进嵌套；
`/metrics` 用 `**Token**：总计` 列表块分节，输入/缓存/输出明细按调试模式展开；
上下文压缩另列次数、模型与 Token，但不从总计扣除或重复相加；
`/diff` 与操作结果保持原文。三渠道分别用飞书卡片 Markdown、Telegram
HTML 和微信结构化字段渲染。

渠道启动通知默认在正式模式显示 Codex Connect 与 Codex 两个版本（分别对应 codexc 网关与
Codex CLI），并在“系统”下方分别显示“App Server 时区”和“网关时区”。App Server 时区使用
Gateway 启动时读取的 `codex.timezone` 并标注“配置”，未配置时显示“跟随系统（未配置）”；网关时区
使用 Gateway 进程的实际时区。App Server 字段不表示已核实其实际生效状态，配置生效条件见
[模型可见时区](model-timezone.md)。Node.js 运行时、连接方式和 App Server User-Agent 仍作为调试字段放在
“运行环境”小节。当前 Codex Home 缺少 `auth.json` 时跳过 OpenAI 启动连通性检查，不显示连通性告警。
此时启动通知额外显示“OpenAI 官方：未登录；请运行 codex login，或发送 /model 选择第三方提供商”；
使用自定义主 Provider 或固定第三方 Provider 时官方登录不参与当前路由，不显示该字段。
存在鉴权文件时，先从 App Server 读取当前认证路由，再只探测对应的 API Key

显示“子代理 · <代理路径>”（如 `/root/ds_probe`），其余显示“主会话”。该标注持久化在
指标库 `subagent_threads` 表中，`codexc metrics threads` 与 WebUI Threads 页面共用同一份数据。

Telegram 和飞书的渠道开始通知：Gateway 在官方 `subAgentActivity.started` Item 完成后向父会话发送一次简短的
“子代理开始 · 任务名”，附带“提供商”、“模型设置”和“思考强度”，不展示子线程 ID。
这三项通过官方 `thread/read` 读取子线程当前配置，不代表每轮实际请求遥测；读取失败、超时或缺失时显示“未提供”，不从父线程或全局默认值推断。
当前官方 v2 活动事件不公开 `fork_turns` 和任务摘要，因此不展示上下文继承方式，也不把可能继承自父会话的 `Thread.preview` 当作子任务摘要。
后续 `interacted` 显示为“子代理继续 · 任务名”，同样在投递时重新读取提供商、模型设置和思考强度，不沿用开始卡的旧值；
不改变正在运行的子代理存活状态；上一轮已经终止时会开启新一轮完成跟踪，`interrupted` 不会重复显示为开始。

Telegram 和飞书的渠道完成通知：成功运行只以 App Server 发给发起父 Turn 的 `subAgentActivity.completed` 为事实
来源，并按父 Thread、父 Turn、子 Thread 与代理路径精确匹配；子线程自己的 `turn/completed` 和
等待工具状态不再重复宣布成功。失败与中断仍使用子线程官方终态、中断活动或
`collabAgentToolCall.agentsStates` 的异常状态。Gateway 不根据模型请求静默时间猜测完成。同一
`subAgentActivity` 只在 Item 完成阶段归约一次，`interacted`、`interrupted` 与 `completed` 不会被
误显示为新建子代理。子线程 `turn/started` 即使先于父线程
`interacted` 到达，也会与待处理活动合并为同一轮；延迟到达的上一轮终态或指标不会污染新一轮。
父 Session 已切到后台时，Gateway 仍保留父 Thread 订阅直到所有已登记子代理运行取得官方终态，
再重试此前挂起的后台释放，避免晚于父 Turn 完成的成功活动丢失。官方终态后
若已经观察到模型指标且终态后出现父线程官方 `wait` Item，会立即等待当前 Writer 水位实际落库并
读取汇总，使“等待子代理 · 已完成”稳定排在子代理完成卡片之前；终态到达时尚无指标或父线程没有
等待时保留最多约 5 秒收敛窗口，后续新指标使旧结算失效。
没有模型指标时仍发送零统计终态，指标写入或读取失败则明确显示“统计暂不可用”，
不把未知值冒充零。卡片展示任务名、模型、提供商、可可靠观测的思考等级、请求次数与 Token；
正式模式保留 Token 总计，调试模式才展开输入缓存、未缓存输入、输出、推理输出和缓存命中率。

纯暂停等待（`sleep`）在 `compact` 模式下不显示运行中或成功完成的卡片，也不新建成功等待的持久投递记录；失败或拒绝仍显示。
`full` 模式保留这类操作，标题为“暂停等待”，“已完成”只表示暂停结束，不表示测试或整个任务完成。
阶段说明与最终回答保持正常展示；该规则仅影响 Gateway 渠道，不改变原生 Codex CLI 的显示。

`display.operation_updates = "compact"` 时，Telegram 和飞书仍展示子代理启动和失败，但不再为成功的
`wait`、`sendInput`、`resumeAgent`、`closeAgent` 分别发送“已完成”卡片；`full` 保留这些操作详情，
`hidden` 隐藏普通操作过程。该设置只控制这两个渠道的过程展示，不改变官方终态和子代理完成统计。
微信不主动发送普通操作或子代理过程事件，以保留单次回复窗口预算。
上下文压缩属于生命周期通知：飞书、Telegram、微信均在官方 `contextCompaction` Item 开始时
独立发送“开始压缩上下文…”，完成时发送“上下文压缩已完成。”，不受 `operation_updates` 影响。
两条通知按会话顺序投递，不合并或原地覆盖；同一 Item 的重复通知不重复发送，只有完成事件时不补造开始提示。
同一 Turn 的成功 MCP、动态工具等查询操作可聚合为摘要：单项保留详情，多项按类别汇总次数，并
展示最多 8 个去重后的查询详情及各自次数；超出时明确省略数量。生产可靠投递入口在每个终态操作后
立即排空该 Turn 的展示缓冲，确保平台确认前不会删除持久结果；因此不再等到最终正文才统一展示这些终态。
飞书网页搜索仍在完成后立即显示，不进入聚合。渠道离线或存在未确认前序结果时，中间快照可以丢弃并记录计数；
关键结果的容量与重启恢复见[投递箱](delivery.md)。

Computer Use／浏览器的 `cua_repl.js` 和 `cua_repl.js_reset` 调用单独展示，不进入查询汇总。
`js` 的操作说明取自调用参数 `title`，经过脱敏和限长后与工具名一起显示；不展示执行代码、
页面正文或原始工具结果。飞书在 `compact` 和 `full` 下为每次调用发送一张开始卡片，终态原地更新
同一张卡片并显示耗时，重复的同一状态不重复发送；开始卡片未送达时直接发送终态卡片，更新失败时
记录错误并单独发送终态消息；`hidden` 仍隐藏操作消息。状态只反映 App Server 的 Item 生命周期，一次调用内的
多次点击不会被拆成推测的步骤，也不自动发送截图或录像。其他渠道沿用各自的开始／终态发送规则。

飞书 MCP 工具审批卡区分“拒绝”（`decline`）和“取消”（`cancel`），两者都不授予权限；
取消、超时或其他客户端已处理后，原卡片的一次性交互令牌失效。一次、会话、持久批准仍以
App Server 提供的范围为准，不从操作标题或工具可用状态推导授权。

MCP 工具目录和普通 Tool Item 中的 `readOnlyHint` 显示为“上游标记只读”“可能写入”或
“读写属性未知”；它只说明上游声明的能力，不表示本次调用成功、实际发生写入或可以跳过审批。
Computer Use 过程卡片不展示该标签，避免将 MCP 工具声明误解为点击、输入等电脑操作的实际权限；
上游字段仍保留，审批规则不变。

MCP Server 详情在 App Server 返回非空、长度受限且符合固定上游 `<plugin>@<marketplace>` 字符规则的
`pluginId` 时显示“来源 Plugin”；
该字段只用于来源排障，不用于授权、审批、命令或脚本来源推断，也不改变 OAuth 自动发现策略。

通过 `/skill`、`/plugin` 或 `/agents` 新建 Turn 时，三个渠道只使用统一的 Turn 生命周期确认，
并在同一条确认中保留具体 Skill、Plugin 或子代理名称，不再额外发送一条扩展启动结果；追加到活动
Turn 时没有新的 Turn 启动事件，因此继续显示明确的追加确认。MCP Server 的首次 `starting` /
`ready` 状态不主动展示；`failed`、`cancelled` 以及异常后恢复为 `ready` 仍会通知。飞书把当前
Turn 的启动回复直接登记为 Thread 状态消息，后续 `active` 不再创建第二张卡，`idle` 原地更新
这张回复并保留扩展身份。

Turn 推理期间，Gateway 消费官方 `item/reasoning/summaryTextDelta`、`summaryPartAdded` 与
`textDelta` 通知。渠道思考状态默认不显示；在 `codexc config → 显示设置 → 思考状态显示` 中开启后，
飞书和 Telegram 按顺序展示“思考中…”状态，连续思考只显示一次，操作打断后再次思考时重新显示一次。
每段独立从 0 开始计时，超过 1 秒时附“耗时”字段并每秒流式原地更新；
飞书使用每段一张的流式卡片，Telegram 原地编辑同一条面板。微信不主动发送推理状态，以保留单次
回复窗口预算。`display.reasoning = false` 时关闭支持渠道的思考状态；摘要与原始思维链内容不进入
渠道；首个回复增量、Turn 错误或完成时结束本段。

Turn 的 `misalignmentPolicyViolation` 结构化错误只在边界和 Core 中保留窄分类，完成卡片统一显示
“请求因安全策略不一致而终止，请调整请求内容或目标后重试。”；上游自由文本和额外细节不直接作为
该分类文案，Turn 指标使用独立的 `misalignment_policy_violation` 分类并保留原协议代码，
`willRetry=false` 与失败终态保持原样。`unauthorized` 结构化错误表示登录或刷新令牌失效，完成卡片
按 OpenAI 官方与其他 Provider 分别提示运行 `codex login` 或发送 `/model`，以及更新对应 Provider
凭据，不展示上游原文。`usageLimitExceeded` 保留明确的用量上限分类，普通额度与 Reserve 额度
耗尽分别提示；自动 Reserve 切换的触发与取消边界见协议索引。其他 `CodexErrorInfo` 沿用脱敏文本。

`/plugin <对象>` 的详情只显示 `plugin/installed` 返回的安全摘要；能力和适用套餐标识各最多展示
8 项并明确省略数量，不显示 Plugin 来源路径、远端 URL、图标、截图或默认提示词。
`/plugin` 与 `/plugin list` 对同一次已安装目录按每页 8 项展示，本地搜索不会调用官方
`plugin/search`，搜索结果仍显示原目录全局序号；`/plugin health` 汇总数量后只列出需要处理的
未启用或不可用项，最多展示 8 项，并单独提示 Marketplace 加载失败。
`health` 与 `list` 是保留的单词子命令；同名 Plugin 带任务时仍按调用处理，查看详情则使用列表中的
全局序号或完整 ID，列表遇到这两个名称时会主动提示。
飞书通过分页卡片和一次性表单收集 Plugin 任务；Telegram 通过当前页按钮选择，并用绑定聊天、Actor
和精确提示消息的十分钟 ForceReply 收集一次任务，搜索结果继续使用文字翻页命令；微信不模拟未验证
的按钮或表单，只为当前页可调用项补充可复制的编号任务命令。

`/mcp` 概览和详情显示当前 Thread 已发布连接的官方运行状态：未启动、正在连接、已连接、需要认证、
失败、已取消或已禁用；未绑定 Thread、配置已经变化或 App Server 未提供运行快照时显示“未知”。
概览为每个 Server 直接提供使用当前列表数字序号的详情命令，不输出不可执行的选择器占位符。
状态查询只读取现有快照，不会启动或重连 Server，工具与资源目录也不代表当前连接可用。
`/mcp health` 先汇总数量，再把需要认证、连接失败或已取消列为需处理项，把认证未知、未启动、
正在连接、已禁用或已连接但未公开能力列为提示；它不把状态读取解释为逐个远端 Server 的网络探测。处理命令使用同次状态列表中的数字序号；需处理
项优先，和提示合计最多展示 8 项，超出时明确省略数量。`/mcp reload` 成功后统一说明已加载
Session 已刷新 MCP 配置；连接建立仍可能异步完成，用户可再次运行 `/mcp health` 查询，不把请求成功
显示为远端握手已经完成。
MCP 详情及分页中的登录、浏览、翻页和资源读取命令沿用用户本次使用的选择器；Server 名称含空格时
使用 `/mcp` 列表中的数字序号，避免把名称重新拼接成无法解析的命令。

## 子代理交互归属

子代理的审批和同步问题沿官方父子 Thread 关系发送到已绑定祖先的渠道会话，支持嵌套子代理。
审批标题标明“子代理”和子 Thread 的短 ID；批准或拒绝仍响应原来的子代理请求，不转换为主代理请求，
也不扩大一次、会话或持久规则授权范围。各渠道复用同一关联和审批逻辑。

父子关系无法确认、工作区或 Provider 不匹配、祖先绑定已撤销或转移时，交互安全拒绝。
无人值守自动化 Thread 及其子代理继续拒绝交互，不因关联到渠道会话而开放审批。
祖先会话的待处理交互保护和取消同时覆盖子代理；解析归属、排队和等待答复共用原有效期。
其他客户端已经处理的请求不会在归属查询结束后重新弹出。
归属查询期间发生的断线取消同样有效；其他会话新建或切换 Thread 不会误拒绝当前审批。

## 文件修改审批

文件审批在批准前显示新增、修改、删除的完整路径；移动同时显示源路径和目标路径。三个渠道
复用同一详情，飞书处理结果卡保留原明细。路径采用 JSON 转义，防止换行、不可见字符或格式符号
改变展示含义。文件清单来自同一 Provider、Thread、Turn 和 Item 的官方文件变更通知，修改理由
单独保留，不用理由或最近一次修改推测文件。关联数据只在当前连接内有界保存，不保存 Diff。

断线清理后重放的审批、未收到对应通知或缓存淘汰时，明确提示“未取得待修改文件明细，请先在
原生 Codex 客户端核对。”；不显示其他 Item 的路径。已观测但无效或超限的清单直接拒绝；完整
审批预览超过 3000 UTF-8 字节同样拒绝，不截断后批准。以上展示不扩大原有一次或会话授权范围。

## 已有终端输入审批

`writeStdin` 审批明确表示向已有终端继续输入，不是运行新命令。飞书、Telegram 与微信复用各自
已有审批入口，完整展示上游输入请求、启动目录和保留权限；预览采用 JSON 转义表示，控制字符及
渠道格式符号使用转义序列，避免显示改变待批准内容。超过共同展示上限时安全中止，不截断后批准。
仅允许一次批准或中止，不提供会话、命令前缀和网络持久授权；原命令获准不代表后续输入自动获准。
无人值守计划任务若收到此审批，会直接中止本轮，不发送交互审批；任务按审批失败记录，Gateway 重启后仍保留这一归因。

## 调试模式

在 `codexc config` 中选择“高级设置 → 日志等级”，设为 `debug` 可全局开启脱敏调试信息，同时启用 Gateway 各模块的脱敏调试日志，并在渠道中显示
启动通知的“运行环境”小节和完成通知的 Token 子项；改为 `info` 后，隐藏这些调试字段，但保留完成通知的
Token 总计。
修改后只需重启 Gateway：

```bash
codexc restart gateway
```

调试日志只记录受约束的类型、阶段、耗时和结果，不记录消息正文、请求参数、上游响应、凭据或
审批内容。分享日志前仍需人工检查。

三个渠道统一提供以下投递诊断，不必为了保留故障证据长期开启 `debug`：

| 等级 | 记录内容 |
| --- | --- |
| `info` | 收到完成正文/轮次结束事件、对应输出任务处理成功、共享路由处理结束；TG 完成正文的格式化与实际投递结果，以及长轮询失败后恢复 |
| `warn` | 输入处理或发送失败、排队加执行总耗时达到 5 秒、执行 10 秒仍未完成的一次告警、格式化降级、输出未入队、容量替换及关闭超时未投递 |
| `debug` | 输入处理、输出执行、平台调用的开始与结束，输出入队结果、同键合并和有序操作取消 |

日志用 `component`、`accountId`、`conversationId`、`threadId`、`turnId` 和 `eventType` 定位；
字段只在对应入口已知时提供；正文事件另带 `itemId`。`inputId` 是平台输入标识，`deliveryId` 关联一次输出任务及其
分片/API 尝试，`diagnosticId` 关联一次阶段的开始与结束。`stage` 为 `input`、`delivery` 或
`api`；共享路由另记录 `stage: routing`、事件总线等待 `eventBusWaitMs` 和路由入队 `routingMs`。
完成统计准备另记录 `stage: enrichment`、本会话等待 `queueWaitMs` 和准备耗时 `executionMs`；
它发生在路由之后、平台输出队列之前，不计入 `routingMs`。飞书正文更新与整卡收尾分别使用
`operation: updateStreamingCard` 和 `finishStreamingCard`，避免把两类请求混在一起。
`purpose` 区分输出任务用途，例如 TG 正文、操作记录刷新和轮次完成卡；“输出任务处理完成”
仅表示该任务回调成功，不表示整个完成事件的正文已发送。“Telegram 完成正文投递完成”只在正文所有分段成功后记录。
`queueWaitMs` 表示进入该阶段前的本地排队时间，`executionMs` 是阶段执行耗时，
`totalMs` 是两者之和，`pending` 是阶段开始时的队列/待处理数量。API 尝试另外记录操作名，
有重试策略时记录 `attempt`、`maximumAttempts`；重试等待仍计入外层输出执行耗时。
飞书 API 阶段完成仅代表 HTTP SDK 调用返回，业务响应仍需经过现有校验；输出任务成功也不代表用户已读。

图片引用准备失败另带 `imageUploadDiagnosticId`、`imageUploadStage`、`imageUploadReason`、
`imageUploadElapsedMs` 和 `imageUploadStageElapsedMs`，与当前渠道的输入标识关联。
阶段区分会话读取、模型配置、本地模型代理、账户与凭据校验、图片校验、文件创建、字节传输和完成确认；
有对应证据时记录白名单内的 `imageUploadNetworkCode`、`imageUploadHttpStatus` 或 `imageUploadRpcCode`。
字节传输另记录 `imageUploadHost`、`imageUploadAttempt` 和 `imageUploadClientRequestId`，只保留目标主机、尝试次数和本地请求标识，不保留 URL 路径或签名查询串。连接、响应头和响应体超时分别提示；目标主机不证明请求实际使用了哪条代理路径。
这些字段不包含原始异常、凭据、签名 URL 或响应正文。微信在发送用户错误提示前也记录图片失败，
不因错误已被处理而丢失诊断。上传耗时不包含后续 Turn 提交等待。

下次出现“终端已有结果，渠道迟迟未收到”时，先保留发生时间和渠道，再查看：

```bash
codexc logs gateway -n 500
```

按 Thread/Turn/Item 找到共享路由记录及“Surface 终态输出已收到”，先检查 `eventBusWaitMs`、`routingMs` 和完成统计准备记录，再按 `deliveryId` 和 `purpose` 查看输出阶段及平台调用：
平台投递阶段的 `queueWaitMs` 只覆盖渠道内等待前序输出，不包含事件总线、共享路由及完成统计准备；`executionMs` 高则检查同 ID 下的 API 超时、错误码、重试或
格式化降级。没有阶段明细时临时开启 `debug` 后复现；缺少日志不能直接认定平台丢消息。
各渠道输出队列独立，同一会话串行；积压可能合并或替换中间状态，关键输出不会仅因容量耗尽被丢弃。
飞书关闭时普通输出可在 5 秒期限内排空，有序交互立即取消；期限结束后，分片、降级、媒体及客户端内部后续请求
都不再启动。短回复未进入流式发送时，正文失败也会独立尝试完成统计。
发送失败与进程关闭仍可能造成未送达，日志本身不提供离线持久化或自动补发；已持久接收结果的恢复与不确定发送处理由独立[投递箱](delivery.md)负责。

需要查看模型请求与响应的完整字段时，在 `codexc config` 中选择“系统设置 → 调用详情记录”，
使用 `[debug].model_traffic_dump` 旁路转储，而不是提高日志等级；文件位置与脱敏边界见
[使用指导](user-guide.md#模型请求转储)。

### 重置券交互

飞书、微信和 Telegram 共用 `/limits reset [页码]` 查看实时可用券，每页最多 8 张；返回券 ID、官方说明和到期时间。飞书和 Telegram 的 `/limits` 附“查看重置券”按钮，券列表使用原生选择、翻页和刷新按钮，预览使用“确认使用”和“取消”按钮。飞书复用模型交互的命令卡片令牌，绑定用户、聊天和消息；Telegram 的选券按钮绑定用户、聊天及列表快照，点击后重新查询，变化或过期则拒绝。微信保留文字交互，其他渠道也支持文字入口。`/limits reset use <券ID>` 只生成预览，显示账户及一次性确认；原用户在原会话、工作区和当前 Thread 明确确认后才消费。消费结果未知时提示查询核对，不自动重试；额度刷新失败与消费结果分开显示。
