# 渠道展示与消息详情

QQ、飞书、Telegram 和微信的可见完成通知统一在原会话正文/流式收尾路径之后，再等待 2 秒发送。该间隔仅为客户端显示缓冲，不是客户端显示完成回执，不改变任务实际结束时间或统计耗时，也不证明此前失败的正文已送达。隐藏完成通知不等待；正文、工具过程和独立投递失败提示不增加该延迟。等待支持取消，发送前仍核对原授权、回复窗口及额度；不新增配置项或持久计时状态。

旧 QQ 群实现及显示配置支持已删除，所有 QQ 群显示覆盖均由严格校验拒绝，不提供查看、修改或恢复继承入口。配置需要由本机操作者先保存私有备份，再明确移除不支持的覆盖，保留单聊及其他设置；不会自动迁移或改写用户文件。删除及本轮单聊修复尚未部署，状态与回退边界见 [QQ 消息合同](qq-message-contract.md#当前实现与待完善范围)。

本页说明 Gateway 完成卡片、`/metrics` 命令和信息类聊天指令的展示口径，以及消息详情
设置控制的技术字段。根目录 README 只保留常用操作，细节以本页为准。

逐批分析、共享呈现与平台适配改动、代码读取和客户端验收进度见 [消息显示统一计划](message-display-unification-plan.md#本轮分批计划)。

微信发送非 `commentary` 的完成正文，包括 Cline 等 Provider 未提供 `phase` 的消息；空阶段保持
官方“阶段未知”的含义，不改写为 `final_answer`。这些正文同样进入可靠投递，超长时使用文本文件发送；
明确标记的 `commentary` 过程消息仍不占用微信回复窗口。
`partial_answer` 是可展示的稳定部分回答，四渠道保留正文及可靠投递，但不据此判定整轮已有最终回答。飞书整轮完成统计统一使用独立卡片，不附着在回答正文上。

## 过程显示范围与继承

可选 `routine_notifications` 布尔值缺省有效为 `true`，读取和安全默认补齐不物化，支持四渠道单聊的全局 → 渠道 → 账号 → 聊天类型 → 指定聊天五层继承。关闭任务开始、普通成功配置提示、成功或运行中的压缩、成功 Hook、自动审批通过、MCP starting/ready、Thread 名称与可用状态。配置提示仅隐藏 `reloaded`、`provider-settings-scheduled`、`provider-settings-restarting`、`provider-settings-applied`；Gateway 即将退出的 restarting 提示保留。失败、拒绝、停止、全部重试、账号与额度、OAuth、需用户动作、正文附件、审批及命令回执保留；Gateway 上线摘要、App Server 连接恢复、会话空闲释放和全局空闲释放始终保留，持久 Workspace 新增回执始终保留。该设置不取消已入 Journal 的投递义务，也不把未发送伪报为已送达。

CLI“常规通知”、WebUI 和 API 使用共享 `display.routine-notifications` 显式 `{ action: "set", value: boolean }` / `{ action: "inherit" }`，拒绝 null、别名和多余字段；读回区分有效 `routineNotificationsEnabled` 与本层 `routineNotificationsOverride`（布尔值或 null）。恢复缺省删除字段；任一渠道启用时全局有效值变化要求重启 Gateway，否则 reload，隐式 true 与显式 true 互换只 reload。范围数组沿整体保守判定。保存前创建私有备份，预览、取消和未变化不写，旧 revision 拒绝；保存后读回不确定不自动重试或回滚。回退不支持此字段的版本前，显式清除全局及所有覆盖中的 `routine_notifications`，核对后续修改，不自动迁移或用旧备份覆盖新修改。当前代码已部署，真实平台完整效果仍待验收。

| 显示字段 | Telegram / 飞书 | 微信 | QQ 单聊 |
| --- | --- | --- | --- |
| `routine_notifications`、`completion`、`presentation_detail` | 支持 | 支持 | 支持 |
| `streaming` | 支持 | 不支持 | 支持 |
| 操作、子代理、过程说明、计划、思考状态 | 支持 | 不支持 | 支持 |

`[display]` 的 `operation_updates = "full" | "detailed" | "compact" | "failures" | "hidden"` 控制工具操作，`failures` 仅展示 `failed` / `declined`；原默认值仍为 `compact`。`plan_updates`、`reasoning` 保留全局含义与原默认值。可选 `subagents` 布尔值缺省有效为 `true`，可选 `completion = "off" | "brief" | "detailed"` 控制完成通知，缺省有效为 `detailed`；二者读取和安全默认补齐均不写入。可选 `[[display.overrides]]` 按全局 → 渠道 → 账号 → 账号的聊天类型 → 指定聊天逐字段覆盖。缺少字段表示继承，`false`、`hidden` 与 `off` 是有效覆盖；恢复继承必须显式删除所选字段，最后一个字段删除后移除该覆盖项。全局子代理和完成通知恢复缺省也删除对应字段，不保存默认值。`display.model_aliases` 独立管理，不参与消息继承。

每项必填 `surface`；可选 `account_id`，`chat_kind` 需要账号，`chat_id` 需要账号及聊天类型。当前聊天类型仅支持 `direct`，`group` 严格拒绝；微信接受 `routine_notifications`、`completion` 与 `presentation_detail`，继续拒绝操作、子代理、流式、过程说明、计划与思考字段。除九个显示字段和上述目标字段外不接受其他键；空覆盖、重复目标、超长身份与超过 512 项均拒绝，读取不修复。Telegram 账号为 `default`，飞书与 QQ 为当前 AppID，微信为配置中的 `account_id`；QQ 单聊 `chat_id` 是收件人的用户 OpenID；不支持物理群或旧成员 Thread 身份。微信精确私聊 ID 与允许名单中的 `allowed_user_ids` 相同，管理仅提供当前启用账号及名单可证明的目标。

可选 `commentary` 布尔值缺省有效为 `true`，普通读取与安全默认补齐不物化。Telegram、飞书及 QQ 单聊按相同五层继承；旧 QQ 群覆盖整体拒绝；微信本来不展示 commentary，覆盖严格拒绝此字段的 true/false，管理字段列表不提供该选项。关闭只隐藏明确 `phase = commentary` 的新过程说明，不控制 `reasoning` 状态或原始推理。未知或空阶段的完整正文保留；关闭时未知阶段增量先缓冲且暂不预览，待明确 `final_answer` 或完整 Item 再展示，避免晚到 commentary 泄漏。已经按可显示正文准入的流仍按原义务收尾；已入 Journal 内容继续投递。正文、附件、审批、失败、任务与模型不受此开关改变。

CLI“过程说明”和 WebUI 使用共享 `display.commentary` 管理：显式 `{ action: "set", value: boolean }` / `{ action: "inherit" }`，读取区分有效 `commentaryEnabled` 与本层 `commentaryOverride`（布尔值或 `null`）。恢复缺省删除字段。有效值变化且 Telegram、飞书或 QQ 任一启用时要求重启 Gateway，否则 reload；隐式开启与显式开启互换只 reload，范围数组继续整体保守判定。预览、取消与未变化不写，旧 revision 拒绝；保存前创建私有备份，读回不确定不自动重试。回退不支持该字段的版本前，显式清除全局及所有覆盖中的 `commentary`，核对备份后的修改，勿直接恢复备份覆盖新修改。当前代码已部署，真实平台完整效果仍待验收。

可选 `streaming` 布尔值缺省有效为 `true`，读取与安全默认补齐不物化；支持全局及相同五层继承，只控制 Telegram、飞书与 QQ 单聊中用户可见的 `text.delta` 正文预览。不改变上游模型流式、思考状态、完整 `text.completed` 正文、附件、授权、原回复窗口或可靠交付义务。微信覆盖严格拒绝 `streaming = true` 与 `false`；QQ 群类型及精确群覆盖整体拒绝；QQ 渠道或账号层可设置，但只作用其单聊。微信管理字段列表不展示流式选项。全局 `display.streaming` 写入接受 `{ action: "set", value: boolean }` 或 `{ action: "inherit" }`，读取区分有效 `streamingEnabled` 与本层 `streamingOverride`（布尔值或 `null`）。Telegram、飞书或 QQ 任一启用时有效值变化要求重启 Gateway，否则 reload；隐式开启与显式开启互换只 reload。范围覆盖数组仍整体保守判定；保存前创建私有备份，预览、取消和未变化不写，过期 revision 拒绝。回退不支持该字段的版本前显式清除全局及所有覆盖中的 `streaming`，核对备份后的修改，不直接覆盖配置。当前代码已部署，平台完整效果仍待验收。

可选 `presentation_detail = "basic" | "detailed" | "full"` 按相同五层逐字段继承，缺省有效为 `basic`，读取与安全默认补齐不物化。它独立控制聊天可见的上线、完成、子代理和自动审批通过通知；基础使用紧凑摘要，详细保留日常明细，完整展开可用统计分项和环境信息。日志等级、调用采集、开发运行方式、任务执行、审批和完成通知开关各自独立。管理读取返回有效 `presentationDetail` 与本层 `presentationDetailOverride`（缺省 `null`），全局写入使用 `display.presentation-detail` 的显式 `set` / `inherit`。四渠道中任一启用时全局有效值变化要求重启 Gateway，否则 reload；缺省基础与显式基础互换只要求 reload，范围覆盖数组仍整体保守判定。保存前创建私有备份；回退到不支持该字段的版本前显式清除全局和所有覆盖中的 `presentation_detail`，核对后续修改，勿用旧备份覆盖新修改。

`subagents = false` 同时隐藏 `subagent.spawned`、`subagent.contacted`、`subagent.completed` 和 `operation.kind = subagent`，其他工具仍由操作档位控制。它只控制新事件的渠道展示，不限制 Core 子代理执行，不影响正文、图片、审批与父轮完成或失败；既有 Journal pending 子代理结果仍按原义务投递。全局管理读取区分 `subagentsEnabled` 有效值与 `subagentsOverride`（布尔值或缺省 `null`），写入使用显式 `set` / `inherit`。全局有效值只在已启用 Telegram、飞书或 QQ 时变化要求重启 Gateway；仅微信时重新读取即可。范围覆盖数组仍作为整体配置单元判定重启。

完成通知 `off` 只隐藏新的成功且没有错误、没有权威 `missingFinalResponse` 的事件；失败、停止、缺少最终回答仍保留准确回执。`brief` 使用精简结果，不意味着最终正文已送达；`detailed` 保留详细统计。基础（紧凑）、详细、完整及 `brief` 完成卡均保留已采集的非零 `OpenAI Credits`，主轮与任务合计（含子代理）分别显示；数值来自上游 `usage_metadata.amount`，缺失不估算；部分已入库请求缺少该字段时标注缺失请求数，也不代表未采集请求没有消耗。既有 Journal pending 完成记录继续按原投递义务发送。Credits 扩展显示尚未部署，四渠道全部显示组合与重启后的平台效果尚未完整验收。

全局完成通知只有有效值改变且存在启用渠道时才要求重启；缺省 `detailed` 与显式 `detailed` 互换只 reload，重复完全相同配置为 none。QQ 隐藏的实时计划、思考及常规状态在共享快照入队前过滤，仍先观察状态变化；不会把主动隐藏误报成原任务来源失效，也不会取消隐藏完成的独立收尾。

`codexc config → Gateway 显示设置 → 范围显示覆盖` 与 WebUI“消息渠道 → 消息展示”使用同一目标验证、计算、修订保护和写入事务。界面分开显示本层覆盖、有效值及逐字段来源。渠道、账号、私聊默认来自当前启用配置；QQ 精确目标仅来自单聊名单，不生成群目标，飞书精确私聊来自当前 Schema 的前台/后台绑定和仍获授权的 Actor。没有状态库不创建它；不可读或不兼容时明确提示，仍可编辑渠道/账号默认。Telegram 历史绑定不含可证明的聊天类型，暂不提供精确聊天编辑。已有目标停用或移除后覆盖保留只读，允许显式恢复继承；不会阻止停用渠道或把旧覆盖归给新账号。 显示管理操作顶层仅接受 `kind` 与 `value`，未知字段一律拒绝；全局单字段的 set/inherit 共用编辑逻辑，目标范围必须通过 `display.scope` 或范围预设明确指定。

Telegram 运行时只从当前进程收到且仍获授权的 `private` 输入确认聊天类型，不按 ID 正负号或历史绑定猜测。该确认仅保存在最多 4096 项的进程内记录中，重启、撤权或容量淘汰后，未重新确认的目标会保守隐藏工具、计划、思考并将成功完成通知按 `off` 处理，直到收到新的授权私聊输入；必要错误、停止和缺正文回执仍保留。全局或账号设置开启不代表后台续跑必然展示这些通知。该限制不取消已经入箱的可靠投递义务，也不影响正文、审批和整轮异常的独立处理。

预览与取消不写，未变化不写、不要求重启；保存拒绝过期修订，并在新增、编辑或清除覆盖前创建私有配置备份。新增覆盖要求新版二进制，普通读取或安全默认补齐不会物化覆盖。保存后重启 Gateway，新事件按新设置准入；已经入箱的 pending 保留原投递义务，仍可能发送，重启恢复不保证与原先详细或紧凑版式完全相同。保存后读回失败保留已保存配置并报告未确认，不自动重复或回滚。

回退时先停止配置写入，核对保存返回的私有备份与后续修改，再选择匹配旧二进制的配置。`subagents` 与 `failures` 要求新版；保存子代理设置与范围覆盖、或选择全局 `failures` 时均先创建备份。发生后续修改时逐字段处理，禁止直接恢复旧备份覆盖它们。回退 P3c 之前版本时显式清除全局及所有覆盖中的 `subagents`，并把全局及覆盖中的 `failures` 改为旧版支持值；若回退到不支持完成与范围覆盖的版本，再显式清除全部新增覆盖并恢复全局完成通知缺省，确认没有 `completion`。不自动迁移、清理或写入默认值。此变更不修改 StateStore、投递 Journal 或其恢复格式。

四渠道的上线通知和实际发送的任务完成通知均显示工作区及已取得的 Git 分支，所有呈现详情档位及 `brief` 完成通知都采用此规则。上线使用当前所选工作区，完成使用事件所属工作区；Git 分支来自登记工作区的只读查询，不表示任务期间固定的分支。未检测到分支（包括非 Git 目录、游离 HEAD、查询失败或超时）时隐藏 Git 整行；完成事件缺少工作区名称时使用 ID，两者均缺失则显示“未知”。工作目录仍仅在详细／完整上线通知中展示。完成通知的发送开关保持原规则。
这项工作区/Git 字段改动已通过 PR #307 合入 `f966f45b`。用户截图已出现完成通知的工作区字段，但未关联精确运行提交，也未覆盖四渠道所有场景；合并状态不等于部署或验收完成。

共享“已开始处理”及后台继续处理内容同样提供任务所属工作区和已取得的 Git 分支，普通任务与 Skill、Plugin、代理任务共用此规则，不受呈现详情档位限制。开始与完成的分支查询使用事件的工作区 ID，不随前台工作区切换而改查其他项目；工作区已移除或缺少 ID 时不猜测目录。查询最多等待 250 ms，失败、超时或非分支状态隐藏 Git 整行。开始通知仍受 `routine_notifications` 控制，关闭时不新增通知。字段与查询改动同属 PR #307，真实客户端验收边界按上一段记录。

开始通知的加粗正文标题、字段顺序和列表结构由共享呈现层决定，QQ 不再单独覆盖标题样式。飞书、QQ、微信使用共享 Markdown，Telegram 在发送边界转换成 HTML；动态标题仅在对应格式边界转义。微信开始通知与上线、完成通知采用同一结构化格式，字段逐项列出，普通标题为“已开始处理”。文本消息接口不代表客户端不会解析 Markdown。飞书已准入的开始回执无论有无回复目标均使用共享内容，与独立更新的 Session 状态卡分开，后续状态更新不覆盖回执中的工作区/Git。交付与验收进度见 [分批计划](message-display-unification-plan.md#本轮分批计划)；代理未执行部署或重启，用户自行重启后的运行版本和效果未确认。微信加粗与列表能力已有修改前截图，不能替代 R1 验收。

## 一次应用显示预设

“静默”是原“简洁”预设的显示名称，接口标识仍为 `concise`，不迁移已有配置。
“紧凑”是原“标准”的显示名称，接口标识仍为 `standard`。详细预设使用 `operation_updates = "detailed"`，呈现日常可读明细；完整预设 `full` 使用 `operation_updates = "full"` 和 `presentation_detail = "full"`，展开可用明细并过滤重复过程通知。
静默预设关闭正常成功完成卡，保留正文结果、失败/中断/无最终回复提示、必要交互及上线、恢复、空闲释放通知；不代表平台消息免打扰或关闭声音。紧凑预设隐藏工具过程，保留子代理动态、过程说明、计划和完成卡。

CLI 和 WebUI 提供“静默 / 紧凑 / 详细 / 完整”，预设一次写入现有显示字段，之后仍可逐项调整。它不是新的运行模式，配置不保存 `preset` 字段；界面按当前有效值识别预设，不匹配时显示“自定义”。已有静默或紧凑字段组合不会自动改写，更新后在原目标范围重新应用预设才采用新组合；旧组合可能识别为自定义。未配置的缺省值保持原状，预设不重置日志、采集、模型统计分组或 Telegram 消息格式。

| 操作详情 | 隐藏 | 隐藏 | 关键详情，失败保留完整脱敏详情 | 逐项完整脱敏详情 |
| 子代理、过程说明、常规通知、计划 | 关闭 | 开启 | 开启 | 开启 |
| 正文流式 | 开启 | 开启 | 开启 | 开启 |
| 思考状态 | 关闭 | 关闭 | 关闭 | 开启 |
| 成功完成通知 | 关闭 | 状态、上下文、耗时 | 本轮关键统计 | 本轮统计及可用分项 |
| Gateway 上线、App Server 连接恢复 | 保留 | 保留 | 保留 | 保留 |
| 会话空闲释放、全局空闲释放 | 保留 | 保留 | 保留 | 保留 |
| 消息详情 | 基础 | 基础 | 详细 | 完整 |

思考状态与完成卡的推理次数独立：只有完整预设开启“思考中”过程状态，详细和完整完成卡保留已观测推理次数。旧详细配置已保存的 `reasoning = true` 不自动改写，更新后需在目标范围重新应用详细预设；自定义开关和下层覆盖继续按原继承规则生效。

完整模式的思考状态仍依赖 App Server 推理事件，不保证每轮出现。当前用户实测反馈：DS 会话在 QQ、Telegram 可见思考状态，OpenAI 会话在飞书未见；这组观察同时存在渠道与 Provider 差异，尚未确认原因，不能据此判定飞书或 OpenAI 故障。该问题单独跟进，不以模式配置、推理统计或摘要配置已保存代替实时投递证据。

紧凑沿用 `completion = "detailed"` 与 `presentation_detail = "basic"`：完成通知保留工作区、已取得的 Git 分支、状态、上下文、已知耗时及必要异常，
`brief` 仍不增加耗时。基础上线通知保留连接状态、版本、工作区、已取得的 Git 分支与必要鉴权/健康警告；当前聊天有效设置匹配紧凑预设或属于自定义时，另显示会话名称、模型与提供商、思考与速度、审批方式和显示模式，避免原紧凑组合改识别为自定义后丢失上线会话信息。未绑定时明确提示，不展示默认模型冒充当前会话；尚未恢复时不展示未确认设置。模式识别沿用现有预设判定，微信仅比较支持字段。上线及完成通知使用正文加粗标题。
子代理启动、继续、完成只显示名称和状态，支持富文本时状态加粗、名称使用普通文字，不使用大标题；失败、中断等终态也保留。
当前生命周期事件不含任务正文摘要，不推测任务内容。自动审批通过只显示结果、动作类别和必要来源，拒绝、超时、中止仍保留理由。
自定义选择基础详情仍使用精简完成、子代理及自动审批摘要，上线保留会话扩展并标为自定义模式；主动 `/status`、`/metrics` 和审批详情不被裁剪。

详细上线在会话摘要上增加工作目录、Session ID 和协作模式，不自动展开系统、时区、Node.js、UA 或账户额度。详细子代理开始/继续保留名称和模型设置，完成保留请求次数、Token 总计及可靠的缓存命中率，不展开 Token 分项。自动审批通过保留来源、动作类别、操作摘要和理由摘要，摘要沿既有脱敏逻辑限制为160字符并标记省略；拒绝、超时、中止和人工审批授权详情保持完整必要信息。
详细工具档正常详情脱敏后折叠为单行，最多600字符并标注省略；失败和拒绝保留既有完整脱敏详情。详细档的批量成功查询仍使用既有聚合摘要；完整工具档逐项显示现有详情，不再把多个成功查询压成摘要。旧配置不自动改写：完整工具＋详细消息组合仍是自定义，完整预设需要消息详情也为 `full`。回退到不支持新值的版本前，将全局和范围的 `operation_updates = "detailed"`、`presentation_detail = "full"` 改为旧版支持值。应用仍经过预览、私有备份和激活流程。

详细和完整模式的完成卡共用“当前账户额度”分区：OpenAI 显示已取得的周限，第三方显示匹配本轮提供商的余额或额度；有重置时间时显示时区、重置时间及剩余时间，缺少数据不补造。静默、紧凑及显式精简完成通知不增加此分区。

完整消息详情在详细版基础上增加上线环境、本轮 Token 分项、可用性能与压缩请求统计及官方 Credits；子代理完成展开其已有 Token 分项，自动审批通过保留操作与理由详情。上下文占用始终独立于累计消耗；缓存和推理输出是总量的子项，不再次相加。完成卡不复制最终正文，不追加会话累计和重复 Session 信息；主轮与任务合计（含子代理）分开。缺失数据不推算，失败、停止和缺正文提示保留。正常子代理等待仍隐藏，渠道字数、脱敏和发送权限限制仍适用。微信仅应用支持字段。

应用全局预设不覆盖已有的下层设置；全局有效值已经匹配时不写入默认字段。应用到渠道、账号或聊天范围时，会在所选层固定全部受支持字段，即使与继承值相同也属于来源变化。微信只写三项；QQ 群目标严格拒绝，不能应用预设；不支持的字段不会被静默塞入配置。之后可逐项恢复继承，最后一项删除后移除覆盖。

精简完成通知始终显示上下文：使用最近一次权威用量的 `last.totalTokens` 与 `modelContextWindow`，不使用会话累计消耗。
缺少用量显示“暂不可用”，只有占用数而没有有效窗口时显示“窗口上限未知”；失败、停止和缺少最终回答仍保留必要说明。
静默预设写入 `completion = "off"`；已有显式 `brief` 不自动改写，再次应用预设后才改变。已有下层覆盖继续生效。

管理请求 `display.preset` 接受 `{ preset: "concise" | "standard" | "detailed" | "full", selector?: ... }`，目标沿用范围设置的严格校验与授权；`custom` 仅供读取，不可写入。确认后一次事务保存，沿用修订保护、私有备份、读回及激活判定。取消、预览和未变化不写；保存后读回失败不自动回滚或重试。失败、审批、正文和既有可靠投递义务不随静默预设关闭。预设不增加持久化格式，回退按其实际写入的字段处理。

## 引用与提醒的渠道能力

引用、是否发送、客户端提醒是三个独立概念。当前没有可保存的 `quote` 或 `silent` 显示字段；关闭常规通知表示不发送对应的新通知，不表示静默发送。入站引用提供给模型的上下文也不由出站展示策略删除。

| 渠道 | 当前出站引用策略 | 当前提醒策略 |
| --- | --- | --- |
| Telegram | Turn 正文首片和完成回执引用已绑定的原输入；后续分片不重复引用，审批与命令面板独立发送 | 支持 `disable_notification`；思考、过程和普通成功完成静默，异常完成及审批最后片按普通提醒发送 |
| 飞书 | 开始与正文可回复原输入，静态分片只首片引用；完成统计、审批及媒体独立发送 | 当前 Gateway create/reply 接口没有显式静默参数；原地更新减少新消息数量，但不等于静默发送 |
| QQ | 单聊不附展示引用；旧群引用实现已删除 | 当前接入没有静默参数；主动/被动模式决定发送资格，不代表提醒方式 |
| 微信 | 当前 Gateway 出站接口不开放展示引用；入站引用仍作为输入上下文 | 当前文本及媒体接口没有静默参数 |

上述描述限定于当前接入，不表示平台不存在其他能力。QQ 的 `msg_id/event_id` 被动回复锚点与 `msg_idx/message_reference` 展示引用不同；微信的 `context_token` 是回复上下文。关闭展示引用或通知不能删除这些发送资格数据。Telegram 静默仅描述提交的 API 参数，实际声音和移动端/桌面端显示取决于客户端；本批未在真实平台观察。

## QQ 上线与任务结束通知

QQ 使用共享 `createStartupPresentation` 和 `createTurnCompletedPresentation`，经 QQ Markdown 适配发送上线及任务结束通知；不适合 Markdown 的内容使用可读原文计划。
上线、Hook 和自动审批同样从共享结构同时生成原文字与 Markdown 候选；发送前无法采用 Markdown 时，工作区、操作和理由中的尖括号、星号与反斜杠保持原值，不展示 Markdown 转义源码。微信 Hook/自动审批直接消费共享结构化内容；Telegram 生命周期按共享结构生成 HTML，字面值中的换行和格式字符不会成为额外标题或字段。子代理所有详情档位均只强调状态、名称保持普通正文，档位只改变明细字段。
上线通知在 Gateway 本次生命周期首次 QQ 就绪后向启动允许名单中仍有授权且工作区有效的用户尝试发送一次，普通重连不重复；不创建或恢复任务回传来源。
任务结束通知沿共享完成信息补全和持久投递取得精确 Thread/Turn 的统计，缺失统计不伪装成零，正文送达仍单独核对。
两类通知沿 QQ 完整文字计划及账号/接收人预算；完成通知还受每 Turn 状态片预算约束。超限明确失败，不截断冒充成功。
关闭或撤权会阻止尚未发送的步骤；平台已接收的消息无法撤回。QQ 可在同一气泡内更新被动正文流，最终全文通过共享投递确认；审批与问题交互使用完整预览及来源绑定的按钮。流式窗口、失败及验收范围见 [QQ 消息合同](qq-message-contract.md#正文流式生产任务与同气泡显示已观察)。

QQ 任务过程沿共享事件与展示配置接入：计划、工具与思考状态分别遵循目标的有效范围设置，思考不显示原始推理内容；完整 commentary 单独交付，不进入正文流或文件回退。每 Turn 过程最多八片，正文十六片与完成状态两片单独计数，但仍共同受账号和收件人限额约束。过程失败不改写任务执行结果，可靠事件的未确认发送留在共享投递箱；任务开始通知复用共享“已开始处理”及权威审批方式，遵守常规通知开关。当前代码已部署，实际观察范围见 [任务过程反馈](qq-message-contract.md#任务过程反馈)。

## 完成卡速度档位

固定规则：完成卡只按本轮实际出站请求的 `request_service_tier` 显示速度，禁止使用响应 `service_tier` 覆盖或补齐请求档位。
2026-10-23 回归记录：`5b693ddd` 曾优先采用响应档位，导致实际请求 `priority` 的 Fast 被响应 `default` 显示成 Standard。
后续维护不得恢复该优先级；响应值仅保留在指标明细中，不能据此改写 Fast 展示或断言 Fast 请求未发送。

完成卡的速度档位使用精确 Thread/Turn 的普通模型出站请求观测，不以当前用户选择或上游响应值覆盖请求档位。
本轮已记录请求档位完整一致时显示 Standard/Fast/Ultrafast；请求为 `priority`、响应为 `default` 时仍显示 Fast。
这表示本轮实际请求使用的档位，不承诺上游调度或计费结果。同轮请求出现多个档位时显示“多档位（请求档位）”；缺失观测不默认成 Standard。
Standard 请求可省略 `service_tier`。新采集在完整解析请求并确认字段省略或为 null 时记录 `default`，因此正常切回 Standard 不被当作缺失；历史空值、解析不完整或异常字段不回填、不猜测。HTTP 超出已有完整解析预算时仍可能显示未观测。
统计排除子代理、自动审查、压缩、图片和 Relay 请求，`priority` 与 `fast` 按既有合同统一为 Fast。
指标读取继续受完成消息的总预算约束，读取失败或超时不从当前会话设置猜测本轮值；完全没有请求档位观测时，
保留完成事件原有的已确认快照并标注“设置快照”。出现部分或混合请求档位观测后，不再用该快照填补缺失。
锁定上游 TUI 的 `chatwidget/service_tiers.rs` 从当前有效设置取得档位，`chatwidget/status_surfaces.rs` 以 `priority`
判断 Fast 开关；该展示没有采用响应 `service_tier`。Gateway 的完成卡进一步限定为本轮已记录的出站请求。

## 模型请求自动重试

App Server 明确报告本轮模型请求仍会重试时，各渠道显示“模型请求暂时中断，Codex 正在自动重试，请稍候。”，不受消息详情、日志等级、思考显示或操作显示档位影响。同一连续重试过程不重复通知；收到后续模型文本或推理输出后显示“已收到模型输出，正在继续处理。”，仅表示已有新输出，不保证整个连接已经恢复。

Telegram 与飞书按渠道、账号、聊天、Thread 和 Turn 隔离状态消息，尽量编辑同一消息或卡片；停止、失败或完成时更新已有状态，不另建过期的终态通知。微信每个 Turn 最多发送一次重试提示和一次收到输出提示，最终状态由既有完成、停止或失败汇报说明；这些提示纳入回复窗口预算。QQ 沿用这两次有界提示，纳入任务过程额度，不尝试编辑已有重试消息。展示使用固定文案和短 Thread ID，不显示原始错误、模型请求地址或推测的重试次数。

重试提示只使用有界内存快照，不写入可靠结果日志或在 Gateway 重启后补发；积压仅保留最新状态，结束后尚未发送的重试过程可淘汰。恢复时仅有“收到输出”或终态快照、但没有对应已发送重试状态时跳过展示。新一轮开始、连接中断、解绑或 Thread 回退、关闭、归档、删除后，已有 Telegram/飞书状态通过独立授权的快照更新为“模型重试状态已失效，请以当前会话状态为准。”；不把失效推断为模型 Turn 已停止，归属变更时不向新归属发送旧状态。微信的同 Turn 提示预算跨断线保留，直至官方完成、新一轮开始或渠道关闭；内存记录有数量上限。状态编辑失败不会取消最终结果投递，未确认的操作不视为已送达。

## 模型统计分组

模型统计分组通过 `codexc config → Gateway 显示设置 → 模型统计分组` 或 WebUI“模型管理 → 模型配置 → 模型统计分组”维护。
配置仍为 Gateway TOML 的 `[display.model_aliases]`，键是精确原始模型 ID，值是统计组名；默认空映射。
例如 `"cline-pass/deepseek-v4.1-flash" = "deepseek-flash"`。映射仅用于控制台“按模型统计”的汇总，
同一 ID 可跨提供商归入同一统计组，组内保留各提供商及原始模型的明细。
模型选择、当前模型、会话与请求明细、调用转储、模型管理及 Relay 均保留原模型，不用统计组名替换。
渠道模型列表继续区分提供商与模型；提供商统一显示为 `DS <账户>`、`CLP <账户>`、`CCG <账户>`、`OCG <账户>`、`CP <名称>`；历史聚合记录保留 `AGG` 标签。
原始 ID 可直接用于 `/model <原始 ID>`，文本选择使用序号或原始 ID；原生 Codex TUI、模型目录、模型升级提示及实际请求使用原模型。

映射区分大小写，只查找一次，不猜前缀或递归展开；`A → B`、`B → C` 分别归入 B、C。
最多 128 个原始 ID，ID 长度 1–265 字符，统计组名 1–120 字符；拒绝控制字符、首尾空白、
空名、不完整 Unicode 及保留对象键。一个 ID 只能属于一个组；未匹配的模型按原始模型 ID 统计。
聚合提供商当前关闭，不展示可选聚合模型目录；已有完整 ID（`账户Provider/成员模型ID`）的
统计分组配置与历史指标保留，不反向改写独立成员目录，也不因关闭删除历史数据。

控制台按模型统计在查询阶段按统计组名合并，请求数、Token、缓存样本及请求状态使用同一请求范围，
审查请求同样按已记录模型归组，并以“其中自动审查”列出；请求及调用转储独立展示用途标签。
不从模型名推断用途，未记录用途的历史请求仍按已记录模型及统计映射处理。
轮次按组内 Thread/Turn 去重，不直接相加各模型的轮数。原始记录、提供商汇总、筛选值、导出、
请求/响应名称对照、Relay 可复制 ID 均保留原值；CLI、子代理与频道指标按原始模型统计。
控制台每张模型卡片可展开明细，按“提供商 + 原始模型 ID”显示请求数、轮次、输入、缓存命中率和输出。
明细与合计使用同一时间范围和读取快照，明细轮次各自在对应来源内去重；同一轮跨模型调用时，
明细轮数之和可能大于统计组的去重合计。展开内容保留原始模型名，便于区分映射前的来源。
配置保存有版本冲突检查与备份，删除映射不删除历史数据。控制台重新读取后生效，无需重启 Gateway 或 WebUI。
WebUI 预览失败或取消确认保留编辑草稿；配置版本变化后需关闭并重新打开编辑，核对最新成员，避免覆盖并发修改。

## Telegram 交互回复

普通问题、异步问题和 MCP 表单的消息以粗体“Codex 交互回复”开头，长消息的每个分片都保留该标记。
回复没有对应活动请求的旧消息时，Gateway 提示已处理或失效，不将内容提交到当前会话。
重启或最近 1,000 条消息身份缓存淘汰后，仍通过当前 Bot 的非转发消息来源和固定标记识别，
不恢复旧交互，也不持久化问题或表单正文。普通引用与其他发送者的消息不凭正文关键词判为交互。
普通回答或面板使用同名首行时，文字保持不变，首行不加粗；Rich Markdown 也遵循该规则，避免引用普通回答时被误判失效。

## Hook 提示

Telegram、飞书和微信仅在收到 App Server 的 `hook/completed` 后提示，忽略 `hook/started`。
提示按上游终态显示已完成、执行失败、已阻断或已停止，并标明触发事件。
Gateway 不按执行模式额外过滤，也不推测或补造通知。当前锁定上游只为非内置的同步 hook 发出这些通知，
因此未发出通知的异步或内置 hook 不会出现提示。
Hook 状态不代表整个 Turn 的状态，也不会自动授予审批权限。只向当前可路由的 Thread 会话发送，
不广播无归属通知，不读取 hook 配置文件推测执行结果。

提示不转发 hook 的原始输出、自由文本状态说明或本机路径，按 Thread 和 Hook 运行 ID 进入已有有界内存快照队列，
等待同会话待发送的持久输出结算后投递，并在发送前重新检查归属；不写入历史或持久输出日志，
重启后不补发。微信将 Hook 完成纳入现有回复窗口预算；平台拒绝或窗口耗尽时仍沿用现有投递错误处理。
真实 hook 触发到客户端显示的完整链路尚待部署后观察。

## 异步问题

模型调用 `request_user_input_async` 时，Telegram、飞书、QQ 和微信显示“异步问题（任务继续执行）”。
工具是否可用取决于上游模型目录，Gateway 没有额外开关。问题不会暂停任务，也不计作最终答复；
等待回答不会挡住命令、文件或权限审批。异步回答不授予这些审批权限。

- Telegram 通过按钮选择建议答案，或选择其他答案后回复对应消息；纯文本问题直接回复问题消息。
- 飞书在原问题表单中选择或填写答案后提交。
- QQ 通过选项按钮或带原请求令牌的文字命令回答，分页和自由填写入口保持独立。
- 微信使用问题中提供的带令牌回答命令，支持选项序号与自由文本。

Telegram 普通及异步题干统一使用安全 Markdown 渲染，包括代码块；标题与问题标签按字面值呈现。长问题的所有分片均可作为当前问题的回复目标；
切换到下一题后，上一题的分片失效。处理结果按纯文本转义并限制长度，避免答案中的代码影响状态更新。

飞书普通与异步问题正文均保留安全 Markdown 与代码围栏，异步处理后的结果卡片仍保留同一段问题正文。
正文沿用 1,000 字符展示上限；超限时闭合反引号或波浪线代码围栏，再明确提示截断，
此时应让 Codex 分段提供完整内容后再复制代码。实际代码块展示与复制入口取决于飞书客户端。

微信普通与异步题干均保留 Markdown，长内容分片时闭合并重开代码围栏，回答指令与正文分开。
标题、题号与选项按字面值转义，选项提交仍使用原值；QQ 同样分离题干 Markdown 与元数据，并保留完整原文字备选。
整组提示仍受 16,000 字符上限约束；超限或围栏无法安全分片时明确取消，要求缩短问题后重新提问。
微信固定选项也须满足既有 1,000 字符回答上限；超过时在展示前明确取消并提示缩短选项，不生成无法作答的按钮或命令。

每批最多展示三个问题，较多问题依次分批，每批完整回答后提交一次普通用户消息。四渠道共享题号文案，
异步分批显示原全局题号（如“问题 4/6”），不再重复附加局部“问题 1/3”；回答命令和按钮仍使用原本的批内索引及问题 ID。
飞书不同选项若在现有 100 字符标签截断后无法区分，则安全取消，不提供歧义选择或修改提交值。
飞书固定选项还须满足现有 1,000 字符表单回调上限；选择提交保留原选项首尾空格，自由填写仍按原规则去除首尾空白。
Telegram 在正文完整列出编号选项，按钮使用相同编号；不依赖客户端截短的按钮文字来区分长选项。
提交时仍须属于原 Thread：当前有活动 Turn 时追加输入，空闲时在原 Thread 启动新 Turn。
普通 Turn 完成后，尚未过期的问题仍可回答；问题本身不自动创建后台队列或重放输入。
卡片显示已提交回答表示渠道已收集表单；如果 App Server 提交失败或结果未知，会另行提示核对原会话，
不会自动重发。

问题只在当前 Gateway 进程内保存，沿用审批超时配置，整个问题组从收到通知开始计时。
切换或解绑会话、回退历史、失败或中断 Turn、App Server 或对应渠道账号连接断开与 Gateway 停止会使问题失效；
渠道恢复后不会重新打开旧问题组的后续批次；已发往 App Server 的回答无法撤回，结果未知时仍提示核对原会话。
后台会话问题不弹出可提交交互，而是提示当前无法回答。重启后不恢复问题卡片，请核对会话后重新发送消息。
问题内容不保存到 Gateway 数据库。上游没有异步问题的跨客户端解决通知，因此在原生 TUI 回答不会自动关闭渠道卡片。

## 等待式问题

模型调用官方 `request_user_input` 时，Gateway 响应原来的 `item/tool/requestUserInput` 请求，
不把回答改发为普通消息。`isBlocking: true` 显示“Codex 等待回答”，`false` 显示“Codex 请求补充信息（可跳过）”。
渠道交互沿用配置的有效期；过期、取消或渠道不可用时返回空答案，不代选建议项。
已弃用的 `autoResolutionMs` 不再决定渠道有效期；缺失或畸形的 `isBlocking` 请求返回空答案。

原生 TUI 对非阻塞问题采用 60 秒宽限加 60 秒倒计时，无人操作时返回空答案继续；
开始操作会停止自动跳过，阻塞问题没有这项倒计时。渠道表单没有统一的开始输入事件，
因此不复制 TUI 的倒计时与输入暂停机制，使用上述渠道有效期。工具等待不意味着必须收到非空答案才能继续。

固定版本在 Default 执行模式下默认不开放该工具；上游 `default_mode_request_user_input` 仍为开发中开关，
Gateway 不自动启用。隔离 App Server 探测确认启用后可等待回答并在原 Turn 接续，且仍返回 `isBlocking: false`；
这不构成暂停全部后台命令或其他任务的保证，也不会把已经发出的异步问题转换成等待问题。

## 完成汇报

WebUI、CLI 人类可读输出、转储详情和渠道的耗时展示统一为自适应单位：不足 1 秒使用整数 `ms`，四舍五入；不足 1 分钟使用 `s`，
最多保留两位小数并省略末尾零；更长耗时四舍五入到整秒，不足一小时组合为 `min` 与 `s`，达到小时后只显示 `h` 与分钟，省略秒和零分钟，例如 `672 ms`、`1.25 s`、`1 min 5 s`、`2 h 57 min`。
进位后切换单位；缺失值保持未知，不显示为零。数据库、API、JSON/CSV 的 `*Ms` 字段仍为毫秒原值。

每次 Turn 完成后，卡片标题表明运行状态。基础仅显示上下文、可用耗时及必要异常；详细增加模型与提供商、思考与实际速度档位、模型请求结果、已观测推理次数、本轮 Token 总计及可靠的缓存命中率，并显示已取得的当前账户额度。有明确子代理合计时单列“任务合计（含子代理）”，不混入主轮 Token；后台身份、Goal、仍运行子代理及必要异常保留。详细不自动展开 Token 输入/输出分项、性能分项、当前会话重复字段或会话累计，主动 `/status`、`/metrics` 的数据不受影响。
完成通知不以会话累计或最近请求冒充本轮 Token；本轮输入或输出统计缺失时省略总计，缺少上下文用量仍明确提示。模型及错误文本按原文处理，换行不能注入新的标题或列表。四渠道复用共享完成卡结构，再分别适配 Markdown、HTML 或文本。
QQ 完成卡从同一共享结构生成 Markdown 与纯文本两种表示；安全规划不接受 Markdown 或分片预算不足时，使用未加 Markdown 转义符的纯文本，发送尝试后不自动改格式重发。

上线会话摘要显示已确认的审批方式，未知时明确提示；Turn 启动卡仅在当前 Session 开启自动审批时显示“审批方式：自动审批”。
该值来自 App Server 的 Thread 启动、恢复或分叉响应及 `thread/settings/updated` 权威设置：
`auto_review` 与 `guardian_subagent` 都显示“自动审批”。上线会话摘要把 `user` 显示为“手动审批”，未知值显示“未知”；未绑定或尚未恢复时省略未确认设置。Turn 启动卡对 `user`、未绑定或未知值仍省略该字段；主动 `/status` 明确展示已知审批方式、未知、未绑定或尚未恢复，不把缺值当作自动审批。
不使用全局 Codex 用户设置推断已有 Thread。工作区列表只展示目录身份，`/permissions` 查询原生 Profile 目录，不显示网关权限覆盖。
Codex 默认审批方式修改只设置新会话默认值；当前会话显示仍以 App Server 的实际设置为准。

`/status` 显示一份状态，不接受参数，也没有总览／详情切换。四渠道共享工作区、工作目录、可用 Git 分支、完整 Session ID、会话与任务状态、模型和提供商、有效消息模式、上下文占用及累计 Token；思考等级、速度、协作模式和审批方式分别显示。使用一个主标题和列表，飞书原生卡片标题替代正文主标题。主动查询不受静默模式或完成卡详情档位裁剪。
不展示 Turn ID、运行目录快照、规则文件清单、设置来源、缓存命中率、压缩次数及 Token 分项。没有检测到 Git 分支时整行省略。开始、上线和完成通知的工作区/Git 规则保持不变。上下文仍按最近一次权威用量与有效窗口显示占用比例，独立于累计 Token；缺窗口不推测百分比，未绑定、恢复中及用量未取得保持明确，不伪装为空闲或零用量。
目录未由 App Server 确认或与工作区不同时才追加提示，保留设置下一轮生效标记；有目标时仅展示状态并指向 `/goal`。Workspace 名称与 ID 相同不重复展示；底层执行上下文、规则来源与加载快照及其校验没有删除，也不因隐藏清单而将工作区配置当作真实执行上下文。
账户摘要展示已有官方周限剩余比例，或同 Provider 的余额、剩余额度及窗口剩余比例；不展开重置时间和完整账户表，零余额及已用尽窗口保持可见，缺少数据不伪报零额度，查询失败明确提示。第三方查询沿现有接口及原会话/提供商守卫，不扩大账户查询范围。完整额度请用 `/usage`、`/limits`；`/metrics` 展示保留请求记录中的已知统计，与 App Server 会话累计不同，不作为相同口径的替代。显示模式只保留当前有效预设，不读取日志等级。
查询仍不读取规则文件正文或主动恢复 Thread。
飞书、QQ 和 Telegram 在状态页提供“请求统计”“账户用量”“账户额度”三个按钮，分别查询 `/metrics`、`/usage`、`/limits`，正文不重复这些命令。微信保留文字命令入口。QQ 正常状态面板直接附按钮，不追加“选择下方操作继续。”；完整 Markdown 无法安全发送时保留完整字面正文，另发“更多查询”按钮消息。

Ollama 渠道 `/usage` 使用官方账户数据，显示请求数量、输入、缓存、缓存命中率、输出、已用费用、账户剩余费用及每亿 Token 平均费用。飞书、Telegram、QQ 提供 24 小时／7 天／30 天与刷新按钮，不展示模型分组入口或正文命令列表；飞书与 Telegram 原位更新，QQ 沿菜单回调返回新结果。微信使用相同含义的文本参数。缓存与缺失数据说明、费用排除规则见 [Ollama Cloud](ollama-cloud.md)。完成卡仍仅显示原有账户余额，不把账户区间费用归为本轮费用。
`/autoreview` 查询当前会话审批方式，`/autoreview on|off` 为当前会话后续轮次切换自动审查或手动审批。
未绑定时不创建会话；实际值未知或为 `guardian_subagent` 时只读。仅权威设置确认后显示已切换，
未确认结果提示重新查询，不能把未知结果描述为成功或确定未修改。
审批方式选项不按 Provider 或模型限制；实际状态始终展示 App Server 返回值。
专用 `/autoreview` 查询与修改回执保留完整状态，包括手动审批和未知，不隐藏开启入口。
飞书和 Telegram 当前会话按钮标明“当前会话：自动审批 / 手动审批”，绑定生成时的 Thread、Conversation 和用户，五分钟内有效且一次性；
微信使用相同文本命令。
飞书与 QQ 当前状态面板保留模型设置、工作区、权限查询与“审批设置”按钮；按钮是操作入口，正文只展示实际状态。

飞书、Telegram 和微信仅在每次自动审批完成后发送一张结果卡，显示“自动审批完成 · 已通过 / 已拒绝 / 已超时 / 已中止”，不发送开始通知。
卡片显示动作类别、操作详情、工作目录、审查理由和耗时；文件修改另显示文件数量，网络访问另显示协议和端口。操作详情按类型显示命令、程序与参数、文件列表、目标主机、MCP 服务与工具名或权限申请理由。Client 对文本做凭据脱敏、控制字符清理及每项最多 320 字符的限制，并保留 ASCII 标点；execve 参数逐项脱敏后再格式化。不显示标准输入正文、完整网络目标 URL、风险等级和用户授权评估。缺失或未知字段省略。
Core 和投递路径保留经处理的有界纯文本。Telegram 在 HTML 面板呈现边界转义字面字段，飞书在 Markdown 呈现边界转义字段内容，微信纯文本保留字符原样。通知没有人工审批按钮，不改变实际审批决定。经处理的摘要可随现有加密投递箱暂存；指标库与 StateStore 不保存审查正文，也不增加字段或 schema。
同一 Thread、Turn、Review ID 的完成通知去重，审查开始通知仅供内部统计与已有归属观察；直接会话归属只在 `turn.started` 时记录，
子代理启动与继续操作等轮次中途活动不能捕获当前会话绑定。状态通知独立于指标写入，
经既有关键结果投递路径发送，微信也将其纳入回复窗口生命周期通知。子代理审查仅按已确认的精确父子 Turn
关系转发到仍有授权的父会话，并标明“来源：子代理”；缺少归属时保留有界短期等待并记录不可路由状态，
不向其他会话广播。完成时复核轮次开始时记录的会话与 Provider；换绑、断线或淘汰后无法确认原始归属时不使用当前绑定兜底。
通知等待和去重只存在于进程内，不重放 Gateway 停止期间未观察到的审查事件。

四渠道完成卡仅在当前 Thread 的实际审批方式为自动时，在标题下本轮指标和“会话累计”分区展示“自动审批”：前者统计本轮任务，
后者累计当前 Session 在指标保留范围内的各轮；两者都递归包含按精确父子运行关系关联的子代理。本轮没有审查记录时，两处自动审批统计均省略；审批方式配置仍按实际值显示。
总数按 Thread、Turn、Review ID 去重，以“请求”展示审批次数，与非零的通过、拒绝、超时、中止、进行中及结果未知合并为一行。
“自动审批”下的“Token”单独累计保留记录中已明确归属该范围的审查请求输入与输出；不混入本轮、任务、会话及子代理的模型请求数、Token、缓存、Credits 或请求性能统计。审查次数与模型请求次数不是同一口径，不按次数推算 Token。输入与输出分别保留已知累计，缺失部分不推算；展示已有累计，没有已记录数值或累计为零时省略该子项，不附加用量缺失标注。读取前等待当前已入队指标（包含子代理），仍受完成卡共享预算及取消信号约束，不受无关会话或普通请求的写入失败影响。
该数量始终只表示已记录用量，不承诺完整成本；IPC 漏采、尚未到达的指标和历史记录裁剪均可能使其少于实际消耗。审批事件覆盖与用量覆盖独立：前者完整不代表后者完整；请求字段齐全也不证明没有整条请求遗漏。
全局请求用量仍包含审查成本，以“其中自动审查”独立列出；控制台按模型统计按已记录模型及统计映射归组，不把用途当作模型。请求详情独立标明自动审查用途。原始父任务归属保留，历史缺少用途标记的请求不猜测或回填。完成卡不再单列审查模型请求数；其采集仍独立于审批次数。
规则或缓存直接放行、手动审批不计入；没有明确分类的历史非通过结果显示“结果未知”，不能推为拒绝。
审查计数及观测完整性持久保存，Gateway 重启后可读取已有记录；官方历史不提供的审查事件不补推。
连续观察完整时显示如 `自动审批：请求 25 · 通过 25`，下方用 `Token：1.27 M` 展示已记录用量；没有记录或零次时省略该统计项。
断线等观测缺口或完整性未知时，有记录按同一格式显示已观测数量，没有记录时省略该统计项。卡片不额外显示统计缺失标注。
未启用自动审批、审批方式未知或未提供该统计字段的完成事件省略此项，即使保留有历史审查计数也不显示。完整仅表示截至卡片生成时的观测范围；原 Turn 的迟到审查结果
仍归属原轮并落库，已发出的完成卡不保证追更，也不把迟到结果算入下一轮。

详细完成卡片显示“上下文压缩”次数，零次不显示。以下压缩用量和性能统计说明用于主动查询及指标口径，不意味着详细完成通知展开这些分项。主动查询的本轮压缩用量显示次数与 Token，例如 `1 次 · 225.13 K Token`。
压缩模型与本轮模型不同时另显示模型，混合或未知模型也明确标注；仅追加非零的客户端中断、其他失败与未完整观测数量。
主动查询 `/metrics` 保留模型及非零结果分类。压缩 Token 是已有总计的子项，不重复相加。

- 普通前台用户 Turn 收到官方 `completed` 终态却没有产生非空最终回复时，完成汇报显示
  “无最终回复”，并提示重试或在上下文较高时使用 `/compact`；该诊断不改变官方 Turn 状态，
  也不把没有用户输入的手动压缩 Turn 或后台任务误报为异常。
- 运行区把统计代理捕获到的本 Turn 非自动审查模型请求聚合为请求次数，并在存在异常尝试时拆分完成、
  中断、未完整观测和失败数量，同时展示 Token 与缓存命中；官方 `Turn.durationMs` 可用时另显示
  从本轮开始到完成的总耗时。主 Turn 与子代理完成卡片不显示“上游轮次首 Token”；上游原始指标采集与存储保留。
  完成卡仅以“本轮耗时”显示官方 `Turn.durationMs`，起点是 App Server 开始执行本轮，包含模型请求与工具执行；不是最后一次模型请求的耗时。零值或未提供时省略该行。
  “推理次数”按已观测正数推理输出的请求计数，不代表思考片段数，直接显示已有次数。输入、输出的字段缺失数仍随查询和实时归约传递；渠道卡片、`/metrics`、CLI Markdown 与 WebUI 的 Token 聚合统一显示已有累计，不添加下限符号、覆盖未知或用量不完整标注，零值或没有数值的统计项省略，表格单元格留空；数据库、API 与 JSON/CSV 的零值及缺失语义保留。Token 合计只加输入和输出，缓存、推理和“其中上下文压缩”不再相加。当前上下文是官方快照，与累计用量分开。
  “首 Token”是有效请求样本的平均值；“速度”是有效完成请求输出与请求耗时之比，任务和审查分开，不代表整轮墙钟吞吐。任务/会话树读取等待当时已入队的所有指标，以覆盖子代理；不等待未来流量，也不承诺无漏采。
  本轮“首 Token”和“速度”的统计口径仍保留，但详细完成通知不展开这两项。首 Token 是本 Thread/Turn 普通模型请求已观测首内容时间的平均值，零毫秒仍参与内部统计；首内容包括非空思考、正文、拒绝文本和工具参数，不包含状态、额度或仅有用量的事件，缺失不以首包回填。速度仅对已完成、输出 Token 和请求总耗时均大于零的请求，计算总输出 Token 除以请求耗时之和，不依赖首 Token 或生成区间。此为请求平均输出速度，包含等待、思考、正文、工具参数和网络接收；不平均各请求速度。不含压缩、其他轮次或子代理。无效请求的 Token 与请求耗时同时排除；没有对应有效样本时不推算。数据从指标库恢复。
  两次模型请求之间的工具执行等待只计入本轮耗时，不计入请求速度的分母；上游在单次请求内部执行工具的等待无法独立剥离，保留在请求耗时中。
  当前会话同样显示“首 Token”和“速度”，沿用会话 Token 的递归范围，包含子代理的普通模型请求；均值、加权速度和缺失处理与本轮一致。历史缺失首 Token 不补算，不妨碍完整输出量与总耗时样本参与速度统计。
  “本轮耗时”与会话“总耗时”作为一级项，各自的“首 Token”和“速度”缩进为二级项；分组仅用于展示，不表示首 Token 或速度是官方耗时的组成项。
  会话的“上下文压缩”保留 App Server 次数；落库的“压缩请求”另列次数与 Token，复用本轮的模型去重和非零异常展示，二者统计来源不同，不相加。
  `/metrics` 显示已有本地请求的“首 Token”和“速度”，不显示上游轮次首 Token；子代理完成卡不显示速度或上游首 Token。请求明细与调用详情的列头为“首 Token”“速度”和“请求耗时”，具体见[WebUI 请求明细](webui.md)。本地观测的 `firstTokenMs` 与上游原始 `upstreamTtftMs` 不混用。
  当前锁定 Codex 0.164.0 的首轮 `generate=false` WebSocket 预热不属于模型推理，
  不计入请求数或 Token。Turn 完成前会等待当前 Thread 与 Turn 已入队的指标写入，并从本地指标库重建本轮统计；因此 Gateway
  在长 Turn 中途重启后，完成卡片仍包含重启前后的本次用量，会话累计也包含本轮已经落库的请求。等待有总预算，
  指标库拥堵或不可用时按当前可用值生成卡片并记录告警，避免一个慢指标库阻塞其他 Surface 与 Conversation 的输出投递。
  Git 分支通过异步子进程读取，与统计补全共享 250 ms 预算；超时取消读取并省略分支。可选信息补全出现未预期异常时，持久与非持久路径都用原始完成事件继续发送，保留已有本轮信息。
  会话总耗时读取若超时、失败或尚未就绪，没有可用数值时省略耗时项，读取失败保留日志；已有非零数值仍正常展示。

## /usage 命令

OpenAI `/usage` 先展示账户活动摘要；当前账户选择和 Conversation 实际绑定都属于 OpenAI 时，
在同一回复追加“当前 Thread 官方估算”区块。待生效的第三方 Provider 选择仍按既有规则决定
`/usage` 的账户来源，不会为其查询当前 OpenAI Thread。官方估算按当前锁定的 0.164.0 App Server 活动
账户读取，只覆盖精确当前 Thread，不递归或合计子代理，也不写入本地指标库。

- Credits 和可选美元费用按百万分之一整数单位转换为有界小数；缺少美元值时不显示费用行。
- 仅对所有分组都提供的 Token 字段求和，缺失字段不按零累计；分组最多显示 8 组，缺失分组名称显示“其他”。
- `threadUsage` 不可用时保留账户摘要，并说明该官方计费能力仅向部分 Business/Enterprise 工作区开放；
  查询失败时显示稳定重试提示。账户摘要失败仍沿用既有失败行为。
- 没有当前 Thread 时不发起官方 Thread 查询；DeepSeek、OpenCode Go、CCG、CLP 和其他第三方 Provider 保持自身账户余额或额度口径。
- 官方估算可能在 Turn 完成后延迟结算；本地请求明细与子代理累计继续使用 `/metrics`，两类金额不得相减或合并为真实账单。

## Luna Reserve 自动回退

OpenAI App Server 对当前 ChatGPT 账户明确返回 Luna Reserve 权益，并且最终 `turn.error` 分类为
`usageLimitExceeded` 时，Gateway 会在该 Turn 完成后轻量读取额度状态，不请求重置券详情。权益、账户 ID、受限模型
和隐藏的 `gpt-reserve` 目录项一致时，当前 Thread 的模型、思考等级、服务层级及 Default/Plan 模式
通过 `thread/settings/update` 一次性切换；同时收到 RPC 成功与匹配的实际设置通知、完成本地同步后才提示成功，
不乐观改写模型缓存。写请求失败或结果未确认时停止该次自动恢复，不自动重试。

切换成功后三个渠道都会提示重新发送失败消息。Gateway 不保存或重放消息正文；已经进入 App Server
原生 Queue 的下一 Turn 仍由 App Server 管理，可能在回退请求完成前自动开始并再次遇到额度错误。
Gateway 检测到活动 Turn 时会等其完成后再写入设置，避免把已启动 Turn 误报为 Reserve。切入后每分钟
发起轻量额度读取，与即时刷新共用当前账户正在进行的读取；请求结束即释放，不缓存已完成结果，
账户失效或 Gateway 关闭会中止共享读取。只有同一账户明确
恢复普通用量、权威普通额度桶没有剩余消费控制或限额阻断、没有未知后端权益 Banner、当前模型仍是
`gpt-reserve`，且原模型仍在可用目录中时才自动切回。用户手工改模、切换账户、关闭、归档或删除 Thread
会取消自动切回；原生 TUI 或渠道改变思考等级、服务层级或 Default/Plan 模式后，下一次恢复检查也会放弃切回，
避免覆盖用户选择。最终写入前再次核对绑定、活动 Turn、待生效选择及已观察到的实际设置。
上游没有版本条件写入接口，不能保证多个客户端同时修改时的原子性。原模型只保存在当前 Gateway 进程内，因此 Gateway 在 Reserve 期间重启后不会猜测
切回目标。

已经由 App Server 接受的设置写入无法撤销。若写入完成前账户发生变化，Gateway 不会把该结果认作
当前账户的自动切换，也不会用补偿写入覆盖新账户或原生 TUI 的后续选择；三个渠道会提示用户确认
当前 Session 模型，并说明自动切回已取消。Reserve 自身用量耗尽时，完成卡片会与普通用量耗尽明确区分。

## /metrics 命令

`/metrics` 可查看当前 Thread 最近 Turn 的运行聚合，以及递归包含全部显式子代理后代的 Thread 会话累计。
当前会话显示完整 Session ID。最近运行在已有记录时显示官方本轮耗时、本 Thread/Turn 的平均首 Token 和请求平均输出速度；会话累计显示主 Thread 各轮耗时之和，以及递归范围内普通模型请求的平均首 Token 与加权速度，不把子代理耗时再次加入主 Thread 总耗时。历史耗时缺失时只标“已知总耗时（历史耗时未完整）”；无对应有效样本、非有限数值或零值省略，不从 Token 推算耗时。速度口径见上面的完成统计说明，全局、提供商和模型聚合视图保持原有字段。
`/metrics global|providers|models <范围>` 按同一口径汇总指标库全部保留记录，并显示请求、Token、缓存、
压缩和错误统计；历史无 Turn 记录不再形成单独的会话分栏。
`/metrics errors` 按来源、提供商、模型、状态、HTTP 状态、错误类型和错误码汇总异常请求，显示异常率与最近
发生时间，并按最近发生时间排序。来源及受限格式的错误码保留在渠道输出中，与 CLI、WebUI 共用同一聚合结果。它不会替代 `/status` 的 App Server 上下文统计。
本机 `codexc metrics run <Thread ID>` 的会话累计使用上述递归口径；
`codexc metrics turns <Thread ID>` 仍列出指定 Thread 自身的 Turn 明细，不把子代理任务拆入公开
Turn 行，避免改变既有输出结构。渠道 `/metrics` 只查询当前绑定 Thread，不接受任意 Thread ID。
范围统一为滚动窗口 `24h` / `7d` / `30d` / `90d` 和 `all`，渠道、CLI 与 WebUI 使用相同名称。
CLI 与 WebUI 还支持 `today` / `yesterday`，分别统计今天截至当前时刻、昨天完整自然日。
WebUI 的每日分组和所有格式化时间统一跟随服务端进程时区，缺省为系统时区，可用
[`codex.timezone`](model-timezone.md) 覆盖；浏览器时区不改变日期归属。
CLI 人类可读的指标报告、导出与菜单使用执行主机本地时间，报告标明 IANA 时区名称，不附加查询时刻的
UTC 偏移；历史记录按各自时间戳采用当时的夏令时规则。转储列表、详情与跟随输出使用同一时区标签，
显示时间统一为 `YYYY-MM-DD HH:mm:ss`。WebUI 顶部实时时钟的 UTC 偏移与显示时刻对应，仍保留。
JSON/CSV 中的时间戳和
UTC ISO 时间以及原始上游转储保持原格式，不迁移历史记录；耗时不受时区影响。
WebUI 菜单只展示今天、昨天、最近 7 天、最近 30 天、全部历史和自定义日期。
本机 CLI 需要精确自然日或账期时使用 `--from YYYY-MM-DD --to YYYY-MM-DD`。
`threads`、`turns`、`report` 与 `export` 共用时间和请求筛选：Provider、模型、`response|compact`
操作、`completed|failed|incomplete|unknown` 状态及关键词可组合使用。`--thread` 精确指定会话，
`--turn` 必须同时指定会话；`turns <Thread ID>` 的会话由位置参数提供。`threads`、`turns`
默认全部保留历史，`report`、`export` 默认最近 30 天。日期按执行主机本地时区解析并包含结束日，
最多查询到当前时刻。

```bash
codexc metrics threads --range 7d --provider openai
codexc metrics turns <Thread ID> --from 2026-09-01 --to 2026-09-15
codexc metrics export --range 7d --thread <Thread ID> --turn <Turn ID> --status failed --format csv
```

期间查询先按请求记录时间筛选，再按 Thread 或 Turn 汇总；跨越时间边界的一轮只计算范围内的
请求。轮数是本机指标库中有记录的不同 Turn 数，不代表完整官方历史轮数。会话列表、每轮明细与
精确 Thread 请求筛选只计算各会话自身，子代理以独立 Thread 列出；`run` 和渠道 `/metrics`
的全部历史累计继续递归包含已关联子代理。请求导出在数据库内筛选，读取全部匹配页；JSON 保留
所用范围与筛选条件，JSON/CSV 保留精确数值。

渠道、CLI 与 WebUI 的 Token 统一使用 `K`、`M`、`B` 紧凑单位：`K` / `M` 最多保留两位小数，
`B` 最多保留三位小数；渠道、CLI 和 WebUI 的汇总请求数使用相同单位且最多保留两位小数，逐条明细及
JSON / CSV 导出仍保留精确整数。
请求明细的 `requestBytes` 按实际提交给模型上游出站传输的请求正文或 WebSocket 请求帧字节合计保留为原始整数；不计仍留在上传队列的块，也不代表远端确认收到的字节量，提交后取消或发送失败仍保留已提交大小。
WebUI 使用二进制 `B` / `KB` / `MB` 展示，JSON 与 CSV 不取整或换算单位，历史缺失保持 `null`。
Turn 级失败独立保留在 Gateway 的 `turn.failed` 诊断日志与用户错误反馈中，不生成模型请求记录。
历史库可能包含旧实现写入的任务失败，缺乏可靠区分字段，保留原值，不按空 Token 清洗。

请求累计将结果分为「完成」「客户端中断」「其他失败」「未完整观测」：已观测到完成响应的请求计入完成；
其余请求中，`client_disconnected` 计入客户端中断，明确的 `failed` 计入其他失败，`incomplete`、
`unknown` 及历史未观测到响应的记录计入未完整观测。原始请求状态和错误类型保持不变，仍可在异常明细中查询。
JSON 中的 `requestOutcomes` 提供四类精确计数；`unsuccessfulRequestCount` 仍表示全部非完成请求，
不能直接作为失败数。失败率仅使用「其他失败」除以总请求数，完成率仍以总请求数为分母。

渠道完成卡的请求结果简写为「完成 · 中断 · 失败 · 不完整」，不另列中断后成功、未观测到后续成功或中断用量缺失说明。
指标查询的会话和 Turn 摘要仍保留中断后同轮有成功请求、未观测到后续成功，以及用量未完整观测的中断次数。
「同轮后续成功」要求相同 Thread、非空 Turn ID，且成功响应的结束时间严格晚于中断结束时间；
它只表达时间关联，不证明自动重试、成功恢复或主动取消。范围查询只采用同一筛选范围内的记录，
缺少时间或关联信息时不推测成功。中断请求的输入或输出 Token 缺失即视为用量未完整观测；
已收到的用量仍保留在汇总中，缺失用量不代表零消耗，也不根据请求时长估算。

统计代理把 `/responses` 上的上下文压缩（remote compaction v2）保留为
`compact` 操作：其请求与 Token 继续计入总计，同时在完成卡片、会话指标和全局/提供商/
模型汇总中单列压缩次数、实际请求模型与 Token。这里的模型是代理实际观测到的请求模型。
当前锁定的 Codex CLI 0.164.0 没有独立压缩模型配置；常规压缩复用 Turn 模型，模型切换兼容压缩
可能先使用上一模型，并在受支持的失败条件下回退当前模型。

完成卡片的模型/提供商之下会单列「自动压缩：X%」。受管第三方 Provider 只配置模型目录里的
`context_window`，压缩阈值由上游按窗口默认推导，因此不显示该字段（会话区「上下文」分母已反映
当前窗口）；官方模型优先读取主配置覆盖值（`model_context_window` / `model_auto_compact_token_limit`），
未覆盖时显示默认 95%。
`codexc config` 的「Codex 新会话与用户偏好 → 模型上下文与自动压缩」可读取并设置官方模型的
上下文窗口与精确自动压缩 Token 阈值，两项可独立设置；留空移除对应用户覆盖，跟随上游配置。

- HTTP 与 WebSocket 客户端在完成事件前断开都计为中断；HTTP/SSE 已完成后的正常收尾断开不重复
  记为失败；上游 WebSocket 断流按可重试失败保留，在 Turn
  完成时归入“自动重试”。
- HTTP 200 但没有模型、Usage 或完成事件的响应计为“未完整观测”，中断与未完整观测都不冒充
  成功请求。
- 缺少 `Content-Type` 但正文包含合法 Responses SSE 事件时仍按正文受限识别，不会误丢成功请求。

请求指标、运行完成卡、CLI 指标报告与 WebUI 的输入 Token 明细统一使用“缓存”和“无缓存”：
前者仍指缓存命中的输入 Token，后者仍按输入 Token 减缓存输入计算；“缓存命中率”保留原名，计算与持久化字段不变。

## /limits 额度与周限估算

渠道额度、用量及 `/metrics errors` 异常报告统一显示“时区：<实际 IANA 时区>”，取当前进程实际用于格式化时间的
时区，不使用客户端设备时区。OpenAI 每日用量仍按上游 `startDate` 展示，区块标注“官方日期口径”，
不按显示时区重新分组；剩余时长按时间戳差计算。

OpenAI 渠道额度卡片在套餐下仅显示“凭证刷新时间”，读取当前 Codex Home 的 `auth.json.last_refresh`，
沿用卡片服务时区并包含年份。仅在登录凭据账户 ID 与 App Server 额度账户 ID 一致时显示，字段缺失、
缓存不可读或账户不匹配时显示“未提供”。不显示登录 Token 内的订阅截止和检查日期。
手动 `/limits` 直接查询官方额度并只读取已有凭证刷新时间；额度查询、启动预热和后台轮询均不主动刷新登录凭据。
该时间不替换为查询时间，不代表订阅续费时间，不写入数据库或官方额度快照，也不展示凭据内容。

飞书同一菜单卡片的“额度”查询及结果卡片发送尚未结束时，重复点击复用该次操作，不重复查询或追加结果卡片；
操作结束后可再次点击查询。结果仍通过当前聊天的有序输出队列发送。

OpenAI Codex 额度卡在时区下方显示生成卡片时的“当前时间”，与重置时间使用同一时区，显示到分钟；该时间不代表额度采集时间或凭证刷新时间。

OpenAI `/limits` 显示可用额度重置券数量，并按到期时间合并 App Server 返回的每券明细；没有到期
时间的券显示为“无到期时间”。服务端只返回数量或限制明细条数时，界面会明确标出未提供到期明细，
不把用量窗口的自然重置时间当作重置券到期时间。有到期时间的明细同时显示查询时刻的剩余天数、
小时与分钟，以 `D`、`H`、`min` 表示，如“剩余：5 D 17 H 42 min”（不足整分钟舍去）；不足一分钟显示“剩余：不足 1 min”，
已到期显示“已到期”。
渠道额度、状态、完成卡和第三方用量窗口统一显示剩余百分比（由 100 减已用比例，并限制在 0–100）；主窗口与次窗口分别显示三行：首行“剩余：59%（7天）”，下方两行分别为“重置：10月7日 18:36”和“剩余：5 D 17 H 42 min”；周期或重置时间缺失时省略对应部分，不推算。带窗口名称的状态、完成卡和第三方用量使用“周限：剩余 59%”的组合形式，避免连续冒号。个人消费限额与重置券列表/确认卡也显示剩余时长；重置时间已过显示“重置时间已过”，券到期显示“已到期”。运行耗时与审批有效期保留原有精度。

OpenAI `/limits` 在额度响应包含 10,080 分钟周窗口和有效重置时间时，从本机统计代理读取相同
`resetAt` 的额度快照。代理对 HTTP/SSE 使用受控额度响应头，对 Responses WebSocket 使用
`codex.rate_limits` 事件，并把快照和对应请求指标写入同一指标记录。
`quotaObservedAtMs` 记录本机收到有效额度响应头或额度事件的时间，与请求结束后的入库时间
`recordedAtMs` 分开保存。缓存用量窗口保留缓存刷新时的观测时间，不以请求结束时间刷新旧快照。
若一条记录同时携带两类独立来源的额度快照，单个采集时间无法对应两者，保持空值。
额度估算、最新额度及历史窗口按采集时间排序，同毫秒按入库顺序排序；未观测采集时间的记录保持空值，
查询时只能按入库时间近似排序。该字段是本机观测时间，不是上游额度的生成时间。

第一个快照只建立基线；同一周窗口按已观测到的最高已用比例计算增长。百分比不变或回退时继续
累计后续请求，只有超过此前最高值才闭合区间，用区间累计 Token 除以新增百分点；回退后恢复到
原值不重复计数，也不把单次回退视为额度重置。重置时间在 5 分钟内的小幅抖动归为同一窗口，
不同窗口的快照会断开未完成区间；再次遇到原窗口时保留其最高值，重新建立采样基线。

“本周期本机实际”统计重置时间前 7 天至查询时刻的本机 Provider 请求；“每 1%”只使用闭合区间，
不包含首个基线请求或尚未闭合的尾部请求，因此不能直接用周期总 Token 除以观测百分点。
观测百分点表示采样覆盖的增长，不等同于当前已用比例；剩余百分比仍以官方额度响应为准。
未形成区间时显示正在采样。其他设备或云端活动若发生在相邻快照之间仍会影响估算，
请求完成顺序与额度快照时序也可能不同，Token 换算只是本机样本估算。

## 信息命令格式

标题按内容职责分级，不统一放大，也不统一降为粗体：一级 `#` 用于完整长文的总标题，日常系统消息不默认生成；有多项内容的通知、命令结果和菜单以二级 `##` 为主标题；“当前会话”“账户状态”“提供商列表”等独立分区使用三级 `###`。字段名、当前模型、历史条目名称只按需加粗，不提升为章节。停止、取消、错误和操作说明使用普通正文；单行回执不自动生成标题。字段使用 `-` 列表，明细按父子关系缩进。
该规则作用于 Gateway 生成的文案，不改写模型回答、用户题干、Diff 或代码块中的标题。QQ 使用原生 Markdown；飞书使用 Markdown 或卡片原生标题，已有卡片标题时正文不再重复。Telegram 系统面板通过 HTML 粗体和段落表现标题，不能承诺不同标题级别具有不同字号；微信现有适配将结构化标题转为粗体与段落，并保留代码围栏。语义层级与客户端字号不是同一合同。

多渠道呈现核对范围包括共享命令结果的全部 kind 分支（会话、工作区、模型、权限、目标、额度、指标、扩展、Hook、队列、计划任务、回退和操作回执），以及以下出口：

| 内容 | QQ | 飞书 | Telegram | 微信 |
| --- | --- | --- | --- | --- |
| 上线、结束、子代理与配置通知 | lifecycle／共享格式器 | renderer／共享格式器 | format、Outbox／共享格式器 | command-renderer、surface／共享格式器 |
| 连接、账户、MCP、空闲释放、警告 | lifecycle | renderer、空闲释放卡 | Outbox、format | surface、Outbox；仅已支持事件 |
| 菜单、选择、管理确认 | command-menu-controller、schedule-menu、privileged-management-menu | command-center-presentation、卡片 | command-renderer、HTML 面板 | command-renderer、文字命令入口 |
| 审批、问题、MCP 交互 | interactions 的主标题／问题分区 | approval-card、input-card 的原生标题／正文 | interactions 的 HTML 标题／题干 | interactions 的审批安全文字／问题 Markdown 题干 |
| 工具、计划、重试和错误 | 已支持通知及共享文案 | operation-format、status-card、共享文案 | operation-format、Outbox、共享文案 | Outbox、共享文案；仅已支持事件 |

共享模型、思考、速度、协作模式和目标面板显式声明主标题，当前值仍为字段。模型各视图共享当前/待生效状态、Provider 切换后新建会话及连续选择思考设置的提示；浏览 Provider 不表示已经切换。工作区、模型和会话动态元数据按单行字面值呈现，各平台仍保留自己的按钮和分页预算。Telegram 不再按首行位置推断标题；多行操作结果与自动计划走 HTML 面板，短回执保持普通正文。重置券字段在渠道边界只转义一次；Hook 系统标签与原值分开，普通与异步题干共用各渠道受限 Markdown 渲染，问题标题和操作说明独立转义。飞书已有原生标题的命令卡去除已知共享主标题；开始回执独立发送，后续 Session 状态卡不覆盖开始内容。可确认原用户、聊天和消息归属的近期失效命令/Doctor 按钮仅回执一次失效提示，不恢复操作权限；未知或重启后归属丢失的按钮不推测身份。
QQ Queue 按钮结果直接消费共享 Markdown，不再压成单行或重复转义；问题选项正文和按钮使用同一页及全局编号。计划任务与重置券组合只保留一个主标题，任务名称与预览按字面字段呈现。微信与共享格式器保留代码围栏内空白，长代码分片独立闭合和重开围栏，新增标记计入原有消息预算；无法容纳完整围栏的内容受控拒绝。以上路径的隔离观察使用生产入口和内存发送接收器，不代表四个平台客户端已逐页验收。
`/metrics` 用 `**Token**：总计` 列表块分节，主动查询固定按已有非零数据显示输入/缓存/输出明细，不受消息详情或日志等级控制；
上下文压缩另列次数、模型与 Token，但不从总计扣除或重复相加；
`/diff` 与操作结果保持原文；飞书把 Turn Diff 放入围栏代码块（内容含围栏时加长标记），
Telegram 使用 `<pre>`，微信使用保留原文的独立围栏，避免字段格式器改写补丁行。三渠道分别用飞书卡片 Markdown、Telegram
HTML 和微信结构化字段渲染。

飞书把 Gateway 文案中独立成行的命令以及“标签：命令”的值渲染为行内代码，消息卡、帮助、配置与
启动通知、命令中心卡片共用这一层；命令名限定为共享命令、别名与飞书专有命令，工作区路径、缩进
代码块、句内提及、代码围栏、表格行、模型正文和用户消息保持原样。独立命令保留整行实参，包括
中文、混合搜索词与标点；帮助在生成处显式分开命令和说明，最终排版不猜测语言或分隔符的含义。
命令含反引号、反斜杠或跨度超过 200 字符时放弃装饰，避免破坏 Markdown 或分片边界，也避免把已转义字段的反斜杠显示在代码中。用户自己命名且恰好与命令同名的取值
（会话名、Workspace 名、计划任务名）在不需要字面转义时仍可能按同样规则显示为行内代码。
空闲解除通知的恢复命令使用围栏代码块，CardKit 卡片与创建失败时的 Markdown 降级文案内容一致（卡片另有加粗与分元素）；

`collabAgentToolCall.agentsStates` 的异常状态。Gateway 不根据模型请求静默时间猜测完成。同一

误显示为新建子代理。子线程 `turn/started` 即使先于父线程
`interacted` 到达，也会与待处理活动合并为同一轮；延迟到达的上一轮终态或指标不会污染新一轮。
父 Session 已切到后台时，Gateway 仍保留父 Thread 订阅直到所有已登记子代理运行取得官方终态，

读取汇总；等待操作本身不再展示正常过程通知，但仍参与统计结算。终态到达时尚无指标或父线程没有

飞书通过分页卡片和一次性表单收集 Plugin 任务；Telegram 通过当前页按钮选择，并用绑定聊天、Actor
和精确提示消息的十分钟 ForceReply 收集一次任务，搜索结果继续使用文字翻页命令；微信不模拟未验证
的按钮或表单，只为当前页可调用项补充可复制的编号任务命令。

`/mcp` 概览和详情显示当前 Thread 已发布连接的官方运行状态：未启动、正在连接、已连接、需要认证、
失败、已取消或已禁用；未绑定 Thread、配置已经变化或 App Server 未提供运行快照时显示“未知”。
概览为每个 Server 直接提供使用当前列表数字序号的详情命令，不输出不可执行的选择器占位符。
状态查询只读取现有快照，不会启动或重连 Server，工具与资源目录也不代表当前连接可用。
`/mcp health` 先汇总数量，再把需要认证、连接失败或已取消列为需处理项，把认证未知、未启动、
正在连接、已禁用或已连接但未公开能力列为提示；它不把状态读取解释为逐个远端 Server 的网络探测。处理命令使用同次状态列表中的数字序号；需处理
项优先，和提示合计最多展示 8 项，超出时明确省略数量。`/mcp reload` 成功后统一说明已加载
Session 已刷新 MCP 配置；连接建立仍可能异步完成，用户可再次运行 `/mcp health` 查询，不把请求成功
显示为远端握手已经完成。
MCP 详情及分页中的登录、浏览、翻页和资源读取命令沿用用户本次使用的选择器；Server 名称含空格时
使用 `/mcp` 列表中的数字序号，避免把名称重新拼接成无法解析的命令。

## 子代理交互归属

子代理的审批和同步问题沿官方父子 Thread 关系发送到已绑定祖先的渠道会话，支持嵌套子代理。
审批标题标明“子代理”和子 Thread 的短 ID；批准或拒绝仍响应原来的子代理请求，不转换为主代理请求，
也不扩大一次、会话或持久规则授权范围。各渠道复用同一关联和审批逻辑。

父子关系无法确认、工作区或 Provider 不匹配、祖先绑定已撤销或转移时，交互安全拒绝。
无人值守自动化 Thread 及其子代理继续拒绝交互，不因关联到渠道会话而开放审批。
祖先会话的待处理交互保护和取消同时覆盖子代理；解析归属、排队和等待答复共用原有效期。
其他客户端已经处理的请求不会在归属查询结束后重新弹出。
归属查询期间发生的断线取消同样有效；其他会话新建或切换 Thread 不会误拒绝当前审批。

## 文件修改审批

文件审批在批准前显示新增、修改、删除的完整路径；移动同时显示源路径和目标路径。三个渠道
复用同一详情，飞书处理结果卡保留原明细。路径采用 JSON 转义，防止换行、不可见字符或格式符号
改变展示含义。文件清单来自同一 Provider、Thread、Turn 和 Item 的官方文件变更通知，修改理由
单独保留，不用理由或最近一次修改推测文件。关联数据只在当前连接内有界保存，不保存 Diff。

断线清理后重放的审批、未收到对应通知或缓存淘汰时，明确提示“未取得待修改文件明细，请先在
原生 Codex 客户端核对。”；不显示其他 Item 的路径。已观测但无效或超限的清单直接拒绝；完整
审批预览超过 3000 UTF-8 字节同样拒绝，不截断后批准。以上展示不扩大原有一次或会话授权范围。

## 已有终端输入审批

`writeStdin` 审批明确表示向已有终端继续输入，不是运行新命令。飞书、Telegram 与微信复用各自
已有审批入口，完整展示上游输入请求、启动目录和保留权限；预览采用 JSON 转义表示，控制字符及
渠道格式符号使用转义序列，避免显示改变待批准内容。超过共同展示上限时安全中止，不截断后批准。
仅允许一次批准或中止，不提供会话、命令前缀和网络持久授权；原命令获准不代表后续输入自动获准。
无人值守计划任务若收到此审批，会直接中止本轮，不发送交互审批；任务按审批失败记录，Gateway 重启后仍保留这一归因。

## 消息详情与日志等级

在 `codexc config → Gateway 显示设置 → 消息详情` 或 WebUI“消息渠道 → 消息展示”选择基础、详细或完整，按目标范围控制上线会话摘要及完成、子代理通知的关键统计。基础使用紧凑摘要，详细保留日常明细，不自动展开环境和统计分项；完整展开可用明细并筛除重复通知。日志 `debug` / `trace` 不会扩大聊天可见信息；日志等级仍在“日志与高级功能 → 日志等级”独立设置，变化要求重启 Gateway。
消息详情保存后按返回提示激活，需要重启时执行：

```bash
codexc restart gateway
```

调试日志只记录受约束的类型、阶段、耗时和结果，不记录消息正文、请求参数、上游响应、凭据或
审批内容。分享日志前仍需人工检查。

三个渠道统一提供以下投递诊断，不必为了保留故障证据长期开启 `debug`：

| 等级 | 记录内容 |
| --- | --- |
| `info` | 收到完成正文/轮次结束事件、对应输出任务处理成功、共享路由处理结束；TG 完成正文的格式化与实际投递结果，以及长轮询失败后恢复 |
| `warn` | 输入处理或发送失败、排队加执行总耗时达到 5 秒、执行 10 秒仍未完成的一次告警、格式化降级、输出未入队、容量替换及关闭超时未投递 |
| `debug` | 输入处理、输出执行、平台调用的开始与结束，输出入队结果、同键合并和有序操作取消 |

日志用 `component`、`accountId`、`conversationId`、`threadId`、`turnId` 和 `eventType` 定位；
字段只在对应入口已知时提供；正文事件另带 `itemId`。`inputId` 是平台输入标识，`deliveryId` 关联一次输出任务及其
分片/API 尝试，`diagnosticId` 关联一次阶段的开始与结束。`stage` 为 `input`、`delivery` 或
`api`；共享路由另记录 `stage: routing`、事件总线等待 `eventBusWaitMs` 和路由入队 `routingMs`。
完成统计准备另记录 `stage: enrichment`、本会话等待 `queueWaitMs` 和准备耗时 `executionMs`；
它发生在路由之后、平台输出队列之前，不计入 `routingMs`。飞书正文更新与整卡收尾分别使用
`operation: updateStreamingCard` 和 `finishStreamingCard`，避免把两类请求混在一起。
`purpose` 区分输出任务用途，例如 TG 正文、操作记录刷新和轮次完成卡；“输出任务处理完成”
仅表示该任务回调成功，不表示整个完成事件的正文已发送。“Telegram 完成正文投递完成”只在正文所有分段成功后记录。
`queueWaitMs` 表示进入该阶段前的本地排队时间，`executionMs` 是阶段执行耗时，
`totalMs` 是两者之和，`pending` 是阶段开始时的队列/待处理数量。API 尝试另外记录操作名，
有重试策略时记录 `attempt`、`maximumAttempts`；重试等待仍计入外层输出执行耗时。
飞书 API 阶段完成仅代表 HTTP SDK 调用返回，业务响应仍需经过现有校验；输出任务成功也不代表用户已读。

图片引用准备失败另带 `imageUploadDiagnosticId`、`imageUploadStage`、`imageUploadReason`、
`imageUploadElapsedMs` 和 `imageUploadStageElapsedMs`，与当前渠道的输入标识关联。
阶段区分会话读取、模型配置、本地模型代理、账户与凭据校验、图片校验、文件创建、字节传输和完成确认；
有对应证据时记录白名单内的 `imageUploadNetworkCode`、`imageUploadHttpStatus` 或 `imageUploadRpcCode`。
字节传输另记录 `imageUploadHost`、`imageUploadAttempt` 和 `imageUploadClientRequestId`，只保留目标主机、尝试次数和本地请求标识，不保留 URL 路径或签名查询串。连接、响应头和响应体超时分别提示；目标主机不证明请求实际使用了哪条代理路径。
这些字段不包含原始异常、凭据、签名 URL 或响应正文。微信在发送用户错误提示前也记录图片失败，
不因错误已被处理而丢失诊断。上传耗时不包含后续 Turn 提交等待。

下次出现“终端已有结果，渠道迟迟未收到”时，先保留发生时间和渠道，再查看：

```bash
codexc logs gateway -n 500
```

按 Thread/Turn/Item 找到共享路由记录及“Surface 终态输出已收到”，先检查 `eventBusWaitMs`、`routingMs` 和完成统计准备记录，再按 `deliveryId` 和 `purpose` 查看输出阶段及平台调用：
平台投递阶段的 `queueWaitMs` 只覆盖渠道内等待前序输出，不包含事件总线、共享路由及完成统计准备；`executionMs` 高则检查同 ID 下的 API 超时、错误码、重试或
格式化降级。没有阶段明细时临时开启 `debug` 后复现；缺少日志不能直接认定平台丢消息。
各渠道输出队列独立，同一会话串行；积压可能合并或替换中间状态，关键输出不会仅因容量耗尽被丢弃。
飞书关闭时普通输出可在 5 秒期限内排空，有序交互立即取消；期限结束后，分片、降级、媒体及客户端内部后续请求
都不再启动。正文与完成统计分别结算，正文失败也会独立尝试完成统计。
发送失败与进程关闭仍可能造成未送达，日志本身不提供离线持久化或自动补发；已持久接收结果的恢复与不确定发送处理由独立[投递箱](delivery.md)负责。

需要查看模型请求与响应的完整字段时，在 `codexc config` 中选择“调用记录 → 调用详情记录”，
使用 `[debug].model_traffic_dump` 旁路转储，而不是提高日志等级；文件位置与脱敏边界见
[使用指导](user-guide.md#模型请求转储)。
调用记录的生产/调试预设只管理采集裁剪与采集阶段，不切换后台日志或开发运行方式，也不控制渠道消息显示。
精确的 3/65536 与 0/0 分别显示生产与调试，其余合法裁剪组合显示自定义及实际数值；只有明确应用预设才会替换自定义值。

### Hook 管理交互

`/hooks` 显示当前 Workspace 和目标 Provider，每页最多 8 项；条目显示事件、来源及独立的启用与
信任状态。飞书使用纯文本卡片与操作按钮，Telegram 使用 HTML 字面面板和 Inline 按钮，仅格式化系统标题与字段标签，保留命令、路径和说明的原值；微信提供相同
语义的文本命令。详情按适用状态提供逐项信任、启用或停用；预览明确用户配置的持久作用域，
确认按钮和文本确认共用 Application 的五分钟一次性确认。配置由各 Provider 共用；结果区分保存、回读与实例刷新，部分刷新失败显示对应 Provider，不表示 Hook 已执行。
命令等审查信息经过脱敏、控制字符清理与限长后若不完整，则引导本地审查，不提供信任操作；
微信还要求审查字段经其文本格式处理后原文不变，不能原样展示时不提供信任入口，预览和确认均拒绝信任。
共享审查格式化仅检查字段展示是否完整；各渠道的字符保真能力由组合根显式注入，未知渠道拒绝信任。列表、详情、预览和确认均重新复核，不依赖旧按钮的展示结果。
不展示内部 Hook key、原始警告/错误或脚本内容。受管项只读，列表为空不推断功能已开启。

### 重置券交互

飞书、微信和 Telegram 共用 `/limits reset [页码]` 查看实时可用券，每页最多 8 张；返回券 ID、官方说明和到期时间。飞书和 Telegram 的 `/limits` 附“查看重置券”按钮，券列表使用原生选择、翻页和刷新按钮，预览使用“确认使用”和“取消”按钮。飞书复用模型交互的命令卡片令牌，绑定用户、聊天和消息；Telegram 的选券按钮绑定用户、聊天及列表快照，点击后重新查询，变化或过期则拒绝。微信保留文字交互，其他渠道也支持文字入口。`/limits reset use <券ID>` 只生成预览，显示账户及一次性确认；原用户在原会话、工作区和当前 Thread 明确确认后才消费。消费结果未知时提示查询核对，不自动重试；额度刷新失败与消费结果分开显示。
