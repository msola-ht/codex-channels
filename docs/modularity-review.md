## 复查与剩余事项

已完成最终复查，未发现本轮引入的行为回归或新的顶层依赖。具体核对：

1. 恢复集合只在 BindingRestoreCoordinator 内分配，调用者通过恢复、断线和重连方法改变状态；不再暴露状态注入参数。
2. 列表排序与数字选择器、历史失败返回、缓存 TTL、并发查询数量及刷新代次保持原实现；查询组件没有绑定写入口，Session 类型仍通过原公开入口导出。
3. ConversationService、Queue、Revert、Reserve 继续共享同一 ConversationLockCoordinator，没有为拆分出的查询服务创建第二把锁。
4. 入站事件顺序保留：异步问题/启动网络观察 → 应用失效与 Reserve 标记 → 子代理跟踪 → Core → Reserve 收尾 → 错误指标 → ThreadState。后台释放仍交给组合根已有任务跟踪与关闭等待，不在 Reader 中等待 RPC。
5. 启动中停止仍先取消与断开 Client，再等待启动收敛并关闭组件；恢复任务仍在存储关闭前收敛，重复 stop 仍返回同一任务。组件图不会主动终止共享 App Server。
6. 未改变模块依赖允许表、配置、数据库 Schema、RPC、公共命令或渠道权限；已更新 Application/Bootstrap 文件索引、协议实现映射及项目文档索引。

## 后续批次：飞书端口关联复查

前四次提交完成且工作区干净后继续审查。发现 `client.ts` 从 `outbox.ts` 导入 `FeishuMessagePort` 类型，同时 Outbox 为识别 `FeishuMessageError` 运行时导入 Client。前者是类型回引，不能称为运行时循环；后者使发送编排依赖 SDK 实现文件，窄端口隔离尚不完整。

本批将 Client 的类型引用直接指向已有 `outbox-message-port.ts`，将原错误码及错误类原样移入不依赖 SDK 的 `message-error.ts`。Outbox 直接引用错误合同，Client 保留原导出，公开模块入口和 `instanceof` 身份不变。不改变平台调用、错误分类、重试或权限语义。

飞书流式状态机继续保留为独立实施项。已核对 `acceptStreamDelta`、`completeStream`、`finishStreamsForTurn` 和 `withStreamFooter`：后续拆分必须共同迁移活动流与已完成流、计时器、合并代次、卡片序号和完成页脚；消息端口须复用已绑定关闭信号的实例，投递仍共用现有 Conversation 队列。不能只搬缓冲 Map 而留下终态更新和关闭所有权。

本批实现与暂存前复查完成，随本节所在提交经正常门禁纳入历史。定向验证为五个测试文件、119 项通过，覆盖消息 Client、Outbox、流式生命周期、路由降级和模块边界；复查确认错误类只保留一份定义，原 Client 与模块入口均导出同一类，未增加顶层依赖。飞书流式状态机整体迁移未计入本批完成范围。
