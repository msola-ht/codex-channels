## 目标与范围

群作为共同讨论空间，每个群有一个共享前台 Thread。成员能够围绕同一上下文协作，群与群、群与单聊保持独立。群需要独立的入口、路由规则和权限呈现，继续复用共享 Application、SessionRouter、App Server、Approval 和 Delivery。

首版不建立任务编号式多话题系统，也不在 Gateway 建立第二套会话历史或任务正文队列。只有后续确认存在并行话题需求时，才另行评估多 Thread 交互。

| 对象 | 目标归属 |
| --- | --- |
| Conversation | `surface + appId + 群身份`，不包含成员 ID |
| Workspace、前台 Thread、模型偏好 | 群共享；首版工作区由本机显式配置 |
| 发言人 Actor | 来自每条事件的真实成员 OpenID，独立传递 |
| 任务来源 | 固定原群、发起人、Workspace、Thread、Turn 和提交身份 |
| 问题回答者、审批者 | 按具体请求和权限确定，不从最近发言人推断 |
| 出站目标及额度 | 物理群；结果向群公开 |

会话隔离不等于文件或工具隔离。群工作区必须适合向该群公开，不能因为 Thread 独立即认为共享目录中的私有文件安全。群成员名单也不控制谁能看到群消息，公开输出授权必须覆盖物理群的可见范围。

### 本轮前置步骤：初始化群工作区

本轮已实现 `codexc init` 的首次初始化布局：在 `~/.codex-connect/workspace` 同级建立 `~/.codex-connect/group`；自定义配置位置时，两目录均位于配置旁。新建 Git 仓库使用 `main` 且不创建提交，已有仓库和文件保留；首次配置登记 Workspace ID `group`，默认 Workspace 仍为 `codex-connect`。

Linux / Node.js 24.22.1 的隔离真实 CLI 观察：`init → work list --json` 返回两个 available 工作区，默认项不变；两个新仓库均为无提交的 `main`。重复初始化前后配置和 Git 配置哈希一致；移除 `group` 注册后目录保留，重跑不补注册。自定义配置位置及已有群目录的仓库、文件保留符合合同，`readWorkspaceConfig → WorkspaceRegistry` 可按精确 ID 选择 `group`。普通文件冲突、符号链接、两工作区实际指向同一目录均拒绝且不写新配置；群仓库缺少 Git 时保留已有默认仓库、清理本次失败的 `.git`，恢复 Git 后重跑成功。类型与模块边界检查、变更 JavaScript 的 ESLint 检查通过；声明文件不在 ESLint 配置范围内。临时数据已清理，未修改真实用户配置或启动服务。Windows/macOS 的权限与 Git 初始化、交互向导及真实渠道使用尚未实机观察。

这只是预置可选目录与注册项，不启用 QQ 群、不选择任何群的 Workspace，也不授予成员、管理者、审批者或公开输出权限。已有配置保持原有注册项，不通过本次 `init` 隐式补注册 `group`；后续新增注册仍走明确的 Workspace 管理流程。

多个群将来若显式选择同一个 `group` Workspace，使用同一目录和文件；各自的 Conversation、前台 Thread、权限与出站来源仍独立。需要文件隔离时，应由本机操作者分别登记和配置工作区，不能把预置目录解释成每群自动创建独立文件空间。

## 架构与路由

```text
QQ Transport / Protocol
        |
        +-- 单聊入口 --> 现有单聊规则
        |
        +-- 群聊入口
              |-- 群与成员准入、操作权限、去重及容量
              |-- 普通讨论上下文采集
              |-- @输入 / 群命令 / 按钮分流
              v
         共享 Application
              |-- 空闲提交 / 原生 Queue
              |-- 会话管理 / 精确请求回应
              v
         共享 SessionRouter --> 本群 App Server Thread
              |
         原任务来源 --> 共享 Delivery --> QQ 群 Outbox
```

### 群入口职责

- 群与单聊在业务分流处明确区分，避免继续在一个控制器中用零散的 `c2c:` 判断定义群行为；传输、协议、媒体能力和公共格式化按既有边界复用，不创建第二套平台连接。
- 明确区分事件解析、群准入、成员操作授权、上下文采集和任务提交。普通上下文不是执行命令的入口。
- 操作级权限必须在取消来源、清理交互、修改绑定等本地副作用之前检查，并贯穿异步等待及最终请求。菜单隐藏不代替文字命令、回调和内部调用的授权。
- Transport 只等待有界准入，不等待模型回合完成。停止与交互回应保留控制容量，不被普通输入占满。

### 共享路由的群约束

1. 所有无绑定输入复用已修复的共享新建规则，不从同工作区的空闲历史中自动选择。获准成员首次 @可在配置的群工作区建立本群 Thread，无需先取得会话管理角色；此过程仍受群准入、提交守卫和会话锁保护。
2. 重启只恢复已明确属于新群身份的现有绑定，复核群权限、Workspace、Provider、权威 Thread 状态和订阅。
3. 首版不向群开放工作区级会话列表、搜索、归档历史、任意 ID 恢复或跨渠道接管。查询与执行边界同时限制，不能只移除菜单。
4. 显式 `/new`/重置、模型调整等共享状态管理操作仅由群管理者执行，与首次合法提交建立 Thread 区分。首版重置要求当前执行、Queue、待处理交互和相关后台活动均已按权威状态收敛；不让重置隐式留下无法解释的旧任务。
5. 未知状态不视为空闲；新建、订阅或绑定失败按已有共享生命周期处理，不发布虚假成功。

实现时向共享服务传递明确的群路由约束，将平台协议和 QQ SDK 类型限制在 Surface 边界内。不另建 SessionRouter；群专用限制不改变其他渠道在上述修复基线上的行为。

### 群绑定生命周期：持久保留，显式重置

以下为首版设计决策，尚未实施：群前台绑定不参与全局空闲自动解除，长时间没有消息后仍回到原 Thread。管理员显式重置是开始新群上下文的入口，执行前满足前述活动、Queue、交互与后台任务收敛要求；不能把无活动或普通讨论缓冲到期视为重置授权。

- 普通讨论缓冲使用独立 TTL 和容量，不续写会话历史，也不以有无缓冲决定绑定保留。缓冲到期只影响尚未提交的上下文。
- 群停用冻结现有绑定、阻止新的输入输出与恢复执行；停用不自动清除绑定。重新启用时重新核对群、Workspace、Provider、成员及公开权限和权威 Thread 状态。
- 成员加入、退出、撤权及管理/审批角色变动触发相应输入、交互、来源和输出权限更新，不自动清除整群绑定；没有有效成员时仍冻结，不能借新成员恢复旧任务的发送资格。
- 实现必须同时约束空闲扫描和共享自动解除用例，不能仅靠群仍暂停时的跳过条件声称支持持久绑定。资源优化留待后续独立设计；当前解除绑定与订阅的能力不能解释成“保留绑定但释放运行资源”。

## 新群实现前必须解决的风险

以下以原审查基线和仍在使用的共享服务为依据，约束将来的新群实现。旧群代码已删除；表中旧实现仅说明需要避免的假设，不再是可恢复或待改造的业务入口。

| 共享边界或历史依据 | 触发与影响 | 新实现要求 |
| --- | --- | --- |
| 旧实现曾把群和成员编码为同一地址；当前 [Policy](../src/policy/qq-access.ts) 和 QQ 来源仅承接单聊 | 新群若继续从 Conversation 反推成员，无法证明共享任务的发起人或回应者 | 成员独立传递，校验精确来源与实时权限，不恢复旧编码或别名 |
| [历史查询与显式恢复](../src/session-routing/router.ts)仍按 Workspace 提供能力 | 群若沿用完整单聊命令，可公开其他会话的名称、预览或历史 | 无绑定自动接续已在 `e54ebe97` 修复；群历史查询与显式恢复限制仍待实施，当前绑定唯一不等于历史公开授权 |
| [组合根](../src/bootstrap/gateway-component-graph.ts) 的 `outputIdentity` 包含完整已登记 Actor 集合并作严格快照比较 | B 首次登记后，A 已入队输出可能失效 | 分开群公开权限、任务发起人及绑定快照，不因无关成员登记失效 |
| 同一组合根的异步问题及[动态计划工具](../src/bootstrap/scheduled-task-tool-request.ts)要求允许 Actor 恰好一人 | 多成员群无法确定问题或任务归属 | 从精确请求/任务来源取操作者；无法证明时失败关闭 |
| [普通提交](../src/application/conversation-service.ts)在活动 Turn 上默认 steer | B 的新需求改变 A 正在执行的任务；来源层又因 actor 不同拒绝合并 | 群普通忙时输入走原生 Queue；首版不开放跨成员 steer |
| [异步问题协调器](../src/bootstrap/async-question-coordinator.ts)与共享 `submitAsyncAnswer` 只固定原 Thread，回答作为普通 Turn 输入提交 | A 的问题仍可回应时 A Turn 已结束、B Turn 已开始，回答可能 steer B | 群回答必须固定原 Turn；首版原 Turn 结束即过期拒绝，不转 Queue 或新 Turn，具体合同见交互归属 |
| Queue 更新（历史文件 `src/application/thread-queue-service.ts`，现已删除）保留条目的 `clientUserMessageId`，Queue 来源（历史文件 `src/surfaces/qq/queue-sources.ts`，现已删除）据此关联原作者 | 管理者改正文后仍保留旧作者来源；原生客户端修改也不能由本地票据可靠归因 | 首版不开放群 Queue 正文更新；修改后的来源不能宣称已可靠，后续另定作者、编辑者和外部修改语义 |
| [Queue 端口](../src/application/thread-queue-port.ts)只支持文本，待生效覆盖可能产生 `queue.pending-overrides` | 忙时附件或结构化输入若绕回普通提交将 steer；模型/Plan 偏好可能使文本入队拒绝 | 首版只接受纯文本排队，准备前拒绝不支持输入，最终提交重查忙状态；覆盖保持并明确提示拒绝 |
| 单聊 [QQ 控制器](../src/surfaces/qq/messages.ts)在共享命令前取消目标的来源、菜单和交互 | 若整体复制为群入口，普通成员的停止/切换命令可能先影响全群 | 新群所有副作用前完成操作级授权 |
| 单聊 [交互](../src/surfaces/qq/interactions.ts)按 Conversation 证明响应者 | 新共享群身份不能证明点击者权限 | 精确请求绑定独立的响应者权限和实时守卫 |
| 已删除的旧群 Outbox 曾以原消息/事件锚点作被动发送 | 排队、长任务或多次审批后原窗口/次数可能耗尽 | 新投递明确发送能力与模式，不恢复旧发送器或用新消息续借旧任务窗口 |
| 当前 [启动组合](../src/bootstrap/surface-composition.ts)与组合根拒绝不支持的 QQ 目标 | 新群若放宽为任意 QQ 字符串，可能消费旧成员会话、计划或投递记录 | 仅接纳新合同定义的精确身份；旧记录不解析、不恢复、不重放 |

存储的 Conversation→Actor 已支持多成员集合，无需为了共享群另造成员历史表。它只记录已观察到的授权操作者，不是 QQ 的完整群成员名册。

## 输入与近期讨论上下文

### 接收范围

锁定上游的 `GROUP_MESSAGE_CREATE` 只有开启“接收所有消息”后才推送。当前业务解析器仅消费单聊，不具备群 @入口或全量上下文采集能力。

- 默认由明确的 @触发任务。普通讨论仅在配置明确启用、平台确实提供该能力时作为上下文采集。
- 首版只采集配置允许成员的文本。未授权成员消息不启动任务、不登记授权 Actor，也不进入上下文。
- 平台只推送 @消息时，继续按 @输入工作，并明确普通讨论上下文不可用；不能将平台无事件解释为群中无人讨论。
- 全量模式中 @的可靠识别、两类事件是否同时投递、机器人身份及回声过滤须按锁定字段核对并实测；不能只靠正文包含某个昵称判定触发。
- 全量模式必须先识别控制信息，再决定是否采集普通讨论。`/respond` 等交互回应即使过期、格式错误或权限不足，也不得进入讨论缓冲或回退成普通任务；文字任务与管理命令必须明确 @机器人。文字回答也要求明确 @，按钮走独立回调入口，两者使用相同的请求、响应者和实时权限合同。
- 普通讨论中的斜杠文本、引用中的命令和伪造发言人标签均不执行。上下文中的成员提议不构成命令、文件或权限批准。

### 临时缓冲合同

缓冲仅保存尚未纳入任务的近期输入上下文，归 QQ Surface 的连接代次持有，不写入 StateStore、Delivery Journal 或日志，不复制已提交的完整会话历史。

- 建议缺省最多 10 条；同时设置单条/单群字节、存活时间和账号总量上限，具体值在阶段 G1 固定并记录为本地限制。
- 当前触发消息与近期讨论分别标记，发言人 ID 来自事件；昵称经过清理且仅作展示。引用和历史均作为低信任用户数据提供，不拼接成 system 指令。
- 普通讨论不自动下载图片、音视频或文件，只允许明确的有限占位说明。主动 @附件沿现有附件权限、容量与取消链路评估。
- 去重分别记录“已采集”和“已触发”，处理普通事件与 @事件任意先后及重投，不能因先采集而吞掉后续任务触发。
- 每次触发在有界并发保护下占用一个上下文快照，绑定群身份、连接代次和会话绑定代次。同一条讨论只能被一个在途快照占用，第二个触发不能再次包含；确认提交或原生 Queue 入队后，只结算该快照中的条目，保留期间新到的讨论。
- 明确未提交时，仅在原代次仍有效且满足期限、容量和权限的前提下解除占用并保留上下文；提交结果未知时不重新开放该批条目，保留有界去重状态并报告不确定性，不将 unknown 当作失败后可重用。
- 超限允许淘汰尚未提交的普通讨论，并标明上下文不完整；显式 @请求不能以“缓存淘汰”名义静默丢弃。
- 群停用、连接代次结束或会话重置时使缓冲及已取出的在途快照一同失效；成员撤权也剔除其未提交条目并使包含这些条目的在途快照失效。最终提交守卫重新检查快照代次和权限，防止取出后绕过 reset/revoke；已经提交到 App Server 的历史不会因此自动删除。

这不是等待执行的消息正文队列：@任务被接纳后必须进入共享提交或原生 Queue，不留在缓冲中等待空闲。需要执行的后续输入始终由 App Server Queue 承担。

## 并发、Queue 与任务归属

空闲时开始新 Turn，活动中普通输入进入原生 Queue；状态判断与最终提交必须在共享执行边界衔接，不能由 Surface 读一次 idle 后继续调用可能自动 steer 的旧入口。

首版忙时 Queue 仅接受纯文本。附件及其他结构化输入在下载、上传和其他准备工作之前拒绝，不借现有 steer 支持规避 Queue 的文本限制。空闲时允许的附件也须在最终提交边界重新核对忙状态；准备期间变忙则明确拒绝，不静默忽略附件、降为文本、隐式 steer 或留在本地等待执行。确认未提交的临时附件沿既有取消路径清理；提交结果未知时保留既有资源保护，不以拒绝提示推断可以删除。后续如扩展结构化排队，需先取得原生 Queue 的对应合同。

有待生效的模型、Plan 或其他当前 Queue 不能承载的覆盖设置时，`queue.pending-overrides` 必须返回可理解的拒绝说明，保留这些设置并说明如何处理；不清除设置来换取入队成功，不回退到 steer，也不把拒绝标记为已经排队。

来源需要分开三种身份：原输入作者、显式启动/管理操作的执行者、原任务输出归属。管理员启动另一成员的 Queue 条目不能替换作者，也不能继承一张已撤销的旧来源票据。现有 `sameQueueSelection` 比较包含 Actor 的完整 scope，需要连同冲突与未知结果逻辑一起修改。

- 不复制 DSH 的本地 merge 任务队列，不隐式把多人的需求合为同一个权限主体。
- Queue 条目目前没有可权威恢复的 Actor 字段，`clientUserMessageId` 也不能反推出成员。首版只让有权限的群管理者删除、排序或显式启动条目，不开放正文更新，也不承诺“成员只能删除自己的项”。
- 上游更新正文保留 `clientUserMessageId`，因此旧来源关联不足以证明更新后正文仍由原作者提交。关闭 QQ 编辑入口也无法阻止原生客户端修改，G1/G3 必须在首版 Queue 启用前定义执行内容与获授权来源的核对方式；不能确认时拒绝沿用旧来源处理回答、审批和投递，不能只因 client ID 相同就认定仍是原任务。后续开放群内编辑时，再分别定义原作者、编辑者、启动者的权限与输出归属。
- 原生 Queue add 是持久写入，可能在响应到达前开始执行。成员撤权后的本地守卫只能阻止尚未发出的请求及后续本地投递，不能保证撤回已提交条目。
- `/stop` 中断当前 Turn 并取消本地准备，不清空原生 Queue，也不表示所有后台任务已停止。首版作为群管理能力；回执分别报告中断结果和队列保留事实。
- 执行停止、群停用、撤权和重启时分别处理本地准备、已提交 Queue、活动 Turn、订阅和输出来源。未知结果不自动重试；无法证明来源的恢复任务不借新来信取得投递资格。

## 权限、交互与群菜单

### 最小能力划分

| 能力主体 | 首版允许范围 |
| --- | --- |
| 获准普通成员 | @提交；查看允许公开的本群状态；回答明确指定给自己的普通问题 |
| 明确配置的群会话管理者 | 在状态允许时重置/压缩、调整群模型、停止当前 Turn、管理本群 Queue |
| 明确配置的审批者 | 对有权处理的精确请求作单次批准或拒绝 |
| 本机配置操作者 | 启用群、选择预配置 Workspace、修改成员/角色和公开范围 |

角色允许重叠，但不能自动推导：群主、QQ群管理员、单聊允许用户和扫码者都不会天然获得本机执行权限。审批权限不等于管理会话的权限。

所有入口先判断结构化操作能力，再执行；管理菜单、文字命令、回调、动态工具及服务重用遵守相同合同。群成员看到按钮或文字 token 不等于有权使用。

### 交互归属

- 请求固定原群、Workspace、Thread、协议提供的 Turn/request ID 和有效期；子代理请求沿权威祖先关系路由，但保留原请求身份。
- 普通问题默认由精确来源的发起人回答，或使用请求明确指定的回答者。无法关联、`turnId: null` 等情况不能猜最近成员，应按对应请求的明确授权合同处理或安全取消。
- 异步问题回答必须同时固定原 Thread、原 Turn、问题请求及响应者。首版设计决策为原 Turn 一旦结束就让该问题过期并拒绝回答，即使同 Thread 已有新 Turn；不将回答自动 steer 到后来任务、转成 Queue 项或开始新 Turn。当前 `submitAsyncAnswer` 的 Thread 校验不足以提供该保证，G4 必须补齐协调器、提交接口和最终执行边界的精确 Turn 守卫，不能只依赖按钮失效。
- 审批按指定审批权限判断，不要求审批者等于任务发起人；每次按钮、文字回应及最终提交前重新校验。
- 保留随机一次性令牌、revision、完整展示就绪门槛和超时；新成员不自动取得旧请求响应权，外部客户端已解决、撤权、切换或重启后的旧回应无效。
- 首版只开放单次批准；会话级批准、命令/网络规则扩展、MCP 始终允许等暂不开放。它们可能影响之后其他成员的任务，需要另行定义群级授权。
- 敏感答案、凭据、OAuth 信息及不能确认适合公开的表单或交互，不在群内展开或收集；保留原协议的拒绝/取消语义，不能静默批准。

### 首版菜单范围

普通菜单聚焦本群状态、帮助和提交方式；管理菜单聚焦共享会话和 Queue。首版不开放跨会话历史、工作区随意切换、全局账户管理、权限模式修改、进程释放、群计划任务和动态计划工具。现有单聊命令目录不能整体复制。

计划任务后续若开放，继续保留 task Actor 所有权及独立 automation 后台 Thread，无人值守权限合同不变；不并入群前台 Thread，也不借群来信恢复发送资格。

## 出站、公开范围与发送能力

输出始终向原物理群公开，并在实际平台请求前复核群、工作区、任务来源及授权。已登记 Actor 集合变化不应直接决定任务成败；成员发言不能重置原来源期限或替换 owner。

### 模式与能力门槛

当前消息合同记录过群主动发送被 `40034105` 拒绝。不能依据单聊主动发送成功、群被动命令成功或官方接口存在，认定该账号具备群主动能力。

- 即时命令使用原消息/回调的被动资格，保持 `msg_id`、外层 `event_id`、ACK 互动 ID 和原生引用 `msg_idx` 各自含义。
- 队列和长任务的完整群交付需要明确可用的发送方案。优先规划经过账号权限确认及实机观察的主动结果投递；能力不满足时不能宣称完整群 Agent 可用，任务准入应明确受限。
- 如未来需要被动模式下人工领取结果，应单独设计准确到结果的新授权流程，不能把“有一条新来信”当作所有旧结果的发送资格。
- 发送模式在计划阶段明确，不在失败、过期或限流后自动换模式；未知结果不重发，不归还可能已消耗的额度。
- 旧实现的本地被动五分钟/五次约束仅作为历史保守依据，未取得新证据前不扩大；新实现须重新落实预算与授权，不保留旧群发送器。排队等待不刷新窗口。

### 展示与预算

- 群不使用单聊正文流式。默认减少可选过程输出，保留完整结果、必要错误和交互；已有可靠投递义务不能被后来显示设置抹去。
- 同群共享出站顺序和额度，不能按成员拆开以扩大额度。正文、审批、完成、附件和显式文件发送纳入统一计划。
- 超长结果只在发送前选择现有受控文件路径；部分发送或未知结果后不自动换成整篇文件重发。
- 引用外观与被动发送授权分离：是否呈现引用不改变原消息锚点要求。客户端外观仍须单独验收。
- 重新核对显式 `send-image`/`send-file`、工具生成媒体、通知和后台结果：这些入口不能从群 ID 反推出操作者，也不能借当前前台 Thread 替换原目标。
- 群禁用或公开输出权限撤销后停止新的投递；已在途请求如无法撤回，记录真实结果或未知状态，不声称已经阻止。

## 配置、旧数据与恢复

### 新配置合同

实施前定义群身份、明确 Workspace、允许成员、管理者、审批者、近期上下文采集及公开输出范围。本文不预先发明可供用户填写的 TOML 字段或隐式默认权限。

先完成共享校验、预览、修订检查、备份、写入和生效语义，再覆盖实际支持的 Setup/CLI、WebUI/API、运行解析、Doctor、配置示例和显示目标。暂不支持的管理入口明确呈现，不留出能保存但运行语义不同的路径。

授权收紧与普通展示变化分开处理。保存成功、权限实际生效和重启完成是不同状态；收紧权限时必须说明从何时阻止新输入/输出。默认缺失、非法配置和未知版本失败关闭。

### 旧群数据处置

1. 新群使用全新规范身份，不兼容旧群与成员复合编码；当前代码不解析旧群身份，也不提供迁移、恢复或别名。
2. 旧 `qq.groups` 和 QQ 群显示覆盖均由严格配置校验拒绝，不读取为有效授权、不自动改写用户文件。新启用需明确确认新的共享工作区、控制权限、审批及公开合同。
3. 旧成员可能有不同 Workspace、Provider、前后台 Thread 和偏好，不自动挑选、合并、删除或重写。旧计划与 Delivery owner 原样留在用户存储中，不能获得恢复、执行或发送资格。
4. 新群从全新 Thread 开始。后续若需要公开某条旧 Thread 的历史，作为单独显式操作处理，不夹带在升级中。
5. 新群重启只恢复自己的绑定；恢复订阅不恢复旧连接代次的消息发送来源，也不重放临时群讨论。
6. 群停用和最后一个已登记有效 Actor 撤权时按持久绑定合同冻结；管理员/审批者变化更新相应权限及在途守卫，不清除整群绑定。不能未经区分调用已有清理行为，意外解除全群绑定。

### 备份、失败恢复与回退

- 本次删除只改源码和文档，不读取、修改或删除本机配置、数据库和投递记录。若现有配置含旧 `qq.groups` 或 QQ 群显示覆盖，先为所选配置文件保存私有备份，再由本机操作者明确移除这些不支持字段；不得顺带清理单聊配置或数据库。
- 配置校验失败时保留原文件，按错误位置核对并人工修正。不要通过重建配置、删除数据库或忽略严格校验恢复启动；未知写入结果先读回核对，不重复提交或覆盖并发新值。
- 新群是否需要 Schema 或 owner 版本变化在阶段 G1 明确。现有 v6 可以存新字符串键，不足以证明恢复语义兼容；没有确定数据方案前不实施隐式升级。未来若授权修改数据库，须另行制定私有一致性备份及写入者协调方案，不能直接复制正在写入的文件充当备份。
- 回退前停用新群并核对旧版本对新配置/身份的处理。旧版可能重新开放旧群配置，必须同时核对旧群权限，不能直接降级启动。
- 备份只在明确范围、确认目标未被后来修改的条件下恢复，不覆盖更新后的用户数据。禁止以删除数据库、旧绑定或投递记录代替兼容处理。

## 验证计划与开放问题

以下均为群方案待执行观察，不是本轮取得的群行为证据。I0 的实际观察见“本轮前置步骤”，P0 的共享组件观察见“状态与依据”，两者均不替代真实群入口、多成员和投递验收。不新增或修改测试、探针或守卫脚本；实现时使用既有静态检查，并通过隔离的真实入口和获授权的平台路径记录实际输出。

| 场景 | 必须观察的结果 |
| --- | --- |
| 同群 A 提问、B 后续发言；其他群和单聊同用户发言 | 同群上下文连续，其他目标不共用 Thread |

| A 活动时 B/C 提交、管理员启动他人 Queue 项 | 不隐式 steer，来源作者与操作执行者分离，结果指向原群 |
| 忙时纯文本、附件/结构化输入、附件准备期间由空闲变忙 | 只有纯文本能排队；不支持输入准备前拒绝；最终变忙也明确拒绝，无降级、steer 或本地正文队列 |
| 待生效模型/Plan 导致 `queue.pending-overrides` | 保留设置并提示未入队，不清设置或回退 steer |
| 管理者请求更新 Queue 正文、原生客户端改已有正文后启动 | 群入口拒绝正文更新；旧 client ID 不被当作修改后可靠作者证据，来源不明执行安全拒绝路径 |
| A 发出异步问题后结束，B 在同 Thread 启动，A 通过按钮或文字回答 | 原问题过期拒绝，不 steer B、不排队、不新建 Turn；同一原 Turn 内有效回答仍按精确请求授权 |
| 非管理者 stop/new、非审批者点按钮、旧 revision、跨群 token | 在本地取消/写入之前拒绝，不改变别人任务和审批 |
| 新成员登记、发起人撤权、群停用、平台请求在途 | 无关登记不失效；撤权不借其他成员续权；在途结果如实记录 |
| `/stop` 后仍有 Queue 项、已提交后撤权、重启后 Queue 继续 | 回执不误称清队或撤回成功；来源未知不自动向群发送 |
| 长任务超被动窗口、审批耗额度、主动拒收、部分及未知发送 | 无续借窗口/自动换模式；完整或不完整交付状态有证据 |
| 旧成员绑定、旧计划、旧 Delivery owner 与新群同时存在 | 旧数据不迁移、不误恢复、不重放 |
| 群超过全局空闲阈值、缓冲 TTL 到期、重启、停用后重启或成员/角色变化 | 保留原群绑定；缓冲独立过期；停用/无有效成员保持冻结，其他变化只更新对应权限；仅获准显式重置建立新上下文 |
| 不同管理入口竞争修改、取消、非法角色、未知字段、保存未确认 | 共享修订规则一致，保留其他配置与新值，结果可区分 |

开放问题及下一步：

- **平台事件能力**：核对实际账号能否获得全量事件、真实 @识别及两种事件的重复关系；先完成协议字段映射，再在获授权群观察。
- **群主动投递**：现有拒绝记录不能被设计假设覆盖。核对账号开放条件与当前权限，在准入长任务前取得足够证据；不能解决则明确限制能力。
- **来源与持久版本**：确定群公开授权和精确作者如何进入来源/owner，以及重启后的未知归属处理；不得从消息正文恢复安全身份。
- **Queue 内容与来源核对**：原生客户端修改不会被群入口禁令阻止，首版启用前必须落实可靠核对或明确失败关闭的能力限制；群内正文编辑暂不开放，后续另行定义编辑者与原作者的权限和来源合同。
- **资源优化**：首版保留绑定且跳过群空闲解除；若后续需要保留会话身份但释放连接或模型资源，须独立明确恢复、订阅、在途操作及 Provider 共享生命周期，当前不宣称支持。
- **新数据与恢复合同**：确定新身份和配置版本、启用及回退过程；旧数据明确不迁入，不为旧编码保留解析或恢复路径。尚未读取真实旧数据。
- **敏感交互与群管理范围**：G1 固定可公开类型及操作能力表，未知请求安全拒绝，不能让现有单聊能力默认进入群。
- **平台与操作系统验收**：群成员退出事件的可靠性、真实按钮身份、移动端/桌面端显示、Windows/macOS 恢复均未观察；仅按取得的证据宣称支持。
