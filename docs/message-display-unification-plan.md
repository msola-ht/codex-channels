# 全渠道消息显示统一计划

状态：实施中；本文件是工作计划，不代表未完成能力已经开放。用户授权逐批关联审查、修复、独立 A 子代理复审及本地提交；不包含推送、部署或真实平台外发。

## 目标与边界

统一 QQ、Telegram、飞书和微信的消息显示含义、配置读写与发送消费。区分运行开发、后台日志、调用记录和用户可见消息；保持平台权限、回复窗口、任务执行与审批规则独立。

当前基线：全局只有工具、计划、思考显示，日志 debug/trace 同时影响生命周期详情；启动/配置通知、命令、交互和显式附件另有入口。QQ 支持单聊和明确授权群聊，群按成员隔离业务但共享物理收件人；飞书和微信限定私聊。TG 文档群聊未支持而入口未排除群输入，需要明确合同，不能借展示设置扩大授权。

不新增或修改测试、测试脚本及冻结资产。采用现有静态门禁、临时隔离配置上的真实管理入口与生产函数观察，记录实际反例输出；没有真实平台权限或现场条件时明确未观察范围。

## 统一合同

- 全局默认 → 渠道默认 → 账号默认 → 该账号的单聊或群聊默认 → 指定聊天覆盖，逐字段按此顺序继承。覆盖字段缺失表示继承，不物化默认；明确 false/hidden 保留；恢复继承是专用操作。只有实际支持的目标可以配置，QQ 群显示目标按物理群而非成员 Thread。
- 显示目标使用明确的 `surface + accountId + chatKind + chatId`，从渠道已校验的地址映射取得；QQ 的 `chatId` 为物理群 ID 或单聊收件人 ID，不从不透明 ID 的前缀猜聊天类型。这个键只用于显示策略，不能替换成员 Conversation、Actor、Thread 归属、来源代次、审批或回复窗口键；同一群 ID 在不同账号下也不共享设置。管理入口仍是本机 CLI/WebUI，群成员有任务权限不等于有权修改全群显示配置。
- 精简、标准、详细是一次应用明确字段的预设，不与自定义字段并存为第二个运行时开关；修改后按实际字段显示自定义。
- 成功结束通知关闭/简短/详细；统计基础/详细；工具隐藏/仅失败/紧凑/完整；计划、思考状态、commentary 分别控制；子代理及常规生命周期分类管理。
- 正文与附件、用户主动查询回执、审批和需回答的问题、整轮异常及交付失败不能被普通过程开关吞掉。未知 phase 不推测为 commentary。无正文结束需要准确的最小回执，不假造成功。
- 出站原生引用与入站引用上下文分离；用户可见流式与完整结果交付分离；静默提醒与不发送分离。能力限制形成有效结果，不静默承诺不支持的格式、编辑或提醒。
- 统一策略不解析模型正文、不修改 Core 权威状态，不复制各平台 Outbox/流式状态机。必要状态观察先执行，显示准入在渲染、分片和额度预留前执行。不能假定现有 `observe` 已覆盖全部收尾：在途流终结、工具缓冲清理、引用释放、临时通知来源释放及投递故障观察目前仍有发送路径内的工作，必须逐项拆出或保留独立结算路径；隐藏成功完成通知不等于丢弃 `turn.completed`。
- 持久记录格式判定不能依赖可变显示偏好。策略隐藏不伪造平台成功，不作为发送故障重试。新设置控制生效后新事件的准入；已经入箱的记录保留原投递义务，发送时继续校验原授权、来源与窗口，不因后改为 hidden 变成不可解码记录或空发送 ACK。管理预览明确说明存量 pending 仍可能投递；uncertain 不自动重发，blocked 不绕过原限制，显式核对或忽略沿用既有投递箱管理。新事件在准入时明确隐藏的不入箱，重启不补发。若要改变这一存量政策，必须先补充独立处置状态、失败恢复与回滚设计，不能在实现中隐式改变。
- 原授权、工作区、任务来源、代次及原来信窗口仍是发送守卫；关闭显示不能延长窗口、借新消息或改变群成员权限。

### P2 接口与恢复约束

配置继承的纯投影放在 `runtime`，由管理端与 Gateway 共同消费；事件显示分类放在 `surfaces`，Bootstrap 负责装配与路由。保持原有业务目标与来源类型，独立映射物理显示目标；渠道映射无法证明聊天类型时明确不支持，不能猜测。

新事件的显示决定在 live 准入时固定，并显式随富化、队列和投递上下文传递；持久 payload 支持判定不接受用户显示偏好。已有记录发送不得再次调用按当前偏好过滤的 `retains`。QQ 的 `supported` 目前混合来源、平台支持与显示过滤，也必须拆分。隐藏终态通过原有顺序队列执行独立结算，不进入 Journal，不伪造 ACK。

本批优先不改变投递箱 payload v1、StateStore 和既有 TOML 三个全局显示键。进程内可保存已准入呈现上下文；恢复记录采用稳定的可见呈现，保留正文、附件和送达义务，但不承诺恢复后精简/详细版式与原来完全一致。若需要跨重启精确保留原引用、静默或版式，必须另行设计持久字段及恢复合同，不能把内存快照说成持久保证。新配置分层的精确结构和管理输入，须在开放前连同消费者冻结并记录。

## 已确认的关联差异

- `src/bootstrap/surface-manager.ts` 在准入前执行 observe；`src/surfaces/persistent-output.ts` 负责存储分类和解码；显示与存储格式不能混为可变判断。
- 飞书 `outbox.ts` 的 `turn.completed` 在发送分支内结束流、清理过程缓存并释放引用；Telegram 观察器已停止输入状态，但其他收尾仍需核对。不能把路由器观察器的存在当作隐藏事件后状态完整的证明。`persistent-surface-output.ts` 仅在投递与 Journal ACK 成功后通知来源释放，隐藏路径需要自己的本地结算语义，不能伪造平台确认来复用它。
- `src/surfaces/types.ts` 当前无聊天类型/显示能力模型；仅靠 Surface 名称不足以确定群能力。
- `src/surfaces/telegram/bot.ts` 按 chat.id 路由并校验 Actor；群支持合同需与入口统一。不得在本计划中未经明确接入设计而扩大群范围。
- TG 思考/完成静默参数与模块 README 描述有差异，P4 明确目标并核对实际参数。
- 调用转储管理提示主要覆盖 App Server；Relay 刷新影响新请求，应分别说明保存与激活。
- 现有文档夹杂历史部署备注；更新受影响的现行合同，不把历史未验收文字当成当前能力证明。
