# 四渠道菜单：现状与下一步

## 当前结论

布局改版前的基础整理已完成并提交，基础交付基线为 `6ffd5a83`，第二阶段只读分析对应合并 main 后的 `62e000db`，分支为 `fix/channel-menu-drift`。静态菜单、帮助以及工作区、模型、会话列表已有共同展示来源；展示抽取保留既有外观与交互合同，已修复的入口漂移见下表。收益在于后续修改共同内容时可以集中维护，减少四份实现各自变化的风险。

当前进入第二阶段的布局方案设计，尚未修改界面代码。用户已报告完成部署重启；运行版本及四端真实客户端表现尚未独立验证，代码收尾不代表平台交互已验收。

本文维护当前决策、后续范围和验收缺口，不记录逐轮操作。命令与使用方式以[用户指南](user-guide.md)为准，文件职责以 [Surface README](../src/surfaces/README.md) 为准。

## 哪些应共享，哪些必须留在渠道

共同展示层维护命令标签、描述、静态操作参数前缀及由 Application 结果派生的展示数据，业务语义与执行由 Application 负责。渠道拥有信息分组、字面转义、截断、分页容量、按钮类型、填写方式及返回路径。相似标签不代表相同交互，当前不再仅为消除重复而增加抽象。

后续布局修改必须守住以下边界：

- **展示不授权。** 静态目录不是能力白名单；飞书仍只接受实际卡片中的动作，QQ 保留自身命令及参数准入，QQ Goal 仍只支持查询和清除。
- **身份不随布局变化。** 工作区使用原始 ID，模型使用 Provider/model 身份，会话保留权威 selector 和完整 ID；不得用标题、显示位置或截断文本代替执行身份。
- **交互仍由原链路管理。** Actor、Workspace、Thread、快照、令牌、有效期、一次性消费和提交前重读继续由原控制器与 Application 校验。
- **渠道能力允许不同。** 飞书卡片与表单、Telegram 命令与键盘、QQ 回调与填写按钮、微信文字入口分别设计；专有诊断和导航不强行合并。

状态快捷按钮、Queue、扩展和计划任务的动态菜单尚未纳入本轮重构。它们不是本轮遗留缺陷；后续确有布局需要时，再按各自的状态和确认合同确定范围。

## 下一步怎么做

第二阶段先统一信息分组、命名、操作方式和导航含义，再适配各渠道。统一不等于四端使用相同布局，更不意味着所有命令结果页一起变化。当前只完善方案，具体分组、标签、排列与实施先后仍待布局对照确定。

### 沿用现有命令

所有入口继续使用现有命令、别名、参数与执行链路，不新增独立命令来替代原命令，也不引入新的分类命令或参数语法。例如，不为了帮助分组新增 `/help <分类>`；QQ 已有的 `/help model 1` 等内部菜单路径保持原有支持范围，不向其他渠道直接复制。

菜单只改变已有能力的查找和呈现。点击后原本直接执行、打开选项、填写后发送或确认的行为保持不变，标签应准确反映实际行为。未来如需新增卡片内导航回调，应在后续批次明确其导航职责及允许动作，不借此建立另一套业务命令入口。

### 首批允许改变的页面

| 范围 | 可以调整 | 保持不变 |
| --- | --- | --- |
| 首页 | 现有入口的分组、顺序、标签和说明 | 命令身份、参数、点击效果及能力范围 |
| 静态分类菜单 | 分组归属、呈现顺序和操作方式说明 | 原有执行、填写和确认链路；既有导航目标 |
| 帮助呈现 | 常用摘要、分段与阅读顺序 | 现有帮助入口和完整用法的可获取性；不新增分类语法 |
| 飞书历史／归档会话选项 | 补充序号、必要的短身份信息，让同名或截断后相同的标题可区分 | 完整 Session ID、权威 selector、查询、排序、分页及恢复动作 |

首批不改 `/status`、`/usage`、`/metrics` 等结果页，不改模型／思考／速度和工作区选择页，不改审批、表单与确认界面，也不改会话列表的其他渠道呈现。状态快捷按钮、Queue、扩展和计划任务动态界面继续保持原样。飞书会话选项是本批唯一明确纳入的动态列表展示调整。

修改共享标签或帮助定义前，必须列出所有消费者及受影响页面；若会波及范围外页面，应在目标渠道或页面保留局部覆盖，不能让共享变更自动扩散成全局改版。

### 先交付布局对照，再实施

方案以“共同分组 → 现有操作 → 四渠道入口”为核心，候选分组包括会话与工作区、模型设置、任务工具、用量与账户、扩展能力及渠道帮助；这些是讨论用的信息分类，不是新增命令，也不是已确定的首页布局。首页保留哪些快捷入口应在对照中说明理由。

| 交付物 | 必须说明的内容 |
| --- | --- |
| 四渠道入口对照 | 每项对应的原命令／既有动作、入口位置、直接执行／选择／填写／确认方式，以及渠道不支持的部分 |
| 修改前后结构 | 首页、分类和帮助的具体变化；列清本批受影响页面及保持原样的页面 |
| 关键路径 | 从入口找到原操作并得到原结果；飞书同名、长标题会话能区分且不会改选目标 |
| 分批实施范围 | 按渠道和页面交付，复用现有目录与展示数据；每批可独立审查和回退 |

飞书可优先解决分组和会话辨识；QQ 复用现有分页及返回，只整理入口层级；Telegram 保留命令菜单与既有键盘，先整理帮助摘要；微信采用分段文字和可复制的原命令。该顺序为建议，具体实施仍以布局对照为准。

### 返回导航与长列表另列一批

后续再设计飞书更多页返回首页、飞书／Telegram 模型返回提供商，以及飞书模型和工作区长列表的完整浏览路径。QQ 已有首页、模型返回提供商和动态分页，飞书会话列表也已有业务分页，应复用，不重复建设。

飞书选择卡的前 18 项限制同时关联模型快照和实际允许动作，不能只增加翻页按钮或取消截断；卡片 `help` 动作当前打开更多页，不能直接改名为首页。返回提供商只能改变浏览范围，不能修改当前模型设置。这批需单独审查导航回调、身份、快照与失效规则，并继续沿用原业务命令。

### 每批完成条件

主代理先审查入口到消费的关联链路及反例，修复后由 A 子代理独立复审，再完成必要修复。检查实际命令、参数、填写前缀、选中身份、页面容量及范围外呈现是否保持；真实客户端观察与静态检查分别记录，未观察项不得写成通过。文档只维护当前决策和验收缺口，相关的旧描述（如飞书 README 首页动作数量）随实际布局同步修正。提交、部署按用户授权执行。
