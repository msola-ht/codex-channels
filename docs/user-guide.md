# Codex Connect 使用指导

QQ 个人认证频控的全链路修复尚未部署：可靠正文、工具终态、完成通知及生成图片遇到分钟额度不足时，在原投递期限内等待名额释放，其他接收人的发送继续；不会延长任务来源授权。额度来不及释放、每日额度不足、取消或授权失效仍会明确保留失败，不自动重发。发送队列中的未派发取消按“未发送”记录，已派发且结果未知仍需人工核对。详情与隔离持久链路证据见 [QQ 复审记录](qq-message-contract.md#全链路复审修复源码调整未部署)。

QQ 当前源码仅开放单聊。旧群实现、群与成员复合身份、群配置、群显示覆盖及配对入口已删除，新群按独立共享会话方案重新设计；本次删除及单聊修复尚未部署，先前 `7898264e` 的部署记录不包含本轮变更。旧群绑定与结果记录原样保留，运行时不解析、恢复或迁移，也不自动删除。

已有配置含 `qq.groups` 或 QQ 群显示覆盖时，严格校验会拒绝启动及管理读取。请先为实际使用的配置文件保存私有备份，再由本机操作者明确移除这些不支持字段，保留单聊及其他配置；本次源码修改不会自动改写本机配置。修正失败时保留原文件核对，不通过删除数据库或重建配置绕过错误。回退旧版前核对旧配置可能重新启用的群权限，逐项恢复必要字段并保留备份后的其他修改；数据库、绑定与投递记录不在本次清理范围。后续方案与数据边界见[QQ 群聊设计](qq-group-design.md#配置旧数据与恢复)。

单聊投递区分可选显示与已入箱的可靠消息：普通菜单及临时过程保留正文/终态余量；已入箱的正文、工具终态与完成通知按实际滚动额度发送，不再受可选过程的每轮累计上限拒绝。未发出的预留会释放，在途、未知结果和已派发拒绝仍占额度。多片完整正文可在发送前因额度不足改为单个文本文件。真正额度耗尽时，明确尚未发送的结果仍保留为 `blocked`，已有预览、部分发送或结果未知仍为 `uncertain`，均不自动重发。此次源码调整尚未部署。流式来源随取消和过期回收；审批与问题正文的文字回应命令继续沿原一次性令牌与版本校验。

“常规通知”使用可选 `display.routine_notifications`，缺省开启且不物化；四渠道支持同名五层覆盖；旧 QQ 群覆盖严格拒绝，不提供查看或恢复继承入口。CLI、WebUI/API 全局管理为 `display.routine-notifications` 的显式 set boolean/inherit，读取 `routineNotificationsEnabled` 与 `routineNotificationsOverride`（布尔值或 null），恢复缺省删除字段。任一渠道启用且全局有效值改变时重启 Gateway，否则 reload；隐式 true 与显式 true 互换只 reload，范围数组沿整体判定。保存前私有备份，取消、未变化不写，旧 revision 拒绝，读回不确定不重试。关闭范围与保留异常、持久 Workspace 回执、已有 pending 义务见[过程显示范围与继承](display.md#过程显示范围与继承)。回退旧版前显式清除全局及所有覆盖中的 routine_notifications，不自动迁移或覆盖后续修改。源码尚未部署，真实平台效果待验收。

本文是 Codex Connect Gateway 的完整用户指导。根目录 [README.md](../README.md) 只保留安装入口、最短配置路径和常用链接；遇到具体问题时按本文或对应专题文档继续阅读。

## 1. 工作方式

QQ 下述前十批能力已随 `9c0d3488` 部署，四渠道已进入 ready。启动就绪与客户端验收分开记录；图片、文件、音视频及高影响管理操作等未取得实机证据的分支仍待验收，具体证据见 [QQ 消息合同](qq-message-contract.md)。后续源码修改不会自动部署。

任务重试、子代理、计划、工具与思考状态反馈及完整 commentary 已随基线部署。计划、工具及思考展示遵循目标的有效 display 范围设置；思考只显示状态，commentary 不流式、不转文件，任务开始通知复用共享“已开始处理”及权威审批方式，并遵守常规通知开关。过程反馈每轮最多八片，还受本轮新增的共同额度保护限制；停止、切换、来源失效及重启后不补发旧进度。过程反馈与最终正文、完成统计分别确认，完整客户端效果仍待验收。

QQ 音视频输入：一条消息只接一个语音或 MP4 视频，可附普通文字需求，不与其他附件混合。语音优先使用平台转写文字，转写中的斜杠命令也只作任务正文；没有转写时只接平台转换后的 WAV，最多 20 MiB、下载最多 30 秒、暂存一小时，实际模型须支持音频。视频最多 64 MiB、下载最多 60 秒、私有引用有效期 24 小时，沿已配置的视频分析 MCP 使用，不分析音轨；未配置时不能声称已看过视频。准备期间停止或切换会话取消提交，提交结果未知时保留已共享的引用，不自动重试。

QQ 支持单聊任务（附件源码支持范围及待验收状态见下文）：`codexc setup → 通讯渠道 → QQ` 可扫码或手工保存 AppID、
App Secret 与同应用下的用户 OpenID 允许名单，默认不启用，确认后开启文字渠道。
空单聊名单拒绝所有单聊用户，OpenID 不是 QQ 号码。扫码直连腾讯，不使用共享代理；
Gateway 的 QQ 连接使用共享代理。QQ 凭据编辑使用 Setup，WebUI 显示已配置及启用状态。
启停、账号、凭据或移除允许用户后按提示重启 Gateway；新增允许用户可热加载。
使用 `codexc doctor` 查看脱敏配置状态，使用 `codexc logs gateway -n 100` 查看连接状态。

QQ 单聊不使用出站原生引用，命令、正文、续接和完成卡保留原 Markdown/文本方式，流式保持原样；此修正已随基线部署。不支持机器人主动引用自己历史消息，旧群引用实现已删除。

当前源码支持读取用户原生引用中的图片：只取 `message_type=103` 事件内唯一匹配 `ref_msg_idx` 的元素，不额外查询历史。当前消息图片在前、引用图片在后，合计最多四张、20 MiB，单图最多 10 MiB；仍校验格式、内容签名和下载授权。引用的文件及音视频只显示未读取注记，引用图片不能与当前文件或音视频混合提交。当前正文中的斜杠命令和交互回答按原入口处理，不下载引用图片；引用内容只作上下文，不作为命令。已有构建部署记录见 [QQ 消息合同](qq-message-contract.md#本轮完整适配审查)，真实客户端仍待验收。

普通文字、图片、文件、语音及视频提交在共享提交结果明确 `steered=true` 时，QQ 使用共享文案确认追加。`steered=false` 不发送这条回执，但不能据此判断一定新建了 Turn：其他客户端并发启动任务时，普通 start-or-steer 请求仍可能实际追加。回执失败仅记录“追加输入已提交，回执未确认”，不将已成功的提交误报为失败或撤销结果来源。已有构建部署记录见 [QQ 消息合同](qq-message-contract.md#本轮完整适配审查)，真实客户端效果仍待观察。

当前没有群 @消息、按钮、`/qq-pair`、审批、附件或群旧结果的业务入口，旧群计划不得恢复执行。底层协议编码保留群 API 不表示业务可用；单聊允许名单不授予未来群权限，旧配置及数据不作为新群的兼容基线。
QQ 支持普通文字、`/help`（`/h`）、`/status`、`/stop`、`/workspace`（`/work`）、`/model`、`/new`、`/sessions` 和 `/resume`（`/r`）。

四渠道的 `/status` 提供一份状态：工作区和目录、可用 Git 分支、完整 Session ID、会话与运行状态、模型及分行执行设置、有效消息模式、上下文占用、累计 Token，以及已有账户额度摘要。没有独立详情页或切换按钮，命令不接受参数。执行目录未确认或不同、设置待生效按情况追加；不展开规则清单、Turn ID、Token 分项或完整账户额度表。主动查询不随静默模式隐藏；请求记录统计使用 `/metrics`，完整账户额度使用 `/usage`、`/limits`。请求记录统计与 App Server 会话累计口径不同，不保证数值相等。
飞书、QQ、Telegram 状态页提供“请求统计”“账户用量”“账户额度”按钮；微信保留文字命令入口。`/metrics` 的当前会话 ID 完整显示，已有记录时增加本轮/会话耗时、平均首 Token 和请求输出速度，缺失值不推算；历史耗时不完整时明确标记。
图片输入与交付仍待实机验收：可发送 JPEG、PNG 或非动画 GIF，支持纯图片或附普通文字需求，每条最多四张、单图 10 MiB、总量 20 MiB；实际还受模型图片能力限制。图片附带斜杠命令或交互回答不会执行，请单独发送命令。下载期间停止、切换会话或模型后不继续提交旧图片。生成图片沿共享可靠投递发送 PNG/JPEG；只有文件引用、拿不到内容时明确提示。显式本机 `codexc channel send-image` 复用现有绑定及校验，QQ 上传本地上限为 5,000,000 字节；生成图因共享投递记录包含 Base64，还受更小的单条存储预算约束。上传成功不等于客户端已确认显示。
文件和引用输入仍待实机验收：每条可上传一个文件，可附普通文字需求，不能与图片混发。`.txt/.md/.markdown/.csv/.tsv/.log/.json/.jsonl/.yaml/.yml/.toml/.ini/.xml/.html/.css/.js/.ts/.jsx/.tsx/.py/.rs/.go/.java/.c/.h/.cpp/.hpp/.sh/.sql` 按 UTF-8 文本处理（扩展名不区分大小写），最大 1,000,000 字节；超过 32 KiB 时使用私有临时路径。其他扩展名或无扩展名的文件作为不透明字节暂存，最大 5,000,000 字节，最多保留 16 项；不自动解压、执行或安装解析器。所有完整暂存保留 24 小时，任务使用现有文件能力读取，不自动扩大权限。附文件的斜杠命令请另发。原生引用只取平台本次提供的唯一匹配元素，文字最多保留 8,000 码点，图片按上文的合并限额及下载授权处理；不读取更多历史，引用文件及音视频不下载。引用中的命令仅作上下文。长结果转文本文件继续沿已有方式交付。
模式与状态批次新增 `/effort`、`/fast`、无参数 `/plan`、`/permissions`、`/autoreview [on|off]`、`/whoami`（真实客户端仍待验收）。菜单使用回调，思考等级和速度可直接选择；速度菜单只查询，裸 `/fast` 会切换速度，主 Provider 同时更新 Codex 用户级默认速度。审批方式按钮固定原会话，运行中或有待处理审批时拒绝修改。权限入口只列可选配置；身份仅显示当前 App ID 与脱敏 OpenID。安全短详情与按钮合并为 Markdown，特殊构造或长详情按完整字面内容发送，全部确认后才开放选择。
扩展查询批次新增无参 `/skill`、`/agents`、`/release`，Plugin 列表/搜索/详情/健康，MCP 列表/健康/详情及工具、资源和模板目录分页搜索，以及 Hooks 列表/分页/详情（真实客户端仍待验收）。从扩展菜单点击查看和翻页，无需手输已有选项；搜索仍可使用共享文字参数。查询不启动任务或结束进程，任务调用见下述显式任务批次。过长详情只发超限提示及导航；会话或 Provider 变化后旧选择失效。无绑定会话时 MCP 目录沿共享主实例查询，不代表待选择 Provider 的目录。
显式任务批次已接线 `/review`、带需求的 `/plan` 及 Skill、代理角色、Plugin 调用，真实客户端仍待验收。“任务工具 → Review”面板提供固定审查入口；技能和角色列表、Plugin 详情可选择名称后填写需求。填入按钮只帮助编辑文字，发送时仍按当前工作区和 Provider 重新解析、授权，不保留旧菜单的执行权限；名字过长或无法准确表示时不生成截断按钮。任务结果只回传本次提交明确关联的 Turn，允许其原本由 TUI 启动；重启或恢复会话不补发旧结果。
MCP 与 Hook 管理批次已接线，真实客户端仍待验收。MCP 详情可点击登录，授权地址通过“浏览器授权”按钮打开，本机地址须在 App Server 所在电脑打开；收到链接不代表认证完成，未收到完成通知时查询 MCP 实际状态。支持共享 `/mcp reload` 和资源读取语法；目录中经过脱敏的 URI 不能直接当原始资源 URI。Hook 可通过列表选择详情、信任、启用和停用；完整字面预览之后的操作提示提供可复制的 `/hooks confirm <令牌>`，不挤占详情预算，仍须详情与操作提示全部送达后才开放按钮及文字确认。文字入口不能绕过展示门槛。已有构建部署记录见 [QQ 消息合同](qq-message-contract.md#本轮完整适配审查)，真实客户端呈现仍待观察。截断或需替换字符的 Hook 必须本机审查；停止、切换、过期及重启使旧确认失效，已经发出的写入不会回滚。Hook 写入影响共享 Codex Home，MCP 重载及 Hook 保存不等于任务已执行。
会话管理批次新增 `/rename <名称>`、`/archived [列表参数]`、`/archive`、`/unarchive <序号、名称或 ID>`、`/pin`、`/unpin`（真实客户端仍待验收）。通过帮助页“会话管理”打开当前会话操作按钮，其中“已归档会话”查看归档列表；重命名需补充名称，其余固定操作使用回调。归档列表支持搜索和分页，点击条目使用精确 ID 取消归档并恢复到当前会话，不能当作普通 `/resume`。
归档会解除当前会话绑定；归档及恢复归档在尝试前撤销旧任务结果和交互来源，失败也不恢复，不补发历史结果。重命名和置顶不撤销现有来源。归档、置顶及取消置顶不接受额外参数；归档、恢复归档和重命名的空闲条件、名称长度及权限复核沿用共享会话服务。
上下文操作批次新增无参数 `/compact`、`/fork` 和 `/revert list [页码]`、`/revert <当前列表序号或完整 Turn ID>`、`/revert confirm <令牌>`（真实客户端仍待验收）。“会话管理”面板提供入口：压缩回执只确认请求，不表示已完成；QQ 按实际事件发送压缩开始和完成通知。派生会切换当前会话并撤销旧来源。
回退采用列表选择、完整预览和确认按钮：共享每页 25 条历史在 QQ 拆为每屏最多 9 项，摘要只用于列表展示，预览完整保留影响范围、活动任务、队列及副作用提醒。预览使用主动消息，完整字面详情送达后才开放最后的确认按钮，计主动额度；确认文字命令也须有本代次完整展示的预览。超限或失败不开放确认、不自动重发；重新列出、停止、切换或重启后旧确认失效。回退只移除历史，不恢复文件或外部副作用；历史/队列变化、过期、跨用户和重复确认均拒绝，执行结果未知时不自动重试。
QQ 的 `/schedule` 沿既有计划任务合同执行；会话 Queue 的命令、菜单和结果来源关联已移除。
启用 Gateway 计划任务后，QQ 复用共享创建预览、列表、运行记录、暂停/恢复、立即运行、重命名、显式重试和删除。创建及删除只有在完整预览送达后才能确认，五分钟内有效，文字 confirm 也不能绕过；停止、切换、取消或重启后请重新预览。暂停或删除不停止已经运行的任务，`/stop` 操作当前前台任务。每次运行结果固定原任务的工作区及后台会话，切换前台仍回原聊天，原绑定移除后拒发；计划任务使用主动完整结果，计主动额度，不使用来信被动正文流，重启不恢复旧结果来源。
当次配置变更通知仍待实机验收，只发给显式单聊允许名单。新增用户热加载后更新名单；重启前同应用只通知新旧名单交集，换应用或禁用时不发送。每轮最多六十秒，复用主动额度与 Markdown 规划，逐人完整确认后才视为该轮成功；失败或结果未知不自动重发。QQ 不接收持久工作区配置事件重放，也不会从历史会话推导收件人。

QQ 启用时，Gateway 首次连接就绪后向允许名单中仍有授权且工作区有效的用户尝试发送上线通知，展示连接状态、版本及按有效模式选择的会话摘要；普通断线重连不重复通知。上线通知失败不阻止渠道使用，也不自动重发。
QQ 上线和完成通知直接复用共享结构化呈现，与其他渠道采用同一数据语义；目标有效消息详情 `presentation_detail = "detailed"` 显示会话与本轮关键统计，不自动展开环境和 Token 分项；缺省 `basic` 保留基础展示，独立于日志 `debug` / `trace`。详细预设的工具档为 `operation_updates = "detailed"`，正常详情有界，失败保留原有脱敏详情；完整预设使用 `operation_updates = "full"` 和 `presentation_detail = "full"`，逐项展示工具详情并展开可用统计分项。旧配置不自动改写，需重新应用目标预设；回退旧版前需将新增值改为旧版支持值。不再每次附加渠道就绪与投递箱提醒；实际正文投递失败或结果未确认时，仍尝试独立提示。完成状态表示任务执行状态，不代表正文全部送达；重启前的任务结果仍不补发。
QQ 也接收会话空闲解除占用、全局空闲释放、连接变化、警告、会话可用性与名称更新、上下文压缩、Hook 和自动审批完成通知，以及账户、额度和 MCP 状态。全局通知只发显式单聊允许名单；空闲解除后若已建立新会话，不再发送旧解除提示。通知不授予旧任务回传资格，重启后不恢复旧通知来源。本轮新增通知的真实空闲释放与客户端显示仍待验收。
可靠完成通知按共同滚动额度与单计划上限交付，异常长字段或额度耗尽会拒绝发送并保留失败状态供本机投递箱核对，不截断内容或自动扩容。当前源码按个人认证处理：账号请求间隔至少 100ms，接收人主动消息每滚动分钟 20 次、每滚动 24 小时 1000 次，仅本进程计数，不代表平台剩余额度。可靠工具终态及持久通知不再扣十片本地余量；大量消息仍可能耗尽接收人额度，不保证正文永远有余量。这项调整尚未部署，不自动清理或重发旧记录。额度菜单保持原查询的容量和超限提示；查询期间切换提供商、会话或进入恢复状态后不发送旧额度。任务命令的启动回执随原来源取消而失效，发送等待期间停止或切换后不会继续发送旧回执。
任务结束时单独发送共享完成统计通知，按实际事件区分完成、失败和中断，展示可取得的模型、耗时、Token 与会话信息；缺失统计不补零。通知仍须满足原任务来源和发送预算，不代表正文已全部送达；已撤销来源（例如 /stop 或切换会话）不会因终态通知重新获得发送资格。

Gateway 把 Telegram、飞书、微信和 QQ 消息接入本机 Codex App Server。`codexc remote` 连接对应 Provider 的同一个 App Server，原生 TUI 与聊天渠道可在工作区与 Provider 匹配时接续同一 Thread，并共享实时运行状态。Workspace 注册表由 Gateway 管理，终端包装入口读取同一份配置；它不是上游 Project 的同步副本。

App Server 是 Thread、Turn、Item 和会话历史的唯一事实来源。Gateway 的 StateStore 只保存渠道与 Workspace 的最小绑定，不复制完整会话历史。独立投递箱按[投递合同](delivery.md)加密保存待送达结果；显式开启的调用转储另按下文保存模型报文。

## 3. 初始化与配置

所有 CLI 命令在结束或失败时显示“命令总耗时”，单位为秒并保留两位小数。计时统一写入 stderr，stdout 的 JSON、JSONL、版本号和导出内容不混入计时文本；主菜单每次执行的命令也单独计时。前台服务、日志跟随和交互命令的耗时包含运行及等待输入的时间，在命令返回时显示；强制终止进程时不保证输出。使用单调时钟，从命令分派开始，不包含 Node 加载 CLI 静态模块之前的启动时间。

在交互终端直接运行 `codexc` 打开主菜单，依次为运行与连接、工作区、日常设置、接入与账户、状态与服务、数据与维护、程序维护和退出。主帮助采用同一分类；现有子命令保持不变。“运行与连接”提供 Codex TUI、工作区与 Provider 选择、WebUI 和前台核心服务，macOS/Windows 另显示 Desktop App；工作区列表按 ID 排序并标注默认项，Provider 只列当前配置可用的实例，隔离实例按 ID 排序，当前不提供聚合项。“状态与服务”先列状态、日志与诊断，再列启停和安装；“数据与维护”集中指标、额度、调用记录、投递核对、Relay 查询与清理；“程序维护”包含版本、初始化与配置向导、更新与卸载，Windows 另显示权限修复。更新、修复和卸载需确认。

菜单在同一次调用的循环内保留上次选择，方便连续操作；该选择不写入配置，也不跨进程保存。交互菜单要求标准输入和标准输出均连接终端；输入重定向时，`config` 显示帮助，`timezone` 仅显示当前时区。配置路径查询明确使用 `codexc config paths [--json]`，返回绝对路径且不创建配置，终端与管道中的行为一致。非交互终端无参数时显示帮助，显式子命令继续供脚本调用。需指定参数的图片发送、投递处理和重置券消费仍使用对应直接命令。

在 `codexc` 主菜单选择“状态与服务”可选择操作和目标。菜单调用顶层服务命令，`restart all` 包含已安装且未关闭的 WebUI。
`all` 覆盖 App Server、Gateway 与已安装的可选服务：`start all` 与 `restart all` 的启动段按配置跳过已关闭的 WebUI 和未启用的 Relay，`stop`、`status`、`logs` 的 `all` 仍包含它们，便于停止和排查。启动逐项等待就绪，停止顺序为 WebUI、Relay、Gateway、App Server。
WebUI 开关位于 `codexc config → 服务访问 → WebUI 设置 → 启用状态`，写入 `[webui] enabled`；未设置时沿用已安装的服务定义。显式 `false` 后 `codexc start all` 不再启动它、`codexc restart all` 会停止它且不再启动，`codexc update` 也不恢复它；设置本身不停止正在运行的实例，也不删除已生成的服务定义。需要时仍可用 `codexc start webui` 单独启动，用 `codexc stop webui` 单独停止。
菜单日志显示最近 100 行，持续跟随仍使用 `codexc logs <目标> -f`。卸载后台服务需确认。

`codexc work` 按列表、设置默认、注册当前目录、注册已有目录、新建目录和移除注册排序；选择默认项即保存，注册前显示实际目录并确认，移除注册不删除目录。`codexc metrics` 按聚合报告、会话列表、会话轮次明细、会话最近运行汇总、请求明细、历史额度和数据库状态排序；会话明细和最近运行汇总共用列表选择，并提供明确的手动输入 Thread ID 入口。清理与重置统一使用 `codexc cleanup`。上述操作菜单完成单项后可继续选择；“运行与连接”完成后返回该子菜单，退出后返回主菜单。Setup 和 Config 单项失败会显示错误并返回各自分类菜单，不自动重试写入。
新增或重复注册工作区保留有效的默认工作区；仅在默认值缺失时选择后备工作区，失效目录仍需显式清理。

```bash
codexc init                  # 首次安装的完整交互向导
codexc setup                 # 跳过接入后补充配置，或之后管理接入
codexc config                # 日常设置
```

Gateway 配置位于：


分别注册为 `codex-connect` 与 `group`，默认工作区仍为 `codex-connect`。指定自定义配置位置时，两目录均位于配置文件所在目录。

CLI 和 WebUI 的 Gateway 设置在读取和保存前均校验当前配置结构；不支持的版本、未知字段或非法值会阻止操作并保留原文件，不以默认显示值掩盖错误。请先修复配置，再重新进入设置。

Plugin 查询与调用不再需要 Gateway 功能开关。旧配置中的 `[experimental].plugin_api`（TOML 写法为
`[experimental]` 表下的 `plugin_api`）及仅含该字段的表已不受支持，不会被自动忽略或迁移。
升级前请备份实际使用的 `config.toml`，再显式删除该键及空的 `[experimental]` 表；未清理时配置校验失败，
原文件保持不变。若需回退旧版本，恢复与该版本匹配的配置备份。程序更新不会代为修改这项旧配置。

项目技能覆盖更新先复制完整候选，再核对确认时的目标并替换；失败保留旧版或报告恢复材料的位置，失败恢复不覆盖已存在目标。更新成功也保留旧目录副本，输出其精确路径；确认旧内容无需保留且没有进程继续使用后，可手动清理。取消覆盖不写入，新会话读取更新后的技能。

技能卸载确认绑定当时的目标路径、父目录和内容修订；等待确认期间发生变化时拒绝旧确认。卸载会把实际原目录移出 skills 根目录，保留在父目录下的私有隔离目录并输出精确位置，不永久删除其中的文件。若跨卷或文件占用导致无法移动，不会用复制后删除替代。原目录仍被编辑器或进程持有时，后续写入也保留在该目录；不会自动清理卸载材料或旧安装备份。取消卸载不写入。

若提示“卸载未确认”，先核对原安装位置与提示的保留位置，不要重复操作。需要恢复时先停止仍在使用这些文件的进程、备份保留材料，并确认原安装位置不存在；原位置已被重新安装时不要覆盖，应保留两份内容并另选位置核对。只有确认保留内容已不需要、且没有进程继续使用旧树后，才手工清理隔离目录。已有会话的技能缓存不因本地卸载立即撤销，新会话按当前安装位置读取。

“Codex 新会话与用户偏好”先显示设置分类，进入具体项目后再读取当前值与可用选项；分类页返回或取消无需等待 App Server。“配置默认值与用户偏好”统一收集模型、加速档位、权限、Plan 思考等级、推理摘要、输出详细程度、更新检查与历史记录，最后一次确认并批量写入；中途取消不保存。可修改项以进入后读取的 Provider 和 Permission Profile 为准；使用 Permission Profile 时保留现有权限，其余偏好仍可设置。保存校验配置修订及对应策略。
CLI 和 WebUI 的等值保存按 Codex 用户层配置判断，没有实际改动时不写入、不提示重启或新会话生效。未配置与显式写入默认值不同；恢复继承仅删除用户层覆盖。合并配置或组织策略的校验不会因为用户层值相同而跳过。
默认模型向导在保存回读未确认或受到高优先级覆盖时保留对应提示，不追加“未写入”或新的生效结论；先重新读取核对，不重复提交。

“普通用户偏好”可单独选择 Plan 思考等级、推理摘要、输出详细程度、启动更新检查或历史保存；预览只包含所选字段，确认后保存，其他字段保持原值。选择继承会清除该字段的用户覆盖。第三方提供商也可修改普通偏好；设置具体 Plan 思考等级仍需 OpenAI 模型资格，无法设置时仍可清除已有覆盖。此单项入口与 WebUI 的“全局设置 → 行为与偏好”共用校验与保存合同。

WebUI 的 Codex 用户主配置集中在“设置 → 全局设置”，按模型默认值、上下文与压缩、行为与偏好、权限与审批、工具策略分组，通过“操作”打开表单。模型管理及提供商页面保留各自配置和直达全局设置的入口。全局上下文及自动压缩不是某个模型的目录字段；压缩比例预设换算为明确 Token 阈值保存，不会随之后切换模型自动重算。Gateway 配置和各账户覆盖继续独立管理。保存回读未确认时先重新读取核对；出现高优先级覆盖提示时，不能据此认定有效配置或已有会话已改变。详细入口和范围见 [WebUI](webui.md)。

显式配置的相对路径（如 `./bin/codex`）相对所选 Gateway 配置文件所在目录解析，不随安装终端或服务工作目录变化；裸程序名仍按 PATH 查找。`CODEX_BINARY` 是独立环境覆盖，其相对路径沿用调用进程工作目录，不套用配置目录规则。此前依赖工作目录的显式相对配置需调整为配置目录下的路径或绝对路径，不自动回退到旧位置。

`codexc setup` 要求标准输入与提示输出均连接终端；不满足时在初始化用户目录前报错。`setup --jsonl` 仍需交互输入及终端 stderr，stdout 输出脱敏 JSON Lines，适合将操作结果重定向到文件，不是无人值守配置接口。

权限设置的保存范围跟随入口：`codexc config → Codex 新会话与用户偏好 → 沙盒、审批与网络` 会逐项询问并确认完整组合；WebUI 的三个独立控件只保存各自修改项，其他未配置权限继续继承默认值。两端共用修订检查与写入规则，启用 Permission Profile 时不能从这些控件改写传统 Sandbox 设置。

命令只接受当前入口：Provider 管理集中为 `codexc provider`，受管账户使用 `provider deepseek`、`provider opencode-go`、`provider ccg`、`provider ollama-cloud`；各家的可用操作以子命令帮助为准。OpenCode Go 的 `release` 只释放实例，后续请求可重新拉起，不禁用账户。会话归档、转储删除与指标维护集中为 `cleanup sessions`、`cleanup traffic`、`cleanup metrics`（含 `prune`、`reset`）。旧独立 Provider 命令、`sessions`、原领域下的清理命令、`setup --json` 和 `config --json` 均被移除，没有兼容别名。脚本读取配置路径使用 `config paths --json`；诊断使用 `doctor --json`。

Setup 仅按具体操作返回的激活范围提示重启。列出账户、停止账户等操作不会因经过模型菜单而附加“重启全部服务”；需要重启的配置修改会返回对应服务目标，Setup 不自动执行重启。

Ollama Cloud 已接入受管多账户，使用范围见 [Ollama Cloud](ollama-cloud.md)。`codexc provider ollama-cloud setup` 或 Setup 第三方提供商菜单可添加、重配、设置默认和移除本地账户；也支持 `add <id>`、`reconfigure <id>`、`default <id>`、`remove <id>` 与 `list [--json]`，各入口支持 `-h` / `--help`。WebUI 提供同一账户事务。账户使用 `olc-<id>`、独立 Key、独立默认模型，所有 OLC 账户共用目录。首次添加选择模式、Key，并从公开远端元数据生成的候选中选择一个默认模型；确认后只生成所选模型，无需手填能力或发起推理验证。已有目录只复用，新增账户从中选择默认模型，编辑账户保留当前默认模型；目录修改走统一模型管理。新模型启用 freeform 与客户端 `tool_search` 适配，不声明上游原生 `web_search` 能力；托管 live 搜索须在联网搜索设置中单独启用。公开元数据及目录定义不代表真实云端能力已验收。

新增或更换 Key 的预览及保存会固定读取 `https://ollama.com/api/balance` 验证认证，不发送推理请求；旧计划缺少 USD 金额不等同于认证失败。无变化操作不请求网络、不写入、不要求重启。保存绑定预览修订，固定模式明确确认主配置字段修改，并复用版本化写入、私有凭据和备份；结果不确定时保留现场，不自动重试。仍有其他账户时，移除默认账户前须先选择其他默认账户；最后一个账户允许直接确认移除。移除只停止对应实例并提示该账户历史会话不可用，保留共享目录、私有备份和凭据历史，不迁移或修改已有 `cp-ollama`。

后续在 CLI/Setup 或 WebUI 模型管理选择“添加受管模型”，从公开 `/api/tags` 与 `/v1/models` 精确 ID 交集读取候选，再由 `/api/show` 自动取得窗口、思考和图片能力；预览后只追加所选缺失模型，不发送推理请求，不覆盖已有 ID、能力或默认选择。模型 ID 原样保留 `:tag`，不提供 OLC 按 ID 手填或继承新增，后端同样拒绝这两类输入。

`codexc provider ollama-cloud discover [--json] [--refresh]` 读取公开模型元数据候选，默认复用一小时持久缓存，`--refresh` 或 WebUI“强制刷新”才立即查询远端（缓存不含 Key，详见 [OLC 缓存](ollama-cloud.md#共享模型远端选择与可选验证)），不使用 Key、不创建账户、不写入或启用模型。缺失思考元数据、能力冲突、缺少 completion/tools 或来源变化会明确标为待确认或排除，已有 ID 不覆盖。思考元数据的 `false` 映射为 `none`；只有布尔选项时，`true` 使用兼容值 `high` 表示开启，不代表强度。布尔 `false` 与命名等级混合时保留关闭和精确等级。图片只在来源声明 `vision` 时启用，窗口受最高 393216 的本地策略上限约束，原图、摘要、详细程度及 WebSocket 关闭。

高级「发现并验证新模型」是可选收费诊断，普通添加无需先通过它。只有选择具体验证账户、精确模型及包含来源默认值的思考等级，并明确确认可能收费后，才逐级发送 Responses 验证请求：每级 2 次 SSE，来源默认等级另加 2 次 JSON，共最多 16 次，每次最多 768 输出 Token、128 KiB 响应，总期限 90 秒含前后公开来源复核，不重试。取消不能撤销已发出的请求或费用。各级须取得完整普通函数调用及配对模拟结果后的文本续答；SSE 还要求实际工具完成项、文本增量与终态一致，只有 JSON 快照不能证明原生流式可用。不执行文件或命令，不以 HTTP 200 或参数回显判定通过，也不证明上游真实思考质量。通过后仍须预览并确认，才由现有共享目录事务追加该模型；目录、账户材料或底座变化会拒绝旧结果。生成能力沿用普通添加的元数据及适配策略，诊断不证明图片、freeform、客户端工具搜索或长上下文已通过。普通添加不生成 `modelDiscovery`；高级诊断成功保存时才记录有界来源与验证范围，不保存 Key、对话或模拟 marker；不自动重启。

App Server Provider Proxy 与独立 Relay 已接通请求级 freeform JSON/SSE 表示适配；原生 Codex 文件创建、修改及历史续跑只在隔离合成上游观察成功，真实云端文件编辑与客户端工具搜索尚未验收。已使用真实 `olc-main` 和 `deepseek-v4.1-flash` 观察共用托管网页搜索入口完成两次模型请求、一次搜索及最终续答，未观察运行中 Gateway 加载本次构建后的渠道交付。自动验证的本地产品流程已接通，真实云端逐模型结果仍需获授权后分别观察；目录保存不证明这些能力已验收。详见 [Ollama 接入进度](ollama-cloud-probe.md)。

新增第三方模型从 ID 自动填写显示名称时会去掉 `/` 分隔的提供商前缀；例如 `vendor/model-name` 默认填入 `model-name`。完整上游 ID 保留，手动填写及已有名称不变。
受管模型上下文窗口在 CLI 和 WebUI 均先读取目录修订，编辑后查看窗口差异与同一提供商的受影响账户，再确认保存；中途取消不写入，目录或账户已变化时须重新打开编辑。
CLP 手动添加的模型可在 CLI 模型管理选择「本地编辑已有模型」，直接修改已保存的名称、窗口、思考等级、能力或指令，无需下载同 ID 模板。模型 ID、请求格式和来源关联保留，差异确认后保存；另有「编辑请求改写」和 WebUI 模型操作中的同名入口，用于编辑模型级 `providerOptions` JSON 并预览差异，字段不设白名单。详见[日常模型管理](provider-integration-guide.md#日常模型管理)和 [CLP 请求改写](cline-pass.md#请求改写)。
原生网页搜索诊断从 `setup → 模型与提供商 → 检测原生网页搜索` 或 WebUI 模型行操作进入，覆盖官方及第三方提供商；明确选择一个账户和模型后主动发起，可能产生模型及搜索费用，仅诊断、不修改搜索策略，见[模型探测](provider-integration-guide.md#添加时探测并写入)。
CLI 按提供商修改搜索使用 `codexc config → 提供商联网搜索`，或 `codexc setup → 模型与提供商 → 提供商联网搜索`。选择账户与模式后预览并确认保存；支持跟随全局、关闭、缓存、索引和实时。OLC 搜索可能收费，未设置时默认关闭，切换账户不继承全局；CLI／WebUI 将缺项选项显示为“默认关闭”。需要 CLP 或 OLC 托管搜索时显式选择实时（live）；OLC 使用所选账户的搜索额度。已显式保存的模式保持不变；若实际请求声明缓存或索引模式，会在模型出站前拒绝整次请求。官方和固定提供商共用主配置，固定 OLC 主配置缺项时也默认关闭；菜单会提示对应修改路径。新默认在 App Server 下次启动后生效，不改变已加载会话；配置不可安全读取时拒绝写入。
内置搜索读取主配置及各提供商 config 顶层的 `web_search`；有独立 config 的第三方账户可在 WebUI「模型管理 → 提供商」预览并确认搜索设置，OLC 缺项默认关闭，其他账户缺项跟随全局。使用主 `config.toml` 的固定提供商在“设置 → 全局设置 → 行为与偏好”中修改，见[独立提供商的搜索模式](provider-integration-guide.md#独立提供商的搜索模式)。模型搜索能力元数据不参与请求过滤；搜索是否执行仍取决于上游接口和模型。受管 CLP 的独立搜索适配需选择 `live`，不支持 cached/indexed，详见 [CLP 网页搜索适配](cline-pass.md#网页搜索适配)。搜索诊断仍检查上游原生工具，不检测该适配线路，也不自动修改配置。
自定义目录、CCG、OCG、CLP 及已注册的 OLC 支持预览后本地移除；账户范围、默认保护、Relay 影响和恢复方式见[日常模型管理](provider-integration-guide.md#日常模型管理)。OLC 支持公开元数据选模添加、可选单模型收费诊断、账户默认值及共享窗口／思考等级管理；只读发现命令本身不能启用模型。账户创建使用上述 CLI、Setup 或 WebUI 入口。
`codexc provider remove <精确 cp-ID>` 在配置已删除但备份、凭据、目录或元数据清理失败时保留删除结果并逐项告警，直接命令返回非零；Setup 和 WebUI 也显示清理告警。修复文件权限或类型后，可用同一精确 ID 重试残留清理，不回滚已提交删除；仅残留 `provider.json` 或归属凭据时仍可处理。备份清理失败会保留依赖的凭据、目录和元数据。
CLI 与 WebUI 模型管理均提供 DS、CLP、CCG、OCG 和自定义模型的[模板更新对比](provider-integration-guide.md#对比并更新账户模型模板)：明确来源，受管模型选择提示词或能力范围，自定义模型可更新提示词及来源，并独立选择“本地工具”以合并异步提问和时钟声明；两类模型均可另行选择有效上下文比例、压缩阈值和截断策略，查看差异并确认后更新目标模型；旧模型缺少来源关联时须手动选择。
已注册的 OLC 使用同一模板更新入口，可选择 `official` 固定底座或受管 DS 模板；所有来源都只允许更新提示词与运行设置，能力参数保留当前目录值。首次目录的 manifest 为 `source: "ollama-cloud"`、空 `modelTemplates`，保存后可显式建立模板关联；旧关联及验证来源仍可读，不迁移或补写。模板来源不能证明 Ollama 模型能力。上游原生 `web_search` 不属于目录支持能力；托管 live 网页搜索由请求声明触发，代理调用 Ollama 独立搜索 API 后携带结果续答。账户权限及真实云端往返仍需独立验收。

公共底座可在 WebUI「模型配置 → 公共底座」获取候选、查看字段前后值并确认更新；长提示词可展开全文。终端使用 `codexc model-base status` 查看当前来源，`codexc model-base update` 对比并交互确认，`codexc model-base update --preview --json` 仅输出完整对比。Setup 的「模型与提供商 → 公共底座更新」提供同一流程。保存位于 Gateway 数据目录，不改安装包或已有账户模型；候选来自当前运行环境的 `codex debug models`，可能读取缓存或联网，不保证远端最新。备份、生效与恢复边界见 [公共底座更新](deepseek.md#公共底座更新)。

`codexc timezone` 设置服务时区，WebUI 同步跟随；网关默认也跟随，可用 `codexc timezone --gateway` 选择系统或自定义时区，细节见[`服务时区`](model-timezone.md)。

Telegram、飞书和微信至少启用一个。Telegram 需要 Bot Token 和允许用户；飞书需要应用凭据和允许的 `open_id`；微信需要扫码凭据、账号和允许用户，Setup 最终确认保存时会直接启用消息接收。

Telegram Bot Token 和飞书 App Secret 使用隐藏输入，不在确认结果中回显。初始化向导仅检查官方凭据文件是否存在，不据此判定登录有效。

通讯渠道接入统一使用方向键选择、回车确认，输入问题中按 Esc/Ctrl+C 取消且不保存配置。Telegram、飞书和微信均在保存前确认；原有风险确认仍保留。发起渠道请求前及最终保存前检查配置版本和结构，不支持的配置会被拒绝，不会自动修正或迁移。

`codexc setup → 通讯渠道 → 启用／停用渠道` 可独立切换已配置的 Telegram、飞书、微信和 QQ，停用保留凭据和授权名单，不用重新扫码。列表显示配置开关，不代表平台连接健康；启用时仍校验必要配置。保存需要重建 Gateway 连接，后台服务自动读取后重启、前台需重新启动，尚未运行时下次启动生效，App Server 不受此开关控制。Gateway 至少需要一个启用渠道，停止全部收发请使用 `codexc stop gateway`，恢复使用 `codexc start gateway`。

Telegram 支持可选 `[telegram].enabled`：`false` 停用，未设置时按非空 Token 判断，`true` 要求有效配置；重新完成 Telegram 接入会启用。直接恢复开关后可能处理平台保留的积压消息，不自动删除远端消息。该开关入口目前在 Setup；Config 总览、WebUI 状态和 Doctor 共用其启用语义，WebUI 暂不提供开关写入。更新源码前请保留配置备份；旧版本不识别 Telegram 的新字段，回退旧版本须在停止 Gateway 后恢复对应备份，不覆盖其后的配置修改。

飞书和微信二维码使用紧凑半块字符及 L 级纠错；终端过窄或渲染失败时取消本次扫码并返回向导，按提示加宽终端后重新接入。Telegram 使用长轮询接收消息，已有 Bot 若设置了 Webhook，须先解除原有 Webhook 再接入，向导不会自动删除。飞书手动配置仅在 App ID 相同时允许保留原用户名单；更换应用必须填写新应用对应的 Open ID。

手动输入多个用户 ID 时使用英文逗号分隔。飞书拒绝单个 Open ID 内的空白、逗号或分号（包括中文标点），不会将误用分隔符的整串内容保存为用户；配置文件中的名单也执行相同校验。Telegram 在预览前将用户 ID 转为规范数字字符串并去重，例如 `00123,123` 只保留用户 `123`，确认后按数字保存。

### 审批方式：手动审批与自动审查（Auto-review）

Codex 默认审批方式入口为 `codexc config → Codex 新会话与用户偏好 → Codex 默认审批方式`，或 WebUI
`设置 → 全局设置 → 权限与审批`。选择自动审查保存 Codex 用户层 `approvals_reviewer = "auto_review"`，选择手动审批保存
`approvals_reviewer = "user"`。保存前须明确确认；WebUI 还要求预览产生的一次性确认令牌，并检查
当前用户配置修订。此操作只修改默认审批方式，沙盒、审批策略和网络权限继续独立设置。

Auto-review 由 Codex 审核需要审批的操作，并按其政策批准或拒绝；它不会把每项请求自动批准。
Gateway 不再按 Provider 或模型白名单限制自动审查；已配置的独立第三方 Provider 均可选择。
审查请求继续由 Codex 原生机制处理，审查失败不会自动放行。开放本地选项不代表所有远端模型
都已验证兼容，实际执行仍取决于上游接口与模型能力。
页面显示的是全局用户偏好，未设置时保留继承状态；上游无覆盖时默认由用户审批。新建 Thread
由 App Server 合并配置，Profile、项目配置、显式参数和组织策略可能覆盖该偏好。
已经加载的 Thread 及恢复的历史会话保留自身审批方式，不随默认值切换；受管 Provider 独立实例
仍以各自有效配置为准。无需为了此偏好重启 Gateway。

Codex 原生审批方式不依赖 Gateway 的 Provider 或模型资格白名单。
新建、未加载恢复和分叉按已有权限继承规则传递审批方式，不因模型变化自动切回手动审批。
已加载会话保留实际审批方式、订阅及活动任务状态。Gateway 不因第三方身份拦截新执行。

已有值不属于 `user` 或 `auto_review`、组织要求限制任一审批方式、组织禁用 Auto-review 或
策略读取不可用时，审批方式选择只读并拒绝写入，不把旧名 `guardian_subagent` 当作可编辑别名。
附加审批策略读取失败、超时或返回无效数据时，仅 Codex 默认审批方式只读，其他 Codex 用户设置仍可读取和修改。
飞书、Telegram 和微信会显示自动审查的开始及通过、拒绝、超时或中止状态。完成卡另列本轮任务和
当前会话的自动审查次数及结果分类，递归包含已确认归属的子代理；断线或历史缺失时明确显示已记录、
至少或未知。状态通知和计数只报告 App Server 的审查结果，具体口径见[渠道展示](display.md#完成汇报)。

飞书、QQ、Telegram 和微信可用 `/autoreview` 查询当前已绑定会话的实际审批方式，
用 `/autoreview on` 开启当前会话自动审查，或 `/autoreview off` 切回手动审批；
设置用于当前会话后续轮次；切换时须无运行任务或待处理交互。未绑定会话时只提示创建或恢复会话，
不会为配置操作创建 Thread。无法识别实际审批方式或旧值 `guardian_subagent` 时只读。
飞书命令中心的当前状态面板、当前会话审批方式面板和 Telegram `/autoreview` 查询结果提供当前会话按钮；按钮绑定原 Thread、Conversation 和用户，
五分钟内有效且只能提交一次，切换会话后须重新查询。只有 App Server 权威设置确认后才报告已切换；
未确认时不会自动重试，应重新用 `/autoreview` 核对实际状态。

Workspace 只保存目录身份，不另存沙箱、审批策略、Permission Profile 或审批方式。
已选择的 Workspace 被移除后，渠道输入会明确拒绝，不自动切换到默认目录；使用 `/workspace` 查看列表，
再用 `/workspace <序号、ID 或名称>` 显式选择当前注册的工作区。
空闲自动释放只解除 Thread 绑定和订阅，仍保留工作区选择；释放后再移除该注册也需要显式重选。
错误提示会给出 `/workspace` 恢复入口，列表标明失效的原选择；飞书发送 `/workspace` 或 `/work` 返回完整文本列表，点击命令中心的工作区入口则打开选择卡片。
飞书与 Telegram 的工作区按钮按精确 ID 选择，纯数字 ID 不会被当成列表序号；手输命令仍按序号、ID 或名称解析。
飞书工作区卡片每页最多显示 15 项，可通过“上一页／下一页”浏览完整目录，列表编号跨页连续；发送 `/workspace` 或 `/work` 仍可查看完整文本列表，并按序号、ID 或名称选择工作区。
本机新增工作区生效后，飞书通知为能确认唯一已授权操作者的会话提供“切换到”按钮，点击后才切换；无法确认唯一操作者时保留文字通知和切换命令。
通知按钮沿用命令中心的短期一次性令牌，重启或过期后请发送 `/work` 查看列表；新增通知不会改变 `/work` 的文本展示。
切换后重新发送之前的请求，不自动重放失败操作。删除已有注册会使 Gateway 按现有监管方式重启，启动恢复清除该工作区的失效绑定；
前台手动运行的 Gateway 退出后需手动重新启动。此过程不删除磁盘目录或 App Server Thread 历史，也不终止共享 App Server。
渠道新会话由目标 App Server 按授权目录加载原生配置；恢复、重连和分叉遵循原生 Thread 权限继承规则，
不会强制重置为当前项目默认。当前会话实际审批方式仍由 `/status`、`/autoreview` 及生命周期卡片展示。
`/status` 不展示指令文件及运行目录清单；底层仍保留 App Server 最近一次新建、恢复或派生时返回的加载快照用于校验。执行目录未知或与工作区不同时才提示，不用登记目录代替未知上下文。开始、上线和完成通知中的工作区及 Git 分支仍指登记 Workspace；此诊断不开放子目录会话互通。
普通输入（包括活动 Turn 的追加输入）在提交前通过 App Server 核对 Thread
仍处于登记 Workspace 的精确目录；等待期间目录或订阅发生变化时拒绝旧操作，需重新核对后操作。
原生端把目录改到其他位置后，渠道不会替用户改回目录、清空 Queue 或重放输入。可在原生端恢复目录，
或通过 `/workspace` 选择对应的已登记工作区后重新选择会话；`/status` 和中断入口仍可使用。
Gateway 不启动原生 Queue；原生客户端的队列调度由 App Server 管理。
这些检查不能提供与其他原生客户端之间的原子提交保证。
空闲普通输入和重连仍沿用既有恢复策略：确认目录不兼容时解除失效绑定并拒绝本次操作；
活动输入的提交校验本身不解除绑定，避免丢失当前任务的中断入口。
本机 CLI 与 WebUI 的 Codex 权限设置修改原生用户层配置；项目级差异使用受信任的 `.codex/config.toml`。
用户层偏好不代表所有 Provider、项目或既有 Thread 的实际权限。渠道不再提供 `/workspaceperm`。

升级前备份 Gateway `config.toml`。先在副本准备配置，待停止旧 Gateway 和会修改配置的 WebUI 后，
再将清理后的配置用于新版；不要让旧 Gateway 热加载清理后的文件，否则旧默认值可能改变执行权限。
显式删除 `[codex].sandbox` 和各 `[[workspaces]]` 的
`sandbox`、`approval_policy`、`approvals_reviewer`、`permissions`。全局 sandbox 可能由旧默认补全写入，
未手动设置也应检查。需要保留的项目差异应先在原生 Codex 配置中明确设置，不会自动搬到全局配置。
旧字段会使严格配置校验失败，原文件保留不改写；清理前不能依赖新版配置菜单自行修复。
失败时保持 Gateway 停止，修正新版配置后再启动；回退需先恢复旧程序及对应配置备份，
再启动旧 Gateway。App Server 独立运行，不因这项清理而停止。现有 Thread 和计划任务数据库不随此次配置清理迁移或删除。

### 计划相关设置

在 `codexc config → Codex 新会话与用户偏好 → 计划清单工具` 中控制上游 `update_plan` 工具，默认关闭：

```toml
[tools.update_plan]
enabled = true
```

三个设置不要混淆：

| 设置 | 作用 |
| --- | --- |
| `tools.update_plan.enabled` | 模型是否拥有创建/更新待办清单的工具，默认关闭 |
| `display.plan_updates` | Telegram 与飞书是否把 `turn/plan/updated` 通知展示到渠道，默认开启 |
| `/plan` | 是否使用官方 Plan 协作模式 |

上游计划工具关闭时不会产生普通计划清单通知；`display.plan_updates` 不能替代它。修改后由新建或重新加载的 Codex Thread 读取；当前已加载的 Thread 保持不变，无需重启服务。

### 子代理规则与配置（可选）

入口为 `codexc config → Codex 新会话与用户偏好 → 子代理规则与配置（可选）`，仅对 OpenAI 主配置开放。
安装、更新和“配置默认值与用户偏好”不会自动应用这套预设；仅在主动选择并确认后写入。
可选择只写全局规则、只写 Codex 主配置，或同时写入。确认前显示实际路径和待写内容，
路径遵循 `CODEX_HOME`，通常为 `~/.codex/AGENTS.md` 和 `~/.codex/config.toml`。

规则只约束协作，不扩大用户授权，也不改变全局规则、项目规则、环境权限和完成要求。
主代理负责需求、最新纠正、授权边界、关键决策、整合及最终交付；未使用子代理时仍完成同样的必要工作。
通常只派发具有独立交付物、可与主代理工作并行或需要独立视角的任务；顺手能完成的简单操作直接处理。
不要求用满容量，不设置固定模型流水线或额外审查轮次。

| 子代理模型 | 思考等级 | 分工 |
| --- | --- | --- |
| `gpt-6.1-sol` | `high` | 默认主力：代码理解、日常审查、实现、重构、执行和故障诊断 |
| `gpt-6-luna` | `max` | 范围明确、低风险、易核对的定位、检索、摘录和清单整理 |
| `gpt-6-astra` | `high` | 明确的复杂取舍、未解决关键疑点或高影响问题的独立审查 |

实质代码修改、跨模块语义、授权、并发和数据一致性判断交给 Sol。
主代理已使用 Astra 时，复杂判断优先自行处理，仅为明确有价值的独立视角或并行工作额外派发 Astra。
文件多、代码长或普通检查失败，不单独构成升级理由；Luna 使用 `max` 是分工策略，不代表已经证明成本最低。

每次使用 `fork_turns="none"`，简报包含用户目标、最新纠正、允许与禁止的操作、工作目录、范围及非目标、
文件与任务归属、必要输入、已有证据、依赖和交付要求，并携带适用指令的必要原文。
父对话中的用户消息不会因此自动传递，不能把全局规则和权限继承理解为用户聊天指令也已交接。
明确告知子代理：`Do not spawn, invoke, or request any new subagents.`。
审查按模块或风险边界拆分，实现按文件所有权拆分；同一文件同一时间只有一个写入者，保留已有改动。
共同接口先约定再并行，不把主代理或其他代理的推断当成已确认事实。

每个子代理从初次派发到交付或终止只执行一轮，任何阶段均不调用 `followup_task`；交付或终止后不复用、不追加任务。
该轮负责范围内调查、执行、修正、自审和异步结果回收；只读任务不得修改，缺失授权或超出范围时报告阻塞。
运行中的同一任务允许澄清、纠正和收缩范围，但不能追加独立交付物或激活已结束代理；
原任务实质改变时由主代理决定停止并重新派发。
用户取消或授权变化影响在途任务时，应停止受影响的后续操作并重新确认范围、归属及证据有效性。
后续工作由主代理处理或新代理接手；交接前停止本任务拥有的冲突操作，不能终止用户或其他任务的服务与作业。
返回异步句柄不等于完成；未完成交接必须说明状态、剩余操作及资源归属，由主代理接管回收。
优先完成通知和现有句柄，不因等待时间长重复执行、重启作业或派发相同任务。

子代理报告具体结论、位置、事实依据、实际改动、观察结果和限制，注明证据对应的产物状态及关键输入。
审查发现给出触发条件、影响和建议；无发现也说明覆盖范围。
主代理读完整报告，核对当前产物、授权边界、关键判断和跨模块影响，按证据定位做针对性复核，
不默认逐文件重读、重复完整调查或重跑仍有效的验证；证据不足、矛盾、输入变化或集成及高影响疑点出现时再扩大。
明确要求的完整或独立审查及项目验证仍须执行，不能用节省成本缩减范围。
独立审查可以复用可核验的输入和实际观察，但必须自行形成判断；发现复核不能冒充完整独立审查。
最终声明区分团队覆盖与主代理亲自重审，说明未覆盖范围及推断，不把子代理自报完成直接当成交付。
实现、规则文档和只读分析分别遵守当前全局与项目的证据要求，子代理无需各自重复完整用户路径。

模型选择遵守当前工具契约与有效配置：有限展示名单缺少目标不单独证明不可用，明确限定值必须遵守。
区分目标或思考等级不支持、参数错误、临时故障和授权拒绝；精确组合不支持时不重复尝试，
临时故障按工具指导处理，授权拒绝不能通过换模型或路径绕过。
不把单模型失败扩展为所有模型不可用，也不盲目省略 `model` 与 `reasoning_effort` 回退，
因为默认值和角色配置可能改变实际模型、思考等级及成本。
无法确认合适目标时由主代理处理自身能力范围内的工作并说明限制，不自动改配置或改用 Astra 强行派发。
完整托管文本以脚本的规则模板为准；这些是行为指令，不是运行时强制的模型限制。

主配置预设为：

```toml
[features.multi_agent_v2]
enabled = true
default_wait_timeout_ms = 600000
```

预设不写或清除 `agents.default_subagent_model` 与 `agents.default_subagent_reasoning_effort`。
派发省略对应参数时，App Server 会使用这些默认值，随后还可能被角色配置覆盖；只有没有有效覆盖时才继承当前对话设置。
选择写配置时，预览会指出主配置用户层已有的这两个键，说明影响并保留原值；
即使旧值来自之前的预设，更新规则或再次保存本预设也不会自动移除它们。
如果希望继承当前对话设置，应人工检查实际生效的配置及所选角色，确认不再需要后移除相应覆盖，再开启新会话。
预览不检查其他配置层或角色配置，也不验证账户或 Provider 可用性。
“仅写规则”不读取主配置，并明确提示没有检查上述覆盖；省略参数仍不保证继承当前对话设置。
规则只更新专用托管段，保留其他内容；已有未托管的子代理章节需要先人工整理，避免叠加冲突。
两个文件不构成同一个原子事务，失败时按终端提示检查已写入部分。
入口不会自动重启服务；请在新的 Codex 会话中使用配置和规则。

### 会话自动命名

渠道中尚未命名的会话，收到本 Gateway 提交且由 App Server 确认完成的用户文字输入后，
会尝试生成标题。普通文字、运行中追加输入、明确的附件附文或转写，以及 Skill、Plugin、Agent、
Plan 任务和异步问题的用户答案可参与；纯媒体、系统附件说明、原生客户端输入、原生 Queue
派发和计划任务不触发，也不批量补写历史会话。

命名会使用原会话当前模型与 Provider，产生额外模型请求；不跨 Provider 回退，不更改主会话
模型或速度。标题在隔离临时 Thread 中生成，提示词和标题 JSON 不进入原对话；仅通过官方名称
接口保存。已有名称保持原样，本渠道手工 `/rename` 会取消尚未回写的自动结果。外部客户端若
恰在最后读取与写入之间改名，协议没有条件写保护，仍存在被覆盖的短暂竞态。

容量不足、没有可靠文字或未知权限上下文时跳过，不阻塞正常消息。同一连续绑定最多尝试两次；
失败后仅后续新输入可再次触发。超时导致身份未知或清理未确认时会暂停该 Provider 的新命名，普通输入继续。
日志 `thread_title.result` 给出结算结果，`thread_title.quarantined` 给出固定原因与已知临时
Thread/Turn 句柄；不记录候选或模型正文。单 Client 最多保留 2,000 个临时身份以隔离迟到通知，
达到上限后本 Client 跳过新命名，需在安全清理后重建 Gateway Client。

已知资源只有得到执行结束及订阅释放证据才解除隔离。重连握手成功后，对已经确认执行结束的
精确临时资源，在五秒总预算内补做退订；日志 `thread_title.recovery` 记录检查前后状态。
身份未知、缺少执行终态或退订仍失败时保持禁用，不重新调用模型。
需要恢复时，管理员应另选维护窗口，沿既有服务管理流程确认原 App Server 实例退出，再启动
所需服务并重启或重载 Gateway。共享 Server 的其他会话会受影响，不由自动命名自行停服。
保留原实例退出与新实例身份的操作证据；单纯 Gateway 重启、断线或读不到临时 Thread 不表示
模型请求已经结束。隔离记录不持久化，崩溃或重启后无法继续追踪未知在途任务。

飞书、Telegram、QQ 的改名提示遵守现有显示设置；微信不新增主动改名气泡，通过会话列表或
后续完成展示读取名称。当前功能已部署，隔离 App Server 与本地受控模型响应的生成、回写、列表
读取已观察，线上也已确认一次自动命名及用户收到名称更新通知；其他 Provider 兼容性、模型质量、
四个平台完整往返及三平台服务故障恢复仍待验收。

### 渠道会话空闲自动解除

在 `codexc config → Gateway 会话设置 → 会话空闲自动解除` 中设置渠道会话自动解除 Thread 绑定的全局
空闲阈值，默认 15 分钟：

```toml
[conversation]
idle_release_minutes = 15
```

飞书和 Telegram 的空闲自动解除通知提供“恢复此会话”按钮，点击后机器人先在聊天中发送
`/r <Session ID>`，消息发送确认后执行恢复，仍受当前工作区和会话恢复权限约束。命令消息发送失败、授权失效或发送期间工作区与会话状态变化时不执行恢复，可手动发送通知中的命令。按钮仅在能确定唯一授权接收者时显示，
限该用户使用一次，通知发送确认后 10 分钟或 Gateway 重启后失效；也可复制通知中的命令恢复。
直接发送普通消息仍会开始新对话。

QQ 单聊的空闲解除通知同样提供“恢复会话”按钮，并保留 `/r <Session ID>`。点击后机器人先在聊天中发送该命令，确认送达后恢复；发送失败或发送期间授权、会话状态失效时不执行恢复。按钮复用当前连接代次的一次性菜单选择，生成后 10 分钟过期；只接受原接收人，在当前工作区、目录和会话状态仍与通知一致时执行恢复。已经进入新会话、工作区不匹配、撤权或 Gateway 重启后不能继续使用该按钮；过期后仍可显式输入 `/r`，由正常恢复流程重新校验。此按钮只出现在更新后新发出的通知中，不补改历史消息。
QQ 通知正文使用 Markdown 标题及 Session ID 列表，恢复命令放在代码块中；完整 Markdown 无法安全发送时，回退完整文字和独立恢复按钮，不截断命令。

`idle_release_minutes` 对 Telegram、飞书、QQ 单聊和微信统一生效，允许 0–1440 分钟，0 表示关闭。用户消息、平台本地命令、
审批与输入交互和任何带目标会话的输出都会刷新活动时间；正在恢复的 Thread 不会被同时释放。
Provider 断线期间也会跳过对应 Thread；断线只取消该 Provider 的候选，其他 Provider 的扫描与补偿继续执行。
扫描保留 Thread 与活动时间快照，在取得会话锁及每次权威读取后复核；新输入、配置禁用、断线、
恢复或关闭会取消旧轮次。取消订阅后若出现新活动且连接仍可用，会恢复同一 Thread 的订阅；
恢复失败交给既有有界恢复任务，保留绑定且不发送解除成功提示。
连续达到配置的空闲时间且没有任何输入和输出时，Gateway 才会在确认 Thread、原生 Queue、审批和子代理都已
空闲后取消订阅并解除前台绑定；如果此时 Gateway 已没有任何前台或后台绑定、进行中的 Provider 操作或
启动任务，还会关闭全部 Provider Client，并在每 60 秒一次的空闲复检中停止全部未被租约占用的
App Server 进程（包括主实例），后续请求会自动启动并重连；`codexc remote` 持有租约期间对应实例
不会被停止。解除后
当前渠道会收到一次“自动解除占用”提示；若 60 秒内没有新消息、`/r` 恢复或新的 Provider 操作，
Gateway 会在关闭 Client 和停止 App Server 前向所有已知授权渠道发送一次
“所有模型连接已空闲，空闲的 App Server 即将停止”的通知。
该通知只属于渠道空闲自动解除后的全局释放轮次；手动 `/new`、切换 Workspace 或 Provider、
后台任务结束等原因导致没有绑定并关闭 Client 时，不发送这条通知。
`idle_release_minutes = 0` 只关闭渠道会话自动解除；无任何绑定时的全局空闲停止仍会执行，其他
非自动解除触发的全局空闲轮次只记录日志，不发送渠道通知。共享 App Server 的原生 TUI 必须通过
`codexc remote` 启动；直接运行 `codex --remote unix://<socket>` 不持有生命周期租约，可能被停止。
WebUI 打开或刷新 Codex 设置、提供商设置和提供商摘要时，会通过监管器按需唤醒主实例，并在读取期间
持有短租约；读取和连接清理完成后释放，不因页面持续打开而阻止空闲释放。管理读取总预算为 20 秒，
启动仍未完成时可稍后刷新；监管服务本身未运行、协议不兼容或私有端点权限异常时，仍需检查服务状态。
本地模型目录在权威管理快照不可用时保留只读展示；快照恢复且目录修订一致后恢复编辑，不使用旧缓存授权写入。
指标、服务状态、全局配置轮询和 UA 探测不会为了展示主动唤醒 App Server。
空闲解除时按渠道会话保存 Provider、模型、思考等级和服务层级；Gateway 重启后直接发送消息仍沿用
这份偏好新建会话。断开后通过 `/model`、思考等级或 `/fast` 速度入口调整设置，会更新保存值。
恢复时若 Provider、模型或设置已不可用，会要求重新选择，不自动换账户或模型。
已有绑定仍以 App Server 的 Thread 设置为准；显式恢复同 Provider 历史会话继续沿用渠道偏好，
跨 Provider 恢复尊重目标 Thread，原生 Queue 存在时清除待生效覆盖。撤权、归档和跨渠道接管
等清理操作不会让旧偏好在重启后重新生效。状态库仅接受当前 Schema v6。
此后直接发送消息只会开启新会话，不会接续旧 Thread；需要继续旧会话时直接使用提示中的
`/r <Thread ID>` 命令显式恢复；飞书显示为 CardKit 2.0 卡片，Telegram 为 HTML 面板，微信为
结构化文本。修改后需要重启 Gateway。

### 代理与权限

共享代理统一保存在当前 Codex Home 的 `.env`，默认 `~/.codex/.env`。执行
`codexc config → 网络代理`，或在 WebUI「设置 → 网络与访问」修改；批量输入留空保持原值，取消不写入。
CLI 单项和批量代理设置均可选择 `127.0.0.1:7890`、`127.0.0.1:7897` 或自定义完整 URL；两个本地选项使用 HTTP 协议。
例如：

```dotenv
HTTP_PROXY="http://127.0.0.1:7897"
HTTPS_PROXY="http://127.0.0.1:7897"
ALL_PROXY="socks5://127.0.0.1:7897"
NO_PROXY="localhost,127.0.0.1"
```

Codex、Gateway 渠道和模型统计代理共用该文件；修改后在任务结束时执行
`codexc restart all`，独立 Codex 进程也需重新启动。Gateway 只读取四个代理变量，
不把文件中的其他变量注入自身环境。代理值使用字面值，美元符号使用单引号包围或反斜杠转义，
不支持代理值中的变量插值。原有注释、其他设置和未修改字段会保留。
`ALL_PROXY` 可保存 SOCKS5 地址，但必须同时在此文件配置 HTTP(S) 协议的 `HTTP_PROXY`，
供 Gateway 的 HTTP(S) 客户端使用；缺少时读取或保存都会明确报错。

`.env` 字段优先于继承的标准代理环境变量；同名大小写同时存在时大写优先。已有任一代理地址时，
不补读系统代理；仅有 `NO_PROXY` 时仍允许自动发现。Windows 不读取 WinINET/WinHTTP。
不支持旧 TOML `[network]`，更新器不会迁移或修改代理配置。

Workspace 只能从已登记项目中选择，不接受聊天用户提交的任意绝对路径；沙箱与审批由 App Server 原生配置及 Thread 状态决定。默认审批方式与当前会话实际设置的区别见[审批方式](#审批方式手动审批与自动审查auto-review)。

## 4. Workspace、Provider 与终端

登记项目：

```bash
cd /absolute/path/to/project

```

新增 Workspace 生效后的渠道通知会逐项以独立代码块提供数字切换命令，例如 `/work 2`，数字与当前完整 Workspace 列表中的序号一致；
发送该命令即可直接切换，Telegram 通知还提供切换按钮。发送 `/work` 可查看全部 Workspace。

`work` 写入前检查当前配置版本和结构，失效目录仍可用 `work add --prune-missing` 显式清理注册。交互移除绑定展示时的配置；等待确认期间配置发生变化时拒绝移除，需重新选择，避免同 ID 已改绑到另一目录。配置保存后若配置锁、通知队列锁或旧通知清理失败，会分别提示已保存的结果与处理路径；先运行 `codexc work list` 核对，不要重复添加或移除。新增配置已经保存时保留待通知事件；Gateway 只在通知完成后确认对应事件，部分投递失败可能导致重复通知。

Gateway 配置和通知队列使用带进程身份和唯一标记的私有目录锁，活进程持锁不会仅因超过 30 秒而被抢占。旧文件锁、无所有者或格式不明的锁不会自动清除；遇到此类阻塞，先确认所有配置和队列使用者已停止并备份配置、队列及锁材料，再检查遗留锁。不要在 Gateway 或 `work` 操作期间直接删除锁，也不要通过删除配置或队列恢复操作。切换到使用不同锁格式的版本前同样要停止使用者并核对锁，不得让新旧实现同时写入。

管理模型 Provider：

```bash

codexc provider list [--json]
codexc provider switch <Provider ID> [模型] [--yes]
```

CLP 的 CLI／WebUI 固定模型候选和模板更新读取仓库 DS 模板，不下载 Cline 官方模型目录。候选仅在当前进程保留 10 分钟，预览和确认复用该快照；失败、过期或目标目录修订变化后重新读取。其他模型按准确 ID 独立填写能力，或继承同一目录中已保存模型的快照；自定义提供商使用同一添加流程。操作及保存步骤见 [CLP 使用说明](cline-pass.md)。

`codexc provider switch` 会把主实例切换到目标 Provider，执行前会二次确认，并提示将改写
Codex 主配置的 `model_provider` / `model`；`switch` 与 `recover` 可用 `--yes` 显式跳过确认（适合脚本化调用）；交互式 Setup 菜单仍会确认。确认期间切换目标或影响范围发生变化时拒绝执行，需重新确认。

添加账户时，Setup 与 WebUI 已有的多账户配置入口均提供 `main`（主账户）、`work`（工作账户）、`other`（其他账户）和“自定义”；已占用的预设不再显示。名称仅作账户 ID，不决定默认账户或自动切换行为。

DeepSeek、OpenCode Go、自定义 Provider 和多账户说明分别见 [`DeepSeek 使用说明`](deepseek.md)、[`OpenCode Go 使用说明`](opencode-go.md)、[`Provider 接入指南`](provider-integration-guide.md) 和 [`OpenCode Go 多账户`](opencode-go-multi-account.md)。

例如 `codexc remote -p ds-main r <Session ID>`。参数值和 `--` 后的文字不展开别名。
普通新建未指定目录时，Remote 使用启动时的当前目录；`resume`／`fork` 未显式指定目录时，
不注入 `-C`，由原生 Remote 与 App Server 处理会话目录继承、列表筛选和新建回退。
因此恢复选择器的默认目录范围、`--last` 无匹配时的新建目录也遵循原生 Remote 语义，
不保证使用包装器的启动目录。显式 `--workspace <ID>` 或 `-C`／`--cd` 仍作为目录覆盖传入；
原生 `tui.resume_cwd="current"` 在 Remote 无显式目录时的限制也予以保留。
从登记目录的子目录普通新建时，Remote 保留子目录作为工作目录；渠道按登记根目录查询和恢复，
不能保证列出或接续这些子目录会话。
直接使用原生 `codex --remote` 不会读取 Gateway Workspace 注册表。

`codexc remote` 与 `codexc app` 的 `-p` / `--provider` 使用同一选择规则：接受已配置的完整
Provider ID（如 `ds-main`、`clp-main`、`ocg-main`、`ccg-main`、`olc-main`、`cp-llm`、`my-provider`），或注册表中精确登记的
规范 `sf-*` Profile 名称（如 `sf-ds-main`、`sf-cp-llm`、`sf-custom-my-provider`）。自定义提供商使用 `cp-` 前缀，支持独立选择 Responses 或 Chat Completions；对应配置文件为 `sf-cp-<名称>.config.toml`。推荐使用完整 Provider ID；
只匹配已登记的名称，不通过任意剥除 `sf-` 前缀推测目标。未配置、歧义或重复选择均明确拒绝。
两个入口默认都连接主实例，不根据 OpenAI 登录状态自动选择第三方，也不沿用上次选择；
Remote 显式指定受管 `--profile` 时仍连接对应实例。
渠道未绑定会话的默认选择仍按登录状态、可选 Provider 和账户注册表执行，详见
[Provider 默认选择](provider-integration-guide.md#6-用户配置的主-provider)。
Remote 的 `--profile` 继续支持原生个人 Profile 和已登记的规范受管 Profile，如
`codexc remote --profile sf-ds-main`；`-p` / `--provider` 与 `--profile` 互斥。
底层 `sf-*` Profile 文件名保持不变；`--` 后的参数原样传给原生 Codex，不参与 Gateway 选择。

直接运行 `codex` 会创建独立 TUI，不共享 Gateway Thread；需要共享会话时使用 `codexc remote`。跨 Provider 切换会创建目标 Provider 的新 Thread，不复制原 Provider 历史。
直接运行 `codex --remote unix://<socket>` 不持有生命周期租约，空闲释放可能停止对应实例；
共享 App Server 的 TUI 请统一使用 `codexc remote`。
`codexc remote` 不注入网关权限参数，原生配置、Profile 和显式参数由 Codex 处理。
受管及自定义切换 Provider（包括 CP）统一通过原生 `--profile` 加载对应配置，其中显式的搜索值覆盖主配置；App Server 仍由受管启动器从同一配置生成必要参数。
可用 `--workspace` 选择登记目录，或用一次 `-C DIR` / `--cd DIR` 指定目录；两者不能同时使用。原生 `resume` / `fork` 上的目录参数同样参与选择，重复目录参数被拒绝。不能透传 `--remote` 或 `--remote-auth-token-env` 替换受管连接；原生 `--` 之后的内容按字面参数保留。
Remote 不按 Provider 或模型限制自动审查，也不为审批资格固定模型或限制个人 Profile。
Remote 的 `resume` 和继承式 `fork` 由原生 TUI 保留历史模型及审批方式，Codex 0.164.0 不应用启动参数中的 reviewer 覆盖；
恢复后应核对实际模型与审批方式。

### Codex Desktop App 共享（macOS / Windows 预览）

同一台 Mac 或 Windows 电脑上的 ChatGPT Desktop App 默认连接主 OpenAI App Server，也可在启动时
选择切换模式下已配置的 Provider 隔离实例。macOS 使用
受管 stdio Proxy 连接现有私有 UDS；Windows 使用受认证的本机回环桥。启用前必须完全退出
ChatGPT App，并确保主 Provider 是 OpenAI、App Server 后台服务已经安装；Windows 还需要
PowerShell 7 和当前用户安装的 `OpenAI.Codex` 包：

```bash
codexc app
codexc app -p ds-main
```

首次运行会询问是否启用共享，并说明重启 App Server 可能中断现有连接与任务；默认拒绝。
确认后自动启用共享并启动 App，取消则不修改配置或服务。以后每次都使用同一命令启动，
不再询问或执行启用步骤；从 Dock 或开始菜单直接打开不会继承本次共享端点。
`-p` / `--provider` 接受上面的完整 Provider ID 或已登记的规范 `sf-*` Profile 名称；省略时连接主 OpenAI 实例，
不记住上次选择，也不修改用户配置。切换 App Server 实例前必须完全退出 Desktop，再执行对应命令。
一次桌面连接固定到一个实例。
本项目不转移会话历史。上游恢复历史可能沿用历史 Provider，
桌面缓存和模型覆盖仍待实机验证；应在目标实例新建会话，不能认为旧会话已转换 Provider。选择目标不重启整个服务；
macOS 需要附加工具 Host 时只短暂重启目标实例。旧服务缺少选择能力时会提示先重启服务。

聚合模式暂时关闭：单个聚合 App Server 无法为成员提供商分别应用网页搜索模式。
服务不再派生 `codexc-aggregate`，渠道 `/model` 和 CLI 菜单不再提供聚合目录；
Remote、Desktop 启动和 `app status` 明确拒绝 `agg`、`sf-agg` 与 `codexc-aggregate`。
请选择独立 Provider。已有聚合 Thread、绑定及派生目录保留；旧聚合绑定因 Provider 不可用而拒绝执行，
不会转到其他 Provider，也不迁移或删除历史。安装新代码后，正在运行的旧服务仍须由操作者按常规重启
App Server 和 Gateway 后加载关闭状态；更新代码本身不会停止现有客户端或任务。

需要诊断时使用 `codexc app status [--provider <Provider-ID>]`；非交互启用或指定 Windows 桥端口时，
使用 `codexc app enable [--port <端口>]`，再执行 `codexc app`。
首次启用确认会显示目标 Provider 与连接方式，并绑定当时的配置和运行目标；确认期间配置或目标变化会中止操作，需重新运行命令。配置已保存后的激活失败单独报告；恢复前再次核对，避免覆盖其他入口的新修改。
`--port` 仅适用于 Windows，接受 1 到 65535 的十进制整数；macOS 使用受管 stdio，拒绝端口参数。Linux 上的启用、禁用与启动会在读取配置前报告不支持，`app status` 仍可只读查询。
关闭功能前同样先完全退出 App，再执行：

```bash
codexc app disable
```

`status --json` 保持脱敏。Windows 只输出不带令牌的回环地址；macOS 的 `port`、`endpoint`、
`tokenReady` 和 `bridgeReady` 不参与连接并返回空值或 `false`，另以 `toolHostSupported` 报告当前
App Server 服务是否支持受管入口。`toolHostAttached` 只在查询目标对应的 Desktop 已交付当前工具 Pipe 且 Host
租约仍连接时为 `true`。`running` 指桌面 App 进程；`primaryInstanceState` 另报告主 App Server
实例的 `running`、`released` 或 `unknown` 状态；`provider` 和 `providerInstanceState` 报告查询目标，
`desktopAppProvider` 报告 macOS 当前 Host 租约所属实例。状态查询不会唤醒已释放的实例。
Windows 状态不建立桥连接；共享启用且令牌可读取时 `bridgeReady: null` 表示未探测，实际连接检查在启动时执行。
`compatible` 仅表示启动入口探测通过，`toolHostAttached` 不表示 `codex_app` MCP 已就绪。
内置工具仍按 Desktop 传入的工具开关启用，不根据模型 Provider 或登录状态推断工具可用性。
如果 Desktop 日志出现 `dynamic_app_tools_peer_rejected reason=untrusted-process-ancestry`，
表示工具 Pipe 拒绝了进程祖先链，重复启用共享不能修复。2026-10-08 在 `26.1002.52244` 的聚合共享路径
曾观察到这一故障；不据此推断其他版本组合的工具状态。2026-10-18 新实测确认 macOS
`26.1013.40934 / 20770` 配合 CLI `0.163.0` 的主 OpenAI 基础会话可用，但 `codex_app`
启动被同类祖先链校验拒绝；App Server 重启后确认人工退出重开能恢复，未证明自动恢复。
具体范围见 [Desktop 跨平台验收](codex-desktop-app-acceptance.md)；历史记录见
[Desktop 验收状态](codex-desktop-app-development.md#实现与验收状态)。
共享功能要求主 Provider 为 OpenAI，第三方通过切换模式的独立账户实例接入；不接入
Remote Control 或手机配对。Desktop 的连接环境属于未公开兼容入口，当前功能是
预览；构建不兼容时命令会拒绝启用。

主 OpenAI 实例的 macOS 路径已由操作者确认验收，Windows 尚未验收；新增 Provider 选择在两个平台均未实机验收。
版本记录与范围见
[Desktop 验收状态](codex-desktop-app-development.md#实现与验收状态)。
macOS 上使用 ChatGPT `26.908.70816` 的既有实机验收已经确认 Desktop 与渠道可以双向发现、继续同一
Thread。新的 macOS 受管入口会把 Desktop stdio 连接代理到同一
私有 UDS，并在首次附加当前工具 Pipe 时短暂重启目标 App Server 子进程，以 OpenAI 签名的 Desktop
Node 托管项目锁定的 Codex CLI；开发基线为 0.164.0，既有私有 Pipe 与签名链实机验收使用 0.154.0，
升级后仍需单独复核。Desktop 传入的内置插件启用值会受控应用到目标实例，
Host 租约存在时空闲释放不会停止目标实例。目标实例已空闲释放时，`codexc app` 会先获取临时租约，
按需恢复实例并保护启动预检，再通过 App Server 的官方 `thread/loaded/list` 和 `thread/read`
检查全部已加载的持久及临时 Thread；临时租约会在打开 Desktop 前释放。发现活动 Thread、
`codexc remote` 目标实例租约，或无法完成
只读状态检查时都会拒绝启动，不会进入子进程切换。隔离实测已经确认该进程链可启动 `codex_app`。
macOS 已有验收结论；由于连接环境属于未公开兼容入口，功能仍保留预览定位，后续构建变化需按实际影响复核。
Windows 先以临时 Provider 租约等待目标实例就绪，再检查桥并启动桌面，成功或失败后释放临时租约。
启动失败时会区分实例未就绪和桥连接失败，不自动重启服务。它只查询当前用户的正式安装包，并直接创建带单次环境的包内 Desktop 子进程，
不写当前用户或系统级持久环境；Windows 的会话双向互通及内置工具兼容均尚未实机验收，不能据此
视为正式平台支持。

### Computer Use 与浏览器排障

配置入口：`codexc config → 工具与 MCP → 电脑、浏览器与已有 MCP`，Codex 用户偏好中的“电脑、浏览器与 MCP”保留同一入口；也可使用 WebUI
「设置 → 全局设置 → 工具策略」。两者修改同一份 Codex 用户配置，使用版本检查；WebUI 写入前需要预览并确认。

当前支持默认应用访问、浏览器历史访问和默认站点策略，以及配置中已有的 macOS Bundle ID、Windows AUMID
和站点规则。普通 MCP 可修改启用状态、启动/调用超时、工具允许/禁用列表与审批策略；已有单工具覆盖还可修改
审批和输出 token 上限。插件 MCP 只开放这些策略覆盖，不修改插件清单里的启动命令、环境和超时。
Strata 的调用超时在 CLI、MCP 编辑菜单和 WebUI 通用工具设置中均须大于分析预算；无法确定实际目标、继承值或宿主参数时拒绝保存，已有不安全的合并时限需通过原生配置修复后重读，详见[视频分析 MCP](video-analysis-mcp.md)。新增 Strata 预设保存 `command = "strata-video-mcp"`、`args = []`，通过实际 MCP 宿主的 PATH 选择独立入口，不经过 `codexc`，不写死 Node 版本或脚本路径；通用 stdio 保留操作者输入的命令。已有配置不会自动改写。
MCP 管理结束时若临时连接关闭未确认，会显示独立告警并保留已保存结果；不要因此重复写入。同进程的后续配置操作先重试清理，仍失败时不创建替代连接。
新增 MCP 使用 `codexc config → 工具与 MCP → 新增 MCP`：支持本地 stdio、远程 Streamable HTTP、AnySearch 搜索和 Strata 视频预设。统一按“选择类型 → 填写必要信息 → 查看脱敏摘要 → 确认保存”执行；预设采用固定默认参数，仅询问服务必需信息，通用类型保留自定义配置。stdio 逐项输入命令、参数 JSON 数组、工作目录、环境变量和继承变量；HTTP 输入 URL、Bearer Token 环境变量名、固定 Header 和环境变量 Header。通用类型可设置启动/调用超时及启用状态，默认 10 秒、60 秒和启用；Strata 预设调用超时为 960 秒。预设 API Key 与密钥类 JSON 均隐藏输入，固定值写入 Codex 用户配置；环境变量引用需由实际启动 Codex 的宿主提供。保存前显示脱敏摘要及目标路径，确认后按配置修订写入；同名服务器拒绝覆盖，配置冲突不自动重试。此入口不安装 MCP 包、不执行命令探测、不自动重启服务，OAuth 登录仍使用 Codex 原生入口。Strata 预设详见[视频分析 MCP](video-analysis-mcp.md)。

所有新增类型（含 AnySearch 和 Strata 预设）在保存前统一选择工具调用审批：跟随其他来源或默认值（不写用户覆盖）、`auto`、`prompt`、`writes` 或 `approve`。选择写入 `mcp_servers.<名称>.default_tools_approval_mode`，摘要明确显示所选策略；未确认不保存。编辑 MCP 也提供“工具调用审批”，可修改或移除用户层覆盖，其他字段与已有单工具策略保持不变。单工具 `tools.<工具>.approval_mode` 优先于服务器默认值，其他权限限制仍然生效。

AnySearch 预设询问 API Key（隐藏输入，仅填密钥，不含 `Bearer ` 前缀）和工具调用审批，随后显示脱敏摘要并确认保存。名称固定为 `anysearch`，Streamable HTTP 地址为 `https://api.anysearch.com/mcp`，启动超时 10 秒、调用超时 60 秒，默认启用。密钥以 `http_headers.Authorization = "Bearer <API Key>"` 保存到 Codex 用户配置，不回显，无需设置 `ANYSEARCH_API_KEY` 环境变量；空值、空白和控制字符会被拒绝。

`codexc config → 工具与 MCP` 同时提供“编辑 MCP”和“删除 MCP”，只列出当前 Codex Home 用户配置中的条目，不修改插件清单或其他来源的配置。编辑先选 MCP，再选字段；支持启用状态、工具调用审批、超时，以及用户条目自身定义的 stdio 命令、参数、工作目录、环境变量，或 HTTP 地址、Key、Header 和环境变量引用。不重命名、不切换传输类型；未选字段及密钥保留。连接类新值隐藏输入，不回填旧值；审批策略通过选项选择并在摘要展示。JSON 字段明确按整组替换，可选字段可显式移除以恢复其他来源或默认值。HTTP 的“API Key”会设置 Bearer Authorization Header，并移除用户层冲突的 Authorization Header 和 Bearer 环境变量引用；Strata 已有 Key 可单独更新，不必重填整个环境变量对象。工具允许/禁用列表和单工具审批覆盖继续使用“电脑、浏览器与已有 MCP”。

设置新的 Bearer 环境变量引用，或在固定/环境变量 Header 中设置 Authorization 时，也会移除用户层其他冲突认证来源；确认前会说明。HTTP Header 名称不允许用不同大小写重复设置，通用 HTTP 添加也会拒绝并存的认证来源。其他来源的认证配置仍可能影响合并后的结果；认证写入后会检查合并配置，若仍有冲突则明确报告用户层已经写入但认证检查未通过，不自动回滚或重试。Header Helper 或企业认证模式须通过原生配置修改认证。

对启动参数明确指向当前安装的视频分析脚本的 MCP，修改环境变量或调用超时还会检查视频配置合同、现有目录及超时关系，并在确认前展示视频读取范围与渠道目录。保留显式声明的宿主 Key 继承方式，不读取当前 CLI 环境冒充 MCP 宿主；分析时限或目录依赖未知宿主变量时停止，需通过原生配置调整。调用超时必须显式大于分析总时限，不能移除后回落到过短的原生缺省值。

删除前显示目标名称、路径和影响，确认后仅移除用户配置条目，不卸载包、不删除附件目录；其他来源或插件中的同名 MCP 仍可能生效。添加、编辑、删除统一使用读取时的配置修订写入并回读确认，冲突或回读未确认时不会自动重试。保存前取消不写入；保存成功不代表 MCP 已连接或已有会话立即采用变化。

“电脑、浏览器与 MCP”策略页不发现插件清单里的服务器或创建应用/站点规则；未列出的高级字段仍在 Codex 原生配置中管理。

新增入口会拒绝用户层、合并配置及已配置插件策略中已知的同名服务器，但不会读取插件清单；尚未出现在这些配置中的插件服务器可能重名。确认时会提示使用独立名称，Codex 的同名用户配置优先于插件服务器。

“用户设置”与“App Server 合并配置”分别展示，未设置时不臆测上游默认值。合并结果来自用户配置管理连接，
不包含当前渠道 Thread 的项目/Profile 配置及历史权限，也不表示组织策略、工具审批或操作系统权限已经放行。
选择“移除用户设置”仅删除该字段；工具列表的 `[]` 是显式空列表，与删除字段不同。
审批模式 `auto` 按工具属性判断，`prompt` 每次询问，`writes` 对非只读工具询问，`approve` 免除此层工具审批；
应用/站点的 `allow` 不会取消其他审批。保存后在新会话中使用；已有 MCP 连接与桌面客户端不保证即时采用新配置。

`app status` 的 `toolHostAttached` 只描述上面的 Desktop 私有工具 Host，不能据此判断
独立 Computer Use 或浏览器插件是否可用。`/mcp health` 可以检查当前 Thread 的 MCP 连接，
但工具已注册、原生应用列表可读、浏览器扩展可发现，都不代表窗口或标签页操作已经成功。

探测时应分别读取原生窗口与浏览器标签页。原生返回 `cgWindowNotFound` 时检查桌面锁屏与目标窗口；
浏览器扩展可发现但读取标签页超时，应继续检查扩展连接，不能直接判为缺少授权。系统辅助功能、
屏幕录制授权和上游应用／网站授权分别管理；Gateway 的批准按钮只回应实际收到的 App Server
请求，不代替系统授权，不解锁桌面，也不自行维护另一套网站允许名单。

飞书 MCP 工具审批区分“拒绝”和“取消”；“本会话允许”“始终允许”只在上游提供相应范围时出现，
“允许一次”不会升级为持久授权。Computer Use 操作说明与过程显示见[渠道展示](display.md)。
命令和 MCP 工具审批必须能完整核对才会投递到渠道：命令详情或 MCP 整体预览超过 3000 UTF-8 字节、
工具原始参数与展示参数缺失或不一致时，Gateway 安全拒绝，请在原生 Codex 客户端核对并重新发起操作。
审批中的 JSON 转义表示保留完整内容；飞书折叠面板展开后不截断，批准范围不会因展示方式变化而扩大。

## 5. 后台服务与更新

安装、检查和重启：

```bash
codexc install
codexc status
codexc restart               # 等同 restart all，包含已安装且未关闭的 WebUI
codexc restart gateway       # 只重启 Gateway
codexc logs -n 200
```

公开目标统一为 `gateway|appserver|webui|relay|all`，不接受 `app-server` 或 `model-relay` 作为 CLI 目标。
日常服务操作直接使用 `codexc <动作>`，不提供 `service` 子命令。
`codexc run` 在前台运行 Gateway，并复用拓扑一致的现有 App Server；没有现有实例时启动受管 App Server。退出时仅停止本次启动的子进程，保留复用的 App Server，不启动 WebUI 或 Model Relay。`codexc start [目标]` 启动已安装后台服务。
`codexc install` 生成服务定义并启动核心服务；`codexc uninstall --services` 仅停止并卸载后台服务，
`codexc uninstall` 自动识别并卸载当前程序，受管源码来源匹配时也删除仓库；两者都保留用户数据。`codexc reload` 只通知 Gateway 重读配置。
安装、卸载、更新与重启按语义阶段显示分隔标题，组间留空行；交互终端显示当前阶段的动态进度，阶段结束保留结果与耗时，诊断信息留在对应阶段下。`install` 覆盖配置检查、服务定义写入、启动及就绪确认；`uninstall` 区分卸载准备、后台服务、程序移除和保留的数据。安装或更新取消时会等待当前操作与必要的恢复结束；卸载会等待当前移除动作结束，再停止后续目标，已移除的内容不自动恢复。
重载成功仅表示已发送通知（Windows 为 Gateway 已接受重读请求），不代表配置应用已经完成；其他设置按保存时提示重启，服务定义或安装环境变化时才需重新运行 `codexc install`。若提示“重新加载结果未确认”，
应先核对服务日志与实际配置状态，不能据此认定请求没有执行。尚未接受的重载请求会在截止或连接断开时取消。

macOS、Linux 和 Windows 安装时若显式设置了 `CODEX_HOME`，该路径必须是已存在的目录，安装器会将规范化后的路径写入四个服务定义；未指定则保留默认 Home 语义。更换目录后需要在设置了新值的终端重新运行 `codexc install`；已有定义不会被后台自动改写，安装失败沿用既有定义备份和恢复流程。Linux 的 ExecStart 禁止变量展开，程序路径中的 `$` 按字面值传递。

App Server、Gateway 和 WebUI 服务会保存安装时选定的 Codex CLI 路径。Unix 旧定义缺少 `CODEX_BINARY` 或需要更换其路径时，同样需要在目标环境中运行 `codexc install`；普通 restart 不会刷新定义。核心服务、Relay 和 WebUI 的状态处理见[本地工作树安装与部署](source-install.md#本地工作树安装与部署)。

macOS 和 Linux 的服务定义为停止预留 50 秒，覆盖内部收尾预算；Linux 首次停止信号只发给服务主进程，由它协调子进程收尾，超时后由 systemd 清理剩余进程。已有安装仅更新程序并重启不会刷新服务定义；升级到包含这些模板变更的版本后，需在本机终端执行一次 `codexc install` 重新生成并激活定义。这会重启核心服务，请先安排停机窗口并记录各服务状态。macOS 已运行的 WebUI 还需执行 `codexc restart webui` 加载新 plist；首次卸载仍使用旧 Job 的期限。

Windows 启动前会检查服务定义所用的 PowerShell、原生构建产物、Node、CLI 入口及工作目录。缺失或不匹配时先返回修复提示，不启动任务；服务进程启动后的故障仍可能在宿主等待超时后报告。此时显示的“最近一次任务结果”不保证来自本次启动，请结合 `codexc logs` 判断。

`codexc restart [gateway|appserver|webui|relay|all]` 是唯一重启入口，默认 `all`。
`start`、`stop`、`restart` 在交互终端逐项显示动态进度，每个服务步骤完成后保留一条结果与耗时（秒，保留两位小数）；启动步骤包含就绪检查，失败步骤也显示耗时。重启先显示预检进度与耗时。重定向输出或 CI 环境使用纯文本；跳过原因和诊断信息始终保留。按 Ctrl+C 中止后不再执行后续步骤，已完成的启停不自动回滚。
单独指定目标时要求该后台服务已安装；`appserver` 包含受监管的 Provider 实例。
全部重启要求 Gateway 与 App Server 已安装，未安装的 WebUI、Relay 明确提示跳过；
已安装但未启用的 Relay，以及配置中关闭的 WebUI，都只停止，不重新启动。显式 `restart relay` 或 `restart webui` 仍会重启该服务，Relay 监听由配置开关控制。

重启先检查配置、所选服务定义和服务管理器状态，全部预检通过后才停服。
停止顺序为 WebUI → Relay → Gateway → App Server；启动顺序为 App Server → Gateway → Relay → WebUI，
每项启动后先确认就绪，再启动下一项。WebUI 未显式配置时也检查默认地址的健康端点。
任一停止、启动或就绪检查失败立即中止，报告已完成、失败和未执行步骤，不自动回滚已完成的启停。
可用 `codexc status` 和 `codexc status webui` 检查状态，排除问题后重试。

`start/stop/status` 默认操作全部后台服务；`start all` 按配置跳过已关闭的 WebUI 与未启用的 Relay，
`stop/status all` 仍包含已安装的可选服务，
`logs` 默认 Gateway，显示最近 100 行；`-n` / `--lines` 接受 1 到 10000 的十进制整数，`-f` 持续跟随。macOS 普通 `start` 不强制重启已运行的服务。
Windows 非跟随日志分块定位和输出尾部，不随累计日志大小占用内存；末尾换行不额外计为空行，超长单行仍完整输出。读取期间文件被截短会明确报错；之后追加的内容可用下一次查询或 `-f` 查看。
macOS/Windows 安装器将受管日志目录固定为安装时 `[codex] socket_path` 的父目录；WebUI 日志页面与最近错误摘要按当前配置解析同一目录，未自定义时为配置目录下的 `runtime`。修改 Socket 位置后须按[安装步骤](source-install.md#本地工作树安装与部署)重建服务定义，避免已加载服务继续写旧位置。配置不可读或日志目录无效时文件摘要不可用，不借旧目录内容冒充当前错误；Linux 保留 journal 查询。
单独重启 Gateway 不停止共享 App Server；单独重启 App Server 时，仍运行的 Gateway 会按真实断线处理并重连。
渠道内禁止停止或重启 App Server，全部重启也必须在本机终端执行。
WebUI 内不执行包含自身的停止、重启或卸载任务；请在本机终端运行对应的 `codexc stop/restart webui`、`codexc stop/restart all` 或 `codexc uninstall --services`。
浏览器开着 WebUI 时也可以从终端重启：停止时主动关闭实时通知、空闲 HTTP 连接及尚未发送请求的浏览器预连接；正在处理的请求最多等待 30 秒，超时会在 WebUI 日志中记录错误并以非零状态退出。本项修复更新程序后即可使用，不需要重新生成服务定义。

受管第三方 Provider 的模型目录、Profile 或管理标记变化会自动校验，并仅应用到当前 Gateway
已启用且受影响的 Provider。原生 TUI/Desktop 租约或该实例的权威活动 Thread 会推迟应用；
其他 Provider 的实例和活动轮次继续运行。目标实例重新读取启动材料，恢复连接和绑定并刷新模型
目录后才提示生效；失败保留待应用状态，冷却后重试，每 Provider 每次文件变化最多失败 12 次，
耗尽后等待下一次设置变化或 Gateway 重建。连续修改不会丢掉尚未应用的变化。
新 Gateway 启动后静默核对宿主的已应用指纹；相同指纹不动实例，未生效变化继续等待安全应用。
模型目录与默认值按 Provider 单独确认：已有实例读取 App Server 的实际目录，并使用宿主已应用的
默认设置；未运行实例只有在宿主确认相同文件指纹后才开放目录，不为读取目录启动实例。
某个 Provider 成功不会提前发布其他仍等待生效的目录。确认失败时保留原有已确认目录；重建后
没有可确认目录的 Provider 暂不可选。显式模型选择及已有 Thread 的实际模型继续保留。
停止或重建 Gateway 会取消未开始的操作；如果目标实例已经停止，监管会完成重新启动以恢复共享
实例，但已停止的 Gateway 不再刷新或发送成功提示。监管端未提供当前所需的定向应用能力时，操作明确失败并提示
重启 App Server 服务后重试，不自动改为整体重启。账户增删或 Provider 拓扑变化仍需显式管理服务。

Linux 使用 systemd 用户服务；Windows 使用当前用户计划任务和隐藏的 PowerShell 7 进程，不需要管理员权限。
Windows 计划任务的 `Ready` 表示等待启动；未检测到运行中的服务宿主时，`codexc status` 显示 `stopped`，不将任务的 `Ready` 当作服务就绪。
Windows 启动时，计划任务宿主等待 15 秒，App Server 应用就绪另行等待 60 秒，以覆盖配置、ACL 和实例初始化；监管确认主实例运行后再检查连接。应用等待超时会报告最后等待阶段，后续服务仍不会提前启动。
Windows 计划任务预检最多 10 秒、查询最多 5 秒、单次变更最多 15 秒。变更超时后只重新查询状态，不自动重做；计划任务状态不代表应用就绪，仍需通过 `codexc status` 确认。DPAPI 操作最多 5 秒，每次进程树终止命令最多 2 秒，超时明确报告结果未确认。
Gateway 与 App Server 监管进程从进入停止起最多等待 30 秒清理；Windows 宿主与前台包装层给子服务 35 秒（含 IPC 交付），外层最多等待 50 秒完成宿主回收，再按计划任务自身的 20 秒期限确认启动器停止。停止后的新重载会被拒绝；父进程控制 IPC 断开会停止其拥有的服务，不影响普通客户端断开时共享 App Server 的独立运行。正常清理失败以非零状态退出；进程树回收不等于已完成原生 App Server 的活动轮次排空。
WebUI 和服务操作使用的 Windows 异步状态查询整体预算为 25 秒，包含 Job 宿主、计划任务查询、权限检查和宿主通信，超时后另行有界回收本次查询进程树；回收失败会明确报告退出未确认。App Server 健康检查对静默 Proxy 单独限制握手等待，使用与服务相同的 Codex 程序及环境，清理失败会返回错误。
Windows 受管 Codex、查询和维护进程由 Job Object 管理，先加入 Job 再运行，包装进程先退出也会回收后代；计划任务停止还需确认外层启动器已停止。IPC 超时属于状态未知，不作为停止成功。私有路径只支持本地盘上的普通目录，拒绝祖先 junction 等重解析点；Proxy 每次连接均校验私有 Socket 目录并固定目录句柄。

Gateway 和 WebUI 关闭投递数据库时，会等待写入 Worker 及其 Windows 权限 helper 的真实退出；超过等待预算会报告关闭未确认，并保留资源归属，不直接终止外层 Worker 来掩盖未完成的清理。服务管理器仍按外层期限处理，实际停止状态需以服务状态和日志为准。本项修复无需重新生成服务定义。
原生 helper 还持有实际调用者的进程句柄，调用者异常退出时也回收其受管子树。Proxy 连接期间，Socket 目录内会有自动删除的 `.codexc-socket-*.guard` 文件，用于阻止空目录原地转换为重解析点；正常关闭或进程退出后由系统清理，不应在连接期间手动删除。只读 Doctor/ACL 检查不会创建该文件。
WebUI 取消任务失败时保留进程归属，恢复为可再次取消的运行状态并显示错误，继续阻止同一操作者提交重叠任务；不会一直停留在“取消中”或冒充已取消。若进程随后退出但未确认完整回收，则报告失败并要求检查实际状态。
Gateway 创建渠道前会初始化并收紧媒体暂存根目录 `uploads`，再由各渠道初始化自己的子目录。
已有目录必须属于当前用户且不是符号链接或重解析点；不满足时拒绝启动，不自动接管所有权。

Windows 私有配置 ACL 修复：

以下修复命令仅处理 Codex Home 顶层 TOML，不是任意数据目录的权限修复入口。

```powershell
codexc security repair
```

该命令只处理当前 Codex Home 顶层的普通 `.toml` 文件，不修改配置内容。主 `config.toml` 所有者与写入权限有效时保留上游读取权限并跳过修复；其余需要修复的文件关闭 ACL 继承，
仅保留当前用户、SYSTEM 与 Administrators 完全控制。若文件归 Administrators 所有，只有当前用户
已有完全控制权限且文件不含拒绝规则时，才把所有者恢复为当前用户；其他用户所有的文件明确拒绝。
使用普通用户终端执行即可；无权限或不满足条件时保留失败信息，不自动提权。
修复逐文件执行，后续文件失败不会撤销此前已成功收紧的权限，处理失败原因后可以重新执行。
日常启动和 Doctor 校验不会自动接管文件。修复后运行 `codexc doctor`，再重试启动服务。
启动或读取 Codex Home 顶层 TOML 时，若发现所有者或访问规则不符合对应文件要求，错误会直接提示
`codexc security repair`。超时、PowerShell 缺失、目录权限问题及修复命令自身失败不重复给出这条建议。

Windows 原生 Codex 会原子替换主配置，沙箱也会为 Codex Home 配置读取权限。Gateway 对共享 `config.toml` 检查所有者和写入完整性，允许只读继承；这不代表文件内容仅当前用户可读。Provider 独立 Profile、凭据、备份及 Gateway 配置仍使用严格私有权限。不要通过递归收紧整个 Codex Home 来修复单个文件，也不要将沙箱组加入通用信任名单。

Provider 配置事务的写入与回滚保留共享主配置已有的 DACL；同名备份仍按私有文件处理。显式指定 Gateway 配置路径时，不因首次保存而收紧已存在的父目录。若共享配置替换结果无法确认，命令会报告保留的恢复目录及可能存放新内容的临时路径；先核对当前配置、恢复目录内的原文件和仍存在的临时文件，不要直接删除目录或反复重试。

Windows ACL 检查在当前命令进程内复用 PowerShell，每次仍重新检查实际权限。计划任务状态批量读取；服务按依赖顺序启动并保留就绪检查。`doctor` 文本模式立即显示标题及检测阶段，`--json` 仍仅在完成后输出一份 JSON。

Doctor 较慢的阶段会在标准错误流显示动态进度，独立连接与服务查询最多四项并发，按原顺序展示结果；查询超时显示“状态无法查询”。设置读取与保存、官方登录前的切换预览、模型能力和 WebSocket 探测、Desktop 检查与启动也显示对应阶段进度。确认框与登录设备码保留各自交互；进度动画不接管键盘，取消仍由执行模块负责收尾。

Windows 的 Gateway、Provider 设置检查、Remote、配置命令及 Desktop 桥接统一使用命令解析与进程树回收接口，支持 npm 安装的 Codex 启动入口。Provider 定向应用失败时，App Server 日志会记录 `provider-settings-apply-failed` 和受控错误代码；重启后的“已安全应用”只确认当前设置，不代表后续热更新路径也已验证。

Provider 添加过程中若报错，不代表账户已经保存；修复原因后需重新完成添加，服务重启不会补做失败的配置事务。已配置但模型目录尚未确认的 Provider 会在渠道模型列表显示“暂不可用”，目录确认成功后再开放真实模型。

源码安装的日常升级统一使用：

```bash
codexc update
codexc doctor
```

安装和更新由本机操作者执行；仅需要交互确认的步骤要求 TTY。本地源码更新后重新执行 `npm run install:global`，该命令不自动停启服务，具体顺序见[本地工作树安装与部署](source-install.md#本地工作树安装与部署)。

官方安装器和本地 `npm run install:global` 在默认 Codex CLI 缺失或版本不符时自动同步项目锁定版本，无需先初始化或配置渠道；它们只提示下一步，不自动执行初始化、接入向导或后台服务安装。首次安装成功后，用户在交互终端运行 `codexc init` 完成完整向导，跳过的步骤再按需补充。显式 `CODEX_BINARY` 由操作者管理，本地安装遇到版本不符时拒绝替换。
更新发现默认 CLI 缺失或版本不匹配时会询问是否安装，确认后先校验临时候选，再更新全局 CLI；
非交互调用会给出精确版本安装命令并退出，不静默安装。

更新先检查源码、公开合同、当前配置和数据库结构，通过后在一个停机窗口完成程序及配套 Codex CLI 安装与服务恢复。已知的指标 Schema v31/v32/v33/v34 会在停服后先创建完整私有备份，再升级至 v35；现有记录保留，v31 历史请求发送大小为 null，v32 已有值不变。v35 新增请求行为摘要，历史记录显示“未记录”；v34 已有请求地址保留。图片生成和图片编辑指标继续支持，不补录过去未采集的请求。升级后程序安装失败时保持服务停止并保留恢复材料，禁止启动旧程序读取 v35 库。其他旧 Schema 明确拒绝，运行时仍只接受当前结构。更新会将 Codex 用户层 `features.daemon_auto_start` 设为 `false`，包括版本无需更新时；不停止已有官方后台。其他用户偏好与 Provider 模型目录不改写。新安装由正常初始化创建当前结构。旧更新器的过渡和详细流程见[源码安装与更新](source-install.md)。

### 本机清理与归档

统一交互入口：

```bash
codexc cleanup
```

清理菜单包含归档、转储删除、过期指标清理、Provider 指标清理和重置五项，完成或取消后返回菜单。下表另列出独立的投递核对命令：

| 维护项目 | 直接命令 | 执行条件与结果 |
| --- | --- | --- |
| 归档短会话及子会话 | `codexc cleanup sessions <最大轮数>` | 停止 Gateway、保留 App Server；预览并确认后归档 |
| 删除请求与响应转储 | `codexc cleanup traffic` | 先预览，确认删除需停止全部 App Server 与 Relay；仅删除识别的 V2 session，菜单确认绑定本次预览，范围变化则拒绝 |
| 清理旧指标 | `codexc cleanup metrics --restart-gateway` | 备份清理；显式 `--restart-gateway` 会停止后启动 Gateway（原先停止也会启动），交互菜单则按原状态恢复 |
| 核对未确认渠道结果 | `codexc delivery status` / `codexc delivery list` | 先停止 Gateway；明确重发、确认送达与停写备份见[投递箱运维](delivery.md) |
| 清理指定 Provider 的指标 | `codexc cleanup metrics prune <provider>` | 指定区分大小写的精确 ID 即执行；备份清理，Gateway 按原状态恢复 |
| 重置整个指标库 | `codexc cleanup metrics reset` | 先停止 Gateway；直接备份并移除当前库，启动 Gateway 后重建 |

`codexc cleanup -h` / `--help` 显示说明，无参数菜单在非交互终端不会执行清理。直接指标维护命令即显式执行，不再询问确认；交互菜单会先确认目标及影响。菜单中的会话归档、旧指标清理和指标库重置会在确认后临停运行中的 Gateway；转储删除先预览并确认，再询问临停 Gateway、Relay 和 App Server。菜单结束、取消或失败后按原状态恢复，原先停止的服务不会被启动；恢复失败会报告具体服务和手动启动命令。底层命令仍检查实际进程已退出，不终止前台自行运行的进程。执行失败会报告错误并返回清理菜单。
旧指标清理菜单收集保留范围和 VACUUM 选择后，再显示默认拒绝的删除确认。旧指标清理和 Provider 清理均校验完整的当前 Schema，并在检查点、备份、删除和 VACUUM 期间持有共享 writer 锁；前台写入者占用时拒绝操作。Provider ID 可为已移除提供商的历史精确 ID，区分大小写。裁剪 Thread 计时记录时会撤销对应历史完整标记，避免剩余数据被误当作完整历史。
重置同样在持锁前后校验完整当前 Schema，未知版本或结构残缺均拒绝且保留原库。备份独占创建、
私有权限保护成功后才移除当前库；备份失败时原库保留，已生成的备份不自动覆盖或删除，需检查后处理。
三种指标维护都要求服务状态明确；无法确认停止状态时不会把它当成已停止继续操作。

指标删除提交后，VACUUM、剩余数量读取、数据库关闭、锁释放或 Gateway 恢复失败不会撤销删除。直接命令返回非零，同时保留已提交数量和备份位置；提交是否成功无法确认时明确显示“未确认”，不要重复清理。WebUI 维护任务展示受控提交状态、失败阶段及恢复提示，不返回原始子进程输出或备份路径；可用 `codexc metrics status --json` 获取 `databasePath`，在同目录核对 `.cleanup-<时间>.bak` 或 `.<精确ProviderID>-prune-<时间>.bak` 备份及当前记录。Gateway 恢复失败按提示运行 `codexc start gateway`。

维护期间收到 Ctrl+C 或 SIGTERM 时，停止后续操作，等待已开始的写入、归档核验及服务恢复收尾后退出。已完成的删除或归档不自动撤销；再次取消不会跳过服务恢复。普通操作失败可返回菜单，终止请求收尾后退出 CLI。

会话归档示例：先停止 Gateway，保留 App Server，预览“主会话不超过 3 轮、整组可查询成员至少空闲 7 天”的候选：

```bash
codexc stop gateway
codexc cleanup sessions 3 --idle-days 7
```

核对后在交互终端执行，命令会重新扫描并再次询问确认；非交互 `--confirm` 在扫描前拒绝，不兼容的绑定库也会在连接 App Server 前拒绝：

```bash
codexc cleanup sessions 3 --idle-days 7 --confirm
codexc start gateway
```

交互归档统一从 `codexc cleanup → 归档短会话及子会话` 进入。菜单在 Gateway 运行时先询问是否临时停止，保留 App Server；预览后的归档仍需确认。完成、取消或失败后恢复原先运行的 Gateway，原先停止则保持停止；恢复失败会提示手动启动。前台自行运行的 Gateway 仍须退出，菜单不终止非受管进程。`codexc cleanup sessions` 无参数显示用法。不指定 `--idle-days` 就没有会话年龄限制。
轮数阈值只计算主会话，子孙轮数不累加；派生子孙随官方归档，Fork 独立筛选。
已移除或改名 Provider 的历史会话仍可归档，无需恢复旧 Provider 或凭据；检查已连接实例的活动状态，其他实例持有的写入锁由官方归档接口拒绝。扫描只读取一份共享历史，候选最多四组并行检查；确认后逐组复核与归档，最后集中核验结果，终端会显示扫描和归档进度。
活动、固定、渠道绑定或状态无法确认的成员会使整组跳过。归档保留历史，不是永久删除；
官方操作可能部分成功，执行期间不要在其他客户端操作候选会话。完整筛选及核验口径见[展示说明](display.md)。
执行确认后，只要有失败、部分成功、结果未确认、复核跳过或展示缓存清理失败，命令就以非零状态结束，并保留逐组结果；不自动重试或回滚。仅预览、执行前筛选跳过或用户取消不视为归档执行失败。

### 卸载

卸载但保留用户数据：

```bash
codexc uninstall
```

卸载不要求配置文件有效，自动处理官方受管源码、本地工作树构建包和 npm Registry 全局包，先卸载服务，再卸载当前全局命令。
只有源码来源记录与受管目录精确匹配才删除受管仓库；本地工作树和缺少来源记录的旧安装源码保留，身份未知或冲突时拒绝卸载。
用户配置、数据库、凭据、日志、输出、Codex CLI 和 Shell 配置均保留。无需另行执行 `npm uninstall`；仅卸载后台服务用 `codexc uninstall --services`。

### Hook 列表、信任与启停

```text
/hooks trust <选择编号>
/hooks enable <选择编号>
/hooks disable <选择编号>
/hooks confirm <预览返回的确认码>
```

列表显示来源、触发事件、启用与信任状态；详情展示经过安全处理的审查信息。
选择编号固定到本次列表，不是可随排序变化重新解释的序号。信任、启用、停用均先生成预览，
再由同一操作者明确确认；选择与确认五分钟过期，Gateway 重启后失效。
确认时 Workspace、会话或 Provider 与预览不一致，Hook 定义/状态改变或用户配置版本变化时，需重新审查。
受管 Hook 只读。仅信息完整的 command Hook 可以在渠道逐项信任；MCP Tool、prompt 和 agent
处理器的完整输入未由列表接口提供，需在本地审查。命令信息被脱敏或截断、来源不明时，渠道也不提供信任操作，
请在本地 Codex `/hooks` 审查。微信还会检查命令、匹配条件和来源路径能否原样展示；需要替换 Markdown 符号时不允许渠道信任，手动输入信任或确认命令也不能绕过。已信任的非受管项仍可启停。不能通过此入口注册 Hook、部署脚本或一次性信任全部 Hook。

**信任和启用是独立状态。** 新增或变更的非受管 Hook 需要信任当前定义；信任一个已停用 Hook
不会替它开启。普通 Hook 的信任哈希对应配置定义，不覆盖所引用脚本的文件内容。
插件 Hook 还核对插件内容指纹；内容变化后需要重新审查，但该指纹不覆盖全部外部依赖，不能代替脚本审查。
Codex 0.164.0 在首次列举或执行已有受信任插件 Hook 时可能在实际用户配置文件同级的
`.hook-trust/` 建立基线；显式信任会写入内容哈希。升级前应连同该目录备份用户配置及插件内容，
回退时保留这些数据；旧版不会提供新版的内容变化保护。
这些操作持久写入 Codex Home 的用户配置。项目的主实例和 Provider 隔离实例共用该配置，
因此会影响其他 Provider 和使用相同 Hook 的会话，并非仅当前聊天的一次授权。
Gateway 数据库不保存另一份 Hook 定义、脚本或信任状态。

写入后通过官方协议协调已连接及正在连接的实例刷新运行配置，并回读列表核对结果，通常不需要重启。
每次新建连接或重连时均刷新，覆盖未连接实例及 Gateway 重启后仍存活的独立实例；不会为刷新而启动未使用的 Provider。刷新请求使用空编辑，不复制或重写 Hook 状态。
某实例刷新请求失败时，结果明确提示“已保存，刷新未确认”及对应 Provider；下一次使用该实例前再次尝试刷新，失败则拒绝继续操作。
首次连接的刷新失败会先清理本次 Client 连接，清理成功后可重新接入；清理未确认时保持拒绝接入，需检查连接清理错误，不会通过终止共享 App Server 绕过。
“设置成功”只表示保存、回读状态匹配且协调的刷新请求已返回成功，不保证上游内部所有 Thread 刷新成功，也不表示 Hook 已执行；
实际运行仍看后续 Hook 完成通知。Hook 状态写入中断或结果不明时不会自动重试，旧选择和确认全部失效，先重新执行 `/hooks` 核对。
列表警告、配置加载错误与空列表分别提示，不向渠道转发上游原始错误正文。

Windows、macOS、Linux 使用同一管理协议；脚本路径、解释器和会话 Shell 仍由实际 App Server
环境决定，信任操作不会修正平台不兼容的命令。此入口不改变 Windows 代理或 Unix Socket 生命周期。

## 7. 指标、WebUI 与图片

```bash
codexc metrics status
codexc metrics threads
codexc metrics report --range 30d --group models
codexc metrics export --range 30d --format json
codexc webui
codexc traffic
```

WebUI 默认展示本机脱敏指标；回环监听未配置令牌时可直接使用设置页，显式配置令牌后所有 API 都会验证。`0.0.0.0` 监听必须配置非空令牌，验证后可远程修改设置；写请求的 Origin 必须匹配访问主机，域名反代须保留原始 Host。原始调用转储仍只允许回环访问。详情见 [`WebUI`](webui.md)。
指标查询与清理、转储查看与清理的同名单值选项拒绝重复，避免后一个值静默改变范围；转储查看最多指定一个 session 目录。
`metrics report/export/run/threads/turns/quota` 默认生成私有导出文件，使用 `--stdout` 输出到标准输出。创建导出前逐级检查数据目录、output 和日期目录的类型、所有者及平台私有访问权限，拒绝将这些目录设为符号链接。组合查询、分页明细及聚合共用一次只读快照，运行中新增记录会在下一次查询出现。服务启动等待 WebUI 健康响应与受管进程身份匹配；其他程序返回 HTTP 200 不代表 WebUI 已就绪。IPv6 地址使用带方括号的 URL。

指标查询与导出在独立子进程执行，耗时超过 250 毫秒才显示进度，进度写入标准错误流，不混入 JSON/CSV 或导出文件。取消会等待当前数据库操作释放资源；失败或取消的导出文件会移除，只有成功后才报告文件路径。
文件导出与 `--stdout` 本地查询使用相同环境，不加载无关的 Codex `.env` 代理配置；服务维护仍执行自身环境检查。运行和会话明细的文件名使用查询解析出的 Thread ID，筛选参数的位置不会改变文件标识。
`metrics report/export` 支持 `--request-purpose autoApprovalReview|unmarked`；不指定时包含全部用途。`unmarked` 表示未标记用途（含历史未知），不能证明是普通请求，可与 Thread/Turn 归属筛选组合。会话、轮次和 `run` 的任务统计固定排除明确审查，不接受此选项。聚合保留已知 Token 累计与 `usageCoverage` 缺失计数，CSV/JSON 同步输出；Markdown 直接显示已有累计，不附加字段缺失标注，零值与未提供的数值留空或省略。全局和提供商总量含审查，以“其中自动审查”列出，不能再次加到总数。模型组只按记录模型归组，涉及轮次不可跨组相加。
请求明细 `metrics export` 通过只读 Worker 从同一快照逐块输出，JSON、CSV、Markdown 均保留原有字段与筛选语义；单次最多 64 MiB，读取和输出共用 120 秒预算，初始化和关闭另有限时。超过容量或时间限制会明确失败，请缩小时间范围或增加筛选条件后重试。Windows 辅助进程退出未确认时会报告关闭失败并保留进程引用，不把超时视为清理完成。

请求明细、会话列表与轮次明细的 Markdown 输出中，思考等级缺失时显示“未观测”，不推断为模型默认；已有等级（包括 `none`）保留原值。JSON 保留空值，CSV 保留空单元格。

### OpenAI 重置券 CLI

Gateway 和主 App Server 可用、已登录 ChatGPT 时，可在本机使用：

```bash
codexc reset-credit list          # 实时列表，日期为 UTC 并明确标注
codexc reset-credit list --json   # 机器可读的账户 ID、数量与可用券明细
codexc reset-credit use           # 交互选券、预览并确认
codexc reset-credit use <券ID>    # 指定券后预览并确认
```

命令不依赖 WebUI 进程。取消或中断已获取的预览会尝试通过私有 IPC 释放记录，清理失败会明确提示并由 5 分钟有效期兜底。消费必须在交互终端明确确认，默认取消；不支持 `--yes` 或非交互消费。
预览展示账户、券名称、官方说明和到期时间；Gateway 复核账户与券状态后单次执行，5 分钟预览过期需重新操作。
最终提交前仍复核预览和券的期限，等待期间过期不会继续消费；这不构成与其他客户端切换账户的原子事务。
中断、超时或丢失消费响应时不自动重试，先重新运行 `list` 核对官方状态。消费结果与账户快照刷新结果分开显示。
API Key 账户、未知类型或未提供明细的券不可使用。渠道使用 `/limits reset` 查询、`/limits reset use <券ID>` 预览，再按返回的 `/limits reset confirm <令牌>` 确认或 `/limits reset cancel <令牌>` 取消。飞书和 Telegram 的 `/limits` 提供“查看重置券”按钮；列表可点选、翻页、刷新，预览提供“确认使用”和“取消”按钮，无需复制令牌。微信使用文字命令，飞书和 Telegram 也保留文字入口；令牌仅限原用户、会话、工作区及当前 Thread，5 分钟过期，重启失效。WebUI 操作见[重置券使用](webui.md#openai-重置券使用)。

### 正常发图与图片引用

视频附件使用独立的视频分析 MCP：三渠道接收 MP4/WebM 后提交单文件随机引用，实际分析需要在承载该渠道 Thread 的 App Server 中启用 MCP 并配置渠道附件根目录。Telegram 接收上限 20 MiB，飞书/微信 64 MiB；只分析画面，不分析音轨。部署、有效期、授权及尚未实机验收的范围见[视频分析 MCP](video-analysis-mcp.md#渠道视频附件)。

照常在渠道发送图片即可，不需要额外命令。使用 OpenAI ChatGPT 登录时，Gateway 上传已校验的
原图并以官方 `fileId` 提交；App Server 保存引用，后续历史继续使用引用。自动引用目前要求
实际模型代理与账户均使用默认 ChatGPT 后端，且账户路由策略为 `NO_CONSTRAINT`；
`us`、`us_cr` 或后端不一致时会在上传前报错。
受管 DeepSeek 账户通过本地代理上传到官方 Files API，取得 `file-api-...` 后以 `fileId` 提交，
上传失败明确拒绝当前 Turn，不回退内联图片。OpenAI API Key、自定义第三方、CLP 等其他 Provider
以及独立自定义 OpenAI 后端保持内联图片输入。Actor、Workspace、模型能力和媒体大小限制继续适用。

图片引用会跳过 App Server 的本地缩放，不能视为与普通原生 TUI 的图片预处理完全相同。
普通准备阶段每阶段最多等待 60 秒。OpenAI 每张图片的字节 PUT 最多 5 分钟，包含最多 5 次尝试及退避等待，完成确认最多 30 秒；
DeepSeek 不自动重试：本地代理整次上传最多 30 秒，包含材料复核与收发；上游 Files POST 自身上限为 60 秒，
客户端传输阶段上限为 5 分钟，实际受最先到达的期限约束；客户端材料及路由准备阶段最多 60 秒。
多张图片依次处理，可通过 `/stop` 取消；主动取消、连接关闭与阶段超时分别提示。
账户或路由变化、上传失败会报告对应环节；网络异常不会统一归因于登录失效，
可按[渠道日志说明](display.md)中的图片诊断字段定位。
OpenAI 字节 PUT 按锁定上游策略对暂时性网络异常及 HTTP 502/503/504 有界重试，尊重服务端等待时间；只重传相同上传地址的相同字节，不重新创建文件或重复提交模型请求，不回退 Base64。远端图片没有自动删除入口，保留时间和跨重启可用性不作保证；
此功能不提供文件管理、按编号下载或用户手动编号输入。
DeepSeek 上传只使用私有监管 IPC 确认的运行实例能力；账户设置尚未应用时拒绝上传。
升级后旧服务缺少该能力时会提示重启 App Server 与 Gateway，不自动重启服务。
DeepSeek 详细合同及限制见 [DeepSeek 图片识别](deepseek.md#图片识别)；OpenAI 实现、验证范围与限制见[图片引用决策](codex-cli-upgrade-decisions.md#图片文件引用需求阻塞与实现边界)。

部署后需要确认自动引用时，先按[模型请求转储](#模型请求转储)开启调用详情记录。为避免历史条目或
长字段被裁剪，可临时把 `model_traffic_input_items` 和 `model_traffic_item_max_bytes` 都设为 `0`，
重启 App Server 后在新会话中发送一张图片，再发送一条只引用前图的纯文本追问。用下面的命令分别
展开首次发图和后续追问对应的模型调用：

```bash
codexc traffic
codexc traffic --exchange <首次发图编号>
codexc traffic --exchange <后续追问编号>
```

首次请求应包含 `input_image.file_id`，且不包含该图片的 `data:image/...;base64`。后续请求可能在
完整历史中继续携带同一 `file_id`，也可能通过 `previous_response_id` 增量接续而完全不再携带图片；
两者都属于官方历史复用。后续请求重新出现该图片的 Base64 才表示自动引用未生效。模型能够回答
后续追问只能证明上下文可用，不能单独证明首次请求已经使用 `fileId`。转储包含未脱敏的会话正文、
工具输出和代码，验证后恢复原来的裁剪配置并关闭转储，不要分享原始文件。

从本机向绑定渠道发送图片：

```bash
codexc channel send-image /tmp/screenshot.png
codexc channel send-image /tmp/screenshot.png --thread <Thread ID>
```

只接受经过安全校验的 PNG/JPEG，具体限制见 [`渠道图片`](channel-image.md)。

显式文件可用 `codexc channel send-file /absolute/path/report.pdf --thread <Thread ID>`，支持 QQ、飞书、Telegram 和微信；默认普通文件，`--type video` 为 MP4，`--type voice` 在 QQ 为 SILK、飞书和 Telegram 为 Ogg/Opus，微信不支持原生语音，不自动转码或降级。QQ 普通文件最多 64 MiB，视频 30,000,000 字节，语音 20,000,000 字节；飞书三种类型均最多 30,000,000 字节，Telegram 均最多 50,000,000 字节，微信普通文件与视频均最多 25 MiB。沿独立私有暂存、原 Thread 绑定和未知结果不重试规则，微信另固定入队时的有效回复上下文；全部媒体类型与异常分支尚未完成真实客户端验收。完整参数、隔离观察范围及归档方式见 [`渠道文件`](channel-file.md)。

## 8. 排障

```bash
codexc doctor
codexc doctor --json
codexc status
codexc logs -n 100
```

常见处理：

- 尚未配置通讯渠道：Doctor 会单独报告 Gateway 启动所需的渠道未配置，并继续检查工作区等独立项目；运行 `codexc setup` 完成渠道接入后重新诊断。
- 工作区路径失效：Doctor 显示实际配置来源，逐项检查所有工作区及默认引用；任何失效项都会阻止 Gateway 使用该配置启动，热加载失败时保留原配置。先检查磁盘挂载、路径与权限；项目搬家时修改对应 `[[workspaces]].cwd` 并保留 ID。确认项目不再使用时，可运行 `codexc work remove <ID>` 移除注册，不删除目录；纯数字 ID 或 ID 与其他工作区名称相同时，请使用 `codexc work` 菜单精确选择。固定默认工作区不可移除。`codexc work add --prune-missing` 会在注册当前目录时清理不存在或非目录的注册，必须先确认这些项目不再使用，无法访问的目录会阻止清理。Doctor 不自动清理，修复后重新运行 `codexc doctor`。
- 配置修改未生效：`codexc reload`。
- 配置应用失败并停止 Gateway：检查日志中的存储或组件错误，修复后运行 `codexc start gateway`。
  配置读取或校验失败仍保留当前配置；应用阶段失败可能已更新部分允许名单或绑定，因此停止服务，
  不再声称已回退到旧配置。共享 App Server 不受此故障关闭影响。
- 只重启 Gateway：`codexc restart gateway`；共享 App Server 与活动 Thread 会保留。
- Codex CLI 版本不一致：按 `codexc update` 或错误提示安装精确版本后重试。
- Codex CLI 报 `Missing optional dependency`：平台原生包缺失，按提示带 `--include=optional` 重装项目锁定版本，先确认 `codex --version` 成功；不要把该错误当作版本号或 PATH 冲突。见[源码安装与更新](source-install.md#本地工作树安装与部署)。
- 飞书无消息：先运行 `codexc doctor`，再检查应用权限、消息事件发布和允许用户。
- Windows ACL 失败：运行 `codexc security repair`，再运行 `codexc doctor`。
- 日志需要脱敏后再分享；不要分享 Token、Cookie、Authorization Header 或完整命令工作内容。

错误码见 [`错误字典`](errors.md)，渠道展示口径见 [`展示说明`](display.md)，协议与支持矩阵见 [`官方文档与源码索引`](index.md)。

### 模型请求转储

需要查看模型请求和响应的完整字段时，运行 `codexc config`，选择“调用记录 → 调用详情记录 → 开启”，
再按提示重启 App Server。也可以手工设置：

```toml
[debug]
model_traffic_dump = true
model_traffic_retention_days = 30
```

```bash
codexc restart appserver
```

App Server 发给统计代理的模型调用会写入 `~/.codex-connect/traffic/` 下的 V2 私有 session 目录；
HTTP 的一次请求对应一条逻辑调用，同一 WebSocket 连接中的每个 `response.create` 也分别对应一条。
每条逻辑调用只保存一条请求索引和一个完成、失败或不完整终态响应，原始 HTTP/SSE 块、WebSocket
握手和双向帧另存为默认不展示的 trace。HTTP 请求头
`x-codex-turn-metadata`、WebSocket 首帧 `client_metadata` 里的 `thread_id` 与 `turn_id`
可以对齐到具体会话和轮次。转储是统计代理的旁路复制，不改变转发路径、指标采集和流式背压，
也不是抓包代理。Authorization、Cookie 等凭据字段只保留认证方案，替换为 `<redacted>`。

每个 session 的 `manifest.json` 声明精确版本，`interactions.jsonl` 保存小型索引，正文通过
offset/bytes 引用轮转的 `payload-*.bin`，原始传输轨迹位于 `trace-*.jsonl`。正文和 trace 文件达到
64 MiB 后轮转；长驻进程约每 24 小时让新逻辑调用进入新的 writer session，已在执行的并发调用继续
写入原 session，因此请求与响应不会被拆分。
同一 Provider 的历史完整 session 约保留 320 MiB，当前写入 session 不在中途删除。
转储写入失败时只停止转储并在日志中报错，模型请求继续正常转发。转储包含 prompt、工具输出和代码，
排查完成后关闭开关并删除 session，不要分享原始转储。

`model_traffic_retention_days` 默认 `30`。App Server 服务每次启动，以及开启转储后建立新 writer
session 时，都会按 session 最后活动时间删除超过该天数的可识别 V2 历史批次；启动清理即使当前已
关闭转储也会执行。清理以完整 session 为单位，含保留期内记录的批次会整体保留；设为 `0` 可关闭按
时间自动清理。未知文件和未知目录不会自动删除。

转储默认按下一节的体积控制规则裁剪，不会把每次请求重发的完整会话历史原样落盘。流被提前终止时，
该逻辑调用会得到 `failed` 或 `incomplete` 终态及明确的 `errorScope`；已收到的传输块仍在 trace 中。

正文与索引分开存储，直接读不方便；用 `codexc traffic` 渲染成人可读文本：

```bash
codexc traffic                                 # 列出最新 session 中的逻辑模型调用
codexc traffic --exchange 12                   # 展开某次调用的一条请求和一个终态响应
codexc traffic --all --grep deepseek-flash     # 只显示匹配关键字的逻辑调用并展开正文
codexc traffic --exchange 12 --max-bytes 2000  # 限制每段正文的显示长度
codexc traffic --follow                        # 从现有文件末尾开始持续输出新写入的记录，按 Ctrl-C 停止
codexc cleanup traffic                         # 预览全部可清理转储，不删除
codexc cleanup traffic --confirm               # 停止全部 App Server 与 Relay 后永久删除预览范围
```

摘要行包含调用编号、时间、请求路径或 WebSocket URL、线程、轮次、模型和终态；详情固定分为“请求”
与“响应”，并补充参数、Token 用量和已完成输出条目。列表区分模型列表查询、连接预热与模型请求。
不传路径时读取 `traffic/` 中最新标签的最新 writer session；也可以用 `--dir` 指定根
目录，或传入一个 V2 session 目录。仅支持 V2 session。`codexc traffic -h` 列出全部选项。
摘要和 `--all` 按编号升序分页读取，`--exchange` 直接定位指定调用，共用进程内只读偏移索引，
不为每条详情重新扫描整批次。列表和全量输出固定本次打开的索引快照，读取期间新落盘的调用留待下次读取；
`--follow` 每轮固定各批次的快照。每次索引读取最多等待 35 秒，仍未完成则明确失败；输出或模型声明
诊断达到读取预算时会标记不完整，后续调用关联未完成也会明确提示，不能据此认定未发生。
每次页或详情读取共用 128 MiB、10 万记录和 10 秒预算；大正文会自动缩小摘要页，单条仍超限时明确失败，
可用 `--max-bytes` 限制详情正文。全量输出按页推进，不将整批正文保存在内存。
`--follow` 默认从当前末尾开始，锁定首次选中的标签，依次读取该标签后来出现的所有批次；
已观察到的旧批次未终态调用会继续按标签、批次和编号等待终态，轮转不会清空这些标识。
跟随按请求记录的文件水位发现新调用，保留旧批次游标以接收轮转后才首次写入的请求，
迟到的小编号也能被发现；同一批次同号调用的重复请求记录不会重复输出。目录或索引被替换会明确失败。
显式传入 session 时只跟随该批次，并输出已有终态调用。批次或调用已缺失会明确报告；
跟随最多保留 2048 个批次、2000000 个已观察编号和 100000 个未终态调用，超限需缩小范围重新跟随。
仅保存标识和文件水位，不缓存正文。
交互和 trace 共用最多 256 项索引缓存；源变化或缓存回收后重建会使已绑定快照失效，
可能先于跟踪标识上限停止跟随。此时会明确报告并要求重新开始，可指定单个 session 缩小范围。
`cleanup` 会预览默认 `traffic/` 或 `--dir` 指定目录中可识别的全部 V2 session，
管理调用可将预览返回的 SHA-256 作为 `--expected-fingerprint` 传入确认命令；目录或对象变化会拒绝删除。WebUI 和交互菜单自动绑定该指纹。
未知文件与目录不处理。实际删除只允许当前配置的数据目录下的 `traffic/`；先运行
`codexc stop relay` 和 `codexc stop appserver`，再加 `--confirm`。删除不可恢复，完成后可按需运行
`codexc start appserver`，此前启用的 Relay 可按需运行 `codexc start relay`。
停止检查期间预览范围或目录身份变化会拒绝删除，需重新预览确认；逐项执行时发现对象被替换也会停止，
已完成的删除不回滚。V2 manifest 只接受当前四个字段，读取拒绝符号链接及非普通文件；manifest
最多 1 MiB、索引和 trace 单行最多 16 MiB，读取超限明确失败，不自动修复损坏材料。

同一份转储也能在 `codexc webui` 的「转储」页查看：摘要列表与 `codexc traffic` 使用同一套解析，
点开某条即进入该条的请求参数、实际输出与用量摘要。终态未携带输出时，从已存 trace 的完成条目
提取；原始正文、诊断信息与传输 trace 默认收起，数据不会回写。页面地址保留标签、writer session、调用编号与分页位置，
返回列表回到原处；App Server 重启后也不会把旧列表中的编号解析成新 session 的同号调用。
该页只接受本机回环访问，展示内容同样是未脱敏原文（转储裁剪过的条目会显示对应的截断标记）。页面
同时显示自动保留天数，并提供“清空转储”的预览确认入口；实际删除前必须先停止全部 App Server 与 Relay。

### 转储体积控制

首个请求或未采用增量接续的请求可能携带完整会话历史，长会话一轮就有几 MB；使用 WebSocket
`previous_response_id` 接续时，后续请求也可能只携带本轮增量。转储对实际出现的 `input` 按下面的
规则裁剪后落盘，不需要额外配置：

```toml
[debug]
model_traffic_dump = true
model_traffic_input_items = 3
model_traffic_item_max_bytes = 65536
model_traffic_retention_days = 30
```

- `model_traffic_input_items`（默认 `3`）：只保留请求 `input` 数组末尾这么多条完整条目，更早的
  条目合并成一条 `{"type": "omitted", "omitted_items": …, "omitted_bytes": …}` 摘要；
  `0` 表示按原样保留整个 `input`；
- `model_traffic_item_max_bytes`（默认 `65536`，即 64 KiB）：单个数组条目（请求 `input` 条目、
  响应 `output` 条目、其中嵌套的数组元素）和超长字符串字段超过该字节数时只保留头尾各一半，替换为
  `{"type": "truncated", "bytes": …, "head": …, "tail": …}` 标记；`0` 表示不限制。它独立于
  `model_traffic_input_items` 生效，只设上限不会折叠 `input`。
- `model_traffic_retention_days`（默认 `30`）：App Server 启动及新 writer session 建立时，按最后活动
  时间清理超过天数的完整 V2 历史批次；`0` 关闭按时间清理。按 Provider 约 320 MiB 的体积上限继续生效。

精简开启时还会折叠响应里重复回显的 `response.instructions` 与 `response.tools`
（`<omitted N 字节>` 占位），并丢弃逐条流式增量事件
（`response.output_text.delta`、`response.reasoning_text.delta`、
`response.function_call_arguments.delta` 等以 `.delta` 结尾的事件）不再写入转储，它们的完整文本
由同一条目的 `*.done` 事件和 `response.completed.response.output` 承载。请求头、请求体其它字段、
`model`、保留的响应事件和事件顺序保持完整。需要逐个字段核对原文时，把两项参数都设为 `0` 按原样
转储。这些参数都在 App Server 启动时读取，改完需要重启服务；使用 `codexc traffic` 查看时不需要
额外参数，折叠、截断与丢弃结果会直接显示在对应位置。

开启精简时正文先整段缓冲再折叠，然后按 1 MiB 分片写入；单个正文超过 32 MiB 时退化为按原样分片，
避免为超大正文占用过多内存。

WebSocket 提供方（OpenAI 官方）同样生效：客户端 `response.create` 帧的 `input` 按同样规则保留
末尾条目，上游 `response.created`、`response.in_progress`、`response.completed` 里重复的工具与
指令回显按同样规则折叠，`.delta` 帧直接跳过。

## 可选模型 API 转发

`codexc relay` 管理独立 Relay 的调用方和访问密钥；`status`、`callers` 只读，
`issue` 签发、`rotate` 轮换、`disable --caller ID` 撤销。新秘密只在保存后显示一次。
`enable`/`disable` 保存服务开关并确认当前进程生效；进程未运行时明确显示仅保存，
通过 `codexc start relay` 启动；停止、重启、状态和日志也使用 `relay` 目标。指标库只接受当前 Schema，新安装直接创建。

Relay 默认禁用、回环监听；可显式使用 IPv4 局域网监听，跨不可信网络使用自己管理的加密隧道。提供原生 Chat Completions 与 Responses JSON/SSE 和
受限模型列表，不提供 App Server 的 Agent、Thread、Turn、工具执行或文件访问。
客户端使用 `/v1/chat/completions` 或 `/v1/responses` 选择原生协议；不会互转或自动重试另一协议。
`codexc relay providers` 和管理页展示账户的实际协议能力：CLP 为 Chat，DS 为 Chat/Responses，其他已接入的 Responses 提供商为 Responses。
自定义主/切换 Provider 必须有可独立读取的 API Key 和有效模型目录；不借用 Codex OAuth 登录态。
Responses 只提供同步无状态创建；`store` 可省略或传布尔值，出站统一设为 `false`，传 `true` 时会关闭存储后继续转发，不因该值拒绝请求。非布尔值仍报参数错误；调试调用详情记录入站与出站差异。
`background` 可省略或传布尔值，传入时统一设为 `false`，继续在当前请求内交付结果，不因 `true` 报错；省略时不补字段。
官方 DS 的 `previous_response_id`、`conversation` 原样转发，由上游按其无状态合同忽略；客户端仍需在 `input` 中携带所需完整历史，引用不会恢复上下文。其他 Responses 提供商仍拒绝服务端会话引用：多个 Relay Key 可共享上游账户，当前没有响应/会话归属校验，不能通过引用读取共享账户历史。Relay 不提供响应管理端点。
普通参数、工具声明和远程图片交由上游处理；Chat 保留原始响应字段与工具增量，客户端须等待有效终态后才执行工具。
OLC 仅提供 Responses，按可信账户材料适配 freeform 和托管 live 网页搜索；搜索可在一次外部请求内执行有界模型续答，仍须独立 Relay Key 及精确模型授权。Relay 按请求声明决定搜索，不读取 App Server 的搜索偏好；不支持的 cached/indexed 或过滤控制会拒绝，不自动降级。详见 [Relay 请求与交付链路](provider-api-relay-development.md#请求与交付链路)及 [Ollama Cloud](ollama-cloud.md)。
完整双协议、提供商接入与升级回滚合同见[转发设计与边界](provider-api-relay-development.md)。
局域网交互设置：运行 `codexc relay listen`，或进入 `codexc config` → 服务访问 → 模型转发监听，选择关闭、仅本机、局域网（0.0.0.0）或指定内网 IP。确认后自动备份、原子保存并向运行中的 Relay 确认生效，保留 Key 和现有端口。若服务未运行，会提示启动命令，不自动安装或启动。配置被其他操作修改时拒绝覆盖，请重新进入菜单。

手动设置：先备份当前实际使用的配置文件并校验备份，再在已有 `[model_relay]` 段设置 `host = "192.168.1.10"`（替换为服务器的内网地址），或 `host = "0.0.0.0"`。不要重复创建同名 TOML 段。保留现有 Key、并发及其他字段；默认端口为 4119。支持 10/8、172.16/12、192.168/16 的规范 IPv4 地址，IPv6 当前仅支持回环 `::1`。不接受域名、URL 或公网 IP 字面量。

运行中的 Relay 会刷新监听配置；配置无效或绑定失败时停止接收请求，不自动换地址。初次启用使用 `codexc relay enable`，已安装的服务使用 `codexc start relay`，通过 `codexc relay status` 确认 `configurationValid`、`enabled`、`listening` 均为 true。改变监听地址会取消旧请求，应在空闲时操作。客户端 Base URL 填 `http://192.168.1.10:4119/v1`，API Key 使用已签发的 Relay Key，模型选择该 Key 允许的 ID。

`0.0.0.0` 监听所有 IPv4 网卡，不是客户端地址，也不保证仅内网可达；自行限制防火墙来源，不做公网端口映射。HTTP 中 Key 和正文未加密，跨不可信网络使用加密隧道。此设置不开放 App Server、控制 IPC 或指标 IPC，不改变 WebUI 的监听与管理授权。

客户端可携带当前 Key 调用 `GET /v1/models` 查看获准且仍在提供商目录中的模型。WebUI 请求页面来源显示“Codex / 转发”，可按来源与真实调用方筛选；接收确认不代表指标已落盘，交付完成不证明客户端已收到。
请求列表的「转发」悬停或聚焦时显示 API Key 当前用途名称；未命名或已移除时显示记录中的 Key ID。可选调用方列保留名称与调用方 ID。完成状态不重复显示「交付：已交付」，断连和交付失败仍保留异常说明，详情与可选交付列保留交付状态。名称仅用于展示，筛选和历史指标继续使用稳定 ID，不回写历史记录。

WebUI 侧栏「模型转发」提供独立 Key 管理页。每个用途对应一把 Key，名称支持中文，内部调用方 ID 在新建时自动生成并保持不变。按提供商分组勾选一个或多个模型，可跨多个提供商，在每个所选模型旁独立选择「跟随客户端」或思考等级；只有「关闭思考…」展开第二级菜单选择参数方式。默认跟随客户端，指定等级或关闭方式会覆盖客户端参数，客户端没有思考选项时也可使用。预览和列表按模型显示；同一 Key 的不同模型、不同 Key 的同一模型均互不影响。
不知道选择哪种关闭方式时，可点击所选模型旁的「检测」，打开「对比关闭思考方式」，选择该模型支持的协议，再手动开始。每组最多顺序发送 9 次可能计费的短请求（不带思考控制的基线与八种关闭方式），使用固定文本，每次请求最多 64 个输出 Token，不自动重试。每次限时 15 秒，整组最多 135 秒；可以取消，关闭弹窗或切换模型会停止探测。界面实时显示已完成项数、当前关闭方式和逐项结果，不必等待整组结束。结果分别展示请求状态、思考正文是否返回和上游报告的推理用量，缺失用量显示未知。没有思考正文或报告零推理 Token 都不能证明内部推理关闭；参数被接受也可能被上游忽略。结果只适用于本次模型、协议和配置版本，不保证未来路由的行为。点击采用仅修改当前模型草稿，仍需预览并确认保存。

九项全部执行并完整返回的探测结果及时间保留在当前浏览器：每个模型与协议保留最近一组，最多 20 组、7 天，关闭弹窗或刷新后可继续查看，不会自动重新请求。缓存仅包含有限结果元数据，不包含密钥、提示词或回复正文，不写入服务器配置或数据库。配置版本变化后的记录只供查看，不能直接采用；取消、断连或整组提前停止的部分结果不覆盖上一次完整记录。可在探测弹窗清除本功能的缓存。浏览器拒绝存储或记录不可读取时会明确提示，本次探测仍可查看；清除缓存不会修改已保存的模型设置。
Key 列表显示原生 Chat/Responses 协议；双协议账户同时显示两者。模型选择中的文本、图片、音频标签来自现有目录，未声明时不推断能力；标签不改变上游参数处理。
账户凭据及自定义提供商地址统一在 WebUI「模型管理 → 提供商」维护；Relay 页不复制上游秘密。新建、编辑、轮换、停用和删除使用居中弹窗，先预览再确认，
完整新 Key 只显示一次，关闭后无法再次查看；响应丢失时先刷新确认记录，不能自动重复签发。
若返回 `cleanupStatus: "failed"` 或页面提示管理锁清理失败，修改已经保存；先保存新 Key，再检查数据目录权限和磁盘，不要重复签发。读取失败可直接刷新；编辑时错误及刷新入口显示在弹窗内。刷新保留草稿，但检测到版本变化会禁止保存，须明确选择“重新加载并丢弃草稿”再编辑、预览，避免覆盖其他端修改。上游能力暂不可读取时保留现有策略，可仅改名或切换到可用提供商；不会把未知状态当作模型不支持。
「查看调用」进入现有请求列表并精确筛选用途。停用后重新使用须轮换生成新秘密。

模型权限只保存在 `model_relay.callers[].models`，每把 Key 必须选择 1–256 个唯一调用 ID。提供商模型目录只读，不保存全局启用列表或思考策略；目录新增模型不会自动扩大任何 Key 的权限。旧 Relay 字段与升级、回退命令均不受支持，不做自动转换。

CLI 使用同一管理逻辑，例如：

```bash
codexc relay providers
codexc relay issue --caller translation --key translation-key --model clp-main/deepseek-v4.1-flash --reasoning off --name "沉浸式翻译"
codexc relay edit --caller translation --reasoning passthrough
```

`issue` / `edit` 可通过 `--name "中文名称"` 设置 1–64 字符的用途名称，不含控制字符或首尾空白。名称可重复、可修改，身份仍以 caller_id 区分；改名不会取消请求或更改历史指标。旧记录未设名称时显示调用方 ID。

`issue` 使用可重复的 `--model 提供商/模型ID` 选择模型；`edit --model ...` 替换该 Key 的完整授权列表，省略时保留原范围。调用 ID 使用本项目提供商前缀，CLP 对外去掉上游的 `cline-pass/`：例如 `clp-main/deepseek-v4.1-flash`，出站精确恢复目录中的 `cline-pass/deepseek-v4.1-flash`。不接受无提供商前缀的名称、不猜测上游 ID；映射重名时拒绝调用。Key 可以同时授权 Chat 和 Responses 提供商，请使用各自支持的原生端点。

`codexc relay delete --caller ID` 删除调用方并撤销 Key，取消其旧请求；历史指标和转储不删除。WebUI 的“删除”先预览再确认。改绑或删除会保留仅用于旧调用指标结算的历史身份摘要，不含秘密，不能用于请求鉴权；删除后新建必须使用新的 callerId 和 keyId。不删除上游账户或凭据。摘要最多 4096 条，同时受配置文件 1 MiB 限制；达到上限时拒绝整次操作，不静默清除历史摘要。

CLP 转发与渠道共用受管模型目录，不再下载或更新独立 Cline 模型文件。在 WebUI「模型转发 → 提供商模型」点击提供商行的“模型列表”，只读查看调用模型 ID、目录声明的输入格式及协议；新增、模板更新和移除在模型配置中完成，模型授权和思考策略仍在 Key 编辑弹窗中单独设置。已有上游账户密钥继续复用，无须申请新 Key；新增目录条目不会自动扩大 Key 权限。旧独立目录文件不自动修改或删除。见[转发模型目录与设置](provider-api-relay-development.md#clp-转发模型目录与设置)。

既有配置或 CLI 的 `off` 显示为“关闭 · 旧自动映射”，WebUI 不再提供这一新选择，也不自动改写已有值。它支持目录显式声明 `none` 的 CLP 模型、CLP 的精确模型 `cline-pass/deepseek-v4.1-flash`，以及 DS 的 `deepseek-flash` / `deepseek-v4-pro`，只对当前请求中明确支持的模型生效。未声明或不支持关闭的模型继续使用客户端原参数，仍可能产生思考内容；可在模型旁改选明确的关闭参数方式。
关闭策略覆盖顶层思考控制参数，通用 CLP Chat 实际出站为 `reasoning.enabled=false`；CLP 保存为 `deepseek-flash` 请求配置的模型使用 `reasoning.effort=none`，未保存配置的旧精确模型 `cline-pass/deepseek-v4.1-flash` 保留同一默认行为。DS Responses 使用 `reasoning.effort=none`，DS Chat 使用 `reasoning_effort=none`；不改历史消息或隐藏上游思考响应。
嵌套 `extra_body` / `extraBody` 的思考控制字段与关闭策略冲突时明确拒绝；跟随客户端不增加此限制。
Chat 和 Responses 的冲突错误均定位到完整字段路径，例如 `extra_body.reasoning`。
显式关闭方式包括 `reasoning.effort=none`、`reasoning.enabled=false`、`reasoning_effort=none`、`thinking.type=disabled` 和 `enable_thinking=false`，受管和自定义提供商都可选择。它们只指定出站参数，上游可能拒绝或继续内部推理，不保证零推理 Token。完整配置值、协议等级映射和回退步骤见[逐模型思考设置](provider-api-relay-development.md)。CLI 使用 `--model-reasoning` JSON 对象提交完整模型映射，与旧 `--reasoning` 互斥。
修改 Key 模型授权或思考策略会取消该 Key 的旧请求。配置保存与运行态应用分开报告，不会自动启动服务。

Relay 的 Chat 请求保留模型参数、消息内容和扩展字段，由所选上游判断是否支持；远程图片 URL
也由上游处理，Relay 不主动抓取。仅本地模型授权、JSON 对象/消息结构、stream 布尔、单选择
n=1 和请求大小等边界由 Relay 校验；Chat 消息和 Responses 输入项不设条数上限，仍受 1 MiB 请求正文预算限制；省略 stream 时默认 JSON。请求参数不能改变本机账户、
凭据或上游地址。参数透传不代表当前模型支持所有能力，响应仍遵循已记录的单选择 JSON/SSE 合同。

Relay 保留普通应用请求头（例如 User-Agent、HTTP-Referer、X-Title），入口密钥不会转发给上游。
上游 Authorization 和传输头由 Relay 控制；Cookie、代理凭据、转发来源与内部身份头剔除。

在 WebUI“请求明细”点击唯一的“查看调用详情”：已采集报文直接打开现有转储视图；未关联时仅显示“未关联”，不提供详情链接。Relay 没有 Codex 会话或轮次，HTTP 200 不等于客户端交付成功。出站 User-Agent 只记录新调用实际发送的值，缺失时不推断客户端类型。

Codex 和 Relay 共用 `[debug].model_traffic_dump`，默认关闭。在 WebUI 的 Gateway 系统设置或 `codexc config → 调用记录` 中控制采集，并用“调用记录预设”选择生产或调试；不再单独按 Key 开启。这里的预设只控制模型调用采集，与后台日志等级、开发运行方式及渠道消息显示设置分别管理。只记录启用后实际出站的调用，不补录历史。

只接受当前全局采集配置，未知字段明确拒绝；不提供旧采集配置转换命令。

预设复用已有裁剪参数：只有 `model_traffic_input_items = 3`、`model_traffic_item_max_bytes = 65536` 时显示生产预设，只有 `0/0` 时显示调试预设，其余合法组合（包括单项为 0）显示自定义，并展示实际输入项数与单项字节数。自定义裁剪值继续在 TOML 中管理；读取或取消不会改写，明确选择生产或调试预设才会覆盖这两项值。CLI 在自定义状态默认选择返回；WebUI 的自定义项仅供显示，不是可保存的预设。配置总览与管理读取使用同一分类。Codex 沿用现有精简/完整转储；Relay 仅在两项都为 0 时增加入站、交付及实际处理记录，其余组合继续记录出站请求与上游响应。调试没有 Key 限定或自动到期；排查完可手动恢复生产或关闭采集。Codex 更改在重启 App Server 后生效，运行中的 Relay 在配置刷新后用于新请求；已开始采集的请求按开始时的设置完成。重复应用已有预设不写入，也不要求重启。

Codex/Relay 在生产和调试模式均保留普通请求/响应头及关联 ID，不按未知字段或诊断格式隐藏。仅遮蔽凭据类头、明显的 Bearer/Basic/Digest 值、URL 用户信息与敏感查询参数/片段、CSP nonce；未知业务头原样记录，可能包含用户业务信息，转储仅用于本机排查。模式仅影响正文裁剪及采集阶段，不决定普通头可见性。新规则只影响后续采集，旧记录无法还原已遮蔽值。Relay 每个头值最多 1 KiB，全部头最多 16 KiB；Codex 保持既有头容量；超限与正文截断明确标记。Relay 调试模式每侧请求最多 512 KiB、每侧响应最多 4 MiB，合计仍为 1 MiB/8 MiB；不是网络抓包。交付完成表示本地 HTTP 写入完成，不等于客户端已处理。鉴权/准入失败且未实际出站的请求不新增调用转储或指标。

Relay 生产记录脱敏后的出站 Chat/Responses 参数、输入和上游 JSON/SSE；请求与响应头遵循上述必要脱敏规则。翻译原文、回答及自由文本内的秘密仍会保存。请求正文最多 1 MiB、响应 8 MiB；Relay 共用 512 MiB 磁盘和 16 MiB 待写预算。保留天数统一使用 `[debug].model_traffic_retention_days`，默认 30 天，0 关闭按时间清理但保留 Relay 容量上限。每批次已接受的 manifest、索引、trace 与正文合计达到 8 MiB 或满 24 小时后，新调用进入新批次；在途调用始终在原批次完成，后续写入可使原批次超过轮转目标。既有历史批次不改写、不迁移；未来批次仍按既有规则整批清理。首次启用在后台进行带取消与超时边界的异步容量初始化；模型请求不等待磁盘，初始化期间跳过转储并记录 initializing/capture skipped。ready 后仅采集新请求，不补录已跳过的请求。随后按实际已写及待写字节记账，并为在途调用预留空间。后台清理保护活动批次及扫描期间新建批次，整理期间继续采集；容量不足时先在后台退休空闲批次，等已接受写入与文件关闭完成后再清理，模型请求仍可暂时跳过采集。容量不足、写入故障或超限会留下日志或截断标记。写入故障会停止本进程后续采集，排除故障并重启 Relay 后恢复，模型转发继续。

自动转储维护与 CLI/WebUI 读取共用严格 manifest 识别，删除前复核私有根、目标目录和 manifest 身份；
未知版本、缺少 manifest 的材料不自动清理。已存在但不合规的 manifest 或路径校验失败会中止本轮维护，
保留尚未删除的材料并记录固定故障；Relay 采集可能因此进入失败状态，模型转发仍继续。代码回退不能恢复
已经合法清理的转储；启用维护前应按需备份希望长期保留的材料，不通过修改未知文件或权限来绕过拒绝。

停止采集不删除已有文件。指标库运行时只接受当前 Schema；`codexc update` 仅支持备份后将已知 v31/v32/v33/v34 升至 v35，不提供运行时回退。不要恢复旧配置覆盖当前凭据。

模型转发管理页显示配置并发上限及运行状态，点击“刷新”更新服务状态，左侧“模型转发”下的二级菜单“请求队列”独立展示当前请求及执行阶段。配置上限不代表运行进程已应用；服务停止或状态无法确认时，不显示虚假的零队列。

Relay 支持 JSON 非流式调用，不要求客户端启用流式。失败响应提供 `code`、`phase`、
`request_id` 和已知的 `upstream_status`；除带安全 `param` 的入口字段错误外，`message` 也包含这些定位信息。
`X-Relay-Request-Id` 可与指标记录关联。`invalid_upstream_*` 表示上游响应类型或字段校验失败；
例如上游 HTTP 200 配合 `invalid_upstream_tools` 表示工具响应字段校验未通过，并非上游返回了 502。
Chat 和 Responses 的 JSON/SSE 内容无法解析为 JSON 时统一返回 `invalid_upstream_json`，不回显上游原文。
上游成功响应的媒体类型须匹配请求的 JSON/SSE 格式；Relay 请求 `identity` 编码，不支持的响应压缩编码返回 `invalid_upstream_encoding`。
本地模型请求超时额外提供 `timeout_stage`：`upload`（408 `upload_timeout`）、`prepare`（504 `preparation_timeout`）、`headers/body/stream`（504 `upstream_timeout`）、`delivery/terminal`（504 `delivery_timeout`）。流式响应已发送响应头时保留原 HTTP 状态，通过流内错误或断连表示失败；排队超时仍按下文的 429 合同处理。
WebUI 请求列表的失败状态提示可查看错误码；诊断不包含请求内容、密钥或上游错误原文。
上游 429/503 提供的 `Retry-After` 在为受限整数秒或规范 HTTP 日期时会保留，客户端可据此退避；Relay 不自动重试。
Relay 的上游 HTTP 429、503、504 分别返回同一状态，408 映射为 504；其他上游 HTTP 错误返回 502，并保留 `upstream_status` 与受控错误码。上游认证失败不表示调用方 Relay Key 无效。HTTP 状态决定错误类别和重试性质，错误正文不能把认证失败改成可重试的服务错误。
需要解析的 JSON/SSE 正文严格校验 UTF-8，非法或截断编码明确失败，不以替换字符继续转换。已记录的失败原因不会被后续断连清理覆盖。启用流量转储时，已记录的本地超时阶段可在调用详情查看；指标数据库仍保留原有 `http/stream` 阶段，未采集的历史细节不推断、不回填。
Relay 指标与新转储共用同一次最终结果判定；上游拒绝不会在转储中被误记为生成未完整完成。列表和调用详情分别展示生成结果与交付结果：模型已完成但客户端断开或交付失败时，保留生成完成并提示交付未完成。详情主提示优先采用本地受控错误分类，再采用实际 HTTP 状态；上游原始错误及内部原因只作为补充证据，不能覆盖主分类。已有历史记录不改写。
Chat 的长度限制、内容过滤、`insufficient_system_resource` 和 `aborted` 终态原样交付，指标与新转储记为未完整完成。
工具参数字符串原样保留，客户端须在执行工具前验证 JSON 与参数含义；Relay 不执行工具或补齐参数。
Chat 与 Responses 的非流式首内容耗时在整包解析校验后观测，不是上游实际生成首 Token 的时间；空内容不填此值。

Relay 返回 403 `model_not_allowed` 时，请使用当前 Key 的 `GET /v1/models` 返回的精确模型 ID，
包括提供商前缀。模型必须同时位于 Key 授权列表和 Provider 的有效模型目录中；此类拒绝发生在出站前，
不会新增上游调用指标，也不表示 CLP 返回了 403。

Relay 的 JSON 非流式响应同时接受标准 Chat 对象和 CLP 的 `{success:true,data:...}` 包装；
客户端收到的仍是标准 Chat 响应。包装失败或内部响应不合法时返回明确错误，不当作成功生成。

Relay 只执行全局限流，不与本机 App Server 的代理共用计数。`[model_relay]` 的
`max_concurrency` 可设为 1–32，默认 10；`requests_per_minute` 可设为 0–600，默认 0
（关闭分钟与突发限制）；`burst` 为 1–32，默认 10，仅在分钟速率为正数时生效。
提供商提供只读模型目录，Key 管理身份及跨提供商的模型授权；提供商和 Key 均不单独设置执行限额。鉴权失败保护始终保留。

Chat 与 Responses 请求在全局并发或令牌不足时排队：上传和等待合计最多 32 个，正文预算合计 16 MiB。
上传前每个请求先预留 1 MiB，正文验证后按原始请求正文的实际字节释放多余预算；单请求原始正文
及处理后序列化的出站正文均不超过 1 MiB。计数和字节预算任一达到上限都会拒绝，所以不能保证同时接受
32 个大请求。上传限时 15 秒，正文验证后的等待最长 30 秒；准备阶段最多 30 秒。
Relay 与 App Server 模型代理共用阶段策略：上游首响应头等待和完整 SSE 数据事件空闲均为 300 秒，非流式 JSON 完整读取最多 300 秒，错误正文最多 5 秒。生成没有固定总期限，持续输出可超过 300/600 秒；注释心跳和不完整字节不延长完整事件等待。下游交付受阻最多 30 秒，终态与失败交付最多 5 秒；更新程序后需重启独立 Relay 生效。
同一 Key 先入先出，不同 Key 轮转；没有每 Key 数量上限。`GET /v1/models` 不排队，仍受全局限额。

队列满返回 HTTP 429 `relay_queue_full`，等待超时返回 HTTP 429 `relay_queue_timeout`，
并带 `upstream_attempted:false`；未出站的拒绝、超时和撤销不会进入模型调用指标。
客户端断开、Key 撤销或 Relay 关闭时取消等待，不自动重试；队列仅在内存中，重启不恢复。
`codexc relay status` 返回执行数 `active` 及 `queue.pending`（上传与等待）、`queue.waiting`
（已验证正文的等待）、`queue.bytes`（正文预留预算），不包含请求正文。WebUI 左侧“模型转发”下的“请求队列”可查看实时阶段与等待情况，详见[WebUI](webui.md)。

Relay 只支持当前严格配置，不接受旧账户模型列表、Key 单提供商字段、分层限流或独立采集字段。控制 IPC 为 v6，更新后需重启相关进程；新旧进程混用时确认结果为 `unconfirmed`，不能据此认定撤销已生效。配置备份不得覆盖当前凭据和撤销记录。

### 渠道文本附件

飞书、微信、Telegram 的独立文本文件输入上限为 1,000,000 字节，要求有效 UTF-8；
网关自动清理常见终端转义序列，不按文件后缀判断文本内容。清理后不超过 32 KiB 的正文直接提交；
较大文本保存到网关数据目录的私有 uploads 子目录，由同机 Codex 工具按路径搜索、分段读取，
不把全文放入当前输入。读取仍受当前权限约束，网关不会自动扩权。

暂存文件随机命名，保留 24 小时；每个渠道暂存目录最多 50 个文件、50,000,000 字节。
运行时每分钟清理过期文件，重启时也清理；停止期间文件保留至下次启动清理。
附件不是永久会话历史，过期后需重新发送。更换执行机器不会自动复制附件。
飞书的 UTF-8 文本附件通过独立文件消息接收，大小上限为 1,000,000 字节。富文本中的 `media` 是视频标签，单条支持一个视频与说明文字，经视频 MCP 分析，适用 64 MiB 视频上限；多个不同视频或视频混合独立图片的富文本消息会被拒绝，请拆开发送。视频封面不作为独立图片处理。
PDF、Office 和压缩包不在文本解析范围内。
