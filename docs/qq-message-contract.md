# QQ 消息开发流程与合同（待实施）

本合同确定 QQ 消息层重做的边界与交付语义，尚未实现。当前基础接入仍为 `connectionOnly`，
不提交任务、不回复、不恢复旧 QQ 绑定。本次整理不改变正在部署的基础接入代码。
代码审查基线为 `0d9b4ba5`。本文中的“必须”“第一版”均为后续实施要求，不表示当前已支持。
阶段推进以本文件的开放门槛为准；仅连接成功不能解锁任务执行、历史恢复或计划任务。

## 当前状态与首版范围

- 已实现：配置/扫码、渠道注册、允许名单、Token 与 WebSocket 基础连接；真实账号保存及就绪证据见
  [基础接入观察记录](../src/surfaces/qq/README.md#基础接入观察记录)。长时间心跳、断线恢复和其他系统部署尚未观察。
- 首个生产版本目标：允许名单内的普通单聊文字、明确列出的必要文字命令，以及完整纯文本 Item 交付。
  命令表必须在开放前确定，至少覆盖帮助、状态、停止和预配置 Workspace 选择；其他命令明确拒绝，不能落入普通任务。
- 首版交互选择：保留共享安全决定，审批拒绝、用户输入返回空答案、MCP elicitation 取消；不提供可批准按钮或回应令牌。
  在原任务授权仍有效时给出受控的交互不可用提示；是否停止 Turn 以 App Server 实际事件为准，不声称取消交互等于停止任务。
- 首版不开放：附件输入、引用输入、群聊、计划任务、历史任务补发、Markdown、流式和主动唤醒。
  长结果超过完整文字预算时保留权威结果并明确交付失败，不以截断结果替代成功。
- 主动发送权限未确认时，只允许明确授权的短文本协议观察，不开放 Codex 长任务。

## 平台合同与未澄清部分

| 边界 | 官方证据 | 本项目处理 |
| --- | --- | --- |
| 普通单聊发送 | `POST /v2/users/{user_openid}/messages`；类型 0 文本、2 Markdown、6 输入状态、7 富媒体 | 每次请求仅一种正文表示；不同时填文本与 Markdown |
| 被动回复次数 | 每条来信最多回复四次；`msg_id + msg_seq` 重复会被拒绝 | 同一原来信统一计次，不能按 Turn、Item 或消息别名重新获得四次 |
| 被动窗口 | 页面概述和总览为 60 分钟，但同页 `msg_id` 字段为 5 分钟 | 未澄清前按 **5 分钟本地保守期限**；明确不是已证明的平台真实上限 |
| 主动普通消息 | 不带被动来源；用户可关闭主动接收；另有权限与频控拒绝 | 与被动回复分开规划；平台可发送不等于业务已授权 |
| 普通消息接口频率 | 总接口 100 QPS；主动另受下面的账号/用户限额 | 多个限制同时满足，不能只检查最宽松的一项 |
| 主动账号限额 | 企业/个人认证 10 QPS；未认证 5 QPS 且 30 QPM | 未证明认证状态时使用较保守档位；不得通过失败试探后自动提高 |
| 主动用户限额 | 20 QPM，1000 条/用户/日 | 所有主动正文、附件、交互与状态共用额度；“日”的重置时区/算法未定义 |
| 正文长度 | 发送字段无明确数值或计量单位；错误包含 `40054007`、`40054018` | 长度上限与字符算法 **待实机确认**；不得声称任意固定字节数保证可发送 |
| Markdown | 单聊自定义 Markdown 已开放；列出标题、样式、链接、图片、列表、引用和分隔线 | 不推定为完整 CommonMark/GFM；代码块、行内代码、表格及转义行为没有充分合同保证 |
| 流式 | 独立接口 50 QPS；支持 `append`、`replace`，返回流 ID | 不从普通发送能力推定原生流已可用 |
| 上传 | 上传返回 `file_info` 和时效，再调用消息接口 | 上传成功不是附件消息送达；固定不使用上传自动发送 |

四次是被动回复次数，不是主动消息通用分片上限。旧分支的每片 3000 UTF-8 字节、
每结果 12000 字节、最多四片、每流 128 帧及 1 MB 文本文件等均为旧实现预算，**本合同不将其继承为平台限制**。
平台“字符”、JavaScript UTF-16 长度、Unicode 码点、用户可见字素及 UTF-8 字节必须分别记录，不能互相替代。

## 输入、身份与授权

首个生产版本只开放已允许用户的单聊普通文字：`C2C_MESSAGE_CREATE`、`message_type=0`、
`message_scene.source=default`，不夹带附件、卡片或引用内容。未知/不支持结构不得把其 `content` 当普通任务继续处理。
后续引用和附件单独扩展；引用正文只作为外部上下文，不作为当前命令或授权。

入站去重采用账号、Actor、事件 `d.id` 与 `message_scene.ext` 的唯一 `msg_idx`。
事件说明同时提到 `msg_seq`，但消息结构未给入站该字段，详细说明与示例提供的是 `msg_idx`；
因此不借用出站序号，也不默认补零。缺少/重复索引暂时拒绝，并记录受控原因，待真实事件核对。
出站 `msg_seq` 是原来信的回复序号，必须和入站消息索引分开。

每次调用 Application 之前复核账号、允许名单与预配置 Workspace；不接受任意目录。
Task 来源在提交前捕获，Thread/Turn 由权威提交响应或可证明属于该提交的生命周期关联确认，不能用“当前最新 Turn”补全归属。
发送前和每次排队/Token/上传等待后重新检查原目标、Actor、任务来源、授权及取消。
新来信不延长旧任务来源，不转移其被动次数，不授权跨账号/目标补发。
重启后不自动重建旧任务发送授权；首版按下述恢复合同隔离旧输出，不能重放未知结果。

### 接收、去重与提交状态

QQ Transport 的接收序号只用于连接 Resume，不证明 Application 已提交任务。
当前 Transport 串行等待 Dispatch 回调，最多容纳 32 个待处理事件；接入业务时必须明确有界准入和关闭责任，
不能在回调中等待完整 Turn 或平台回复，也不能无限堆积等待任务的消息正文。
需要为下一 Turn 排队时使用 App Server Queue；首版不新增 Gateway 正文队列，也不隐式开放 Queue 命令。

| 入站状态 | 重复来信处理 | 允许的后续行为 |
| --- | --- | --- |
| 校验/授权失败 | 不进入任务去重准入，不调用 Application | 仅受控诊断；不向未授权用户发送错误 |
| 已原子占用去重键、准备或提交中 | 合并为同一次处理，不再次调用 | 在现有作用域内等待，禁止并发重复提交 |
| 已确认提交 | 不再提交 | 保存最小关联元数据，不保存第二份消息历史 |
| 确定尚未提交 | 不自动重试该事件 | 结束本次处理；用户可发一条新的请求 |
| RPC 可能已发出但确认未知 | 不释放为可重试输入，不猜 Turn ID | 保留未知标记，核对权威状态；不自动重启任务 |

去重占用必须早于任何异步准备；容量不足时拒绝新准入，不淘汰处理中/未知项后接受重复请求。
容量、保留期限、过期事件拒绝规则及重启去重语义是阶段 0 的必填参数；未经明确设计不得声称跨重启恰好执行一次。
若使用持久去重，只保存必要身份与状态，并先完成数据格式、备份和回退设计，不复用旧 QQ Ledger。
不支持的结构与重复 `msg_idx` 字段分别处理，不能把畸形索引当成正常重复事件。

### 来源与 start/steer 关联

来源最少绑定账号、Actor、Conversation、原来信 ID/索引/时间、捕获的 Workspace ID/目录、发送模式、
本次运行授权代次及取消范围。被动窗口依据原事件时间保守计算，重复投递不能刷新期限；时间缺失、异常未来时间
或无法建立可信期限时不授予被动发送资格。等待使用单调时间预算，系统时钟跳变不能延长已确定期限。

当前 Application `submit()` 会新建 Turn 或 steer 当前 Turn，返回 `{ threadId, turnId, steered }`；
响应前也可能已经到达输出。实现必须在提交前登记临时来源，并在共享提交边界取得可关联身份；
早到输出只允许有界等待关联确认，不能借用同会话最近来信。无法关联则保留待核对或失败，不发送。
当前普通提交端口尚未暴露完整的来源关联/可能已提交状态；阶段 0 必须选定最小共享接口调整及所有调用方的保持行为，
不能把仅供附件的提交作用域强行当作普通文字合同，也不能往 Core 塞入 QQ SDK 或凭据。

同一 Turn 的 steer 来信有自己的去重和即时响应来源；不得替换该 Turn 已确认的结果发送授权、期限或被动额度。
首版没有本次运行已确认发送授权的活动 Turn，不接受通过新来信 steer 来为旧任务补授权；不得自动中断或转移该 Turn。
新来信属于新 Turn 时，建立独立关联。Thread 切换、Workspace 变化、账号变化和撤权均使不再匹配的待发送计划失效。
`/stop` 必须能绕过普通输入等待取消本地准备，并通过共享用例中断精确原 Turn；确认只描述已观察到的结果。

## 发送模式与内容角色

| 内容角色 | 约定模式 | 理由与降级边界 |
| --- | --- | --- |
| 当前 `/help`、状态查询、停止确认等即时响应 | 原来信的被动回复 | 在原窗口及剩余次数内发送，原来源失效则失败，不借用后来的消息 |
| Codex 普通任务的最终正文 | 原任务授权下的主动普通消息 | 长任务不能依赖有歧义的短回复窗口；实际账号主动发送能力必须先验收 |
| 错误、审批与问题 | 明确属于当前来信或原任务的相同模式 | 不建立隐式全局发送授权；审批未完整展示或来源无效就安全取消 |
| 过程、思考、计划、工具成功通知 | 首个生产版本不发 | 不让过程消息消耗正式结果预算；后续由统一投递策略决定，而非每个事件自行发送 |

模式由来源和内容角色在规划前确定。主动拒收/无权限不能通过切到被动、换 `msg_id` 或 `is_wakeup` 绕过；
被动超时也不自动升为主动。互动召回是单独能力，本轮不开放。
若主动权限尚未验收，可以先做明确标识的短被动回复验收，但不能将它宣称为完整的 Codex 长任务交付。

正文只消费权威 `text.completed`，保持 `target/Thread/Turn/Item` 身份；`text.delta` 不承担最终确认。
`turn.completed` 是任务终态，不代替正文送达。没有正文的失败/取消也应有明确状态，不能凭空生成成功结果。

| `text.completed.phase` | 首版处理 | 完成语义 |
| --- | --- | --- |
| `commentary` | 不发送，不纳入 QQ 正式正文持久投递 | 不能证明回答完成 |
| `partial_answer` | 按独立回答 Item 完整交付，计入同 Turn 总预算 | Item 已完成，不表示 Turn 或最终回答已完成 |
| `final_answer` | 按独立回答 Item 完整交付 | 正文片全部确认才算该 Item 交付完成 |
| `null` / 缺失 | 保留完整 Item，不因阶段未知丢弃正文 | 不根据阶段猜任务终态，沿用 Core 权威生命周期 |

此处保留 `partial_answer` 是本项目的正文策略，不把它归为思考/过程通知。
多个 Item 分别计身份和交付状态；不能只保留最后一个，也不能用一个 Item 成功确认整个 Turn。
Turn 终态提示必须与正文交付状态分开：结果缺失、部分交付或未知时不能展示“结果已完整送达”。
QQ 事件白名单必须同时用于 `delivery-policy.ts`、`persistent-output.ts`、Surface 的 `retains/handle/deliver`，
明确处理关键失败与交互不可用提示；不得在入箱后静默忽略事件再返回成功。

## 渲染与完整结果规划

1. **第一版正文使用普通文本。** 原始内容和顺序保留，不删除代码围栏、链接目的地址或缩进来假装获得“更短纯文本”。
2. 命令面板从共享结构化结果生成可读文字，动态字段按字面处理，不把整个命令字符串重新解析成模型 Markdown。
3. Markdown 在后续阶段作为受控表示加入。平台专用交互标签只由受信交互构造器产生；模型输出不能生成点击授权、命令或任意媒体下载请求。
4. 每个完整 Item 在首个请求前一次决定表示和完整交付方案。不得仅因某个字段或某片的格式不支持，就在已发送的多片中反复切换 Markdown/文本/文件。
5. 分片按最终请求正文计量，优先段落、换行、词边界，硬分割不得切断 Unicode；图片 Base64、JSON 外壳等预算独立核算。
6. 先计算全部片数、剩余额度、时限和附件可用性，再产生第一个外部副作用。被动计划超过剩余次数时不发送一个注定不完整的前缀。
7. 超出完整文字预算后，可规划完整 UTF-8 文件；文件内容来自完整原文，不能从已渲染或截断的预览回构。附件未实现时明确报无法完整交付，保留结果，不把截断正文确认成成功。
8. 确认预览和审批不自动改成附件。展示必须完整、授权范围无歧义，且全部提示确认后才开放一次性回应。

**本地资源数值尚未冻结。** 下一实现阶段应根据真实长度边界确定文字软上限、单结果主动片数上限、完整文件上限和发送总预算，
在模块中作为有名称、有单位的独立策略维护；不新增让用户猜测平台常量的配置项。
未验收前只允许有界短文本试运行，不能通过逐次增大/缩小并重复发送用户正文来自动探测限额。
每日限额如采用滚动 24 小时计数，必须标注为本地保守算法，不称为平台日重置语义。
普通请求预算与共享 Coordinator 默认 60 秒投递期限必须协调；不能让排队或限流等待跨越外层取消后继续发出。
原来信次数、账号/接收方额度及同 Turn 本地预算由唯一调度所有者原子预留，正文、命令和错误提示不能各算一份。
明确未发出的预留可释放；已经发出但结果未知时不得按“失败”退回额度或复用序号。
阶段 0 记录各项预算的单位、作用域、时钟、容量耗尽行为；阶段 1 仅用合成样例观察，不重复发送用户正文探测边界。

## 发送、失败与确认

| 结果 | 处理 |
| --- | --- |
| 请求尚未发出：取消、授权失效、额度不足 | 停止该计划；记录未发出，不声称已送达 |
| 合法成功响应及消息 ID，且本地检查点已确认 | 仅确认对应片；全部内容或完整附件确认后才能确认完整结果；不声称客户端已读 |
| 明确业务拒绝 | 按权限、拒收、过期、次数、频率、长度、格式等分类；保留受控码，不把未知上游正文发给用户 |
| 超时、断线、畸形响应、响应与错误码矛盾 | 结果未知；停止后续片，不自动重发或换格式/来源 |
| 前片成功、后片失败 | 标为部分交付并保留完整结果；不得重发整条造成重复，也不得因前片成功而确认全文 |
| 平台成功、本地确认写入失败 | 保留未知边界，不把网络和数据库误当原子事务 |

长度拒绝 `40054007/40054018` 不证明某个数值阈值；格式拒绝 `40034011/40034124` 不等于网络失败。
权限/拒收/无好友关系、被动过期和次数超限不自动重试。频率拒绝如需重试，必须明确证明本次未发送，
有界等待并重新核对原授权/期限；不能盲目套用通用 HTTP 重试。
明确格式拒绝的整条重规划只可发生在尚无任何正文片确认、无在途未知请求的情况下；禁止逐片自动降级。

正式结果复用共享 Delivery 和 `DeliveryReceipt`/`checkpointDelivery`，由 Bootstrap 保持唯一所有权；
Surface 不能维护完整第二份会话历史。传输去重、次数和授权元数据如需持久化，应单独先给出数据合同及恢复/回滚方案，
不得在 StateStore 中写正文，亦不得静默复用或迁移旧 QQ Ledger。
同会话输出有序，不阻塞 App Server Reader；审批/关键失败不能被过程消息挤掉。
外部请求总时限覆盖 Token、限流、上传及真正发送；取消后未发出的步骤不再启动，已发出的不假装撤回。

### 回执适配与检查点

QQ 普通发送响应使用 `id`。协议客户端先验证 HTTP/业务结果一致、成功字段类型与非空 ID，再返回共享可消费的
`messageId` 或 ID 字符串；当前 `checkpointDelivery` 不识别原始 `{ id }`，不能直接传递 QQ 原始响应。
响应缺少合法 ID、返回矛盾字段或无法解析时按结果未知处理，不能因为 HTTP 200 写入 confirmed。

每个完整计划有稳定身份，各片有稳定次序与操作标识，明确关联原 Item、来源和实际表示。
所有异步发送工作必须纳入 Receipt 的 retain/release 和取消范围；首片成功不满足全计划确认。
任何内容省略必须标记不完整，只有完整原文的已确认交付才能解除；不把“曾有一条 confirmed”当作全文成功。
上传与发消息分别核对，上传成功不能满足正文送达条件。

### 恢复与人工操作

首版保留失败结果供核对，但不恢复上一进程的 QQ 发送授权。共享 `outputIdentity/outputAuthorized` 只核对
绑定、Actor、Workspace、Provider 等身份，不能单独证明 QQ 原来信和任务发送资格；QQ 来源校验必须与它共同生效。
运行代次只用于区分授权存续，不进入日志作为用户凭据，不因相同 Actor 再次来信重建旧资格。

| 持久记录/操作 | 首版合同 |
| --- | --- |
| 本次运行、来源有效的新输出 | 通过共享身份和 QQ 来源双重检查后才可发送 |
| 重启后的旧 pending / blocked | 保留供核对，禁止自动发送；失效授权不得由恢复绑定推导回来 |
| sending 恢复、部分发送、结果未知 | 保留未知边界与已有检查点，禁止自动续发或重发全文 |
| 管理端 retry | 首版拒绝 QQ 旧授权/部分/未知记录的重试；不能先清空进度再校验 |
| 管理端 ignore | 仅在现有显式管理授权下解除对应记录，不宣称平台已送达，不清理其他数据 |

当前共享重试会将记录置为 pending 并清空进度，不能直接继承为 QQ 的安全续传。
限制必须覆盖 CLI、WebUI/API 与控制服务实际写边界，不只隐藏按钮；已有其他渠道行为保持不变。
阶段 0 选择与现有投递箱一致的最小持久元数据方案，说明旧记录识别、数据版本、容量及失败恢复。
不新增正文历史库，不静默迁移；需要改变用户数据格式时先准备备份/恢复/回退方案并按已有授权范围处理。
旧授权或未知结果可以沿共享的保留核对策略释放顺序屏障，但不释放记录占用的存储额度、不授予发送权限；
新任务仍受账号/全局容量准入约束。正文读取由现有投递箱管理入口或 App Server 权威历史负责，不复制到 StateStore。
共享投递箱当前单记录上限为 4 MiB（含载荷开销）；超过准入容量的结果不能宣称已保存在投递箱。
此时只报告实际入箱失败，并指向仍由 App Server 管理的原 Thread；不得另建正文缓存绕过容量，
也不承诺权威历史中尚未核实的内容一定可恢复。

## 流式是后续独立能力

平台 `replace` 表示当前完整正文，且须保留平台已经下发的前缀；不是发送下一段增量。
`append` 才表示追加输入。首帧取得服务端流 ID，后续沿用该 ID，索引从零递增，结束状态为 10。
流式不得共用普通多片文字的计数与长度假设；需要单独核对每帧计次、主动流权限、Unicode 单位和终态确认。
`remain_msg_len` 文档只定义为剩余字符数，未定义零值等于结束；不能据此自动清空、结束或重建流。
未来若支持预览，预览与完整结果必须分别记账；退出流式不能先发送空 replace 清空已显示的内容。
本轮不选择 append/replace 的实现，也不移入旧流式状态机。

### 失败场景与证据要求

| 场景 | 必须观察或证明的行为 |
| --- | --- |
| 相同事件并发/重推、容量耗尽 | 原子准入最多产生一次提交；处理中项不被淘汰；过载明确拒绝 |
| 输出早于响应、迟到响应、start/steer | 输出只归原已确认来源；未知请求不重复提交；补充输入不覆盖旧 Turn 发送授权 |
| 撤权、Workspace 切换、停止、关闭 | 等待后复核原作用域；未发操作停止；已发结果照实结算，不伪造回滚 |
| 长结果、多个 Item、未知 phase | 不截断确认；每个应发送 Item 独立核对，同 Turn 共享预算；过程文本不混入正式结果 |
| 第一片成功后失败/超时 | 记录部分或未知，停后续片，完整结果可核对；不自动整条重发 |
| 平台成功后检查点失败 | 不宣称可靠完成，不重复发送；存储不可用时不能继续无保护准入 |
| 重启、旧绑定、旧投递、管理 retry | 不恢复旧发送资格，保留核对记录；拒绝操作不擦除进度，新任务不借用旧授权 |
| 审批/问题到达、投递屏障等待 | 首版返回类型匹配的安全决定并受控提示；不开放回应、不扩大权限、不把取消问题称为任务完成 |
| Token/限流等待、被动期限、重复来信 | 外层总期限生效，等待不刷新窗口；配额原子预留，未知结果不返还为可重用额度 |
| 不支持输入、命令或账号能力 | 不调用任务能力、不隐式降级或切换来源；主动权限不足不开放长任务 |
