本合同确定 QQ 消息层重做的边界与交付语义。第一层纯解析和单片文字协议已进入源码实现，尚未接线或实机验证。
当前基础接入仍为 `connectionOnly`，不提交任务、不回复、不恢复旧 QQ 绑定；源码实现不改变已部署的基础接入行为。
生产代码审查基线为 `0d9b4ba5`，文档基线为 `14b5c6b4`，补充采用文末的有界探测证据。本文中的“必须”“第一版”均为后续实施要求，不表示当前已支持。
阶段推进以本文件的开放门槛为准；仅连接成功不能解锁任务执行、历史恢复或计划任务。

## 第一层源码实现状态

用户在阶段 0 续查后授权开始第一层实现，继续要求不再探测、不启用正式 QQ、不自动提交。
本层入口通过 `src/surfaces/qq/index.ts`（或 Surface 公共懒加载入口）公开，尚无业务调用方：

| 入口 | 已写入源码的边界 | 仍不承担的职责 |
| --- | --- | --- |
| `parseQqTextEvent(unknown)` | 完整 Dispatch 中仅解析普通默认场景单聊；supported 返回 id/actorId/content/msgIdx/sentAtMs；ignored 仅非目标事件；rejected 只含固定 category/field/reason，不回显原事件 | 允许名单、Workspace、去重、新鲜度、任务提交与正文存储 |
| `QqProtocolClient.sendText` | 显式 active/passive 单片请求；2000 UTF-8 字节本地上限；被动序号 1–4、原时间起 300 秒的保守窗口；成功转换为 messageId | 分片规划、计次/频控、任务来源创建、Delivery 检查点、自动重试或模式切换 |
| `QqTextSendContext` | 必传 AbortSignal 与同步 beforeSend；Token 前及 HTTP 写出前复核，拒绝异步守卫并消费其拒绝；总 15 秒包括 Token/HTTP/响应读取，取消后未发步骤不启动 | 不自行推断 Actor、配置或平台额度，下一层必须提供真实作用域守卫 |
| `QqTextSendError` | outcome 为 not-sent/rejected/unknown；reason、HTTP 状态、受控业务码/trace 可核对，不携带上游正文或秘密 | 不证明客户端已读；未知结果不得用“失败”释放已发计数或自动重发 |

输入保持 Unicode 原文，不修补非法代理项；RFC3339 按日历/时区解析，时间字符串最多 128 字节，
超出 Unix 毫秒表示范围的闰秒明确不支持；有效小数秒截到毫秒。首次索引等号后内容原样保留，含尾部 `=`。
无时间字段默认值；时间新鲜度留给下一层，被动发送调用时把原时间的剩余期限转换为单调时钟并在等待后复核。
HTTP 200 必须有合法非空 ID；相互冲突的 code/err_code、错误与 ID 同时存在、5xx、畸形/过大响应及发出后取消均不能证明未送达。
只有文档已定义且响应一致的业务拒绝判为 rejected；未识别的业务码保留为 unknown，不自动猜测重试策略。

代码审查覆盖取消先于 Token、共享刷新仍在途、守卫错误/错误异步返回、窗口在等待中失效、响应矛盾、尾部索引等号、
重复索引、无效日期和引用伪装成普通文字等失败分支；这是源码反证，不是运行成功记录。
用户禁止再次探测，因此本轮不新增测试、不执行模拟或真实收发；已有脚本样例仅支持所用协议样例，
不能证明新方法的取消、错误分类及解析分支已实际跑通。静态检查与独立复审状态在交付时分别报告。
`surface.ts` 仍为 connectionOnly，不调用上述入口；QQ 运行时来源接线与完整交付均未实现，Journal 升级不再预设为接入前提。

本轮独立复审覆盖 Transport→解析及输入快照→Token→HTTP→回执/取消→公共出口/未接线 Adapter。
发现并修复 `() => void` 容许 async 授权守卫、拒绝可能被忽略的问题：改为 `() => undefined` 并在运行时拒绝非 undefined 返回值，
消费其 Promise 拒绝，不允许等待中的授权结果触发发送。主代理另补响应晚于取消到达时的 body 清理。
最终独立源码复核未确认其他需调整缺陷；`npm run check`、变更文件 ESLint、`npm run build`、`docs:check` 与差异检查通过。
这些均不替代未执行的真实用户路径或故障运行观察；本轮没有新增/运行测试或探测。
用户随后授权全链路审查、修复并提交第一层，再继续下一步；本次提交不开放运行时消息能力。

## 输入、身份与授权

首个生产版本只开放已允许用户的单聊普通文字：`C2C_MESSAGE_CREATE`、`message_type=0`、
`message_scene.source=default`，不夹带附件、卡片或引用内容。未知/不支持结构不得把其 `content` 当普通任务继续处理。
后续引用和附件单独扩展；引用正文只作为外部上下文，不作为当前命令或授权。

入站去重采用账号、Actor、事件 `d.id` 与 `message_scene.ext` 的唯一 `msg_idx`。
事件说明同时提到 `msg_seq`，但消息结构未给入站该字段，详细说明与示例提供的是 `msg_idx`；
因此不借用出站序号，也不默认补零。已有来信确认包含唯一索引；缺少/重复索引仍拒绝并记录受控原因。
`ext` 每项只在第一个 `=` 分隔，保留 `msg_idx` 值里的后续 `=`；索引按非空、不含控制字符、最多 512 UTF-8 字节的不透明字符串处理，
不转成数字、不解码、不记录 auth_token。原来信 ID 和 Actor 各设 512 字节上限，ext 最多 32 项、合计 8 KiB；这些是本地输入预算。
即使类型为 0，只要带 `ref_msg_idx`、非空附件/卡片/引用元素也拒绝普通任务准入；未知扩展不解释成权限。
出站 `msg_seq` 是原来信的回复序号，必须和入站消息索引分开。

每次调用 Application 之前复核账号、允许名单与预配置 Workspace；不接受任意目录。
Task 来源在提交前捕获，Thread/Turn 由权威提交响应或可证明属于该提交的生命周期关联确认，不能用“当前最新 Turn”补全归属。
发送前和每次排队/Token/上传等待后重新检查原目标、Actor、任务来源、授权及取消。
新来信不延长旧任务来源，不转移其被动次数，不授权跨账号/目标补发。
重启后不自动重建旧任务发送授权；首版按下述恢复合同隔离旧输出，不能重放未知结果。

### 接收、去重与提交状态

QQ Transport 的接收序号只用于连接 Resume，不证明 Application 已提交任务。
当前 Transport 串行等待 Dispatch 回调，最多容纳 32 个待处理事件；接入业务时必须明确有界准入和关闭责任，
不能在回调中等待完整 Turn 或平台回复，也不能无限堆积等待任务的消息正文。
需要为下一 Turn 排队时使用 App Server Queue；首版不新增 Gateway 正文队列，也不隐式开放 Queue 命令。

| 入站状态 | 重复来信处理 | 允许的后续行为 |
| --- | --- | --- |
| 校验/授权失败 | 不进入任务去重准入，不调用 Application | 仅受控诊断；不向未授权用户发送错误 |
| 已原子占用去重键、准备或提交中 | 合并为同一次处理，不再次调用 | 在现有作用域内等待，禁止并发重复提交 |
| 已确认提交 | 不再提交 | 保存最小关联元数据，不保存第二份消息历史 |
| 确定尚未提交 | 不自动重试该事件 | 结束本次处理；用户可发一条新的请求 |
| RPC 可能已发出但确认未知 | 不释放为可重试输入，不猜 Turn ID | 保留未知标记，核对权威状态；不自动重启任务 |

去重占用必须早于任何异步准备；容量不足时拒绝新准入，不淘汰处理中/未知项后接受重复请求。
容量、保留期限、过期事件拒绝规则及重启去重语义是阶段 0 的必填参数；未经明确设计不得声称跨重启恰好执行一次。
若使用持久去重，只保存必要身份与状态，并先完成数据格式、备份和回退设计，不复用旧 QQ Ledger。
不支持的结构与重复 `msg_idx` 字段分别处理，不能把畸形索引当成正常重复事件。

### 来源与 start/steer 关联

来源最少绑定账号、Actor、Conversation、原来信 ID/索引/时间、捕获的 Workspace ID/目录、发送模式、
本次运行授权代次及取消范围。被动窗口依据原事件时间保守计算，重复投递不能刷新期限；时间缺失、异常未来时间
或无法建立可信期限时不授予被动发送资格。等待使用单调时间预算，系统时钟跳变不能延长已确定期限。

当前 Application `submit()` 会新建 Turn 或 steer 当前 Turn，返回 `{ threadId, turnId, steered }`；
响应前也可能已经到达输出。实现必须在提交前登记临时来源，并在共享提交边界取得可关联身份；
早到输出只允许有界等待关联确认，不能借用同会话最近来信。无法关联则保留待核对或失败，不发送。
普通提交端口现已实现可选 `SubmissionObserver`，提供精确准备身份、可能已提交与权威响应确认；QQ 内存注册表已实现，Adapter 和输出接线仍待实现。
不把仅供附件的提交作用域强行当作普通文字合同，也不往 Core 塞入 QQ SDK 或凭据。

同一 Turn 的 steer 来信有自己的去重和即时响应来源；不得替换该 Turn 已确认的结果发送授权、期限或被动额度。
用户已明确选择“允许参与任务回传”：即使 Turn 由 TUI 先启动，只要本次 QQ 输入经权威响应确认加入该 Turn，
且原 Actor/Workspace/账号/代次仍有效，就可为它建立本次运行的结果发送资格。不得自动中断或转移该 Turn。
这不是历史补发授权：只处理本次提交进入 requestAttempted 后准入的实时输出，不扫描或重放此前已完成 Item；
之后完成的完整 Item 可以包含本次输入之前的同轮内容。早到候选只有在确认同一 Thread/Turn 后才可发送。
若该 Turn 已有有效 QQ 来源，继续使用原来源，不延长期限或改换目标；来源已撤销的旧票据与旧投递记录不复活。
新来信属于新 Turn 时，建立独立关联。Thread 切换、Workspace 变化、账号变化和撤权均使不再匹配的待发送计划失效。
`/stop` 必须能绕过普通输入等待取消本地准备，并通过共享用例中断精确原 Turn；确认只描述已观察到的结果。

## 发送模式与内容角色

| 内容角色 | 约定模式 | 理由与降级边界 |
| --- | --- | --- |
| 当前 `/help`、状态查询、停止确认等即时响应 | 原来信的被动回复 | 在原窗口及剩余次数内发送，原来源失效则失败，不借用后来的消息 |
| Codex 普通任务的最终正文 | 原任务授权下的主动普通消息 | 长任务不能依赖有歧义的短回复窗口；实际账号主动发送能力必须先验收 |
| 错误、审批与问题 | 明确属于当前来信或原任务的相同模式 | 不建立隐式全局发送授权；审批未完整展示或来源无效就安全取消 |
| 过程、思考、计划、工具成功通知 | 首个生产版本不发 | 不让过程消息消耗正式结果预算；后续由统一投递策略决定，而非每个事件自行发送 |

模式由来源和内容角色在规划前确定。主动拒收/无权限不能通过切到被动、换 `msg_id` 或 `is_wakeup` 绕过；
被动超时也不自动升为主动。互动召回是单独能力，本轮不开放。
若主动权限尚未验收，可以先做明确标识的短被动回复验收，但不能将它宣称为完整的 Codex 长任务交付。

正文只消费权威 `text.completed`，保持 `target/Thread/Turn/Item` 身份；`text.delta` 不承担最终确认。
`turn.completed` 是任务终态，不代替正文送达。没有正文的失败/取消也应有明确状态，不能凭空生成成功结果。

| `text.completed.phase` | 首版处理 | 完成语义 |
| --- | --- | --- |
| `commentary` | 不发送，不纳入 QQ 正式正文持久投递 | 不能证明回答完成 |
| `partial_answer` | 按独立回答 Item 完整交付，计入同 Turn 总预算 | Item 已完成，不表示 Turn 或最终回答已完成 |
| `final_answer` | 按独立回答 Item 完整交付 | 正文片全部确认才算该 Item 交付完成 |
| `null` / 缺失 | 保留完整 Item，不因阶段未知丢弃正文 | 不根据阶段猜任务终态，沿用 Core 权威生命周期 |

此处保留 `partial_answer` 是本项目的正文策略，不把它归为思考/过程通知。
多个 Item 分别计身份和交付状态；不能只保留最后一个，也不能用一个 Item 成功确认整个 Turn。
Turn 终态提示必须与正文交付状态分开：结果缺失、部分交付或未知时不能展示“结果已完整送达”。
QQ 事件白名单必须同时用于 `delivery-policy.ts`、`persistent-output.ts`、Surface 的 `retains/handle/deliver`，
明确处理关键失败与交互不可用提示；不得在入箱后静默忽略事件再返回成功。

## 渲染与完整结果规划

1. **第一版正文使用普通文本。** 原始内容和顺序保留，不删除代码围栏、链接目的地址或缩进来假装获得“更短纯文本”。
2. 命令面板从共享结构化结果生成可读文字，动态字段按字面处理，不把整个命令字符串重新解析成模型 Markdown。
3. Markdown 在后续阶段作为受控表示加入。平台专用交互标签只由受信交互构造器产生；模型输出不能生成点击授权、命令或任意媒体下载请求。
4. 每个完整 Item 在首个请求前一次决定表示和完整交付方案。不得仅因某个字段或某片的格式不支持，就在已发送的多片中反复切换 Markdown/文本/文件。
5. 分片按最终请求正文计量，优先段落、换行、词边界，硬分割不得切断 Unicode；图片 Base64、JSON 外壳等预算独立核算。
6. 先计算全部片数、剩余额度、时限和附件可用性，再产生第一个外部副作用。被动计划超过剩余次数时不发送一个注定不完整的前缀。
7. 超出完整文字预算后，可规划完整 UTF-8 文件；文件内容来自完整原文，不能从已渲染或截断的预览回构。附件未实现时明确报无法完整交付，保留结果，不把截断正文确认成成功。
8. 确认预览和审批不自动改成附件。展示必须完整、授权范围无歧义，且全部提示确认后才开放一次性回应。

**本地资源预算采用阶段 0 的明确数值。** 它们是项目资源与交付策略，不是平台上限，
在模块中作为有名称、有单位的独立策略维护；不新增让用户猜测平台常量的配置项。
不得通过逐次增大/缩小并重复发送用户正文来自动探测限额；本轮不再执行探测。
每日限额如采用滚动 24 小时计数，必须标注为本地保守算法，不称为平台日重置语义。
普通请求预算与共享 Coordinator 默认 60 秒投递期限必须协调；不能让排队或限流等待跨越外层取消后继续发出。
原来信次数、账号/接收方额度及同 Turn 本地预算由唯一调度所有者原子预留，正文、命令和错误提示不能各算一份。
明确未发出的预留可释放；已经发出但结果未知时不得按“失败”退回额度或复用序号。
阶段 0 记录各项预算的单位、作用域、时钟、容量耗尽行为；现有合成样例证据直接复用，本轮不再探测。

## 发送、失败与确认

| 结果 | 处理 |
| --- | --- |
| 请求尚未发出：取消、授权失效、额度不足 | 停止该计划；记录未发出，不声称已送达 |
| 合法成功响应及消息 ID，且本地检查点已确认 | 仅确认对应片；全部内容或完整附件确认后才能确认完整结果；不声称客户端已读 |
| 明确业务拒绝 | 按权限、拒收、过期、次数、频率、长度、格式等分类；保留受控码，不把未知上游正文发给用户 |
| 超时、断线、畸形响应、响应与错误码矛盾 | 结果未知；停止后续片，不自动重发或换格式/来源 |
| 前片成功、后片失败 | 标为部分交付并保留完整结果；不得重发整条造成重复，也不得因前片成功而确认全文 |
| 平台成功、本地确认写入失败 | 保留未知边界，不把网络和数据库误当原子事务 |

长度拒绝 `40054007/40054018` 不证明某个数值阈值；格式拒绝 `40034011/40034124` 不等于网络失败。
权限/拒收/无好友关系、被动过期和次数超限不自动重试。频率拒绝如需重试，必须明确证明本次未发送，
有界等待并重新核对原授权/期限；不能盲目套用通用 HTTP 重试。
明确格式拒绝的整条重规划只可发生在尚无任何正文片确认、无在途未知请求的情况下；禁止逐片自动降级。

正式结果复用共享 Delivery 和 `DeliveryReceipt`/`checkpointDelivery`，由 Bootstrap 保持唯一所有权；
Surface 不能维护完整第二份会话历史。传输去重、次数和授权元数据如需持久化，应单独先给出数据合同及恢复/回滚方案，
不得在 StateStore 中写正文，亦不得静默复用或迁移旧 QQ Ledger。
同会话输出有序，不阻塞 App Server Reader；审批/关键失败不能被过程消息挤掉。
外部请求总时限覆盖 Token、限流、上传及真正发送；取消后未发出的步骤不再启动，已发出的不假装撤回。

### 回执适配与检查点

QQ 普通发送响应使用 `id`。协议客户端先验证 HTTP/业务结果一致、成功字段类型与非空 ID，再返回共享可消费的
`messageId` 或 ID 字符串；当前 `checkpointDelivery` 不识别原始 `{ id }`，不能直接传递 QQ 原始响应。
响应缺少合法 ID、返回矛盾字段或无法解析时按结果未知处理，不能因为 HTTP 200 写入 confirmed。

每个完整计划有稳定身份，各片有稳定次序与操作标识，明确关联原 Item、来源和实际表示。
所有异步发送工作必须纳入 Receipt 的 retain/release 和取消范围；首片成功不满足全计划确认。
任何内容省略必须标记不完整，只有完整原文的已确认交付才能解除；不把“曾有一条 confirmed”当作全文成功。
上传与发消息分别核对，上传成功不能满足正文送达条件。
QQ 为整个计划持有一个 retain，各片串行等待 started/confirmed 检查点，任一失败调用 fail 后停止后片，
最后一片检查点完成才确认全文并释放计划 retain。普通 API 的有效 id 必须先转换为 messageId，
不能利用共享 Receipt 容许缺少 messageId 的宽松路径确认 QQ。现有每记录 256 个检查点/64 KiB 上限也在计划前核对。

### 恢复与人工操作

首版保留失败结果供核对，但不恢复上一进程的 QQ 发送授权。共享 `outputIdentity/outputAuthorized` 只核对
绑定、Actor、Workspace、Provider 等身份，不能单独证明 QQ 原来信和任务发送资格；QQ 来源校验必须与它共同生效。
运行代次只用于区分授权存续，不进入日志作为用户凭据，不因相同 Actor 再次来信重建旧资格。

| 持久记录/操作 | 首版合同 |
| --- | --- |
| 本次运行、来源有效的新输出 | 通过共享身份和 QQ 来源双重检查后才可发送 |
| 重启后的旧 pending / blocked | 保留供核对，禁止自动发送；失效授权不得由恢复绑定推导回来 |
| sending 恢复、部分发送、结果未知 | 保留未知边界与已有检查点，禁止自动续发或重发全文 |
| 管理端 retry | 旧代次或失效来源始终不能发送；是否允许本代次记录复用现有显式人工重试待用户选择，不把人工重试描述为无重复续传 |
| 管理端 ignore | 仅在现有显式管理授权下解除对应记录，不宣称平台已送达，不清理其他数据 |

当前共享重试会将记录置为 pending 并清空进度，不能直接继承为 QQ 的安全续传。
限制必须覆盖 CLI、WebUI/API 与控制服务实际写边界，不只隐藏按钮；已有其他渠道行为保持不变。
阶段 0 选择与现有投递箱一致的最小持久元数据方案，说明旧记录识别、数据版本、容量及失败恢复。
不新增正文历史库，不静默迁移；需要改变用户数据格式时先准备备份/恢复/回退方案并按已有授权范围处理。
旧授权或未知结果可以沿共享的保留核对策略释放顺序屏障，但不释放记录占用的存储额度、不授予发送权限；
新任务仍受账号/全局容量准入约束。正文读取由现有投递箱管理入口或 App Server 权威历史负责，不复制到 StateStore。
共享投递箱当前单记录上限为 4 MiB（含载荷开销）；超过准入容量的结果不能宣称已保存在投递箱。
此时只报告实际入箱失败，并指向仍由 App Server 管理的原 Thread；不得另建正文缓存绕过容量，
也不承诺权威历史中尚未核实的内容一定可恢复。

## 流式是后续独立能力

平台 `replace` 表示当前完整正文，且须保留平台已经下发的前缀；不是发送下一段增量。
`append` 才表示追加输入。首帧取得服务端流 ID，后续沿用该 ID，索引从零递增，结束状态为 10。
流式不得共用普通多片文字的计数与长度假设；需要单独核对每帧计次、主动流权限、Unicode 单位和终态确认。
`remain_msg_len` 文档只定义为剩余字符数，未定义零值等于结束；不能据此自动清空、结束或重建流。
未来若支持预览，预览与完整结果必须分别记账；退出流式不能先发送空 replace 清空已显示的内容。
本轮不选择 append/replace 的实现，也不移入旧流式状态机。

### 阶段 0 实施决定与阶段 2 进度

本节给出接口方向、所有者和有界失败行为。共享提交观察已实现，其余按下文待实施边界推进，不改用户数据或运行配置。

#### 提交后续查：原子 Queue 路径的代价

在提交 `20516498` 后继续只读核对同一锁定上游，未运行历史测试或真实探测。结论：
**不能将 queue/add → queue/start 作为原 submit 的透明替代**；原子 start-only 是真实能力，但完整两步不是原子事务。

| 边界 | 源码证据与设计影响 |
| --- | --- |
| 原子新建 | `app-server/src/request_processors/thread_queue_processor.rs` 的 start 只接受 Started，NotIdle/PendingTriggerTurn 明确拒绝；`ext/queue/src/service.rs` 的 start 在同 Thread dispatch 锁内按 queuedSubmissionId 选取条目，并调用 start_turn_if_idle，不会偷偷 steer |
| 入队已经可能执行 | service.enqueue 持久写入后主动调用 wake_if_loaded；idle contributor 的 dispatch_if_idle 同样通过 start_turn_if_idle 自动消费。因此还没发显式 queue/start，甚至 add 响应未到，任务就可能已开始 |
| 取消与未知 | start 成功后才删除队列项；删除失败可能出现任务已开始但调用报错。add 响应丢失不能重发入队；start 的 item-not-found 也不能解释为从未执行，自动消费或其他客户端可能已启动/删除它。Gateway 退出不能撤回官方已持久的输入 |
| 他人队列 | 无 queuedSubmissionId 会选择队首，不能用来启动未知条目；删除、更新和重新排序均由其他客户端可操作。update 还会保留原 clientId，所以仅匹配 clientId 不能证明正文仍与原来信相同 |
| 模型和模式 | 当前 `ThreadQueueService.add/start` 通过 rejectPendingOverrides 拒绝待生效模型、effort、serviceTier 或 Plan；queue/start 的官方参数只有 Thread/条目 ID，不携带普通 start 的本次覆盖。不能直接清空 pending、假装已应用，或把单次覆盖改成全局设置 |
| 既有消费链 | 项目 `dispatchNativeQueueBeforeRelease` 会按既有后台释放规则启动官方队列；上游还有持久修订观察与 idle 自动消费。QQ 若改用 Queue，必须同时覆盖这些入口，不能只审查手动 start 命令 |

若今后选择“持久排队任务”作为明确的新产品语义，至少需要新的共享用例而非在 Surface 拼两个 RPC：
提交前登记来源/输入摘要，add 前就进入可能执行状态，按精确 clientId、输入摘要和权威 Turn 关联核对自动或手动消费，

#### 去重、来源与恢复

`src/surfaces/qq/task-sources.ts` 已实现本节的内存注册边界，尚未接入 Adapter、共享 owner 或 Delivery。
`reserve(scope, messageIdentity)` 只存原账号/Actor/Conversation/Workspace、来信 ID/索引/时间及关联状态，不接收正文。
调用方须先完成真实授权，再将精确 Actor/Workspace/Thread 的同步实时检查交给注册表；解析成功或注册表自身都不能替代 Policy。
标识符各最多 512 UTF-8 字节、Workspace 目录最多 32 KiB，属于本地元数据预算，不宣称为平台上限。
调用者还须在撤权、Workspace/Thread 归属切换时调用 cancelTarget，Adapter 重建时 close；实时检查不能代替变化通知，
注册表不自行监听配置，不能发现两次检查之间发生且已经恢复的权限变化。
票据含取消信号、Application 观察器和提交守卫；prepared 固定 Thread，请求尝试之前不捕获新候选，
confirmed 仅记录返回 Turn，settled=confirmed 且作用域仍有效才建立结果资格。错误结算不能把已尝试请求降回未提交。
`capture` 返回冻结的代次/sourceToken/目标/Thread/Turn 引用，`awaitSource` 等待时另取冻结快照，
`isCurrent` 只允许最终确认的精确 Turn；错误 Turn、旧代次、取消、撤权及旧引用重新获准均不恢复资格。
同一 Turn 已有有效来源时，新输入引用可以关联原来源，但不能替换 Actor/Workspace、刷新授权期限或复活旧引用。
`terminal` 支持终态先于提交响应到达：只保存每票据最多 8 个候选 Turn 的单调排空期限，溢出禁发，重复终态不续期。
输入总期限 30 秒；来源最久 24 小时，终态最多再排空 60 秒。每账号 4096 条去重记录、128 个活动/预留来源、
128 个等待；未知及未结算条目不靠 TTL 驱逐，已结算条目至少保留至最后结算/失效后 10 分钟且来源不再活动。
取消会唤醒等待、取消票据并清理所属计时器；没有 App Server 中断副作用，实际 `/stop` 仍须调用共享用例。
取消/超时也释放目标的待提交名额：尚未尝试的输入记为未提交，已尝试的输入记为未知并保留去重占位。
迟到的 Application 结算只收尾，不能复活来源或把未知写入降为未提交；取消发生在调用 Application 前也不会一直占住目标。
注册表仅管理普通任务的主动结果资格，不管理被动命令预算、分片、频控、正文或持久授权。

准备守卫、有效来源守卫、来源复用及准入现在均在回调后复核关闭、取消和期限，等待在守卫后再次复核调用方 AbortSignal。
入站 ID/索引/时间先取快照；30 秒预算从 reserve 入口开始，包含同步守卫与清理耗时，不能到创建票据时重新计时。
修复后实际观察为 currentReturned=false/actuallyCancelled=true、sourceCancelledDuringGuard=false、
waitCancelledDuringGuard=false，以及 reservationDuringClose=rejected/closed。没有运行平台收发或模型任务。

现有持久链路尚不能直接承载 QQ 来源：owner 仍为共享 v2，授权端口未给来源等待透传 AbortSignal，
历史解码仍调用实时投递策略；这些是接线前置工作。当时还预设了完全禁止人工 retry 的存储改造，
该额外前提已在后续复用审查中撤回为待用户选择，不代表必须改造数据库。
本次没有改变上述数据/恢复合同或打开接线，`connectionOnly` 仍排除 QQ 的执行与持久账号准入。
因此复审结论覆盖已写入的共享观察/来源代码及其交接边界，不代表尚未实现的 QQ 持久交付闭环通过验收。

首版选择**进程代次内的有界元数据**，不改 StateStore v6，不复用旧 QQ Ledger，不新增消息历史库。
代次由每个 QQ Adapter 生命周期创建，网络 Resume 沿用代次；Adapter 重建、配置重载或 Gateway 重启重新生成。
去重键是账号、Actor、`d.id`、唯一 `msg_idx`；条目记录占用状态、来源 token、接收时间及已确认 Thread/Turn，不存第二份正文。
原事件时间早于代次开始、晚于接收墙钟或距接收超过 60 秒时拒绝；时间不可信直接拒绝，不靠默认值授予资格。
同代次去重保留至少 10 分钟，活动来源及 unknown 条目不因普通 TTL 淘汰；容量不足拒绝新输入。
此方案不宣称跨进程恰好一次：重启不恢复 QQ WebSocket session、拒绝旧时间事件，未知任务由用户核对原 Thread。
系统时钟回退时当前代次停止新准入；无法证明跨进程时钟连续性仍是限制，不把时间过滤等同持久幂等。

来源持有原 Actor、Conversation、Workspace ID/目录、Thread/Turn、发送模式和代次；活动授权最多 24 小时，
终态后最多再保留 60 秒用于排空投递。撤权、Workspace/Thread 归属变化和 Adapter 关闭立即禁发；新来信不续期。
`/stop` 取消未提交准备及未发出的普通结果，仍允许它自己的被动确认；已发请求照实结算。

持久结果继续使用共享加密 Delivery，QQ owner 已实现 `version: 3, kind: qq-live, identity, source`：
identity 为既有共享身份快照字符串，source 为代次、来源 token、账号/会话和精确 Thread/Turn 引用，或无候选的 null；不存 Token、原来信正文或可重建授权的秘密。
非 QQ 保持 owner v2；当前 QQ v2 或缺少字段的记录保留但禁发。QQ v3 只有与内存来源、精确事件和实时共享身份都匹配才可发送。
因此 Decode 只读理解记录不等于恢复授权，重启后旧 v3 也禁止发送。owner 序列化与 `outputAuthorized` 必须同时调整，
不能把新增字段直接塞入现有 v2 字符串等值比较，也不能让事件富化副本丢失来源身份。
当前 `decodePersistentOutput` 用 `isPersistentOutput` 校验历史载荷，这会把新的 QQ 发送白名单误当历史格式校验。
必须拆分版本化载荷结构解码与实时发送/准入策略：认证通过、旧格式可理解的 commentary、turn.started、warning 等记录仍可读取核对，
QQ 旧来源在授权层禁发并按既有策略释放屏障；不得因新白名单在解码时抛错，导致整个 Coordinator 进入 storageFailed。
未知格式或认证失败仍失败关闭，不用宽松强制转换绕过格式校验；新准入和实际发送继续严格执行同一 QQ 白名单。

来源 owner 子版本不改变 Surface payload v1，也不因此要求升级 Delivery Journal。
QQ 来源只持久记录身份凭据的引用，不持久恢复发送授权；人工重试策略另见管理操作，不与 owner 版本绑定。

#### 首版本地预算

以下数值是保守项目策略，样例成功不保证任意同长度正文都可发送；平台拒绝按原合同处理，不重规划重发来试长度。
所有内存容量在分配或异步排队前占用，所有发送预算在第一个请求前预留完整计划。

| 对象 | 预算、单位与耗尽行为 |
| --- | --- |
| 输入 | 普通文本最多 16 KiB UTF-8；空文本、非法 Unicode、未知结构拒绝；每目标一次提交准备、每账号最多 32 次、全局最多 128 次，不增加正文等待队列 |
| 提交期限 | 从接收入站开始 30 秒，涵盖锁、Provider/Thread 准备与关联等待；超时禁止未发请求，可能发出则 unknown；stop 独立取消路径 |
| 去重 | 每账号 4096 条，终态最少保留 10 分钟；活动/未知项固定占位，满时拒绝，不靠驱逐恢复准入；unknown 可持续占位到代次结束 |
| 来源 | 每账号最多 128 个活动 Turn；最长 24 小时，终态排空 60 秒；被动来源只用原时间起 300 秒及最多 4 个不同序号 |
| 早到输出 | 复用既有持久准备上限 128 项、8 MiB 总计和单记录 4 MiB；关联等待不超过输入剩余 30 秒；超限明确报告未入箱 |
| 普通文本计划 | 每片含序号包装最多 2000 UTF-8 字节，按字素边界分片，单个过大字素拒绝；每 Item 最多 8 片，同 Turn 正文合计最多 16 片。完整 Item 先规划，不能承诺未来 Item 永不超额 |
| 状态及错误 | 每 Turn 另留最多 2 条受控状态/错误；仍计入账号和接收人额度；即时命令共享原来信 4 次预算，不占任务正文片数 |
| 调度速率 | 单账号请求间隔至少 250ms；主动滚动 60 秒最多 24 次/账号、16 次/接收人；每接收人本代次滚动 24 小时最多 800 次。统一调度计数，不按正文/命令另起计数器 |
| 计数限制 | 上述主动计数仅本进程代次保守保护，不宣称跨重启或跨机器总额度保证；平台限流/拒收是最终限制，明确拒绝即停，不自动重启或换账号规避。本轮不新增持久配额库 |
| 发送期限 | 一个完整计划最多 45 秒，含队列等待、Token 与所有片；单次网络请求最多 15 秒，与共享 Coordinator 60 秒外限协同，取剩余期限最小值；未知发送仍计占额度 |
| 文件、Markdown、流式 | 首版预算为零，不调用这些接口；超出文字预算明确标记无法完整交付，已入箱部分保留核对，权威正文仍在 App Server |

跨重启去重与日配额若未来成为本地硬保证，必须另行设计持久元数据及版本/备份/回退；不能用此内存方案宣称已经满足。
首版所有者为 QQ Adapter 的单一调度器，HTTP Token 客户端只负责协议，不自行重试、计次或续授权。

#### 管理操作与实施顺序

复用审查确认：`DeliveryCoordinator` 已经不自动重发 uncertain，三个渠道共用队列、Receipt、Journal 和管理入口。
此前“QQ 所有人工 retry 都拒绝 → retryPolicy 持久字段 → Journal v1 → v2 升级”是额外设计约束，
不是 QQ 协议接入的既定要求；撤回其作为阶段 2 必经步骤的结论，不修改现有数据库或管理行为。

本代次人工重试策略尚待用户选择：建议复用现有显式重试，并告知可能重复已收到的分片；
发送时仍须复核精确来源、Actor/Workspace、期限及预算，清空 Journal 检查点不重置这些资格或计数。
旧代次/已失效来源不因 retry 重新获得发送资格。CLI confirm 与 WebUI ignore 继续保留既有含义，不自动调用或互相改名。
如果用户仍要求完全禁止 QQ 人工重试，再单独审查在线/离线最终写入约束及是否确需数据格式变更；
届时才给出实际版本、备份、失败恢复和回退计划，不能以本段授权执行升级。策略未确定前不开放正式 QQ。

实现收敛为一条共享链：QQ Adapter/来源 → SurfaceManager → 共享持久投递 → QQ 文本 Outbox → 现有协议客户端。
Outbox 复用 `ConversationDeliveryQueue`、`captureDelivery`、`checkpointDelivery`，不新增正文恢复队列、回执状态机或 Journal。
微信的最新会话回复上下文、飞书/Telegram 的回复引用表不等于 QQ 的输入参与授权，来源模块保留这一窄职责。

`qq/outbox.ts` 已实现独立的完整文本执行组件：先规划全部字素分片（包装后每片最多 2000 UTF-8 字节、最多 8 片），
再以一个共享队列操作发送；被动计划在任何发送前核对完整序号范围不超过 4。非法 Unicode、过大字素或完整计划超限均拒绝，
不截断正文。每片通过共享 checkpoint 记录，失败即停后片，不自动重试或换模式；全部完成后才标记完整内容确认。
45 秒期限覆盖规划、排队和发送，Token/HTTP 仍复用协议层的 15 秒期限；授权守卫在等待后和 HTTP 前复核。
关联复审修复了被动计划逐片重新换算窗口可能受墙钟回退影响的问题：整条计划固定原来信的单调截止时间，
与协议单次窗口同时约束发送。隔离本地观察中，在剩余约 10 毫秒时于守卫内回退墙钟 60 秒并消耗 25 毫秒，
实际返回 expired、守卫调用 1 次、检查点 0；未读取真实凭据或联网发送。
该组件尚未接到 SurfaceOutputPort。调用方仍须完成事件白名单、来源引用和账号/Turn/接收人预算预留；
本组件不自行授予来源资格、不提供全账号频控或每日配额，不以其完成表示生产门槛已通过。

共享 owner/可取消来源等待已接通，下一步装配 QQ 来源端口、分离历史解码与实时策略，再接事件、预算和必要命令。
正式接通的最小剩余范围是：Adapter 的允许名单/Workspace/普通提交/来源生命周期与输出端口装配，
统一事件白名单和账号/Turn/被动预算，及真实 QQ → App Server → 完整文本/任务终态的验收。
同时验证撤权、取消和重启后旧来源禁发；人工重试沿前述待决策略收口。上述完成后才移除 connectionOnly，
不以基础组件提交、静态检查或历史脚本成功代替接通验收。本轮复审覆盖当前组件与共享接线，未完成的 Adapter 链路不计为已验收。
不增加任务 Queue 替代 submit，不为了接 QQ 默认升级数据库；实际启用仍需完整链路验收。
每步先完成代码和文档审查，不为了演示临时开放入口。优先复用输入不变的已有证据，必要探测遵循本文最新授权范围；
未来生产真实路径若无法观察，按未观察报告，不将有限探测授权扩大为正式接入。

平台真实上限无法从少量样例穷尽证明。本地预算可以在证据范围内保守确定，但必须把样例成功、
已观察拒绝和未知范围分开；不能以“等所有上游歧义消失”无限阻塞，也不能把猜测写成保证。

每阶段先明确输入、输出和业务不变量，沿入口、处理、持久化与最终消费做关联审查并修复；
复用已有静态检查，执行相关失败/对抗场景及真实用户路径，记录实际结果与未观察项。
不新增或维护测试文件，不以静态检查代替功能证据；提交仅覆盖已经完成的阶段，未实现合同继续标记待实施。

### 失败场景与证据要求

| 场景 | 必须观察或证明的行为 |
