# 消息交接与恢复

独立待处理日志已获用户批准。本文描述当前源码的交接边界；新实现尚需部署后的真实平台验收，不代表运行服务已经更新。

## 存储与确认

Gateway 在绑定数据库同级目录建立私有 `delivery-v1/`，使用独立 SQLite 版本 1 日志和随机 256 位密钥。
消息正文、媒体引用及身份载荷使用 AES-256-GCM 加密；检索字段只保留哈希身份、顺序、时间和状态。
不修改绑定 StateStore，不读取 Codex 内部会话文件，不保存完整会话历史，不替代 App Server 原生下一 Turn Queue。
微信回复上下文令牌属于待处理消息的加密交接信息；机器人凭据不复制进日志。

首次启用在 `pre-enable-backup/` 备份当前配置和绑定数据库，原文件不变；备份检查私有权限和 SQLite 完整性。
未知日志版本、丢失密钥、非私有文件或并发写者均失败关闭。Unix 目录/文件为 `0700/0600`，Windows 检查当前用户私有 ACL。
SQLite 事务使用 `synchronous=FULL` 与回滚日志，成功交接即清空载荷；最多保留 10,000 个完成标识用于有界去重。
跨重启去重有这个有限范围，不提供跨平台的恰好一次保证。

- TG：可靠落盘后推进下一次 `getUpdates` 的确认位置。后台提交不占住平台 100 条拉取窗口。
- 微信：整批可靠接纳后才保存平台游标，后台提交与下一批拉取分离；部分落盘后失败的重复批次按消息 ID 去重。
- 飞书：授权后同步可靠接纳，写入失败向 SDK 抛错。锁定 SDK 的长连接回调对此返回失败确认；不能据此保证平台必然重投。

每个渠道输入流最多八个普通会话并发，控制入口额外最多四路；同会话普通输入保持顺序。
停止和受支持的审批文本/回调使用独立控制入口，仍需当前授权及有效的一次性交互令牌。
TG、微信在已拉取批次中遇到普通接纳失败后，暂停后续普通接纳，继续尝试已授权的控制消息；确认位置不会越过失败消息，重复批次由日志去重。
TG 未授权提示最多八路并发，每次最多等待十秒并支持关闭取消；饱和时省略非关键提示，不阻塞合法消息接收。
飞书相邻图片按同一 Actor、原生引用目标成组提交，组内记录通过同一事务进入处理、完成或未决状态；错误提示仍等待实际投递。
微信在接纳平台批次前，按批次顺序为每个已授权私聊选定最后一条消息的回复上下文，先写入现有加密存储再接纳正文。
后台执行、重复交接和重启恢复只读取最新上下文，不按消息落盘顺序改写；尚未建立绑定的待处理输入也按精确目标读取。
上下文写入失败或准备期间取消时，不接纳该批正文、不推进平台游标。历史错误覆盖的上下文不能凭日志序号推断修复，后续有效平台批次会重新选定上下文。

## 取消与不明确结果

记录先进入 `processing`，再执行输入处理或平台投递。准备期取消传至 Application、Client 图片准备及写 RPC 发送前边界。
已经发出的写 RPC 等待其结果，本地取消不能证明远端未接受，也不能撤回远端执行。
关闭先停止接纳，再取消准备并限时等待；每个持久处理器最多等待 5 秒。

重启仅自动处理 `pending`。遗留 `processing` 转为 `uncertain`；未知处理失败也保守进入 `uncertain`，不自动重发。
这可能包含实际尚未发送的请求、用户错误提示发送失败或结果已在远端成功的请求，需要人工核对。
同一渠道流、同一会话的后续普通记录暂停；输出未决也暂停该会话的新普通输入执行，其他会话与控制入口可继续工作。

三渠道的已明确拒绝的结构化用户错误在提示实际送达后结束交接；`revert.result-unknown`、无法确认结果的 `queue.failed`、未知内部错误或提示投递失败保留未决。
输入处理后的命令结果与错误提示也等待实际平台操作；不能把仅进入内存发送队列的提示算作输入交接完成。
关键 Core 输出先可靠接纳，再由后台核对当前接收者授权并等待平台操作实际结束。TG、飞书的可见操作完成通知在持久投递路径中直接发送（微信继续隐藏操作进度以保留回复预算），
不把仍在内存汇总器中的消息算作送达；非关键中间事件可丢弃。配置通知、审批交互和显式图片发送保留各自已有的实际结果确认接口。
媒体只保存引用，平台资源过期或本地图片被清理后无法凭日志重建文件；失败记录保留待核对，不标为成功。

## 配额与故障

全局未完成记录上限为 10,000 条、加密载荷合计 256 MiB，其中 256 条、8 MiB 留给控制入口。
SQLite 主文件另限制在载荷上限加 16 MiB 元数据预算内；事务期间还需要回滚日志空间，备份也占用独立磁盘空间。
达到普通配额时不再可靠接纳新普通输入，不推进未接纳消息的确认；控制入口只能在仍可拉取且预留空间可用时继续接纳。
配额不能保证无限积压下持续收到后续控制消息。

关键输出、事件总线溢出或存储故障会设置 `recovery-required`，停止新普通输入接纳及已有普通输入执行；执行中遇到该故障的输入保留未决，不清空载荷。
已有任务的关键输出仍可在硬配额内接纳并投递，控制入口继续处理；不确定记录仍禁止自动重发。
该标记在运行前预先落盘，异常退出也需要核对；即使故障时无法新建文件，启动保护仍在。
不增加无限内存兜底。诊断只显示哈希身份、状态和时间，不显示正文。
磁盘彻底损坏时无法保证日志可恢复；Gateway 停机期间的输出也不在本地捕获范围内，须查询 App Server 权威会话。

## 核对与恢复

```sh
codexc delivery status --json
codexc service stop gateway
codexc delivery resolve <记录的完整哈希 ID> --acknowledge
codexc delivery clear-fault --acknowledge
codexc service start gateway
```

`status` 可在运行时只读查看，通过所有权锁区分正常运行标记与异常退出遗留标记。其他命令要求独占日志，Gateway 仍运行时拒绝操作。
先在渠道与 App Server 核对实际结果，再执行 `resolve`：它表示操作者确认结束该记录，清除其暂存正文，**不会重发**。
无法确定结果时保留记录。已停止的 `processing` 记录也必须先核对结束；仍有 `processing/uncertain` 时不能解除故障。
`clear-fault` 是对可能未可靠捕获事件的人工核对确认；后续 `pending` 可在启动后继续。
配置或媒体资源已改变的消息可能仍失败，不因解除标记而放宽授权。

## 回滚

回滚前停止 Gateway，导出 `delivery status --json` 的脱敏清单，在私有备份目录完整保留 `delivery-v1/`（包括密钥和备份清单），然后执行：

```sh
codexc delivery check-rollback
```

存在任何未决记录或交付故障时检查失败。先继续恢复，或人工核对并明确结束记录，再检查。
通过检查后才能按部署流程恢复原程序及必要的配置备份；绑定数据库未升级，无需为了回滚删除数据库。
旧程序不认识日志，不能保证它主动执行此检查；手工替换程序绕过检查不受保护。加密日志与密钥备份必须一并保留，不能只备份其中一个。

## 故障定位

TG 的 typing（`sendChatAction`）属于辅助状态，使用有界队列但不参与输入或关键输出的交接确认。
其失败保留平台操作名、脱敏错误分类与队列耗时日志，不将已处理输入转成 `uncertain`；命令结果、错误提示、审批和最终回复仍保留原有确认边界。

三渠道及关键输出的“结果待核对”日志包含 `deliveryId`，执行失败时还包含以下字段：

- `phase`：`processing` 表示写入处理中状态，`handoff` 表示执行输入处理或平台投递，`confirmation` 表示处理返回后的取消/故障复核与完成确认；该阶段不能单独证明远端是否接受请求。
- `purpose`、`lane`、`control`、`groupSize`：区分输入/输出、散列会话、控制消息与媒体批次。
- `queueWaitMs`、`elapsedMs`：分别表示接纳至开始处理、开始处理至记录故障的耗时。
- `errorType`、可用时的 `errorCode`、`aborted`、`recoveryRequired`：记录脱敏错误分类、取消和全局恢复状态；不记录异常原文、正文或凭据。

定位时先用 `codexc delivery status --json` 取得状态和散列 ID，再用 `codexc service logs gateway -n 400` 查找对应 `deliveryId`，按时间关联同一渠道的平台 API 操作与输出队列错误。
同一流与 `lane` 下的 `uncertain` 可以解释后续普通记录的 `pending`；也需检查输出流对输入的阻塞以及全局 `recoveryRequired`。
启动恢复与存储级故障仍分别使用 `recovered`、`storage-failure` 标记，没有单条执行阶段信息。
这些诊断使用现有运行日志，不新增消息历史存储；日志轮转后可能不再保留现场，待处理记录仍按上述核对流程处理。

TG 接纳阶段的恢复保护使用明确的 `recovery-required` 错误码，容量不足为 `full`，其他存储错误单独分类。
接纳失败不会计入网络失败次数，也不会因成功拉取更新而清零：重试等待按 1、2、4、8、16、30 秒递增，随后最多每 30 秒检查一次。
首次、原因变化及每十次持续失败记录告警，成功接纳后记录恢复；不推进失败位置，仍尝试当前批次中的控制消息。平台批次窗口之外的控制消息不保证能够越过阻塞。

`codexc service start/restart gateway`（以及包含 Gateway 的 `all`）完成进程就绪检查后，会额外只读检查恢复保护与未决数量。
存在限制或无法核查时明确提示消息恢复尚未确认，不自动清除记录。普通 `pending/processing` 不单独视为故障。
当前 App Server 会话中的停服限制仍保留：维护恢复应先在本机终端停 Gateway，再核对记录、解除和启动；App Server 无需停止。
